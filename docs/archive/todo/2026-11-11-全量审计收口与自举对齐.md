## 要解决什么

一份外部全量审计报了 34 项：6 项 P0（运行期崩溃、100% 漏读核心文档）、18 项 P1
（机制漂移、场景误判）、10 项 P2（细节与门禁加固）。其中两类最要紧：

1. **跨文件契约错位**：`update.mjs` 与 `sync-toc.mjs` 按错的函数签名调用 `lib/`，
   真跑就是崩溃或静默失效；`render.mjs` 的导航永不输出 `docs-set.md` 与
   `remote-github.md`，而 `SKILL.md` 命令 AI 只照导航读——越守规矩漏得越彻底。
2. **两套规矩用混**：本仓库自己的 `AGENTS.md` 说「拉分支 → 推分支 → 开 PR」，
   而 `SKILL.md` 的硬不变量把「推送」整体列为要等人工确认的对外动作。AI 在维护本仓库
   时套错了那一条，于是把「推自己的分支、开 PR」也当成需要批准的事。

不做会怎样：前一类让工具在真实项目上崩，后一类让每一次维护都多停一步、并让
「日常该自动做到哪一步」在不同文档里说法不一。

## 断点

**已合并、已发版。** PR #18 合入 `main`（`64281b4`），随后按 `RELEASING.md` 发了 `v4.0.0`。

发版走的是规范里的五步顺序：说明与版本号同一次提交 → 推 `main`（走 PR #20）→ 合并之后
才打标签。**顺序反过来就是最常见的失败**，所以第 5 步等合并之后才做。

回读确认三项都过：发布页正文与仓库里那份说明逐字相同（2019 字）、附件 `project-forge.zip`
在（254409 字节）、下载解开之后里面是 `project-forge-4.0.0/` 共 43 个文件，
`AGENTS.md` / `docs/` / `scripts/dev/` 一类自用设施一个都没进去。

发版后 `main` 上复跑了全部门禁，全绿。分支已清干净，只剩 `main`。

**主版本的原因**：`handoff.mjs --verify` 的退出码从三档变四档（多了一个 `4` 表示「不适用」），
以前这种情形给的是 `0`。按退出码分支的调用方需要多认一档，属于对外契约变化。

这一版把「同一件事在两处说法不一」从**靠人记**变成**靠门禁抓**。最典型的三处：

- `SKILL.md` 把「推送」整体列进「等人批准的对外动作」，而 `AGENTS.md` 说日常就是推分支开 PR。
  两句话单独看都成立，放在一起就把执行者逼进二选一。修法不是统一措辞，是**把分档判据
  从「是不是对外」换成「能不能撤回」**——判据一换，两处的结论自然一致，而且新的判据能自己
  回答以后出现的新情况。`preflight` 现在会核对这条说法在 8 份文件里都在场。
- 发版门禁的「未填占位」判据原来是全文 grep，于是**一份正当地提到 `project-forge: fill`
  的说明会被判红**。改成「独立成行的注释标记」之后，判的是它真正关心的那件事。
- `review.mjs` 原先只查「有没有未填的 fill」，标记被手改坏、缺了节、内容漂移三种情况
  都会报「已就绪」。现在它直接取 `compose-agents` 的结论，不再自己算一遍。

还有一条贯穿全程的经验：**判据必须有证据来源**。`pytest` 只在有测试证据时给、`./gradlew`
只在真有那个脚本时用、`mature` 只在项目类缺口为空时才成立——凭空按惯例补一个，得到的
是一条在 CI 里必挂的命令，而那条失败看起来像「代码坏了」。

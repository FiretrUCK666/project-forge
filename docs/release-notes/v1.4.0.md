# v1.4.0

## 这一版更新了什么、修复了什么

这一版只改一件事：**发版说明从此是版本库里的一份文件**，不再是「被标签指到的那次提交的
正文」。装过旧版本的人更新即可，新项目直接按新流程走。

**为什么要换。** 提交正文的读者是「读历史的人」，发布说明的读者是「使用者」——塞进同一个
字段，两边都写不好。它还经常是空的，于是只能靠一个额外的「还没写完」标记去判，等于给一个
本身就不牢靠的载体打补丁。换成文件之后，那份说明在打标签之前就躺在版本库里，可读、可改、
可 diff，而这在旧做法下做不到。

**新的顺序是**：写说明 → 提交 → 推送 → 打标签 → 自动化把文件原文贴到发布页。说明没推到
远端就失败。工作流读的是**默认分支**而不是标签那棵树——标签不可变，读它的话漏推一次说明
就只剩「挪标签」（等于改别人的依据）或「发一个新补丁版本」两条路；读默认分支时，补推说明
再手动触发一次就修好了。顺序要求一点没松：说明不在默认分支上，这一步直接红。

**给目标项目的配套也换了。** 新增 `templates/release-spec.md`：每个要发版的项目落一份
`RELEASING.md`，写清说明放在哪、分成哪几节、按什么顺序发、失败了怎么补。`AGENTS.md` 里只
留一行指针指向它——那份契约每次会话都注入，把发版细节抄进去既白占预算，又制造第二处会漂移
的副本。说明的章节结构在生成时问使用者，不套通用模板：不同项目的读者关心的事不同。

**`templates/ci-release.yml` 整份重写。** 检出默认分支、先断言说明文件存在、用
`gh release create --verify-tag` 建或 `gh release edit` 更新、回读后按行尾与末尾空行归一
再逐字比对。`--verify-tag` 是护栏：标签名打错时它当场失败；没有它，创建命令会拿默认分支
的状态自动建出一个同名新标签，而这次发版看起来还是绿的。

**`templates/agents-project.md` 的发版顺序改对了。** 原来写的是「打标签并推送 → 写发布
说明」——把顺序写反了，而按它做出来的项目会在第一次发版时才发现说明来不及进远端。

**删掉了那个从提交记录起草说明的脚本。** 它生产的正是被替换掉的那种说明；留着就是两套
形状并存。它里面「取完整提交信息而不是只取主题行」的经验，搬进了
`references/remote-github.md` 的写作判据——拿提交记录当素材仍然可以，但必须改写成使用者
能读懂的说法。

**`scripts/release-notes.mjs` 多拦一道。** 除了原先拒绝带骨架标记的说明，现在也拒绝空文件；
两条都发生在任何网络动作之前，所以失败是当场可见的，不是发出去之后才发现。

**交付门禁多问一句。** 有发布 job 却没有发版规范时，它会问一句——那个说明路径总得有个权威
出处，否则它只是散落在工作流里的一个字符串。出路是补一份 `RELEASING.md`，或加
`--no-release-spec` 确认「说明的位置我自己记着」。判据挂在发布链路上，不挂在项目上：从没
配过自动化的项目不会被问。

**规范里不再出现具体版本号。** 发版规范和它的模板里原先用 `v1.2.3` 这类示例，发一次版就
变成一句过时的话，而读的人还容易把它当成「当前版本」。现在统一写成 `vN.M.P` 这样的位置
说明，真正的号只在标签里。

**完整改动**：[v1.3.0...v1.4.0](https://github.com/FiretrUCK666/project-forge/compare/v1.3.0..v1.4.0)

## 需要你动手的

只有一条，而且只影响已经在自己项目里配过发布自动化的使用者：

- **配过发布工作流的人**：按新的 `templates/ci-release.yml` 更新那个文件。旧模板从提交
  记录起草说明，新模板读版本库里的说明文件——两者不兼容，混用会报「找不到说明文件」。
- **没配过的人**：什么都不用做。下次让 AI 给项目配发布时，它会问你「这个项目的发布说明
  分成哪几节」，然后落一份 `RELEASING.md`。

正在用旧流程发版的项目，按新规则重配一次即可，不需要迁移历史发布页——已经发布的那几页
留在原地，新规则只对下一次发版生效。

# v1.6.0

## 这一版更新了什么、修复了什么

这一版改的是**改动怎么落地**这条主线——它以前在契约、模板、参考文档里各说一套，而且互相
打架。装法、命令名、配置格式都没变。

**日常流程以前自相矛盾。** 契约开头的「日常流程」教的是改完直接提交推主干，同一份文件靠后
的「协作」节又说看得见或收不回的改动要走提案。现在是一条线：先判角色（维护者，还是改别人
仓库的贡献者），再判改动性质（三条判据：主干受不受保护、会不会有第二个人改、改动可不可见
收不收得回），任一命中就走分支 + 提案，全不命中才主干直推。**判断不了时按「命中」处理。**

**接外部报告有固定流程了。** 别人贴来一段问题描述、一个链接或一段报错时，先核实四要素
（期望、实际、怎么复现、什么环境），缺关键信息先出追问清单、不盲猜写代码；接着查有没有
人已经在做、认领；然后拉分支，**先写一个能复现的失败用例和一个容易误判的反例**，才动实现。
五步走完才是审查与合并。

**审外部提案的顺序定死了：先只读，再检出。** 因为「检出」之后一次本地装依赖就可能执行陌生人
的代码。先用只读方式看 diff，重点看持续集成配置、依赖装起来就会执行的那些钩子、以及门禁
判据有没有被改松；确认干净才检出到本地跑测试。外部提案一律人工合并。

**合并之后给了确定的顺序与命令。** 合并、回读验证、关单、切回主干更新、删本地、删远端——
六步一个命令块，每步先验证再往下。顺带写了四个坑：合并与删除不能用一条命令混着做、切回主干
必须在删本地之前、必须先去本地后去远端、以及**平台开着「自动删除已合并分支」时，远端那条
分支被删掉是完成态，不是失败**。

**往平台上写字，中文不再拼进命令行。** 创建或更新问题、提案、审查评论时，正文先写成 UTF-8
文件再按文件提交，提交后回读比对。以前这条规则只管发布说明；其余几处同样会静默吞字，而且
接口照样返回成功。

**包里多了两份问题模板。** 缺陷报告问四件事（期望、实际、复现、环境），需求模板问三件事
（要解决什么问题、期望的行为、影响范围）。以前只有提案模板，外部提问拿到的那份「模板」是
空的。目标项目的契约也不再指向它拿不到的文件——协作那半部分现在是自包含的。

**发布自动化不再强制你手工建一个令牌。** 凭据优先用仓库里的令牌，没配就退回平台内置令牌，
而内置令牌只要那个 job 声明了写权限就能建发布页——新项目零配置即可发版。只有要让这次发版
继续触发下游流水线、或保护规则要求特定身份时，才需要单独建那个令牌。

**勘察现在会判「你是谁」。** 远端指向的是这个项目自己声明的仓库，你就是维护者；指向别处、
或存在一个不同的上游远端，你就是贡献者；两者都判不出来时会**明确说判不出来**，不默认当成
维护者——那会让一个贡献者读到「推主干、打标签、发版」那套流程。判出贡献者之后，发布相关的
判据整体跳过，不再要求他配一套自己做不了的事。

**几处会判错的地方。** 一个空的 `.github/ISSUE_TEMPLATE/` 目录以前算「有模板」，于是跳过一
整轮本该发生的追问；目录形式的多份提案模板以前会被当成一个文件去读。两种形态现在都按真实
文件判断。问题模板的要素也按类别分开判：缺陷要四件、需求要两件，不再拿同一套标准要求两份
不同的模板。

**手写契约升级不再要你手抄标题。** `--upgrade` 以前只补「能自动生成」的节，需要读代码后写
的节一个都不补，于是完成判据（逐字比对节标题）永远到不了，而没有任何提示说明差在哪。现在
缺的节全部补齐：能生成的写全，要人写的补成带指引的骨架，你填完删掉标记即可。

**只保留 GitHub。** 文档与判据里其它托管平台的提及、对比、以及一处测试夹具全部清掉；贡献
指南判据里那个「另一种叫法」也换成通用说法——**换的是更宽的一层匹配，不是更窄**，所以用别的
措辞写的贡献指南照样判得对。

两处小修：README 里对「发布页上的 Source code 包」的描述以前是错的（说文件集合与安装包相同，
实际是仓库全量），已改正；交付门禁里要问你的那几个决定现在可以固化进账本（`--remember` /
`--forget`），不必每次重问。

上一版 v1.5.0 的说明当时写好了、但那次漏了打标签，本次发布时一并补上——如果你之前只看到
v1.4.0，现在发布页上也能看到 v1.5.0 了。

## 需要你动手的

没有必须做的。三件可选：

- **想把新的协作协议带进某个已有项目**：对它重跑一次生成（`compose-agents.mjs <项目目录>`）。
  契约是手写的那份加 `--upgrade`——它只做加法，缺的节会补成带指引的骨架，已有的段落一个
  字不动。
- **之前给项目落过提案模板的**：可以补上「风险与影响范围」一栏，审查时最有用（不影响使用）。
- **项目里已有问题模板的**：新的两份（缺陷 / 需求）可以直接落盘；旧的那份留着也不冲突，
  但两类问题共用一份模板时，必填信息总会缺一半。

# v2.0.0

## 这一版更新了什么、修复了什么

这一版换掉了**审查循环的输入形状**。装法没变，但如果你已经在用一个项目的提案流程，
**下一节必须看**——旧格式的审查评论不再被识别。

### 审查不再由人写一句结论

以前审查者写完理由，末尾写一句「通过」或「需要返工」，脚本去读那句话是肯定还是否定。
这条路走不通：中文里否定的写法列不完（不通过、通不过、尚未通过、通过不了、未正式通过），
漏掉一种，方向都是**放行**。

现在审查者只回答一件事：**冻结清单里哪几条标准没过**。

- 全部通过就把 `fail` 留空；
- 有没过的就写编号，逗号分隔；
- 结论由脚本从「哪几条没过」推导出来。

**「通过」这个词从机器的输入里消失了。** 整类「机器读中文否定」的误判从此不可能发生。

### 验收标准在动手之前冻结

开工前把「这件事怎样算做完」写进工作记录的一个块里，一条标准一行。提案正文只放一行
指针指向它。

为什么必须事先：**没有事先说定的清单，审查就只能回答「还能不能再找出一个问题」，
而那个问题永远找得到。** 任何代码都还能再补一处边界处理，任何命名都还能更贴切。
「做得更好」没有上限，所以它不能当完成标准。

### 判通过要交故障注入记录

审查说「过了」的时候，必须同时写清：**你故意把哪一处改坏、看着哪几条用例变红、还原后
是否全绿。**

这把「通过」的成本从「写一句话」抬到了「真跑一遍」。做不到的话，说明你没验过它会不会拦。

### 两条止损：什么时候停

- **同一条标准连续两轮都没过** —— 说明方向错了，不是「再修一轮就好」；
- **轮次超过上限**（默认 2 轮自动返工）。

撞线之后停下，把卡点写进工作记录，升级给能拍板的人。确有理由继续时由维护者加豁免标签。

**豁免只免止损，不免「还有标准没过」。** 这一点是刻意的：标签表示「我认了这个风险」，
不表示「可以不合」。

### 改动大的地方直接判给谁审

开工前先判这件事有多大：小改、中等、较大、高风险、纯文档。较大的直接要求先写实现依据
（凭什么这么改、放弃了什么），再动代码。

问题模板和提案模板都加了对应的栏位。**问题模板的「验收标准」栏是别人写给你的清单**，
动手前把它转进工作记录；提案模板的「实现依据」栏是第一道自查。

### 防漂移改成结构，不靠清单

原来有一张「模板与本仓库实例的同步对照表」，靠人记得改——漏一行就开始说假话。

现在**完整性由目录驱动**：`templates/` 下每个文件都必须在登记表里有落点，新增一个不登记
当场红。机器契约的示例由脚本生成，四处逐字比对，改字段不同步就红。

### 判据注册表：新增判据必须说明谁来看着它

这是这一版最重要的一条，它治的是一个反复出现的病：

> 一条判据被写出来、跑起来、看起来在工作，但它被削成恒真也没有任何东西变红。

四条独立审查里有三轮找到的都是这同一个病在不同位置的新实例。根因不是某条判据漏了，
而是「写判据」与「给它配断言」是两个动作，只有前一个有推动力。

所以合成了一个：新增判据必须在注册表里登记，登记时要交一句「谁来看着它」——
断言名、为什么判不了、或声明它不含判断。答不上来当场红。

## 要怎么跟着升级

**如果你在用这个 skill 配好的提案流程，旧格式的审查评论不再被识别。** 下一份提案之前，
把审查模板换成新版。

1. 在你的项目里重新跑一次：`node scripts/compose-agents.mjs .`
   它会拿到新的契约与新的 `scripts/review-record.mjs`。

2. 如果 `.github/pull_request_template.md` 是你自己写的（不是从 `templates/` 拷的），
   打开它，确认「审查怎么留痕」一节里的字段块是新的四个字段：

   ```
   round: 1
   fail: C2
   inject: 删掉某处兜底分支 → 3 个用例变红 还原全绿
   ```

   旧的是 `verdict` / `blocking` / `suggestions`，已经不认了。

3. 如果你的工作记录里没有冻结过验收标准，下一次开工前补一个：在工作记录的
   「目标与验收」一节放一个 `pf-done` 块，一条标准一行。

4. CI 跑检查的那一步：新的脚本会读提案正文与评论，需要把 `--body` 与 `--comments`
   传进去。`templates/ci-check.yml` 里有现成的写法。

**不重跑第 1 步的项目完全不受影响**——它们拿的是旧脚本、旧契约，行为与以前一样。

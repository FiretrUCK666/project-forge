## 目标与验收

**问题**：同一个改动派了十一轮独立审查，每轮都返回「需要返工」，每轮指出的问题都是真的。
这不是审查太严，是**结构**决定的必然结果。

三个根因，各有实测证据：

| 根因 | 证据 |
| --- | --- |
| 机器契约散在多份手写副本里 | `pf-review` 的格式同时写在脚本、判据、两份提案模板、`AGENTS.md`；九对「模板 ↔ 本仓库实例」里八对没有任何机器检查；同步对照表还漏了三样（`readme.md`、五个许可证、`agents-kernel.md`） |
| 同一条规则为每种项目形态各写一遍 | `templates/agents-project.md` 450 行里有 48 个 `pf:if`、21 种条件；`AGENTS.md` 因「手写编排」不走刷新，于是协作机制有两份手写版 |
| 审查循环没有收敛条件 | 冻结验收标准：无。故障注入：无。返工上限：无。审查者自己声明「通过」 |

**为什么十一轮是这个结构的必然结果**：每轮我改的都是「审查机制」，而它有五个手写落点。
改一处、其余不同步，下一轮必然能指出一处不一致。R2 的 `pf:author` 丢失、R10 的围栏写坏、
R11 的执行点正则，全是这个形状。

**本次要一次解决这一整类**：让机制只有一个来源，且**漏了会红**。

### 冻结的验收标准

改动前冻结。CI 会拿它判这次的提案。

```pf-done
C1: preflight --no-behavior 退出码 0
C2: selftest 全绿；新增用例覆盖轨道判定、pf-done 缺失、未知 id、通过缺故障注入、同标准连续两轮、轮次超 cap、工作记录三种坏指针、实现依据占位词、同一轮两个 fail 集合、模板未登记、字段新增未同步示例
C3: review-record.mjs 里 VERDICTS / cnNum / CN_DIGITS / reviewRecordState / matchRoundsToComments 五个符号 grep 为 0
C4: review-record.mjs 里「通过」这个词不进入任何判定分支（只允许出现在说明文字里）；判定只读 fail / escalate 两个字段
C5: canonical*Snippet() 的输出在 CONTRACT_SITES 四处逐字存在
C6: TEMPLATE_INSTANCES 与 TEMPLATE_NO_INSTANCE 覆盖 templates/ 下每个文件
C7: SKILL.md 不超过 30720 字节；AGENTS.md 不超过 49152 字节；collaboration.md 不超过 45000 字节
C8: templates/agents-project.md 的 pf:if 数量下降，且每条保留的都能说明「不满足时讲的是另一件真事」
C9: 两份 issue 模板都有「## 验收标准」栏；两份提案模板都有「## 实现依据」栏
C10: compose --check 内核逐字一致；package --at HEAD 0 失败；两份 README 目录同步
C11: 行为下限 BEHAVIOR_MIN_PASSED 按重写后实测值调整，并在决策表写明为什么变
```

**C4 从「行数下降」改成了「结论词不进判定」**，理由记在决策表：第一版冻结的是行数，
实测发现自己把它定错了。行数是代理指标，不是判据本身——真正要保证的是「机器不读结论词」，
而这条可以直接判（grep 结论词出现的位置，只看它是否在判定分支里）。用行数当判据会和
「加一条真有价值的判据」直接冲突，那种冲突会逼人删掉有用的东西去满足一个假指标。

## 决策与放弃的方案

| 时间 | 选了什么或放弃了什么 | 为什么 |
| --- | --- | --- |
| 2026-11-09 | 搬 trust-gateway 的**判断机制**，不搬**记账机制**（状态标签、认领标记、P0–P3） | 记账那部分它需要，是因为它的工具靠平台状态工作。我们的状态由提案本身加派生结果算出来，再加一套就是第二个真相源 |
| 2026-11-09 | 机器契约的示例文本**由常量生成**，不手写 | 手写就必然漂移。生成之后，「示例与实现不符」是一条精确判据，不是关键词匹配 |
| 2026-11-09 | 模板完整性**由目录驱动**，不靠清单 | 清单要人记得改，目录不会。这是本项目对「用户包边界」已经验证过的做法 |
| 2026-11-09 | 审查者**只报哪条标准没过**，不写结论词 | 「通过」这个词从机器输入里消失，中文否定的整类问题就不可能再发生 |
| 2026-11-09 | 判「通过」**必须交故障注入记录** | 这是唯一能逼审核者真跑一遍的机制。十一轮里没有一次做过 |
| 2026-11-09 | 止损用两条：同标准连续两轮 + 轮次超上限 | 前者局部、精确；后者兜底。只有上限会让「还差一点」被误停 |
| 2026-11-09 | 不搬 `status::*` 状态标签 | 平台自带状态机加派生结果已经够 |
| 2026-11-09 | 不搬 P0–P3 严重度 | `fail:` 的 id 集合已经表达阻塞；散文观察不进机器字段 |
| 2026-11-09 | 删掉提案正文的「审查记录」索引栏 | 它是「两处必须对上」的持续故障源，带来的不是信息 |
| 2026-11-09 | 新分支从 `main` 起，不从 `41fd6fc` 起 | #10 里八成轮次在修「这次要删掉的那块代码」；从它起等于让新提案背上一笔作废的旧账 |
| 2026-11-09 | 不新增「履历叙述」的机器检查 | 实测这类文字只占 4.2KB，且「为什么这条判据存在」是合法写法，字面特征抓不住 |
| 2026-11-09 | **改了冻结的 C4**：从「行数下降」改成「结论词不进判定」 | 动手后才看清行数是代理指标，不是判据本身。要保证的是「机器不读结论词」，那一条可以直接判。用行数当判据会和「加一条真有价值的判据」冲突，那种冲突会逼人删掉有用的东西去满足假指标。冻结是为了防止标准被无限扩大，不是为了用一个粗糙的代理指标把自己锁死——改判据本身必须写明理由，这次写了 |
| 2026-11-09 | 审查块删掉 `verdict` 字段，改由 `fail` + `escalate` 派生 | 结论不该由审查者声明。声明就需要判断「我算不算通过」，而机器只能读字面——那一步是整类误判的来源 |

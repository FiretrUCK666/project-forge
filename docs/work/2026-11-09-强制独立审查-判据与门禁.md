## 目标与验收

**问题**：第 9 号改动（34 文件，动到判定逻辑与模板）执行者看到 CI 绿了就合并，**从来没有
派独立审查**。事后追问「为什么没派」，答案是：规则里确实没写到这一层——

- `references/collaboration.md` 第五节只说「高风险必须**人合**」，没说「高风险必须有**人审**」；
- `AGENTS.md` 与 `templates/agents-project.md` 复述了同一句话，同样缺「审」；
- 提案模板里没有任何一栏让人填「谁审的」；
- 于是「CI 绿了直接合」在字面上并不违规。

**根本问题不是漏了一步，是这条规则只存在于措辞里**：它没有任何机器判据，「审过了」是一句
无从核对的自述。

可验证的验收：

1. **判据分开**：文档里「审不审」与「谁能合」是两张表、两个问题，不再混成一句。
2. **四处同时成立**：判据（`references/collaboration.md`）、本仓库契约（`AGENTS.md`）、
   落盘模板（`templates/agents-project.md`）、提案栏目（两份 pull_request_template）
   都说到同一件事；`preflight.mjs` 核对这四处，缺一处即红。
3. **机器可判，而且随包发**：`scripts/review-record.mjs` 在随包分发的 `scripts/` 下
   （不在 `scripts/dev/`），能回答「这次改动动没动高风险路径」与「提案里有没有可用的
   审查记录」。它零依赖、单文件，整个复制进目标项目就能跑。
4. **判据不写死在工具里**：高风险路径从**项目自己的** `AGENTS.md`「## 高风险路径」表读——
   哪几处算高风险因项目而异，写死在工具里换个项目就判错，而判错的症状是该拦的没拦。
   读不到那张表时不静默放行，明说「这一趟没查」。
5. **能证伪**：新脚本的每条判据都有正反用例（空模板不算填过、注释不算、免审与没审分得开、
   参数错与判定错分得开、空清单不当通过）。

## 计划

1. 判据：`collaboration.md` 第四、五节改成「先判审不审，再判谁能合」；
2. 契约：`SKILL.md` 硬不变量拆成 11（审不审）与 12（痕迹），`AGENTS.md` 协作表补一行，
   并新增「## 高风险路径」一节（它就是机器的判据来源）；
3. 模板：`templates/agents-project.md` 加「## 高风险路径」一节并把审查规则移出
   `pf:if has-remote`；两份 pull_request_template 加「## 审查记录」；
   `templates/ci-check.yml` 加那一步检查；
4. 机器：新增 `scripts/review-record.mjs`（**随包分发**，零依赖、单文件、可整个复制进
   目标项目）；`preflight.mjs` 加 `checkReviewRuleSources`；`check.yml` 在提案事件上跑它；
5. 用例：`cases-4.mjs` 加一组，并把行为下限抬到 735（实测 740，留 5 项余量）。

## 决策与放弃的方案

| 时间 | 选了什么或放弃了什么 | 为什么 |
| --- | --- | --- |
| 2026-11-09 | 机器判据只判「有没有记录」，不判「审查得对不对」 | 后者机器判不了。假装能判会让一条真检查被读成一条假保证，那比没有更坏 |
| 2026-11-09 | 高风险路径用**目录前缀**，不用逐文件清单 | 清单要人记得改；目录不会长出新的一处。这也是这次体检反复确认的那条通则 |
| 2026-11-09 | 「低档免审」允许写一行「本档不需要审查」，而不是留空 | 留空分不清「没审」与「不需要审」，而这两种的处置完全相反 |
| 2026-11-09 | 不新增「审查轮次上限」 | 轮次是症状；写死数字会在「还差一点就修好」时被误停 |
| 2026-11-09 | 高风险路径**不写死在脚本里**，从项目自己的 `AGENTS.md` 读 | 哪几处算高风险因项目而异。写死在工具里，换个项目就判错，而判错的症状是该拦的没拦 |
| 2026-11-09 | 脚本放 `scripts/` 而不是 `scripts/dev/`，并做成零依赖单文件 | `scripts/dev/` 整目录 `export-ignore`，放那里的东西拿到包的人一个字节都收不到。零依赖是为了「复制一个文件」而不是「复制一棵树」 |
| 2026-11-09 | 读不到高风险路径表时**喊出来但不失败** | 项目可能还没走到填表那一步，为此卡死构建代价太大。但「没查」与「查过没问题」必须分得开 |
| 2026-11-09 | `--expect-changes` 只在提案上给，本地不给 | 提案不可能零改动；本地「这轮只改了别处」是正当用法。同理 `fetch-depth: 0` 与去掉 `\|\| true` 只在 CI 里做 |
| 2026-11-09 | **推翻上一条判定**：审查记录不再接受「本档不需要审查」这句自称 | 那句话谁都能写，填一个字就过——而审查记录的作用是让漏审**事后可核对**，一句口令核对不了任何东西。免审改由机器按改动路径自己算：不落在高风险路径时，脚本根本走不到那一步 |
| 2026-11-09 | 审查记录要求「轮次 + 审查者 + 结论」三样齐全，且**最后一轮必须是通过** | 只看「有字」时，`| 无 |`、`| 1 | | | |` 都能过。而最后一轮是「需要返工」说明还没修完，那是当前状态，不是历史 |
| 2026-11-09 | 高风险清单补上 `.github/`（原来只列 `.github/workflows/`） | 提案模板是这条门禁的**输入页**：删掉「审查记录」那一节，门禁从此对任何提案都判绿，而改它本身既不需要审查也不要人合 |
| 2026-11-09 | 非 ASCII 路径按 git 的 C 风格转义解码，不依赖调用方设 `core.quotepath=false` | 默认配置下中文文件名会变成 `"templates/\345\256..."`，前缀判据匹配不上，中文名的风险改动被判成非高风险、绿着放行。让调用方记得加参数，是又一条要人记住的规矩 |
| 2026-11-09 | **审查结论必须落成平台评论**，正文那一栏降级为索引 | 契约里一直写着「每轮写回提案评论」，而**没有任何判据看评论**——实测跑完两轮审查、门禁全绿，提案上评论数是 0。只填正文等于让执行者自己给自己出证明，而独立审查的全部意义恰恰在于它不是执行者自己给的 |
| 2026-11-09 | 评论核对**不给就是不过**，不当作「跳过」 | 「没查」与「查过没问题」必须分得开。允许跳过的那一版，等于给了一条默认放行的路 |
| 2026-11-09 | issue 那条路同样要求每步留评论 | 追问清单、核查结论、改完了、关掉了——那条 issue 才是别人看得见的地方。只留在自己的会话里，换个人接手就读不到你判断过什么 |
| 2026-11-09 | 越界防护那条用例从**行为断言**改成**结构断言** | 删除候选集已改成结构规则常量，包里那份文档改不动它——对应的行为反例被结构消灭了。如实说明，不硬造一个已经不可能发生的场景 |

## 断点

**十轮独立审查都已落盘并实测，十轮结论全是「需要返工」。**

前八轮修的都是同一块代码的不同形态。第九轮之后我看清了一件事：

> **九轮的严重问题 100% 落在「判断中文结论词」那 247 行里。**

那块代码只做一件事：判断一条中文评论里「通过」两个字是肯定还是否定。为这一件事写过
结论词表、否定前缀的语法结构、轮次解析（含中文数字）、段落边界、行首与句中的区分、
时间回指、取更严还是取最后一个。每修一轮，下一轮又找出一种新写法。

**根因不是哪条判据写错，是「让机器读中文散文」这个决定本身。**
中文里否定的「通过」写法列不完：不通过 / 未通过 / 没有通过 / 不能通过 / 通不过 /
通过不了 / 不算通过 / 未正式通过 / 未能顺利通过 / 尚未通过……每漏一种，方向都是**放行**。

### 改法：改判据的输入形状，不改判据

评论里带一段固定格式的字段块，机器只读那几行：

```
```pf-review
round: 1
verdict: 通过
blocking: 0
suggestions: 2
```
```

正文照旧随便写——「通过不代表没问题」「未正式通过」都不再影响判定，因为机器不读那句话。
人读正文、机器读字段，两边互不干扰。

这一套在本项目里已有先例：`pf:author`、`pf:if` 都是「结构化标记 + 人类可读正文」。

**结果**：那块代码从 286 行缩到 199 行，而且里面**没有再判断任何中文语义**——
它只读 `round:` 和 `verdict:` 后面那两个字。

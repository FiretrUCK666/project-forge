# 协作：改动从哪来、谁来审、谁能合

本文件回答的是**项目配好之后每天怎么干活**：一个改动从出现到落进主干，中间要经过谁、
留下什么记录、什么条件下可以自己往前走。它管的是**判据**，不是操作步骤——具体命令
按项目自己的工具链现场取。

## 何时读本文件

- 有改动要落地时（修缺陷、加能力、改文档、升级依赖，全算）；
- 判断「这次要不要开工作记录 / 要不要开提案 / 要不要拉分支」时；
- **用户把一段 Issue 正文、Issue 链接、提案链接或一段报错反馈贴进来时**（外部报告，见第一节）；
- 要跑审查、或要判断审查算不算通过时；
- 决定谁能合并、能不能自动合并时；
- 处理外部贡献（别人提的 issue 或提案）时；
- 要在平台上发 Issue、提案或审查评论时（正文怎么写，见第九节）；
- 合并之后要收尾时。

**跟 `references/remote-github.md` 的分工**：那份讲**怎么把仓库与自动化建起来**（一次性），
本文件讲**建好之后怎么用它**（每天）。两份都会提到提案与模板，各自只说自己那一段，不复述。

## 一、三种入口：先判这次该走哪条

改动有三个来路。**它们的信任等级不同，混进同一条流程，要么过度仪式，要么留下洞**。

| 入口 | 发起人 | 工作记录 | 提案 | 谁审 | 谁能合 |
| --- | --- | --- | --- | --- | --- |
| **外部报告** | 仓库外的人提缺陷或需求 | 接活后建 | 要 | 独立审查 | 按第五节分级 |
| **外部贡献** | 仓库外的人直接提改动 | **不建**（那是我们的内部记录，他没有义务写） | 他提 | 独立审查 + 人复核 | **人合**，不自动 |
| **日常改动** | 仓库内（维护者或替他动手的 AI） | 见下 | 见下 | 按第五节分级 | 按第五节分级 |

### 第一步：判角色——这一步决定「你能做到哪一步」

同一个改动，维护者与贡献者能做的动作不同。**判断靠项目自身的事实，不靠问**：

| 事实 | 结论 |
| --- | --- |
| `origin` 与项目**声明的源仓库**是同一处 | 维护者 |
| 两者不同，或存在一个与 `origin` 不同的 `upstream` 远端 | 贡献者（Fork） |
| 项目没有声明源仓库，也没有 `upstream` | **判不了**——按贡献者处置 |

**为什么判不了要按贡献者走**：走错这一边的代价只是少做几步（不推主干、不打标签）；走错
另一边，代价是把改动推进一个不属于自己的仓库，而那一步收不回来。

**判不了 ≠ 契约会按贡献者渲染**：生成契约时，判不出角色仍按「可能是维护者」给内容（单人
项目最常见的样子：有 `origin`、没声明源仓库、没有 `upstream`）。所以「契约里写着发版步骤」
不能当成「我一定是维护者」的证据——**判断依据是那两条事实，不是文档的默认值**。

**贡献者的路线是固定的**：与上游同步 → 从主干拉新分支 → 门禁全绿 → 推到自己仓库的那条
分支 → 向正本开提案。**不推正本主干、不打标签、不发版**——前两者没有权限；而请求事件天然
拿不到密钥，需要钥匙的步骤不会跑，也不会泄。

`git.role` 这个字段就是这一步的机器答案（`maintainer` / `contributor-fork` /
`undetermined`），勘察会连判据原话一起给出，不用手判。

### 第二步：判改动性质——只有维护者这一侧需要问

**判据只有一句：这个改动会不会被别人看见、会不会收不回来。** 拆开是三条，任一命中就走
分支 + 提案：

| 问什么 | 命中的含义 |
| --- | --- |
| 主干**受不受保护** | 受保护就不能直推（平台会拒绝），只能走提案 |
| 会不会有**第二个人**改这个仓库 | 有，就必须有审查；而审查只能发生在合入之前 |
| 改动**可不可见、收不收得回** | 随包发出的文档、命令、行为是可见的；认证、权限、CI 判据、发布配置是收不回的 |

**「会不会被别人看见」以发布范围为准**，不是以改动大小为准：一个字的改动也可能改的是随包
发出的说明，那就是看得见的。

三条都不命中（单人、私有、主干没有保护、改动不可见且随时可回退）→ **直接改、验证、提交、
推送**，不开单、不开提案。**日常小改走完整仪式，是把流程当目的，很快就没人守了。**

**判断不了时按「命中」处理**：多开一条分支的代价是几条命令；漏掉一次审查的代价是别人替你
承担后果。

**「主干受不受保护」读不到时要说明**：它需要平台接口与管理员权限，脚本查不了。这一项永远
是人工核对项——**不要因为查不到就当作「没有保护」**，也不要在报告里写成已核对。

### 外部报告：从「贴进来的那段话」到一次能定位的修复

**触发**：用户把一段 Issue 正文、一个 Issue 链接或一段报错反馈交给你（**提案链接不算**，
那是另一种来路，见下一小节）。这时候**不要直接开始写代码**，先走这五步。

**一、核实四要素。** 对照项目自己的 `.github/ISSUE_TEMPLATE/`（没有模板时按同一套判据）：
期望发生什么、实际发生什么（**完整报错文本**，不是转述）、怎么复现（从干净状态能照着走一
遍）、在什么环境上。
**缺关键信息、因而无法定位时，先写出追问清单让维护者贴回 Issue，不盲猜写代码。** 猜出来的
修复会引入一个没人要的行为，而且它看起来像「按需求做的」。

**追问清单要贴在 issue 的评论里，不是只留在会话里。** 这条 issue 是别人看得见的地方：
他会话关了、人走了，清单留在你的对话里就等于没问。判据是**那条 issue 下有你写的一条评论**，
里面有具体要什么。同一条规则贯穿整条路——认领、核查结论、改完了、关掉了，每一步都要在
那条 issue 上留一条评论（怎么写入见第九节：正文走文件，不经 shell）。

**二、防撞车与领活。** 先看工作记录目录里有没有关联这个问题的工作记录：有就读它的断点，不要
从头再来。跨会话或问题复杂时按 `templates/work-item.md` 建一份，写清「关联问题 #N」，状态
改成「进行中」并提交——**提交成功才算领到**（第三节）。

**三、拉分支，先写证伪用例。** 从最新主干拉一条分支，先写一个**能复现该问题的失败用例**，
再补一个**容易被误判成同一个问题的反例**（没有这个反例，修复很可能把不该动的地方一起动
了）。然后才改实现，修的是根因不是症状。

**四、开提案并关联。** 门禁全绿之后把分支推上去，按项目的提案模板开提案：正文写
`Fixes #<编号>`、贴**实际跑过的验证输出**、写清回滚点。只写「测试通过」等于让审查的人替
你重跑一遍。

**五、独立审查 → 按档位合并 → 按第七节的顺序收尾。**

**外部贡献那一行「不建工作记录」是刻意的**：工作记录是我们的工作记录，要求外部贡献者先学一遍
我们的内部约定，等于给参与设门槛。他提的改动本身就有平台上的讨论记录，那够用了；需要长期
跟踪时由**我们**接过来建工作记录。

### 外部提案：别人已经改好了，你决定接不接

**触发**：用户把一个提案链接、或一段「有人提了个改动」的描述交给你。**它和外部报告不是同
一条路**：报告是「有问题，请你修」，提案是「我已经改了，请你接」。所以**不要照上面那五步
做**——先写失败用例那一套在这里没有意义，改动已经存在了。按这四步走：

**一、先只读审 diff，不检出。** 顺序不能反：检出之后一次本地装依赖就可能执行陌生人的代码。
重点看四处（工作流配置、依赖的生命周期钩子、门禁判据有没有被改松、发布范围与锁文件），
判据见第六节。

**二、判它有没有说清「要解决什么问题」。** 提案正文要能回答四件事：要解决什么问题、改了
什么、怎么验证、影响谁。**没有关联的问题不是退回的理由**——很多人直接提改动、不开问题，
这是完全合法的路径，提案模板里也写着「没有关联就说清这个改动解决的是什么问题」。缺的是
那四件事，不是那张票。答不上来时写一条评论把问题问清楚，**不要猜着他的意图去改**。

**三、在隔离环境里跑一遍门禁。** 装依赖时关掉生命周期脚本（各生态的开关不同，按当前位置
的文档查）。跑不过就先在评论里说清要什么，不要替他改。

**四、审完给出结论，合并一律人工。** 外部改动进主干是维护者替他承担后果；能自动合的只有
文档与新增测试那一档（见第五节）。合并后按第七节收尾；提案正文写了关联问题的，平台会随
合并关闭它，**回读确认**它真的变成「已关闭」。

## 二、工作记录：跨会话的载体

**它解决的是「换个会话就接不上」**。对话历史会被压缩、会丢；文件不会。所以一件事只要
跨过一次会话、或者可能换人接手，就该有一份工作记录。

### 放哪

**先探测，探到就用项目已有的那个**，不要另建一套：

| 候选 | 说明 |
| --- | --- |
| `docs/work/`、`docs/tasks/` | 默认建议（前者优先） |
| `todo/`、`work/` | 项目自己起的，照用 |

探不到任何候选时，才建议 `docs/work/`。**路径是项目的决定**，本文件给的是候选与判据。
**探到了就不要搬家**：搬家会让所有旧引用断链，而断链的引用没有任何东西会提醒你。

**为什么不叫 `todo`**：那里存的是进行中、已完成、被放弃的**全部**工作记录。叫 todo 会让做完的
事看起来还没做；编辑器还会把 `TODO.md` 高亮成待办清单，和真实状态打架。

**为什么默认一个文件而不是一个文件夹**：工作记录是「有状态的记录」，不是「一组文件」。
默认一个文件、里面用节管；只有计划确实要独立演进（要贴大量设计细节、要多份附件）时才拆目录。
判据是**新会话读完能不能接手**，不是「有几个文件」。

**完成的单子不搬家**：留在原目录，状态改「已完成」。不建 `done/` 子目录——搬家同样断链，
而且它仍然是同一件事的历史：下一个人可能要看「当时为什么那么选」。

### 叫什么

**`YYYY-MM-DD-一句话主题.md`**（`2026-11-08-修好导出报表缺最后一页.md`）。三段各有理由：

| 段 | 写什么 | 为什么 |
| --- | --- | --- |
| **日期在最前** | **建单那天**，之后不改 | 目录按日期排序，一眼看出先后与年龄；日期是这个文件唯一不会变的东西，所以它不会带来改名。它换来的是「这份记录什么时候开始的」——文件系统时间不可靠（克隆、复制、检出都会重置），平台时间只覆盖平台上的东西 |
| **主题** | 一句话说清要做什么 | 按主题找，半年后仍然认得出。编号做不到这件事：`task-17` 没人记得住，编号还会重排、会撞 |
| **不带状态** | 状态只写在表头 | 状态会变（待办 → 进行中 → 已完成），写进名字就要求改名，而改名会把所有引用断掉 |

**已经在用的老文件不强制改名**：改名会断掉所有引用。新单照这条走，老单留在原处——它缺的
日期去版本历史里查（那件事发生时就记在提交里了），不要为了整齐去动一份别人的记录。

**日期只管起点，别的事件的日期去它们该去的地方**：

| 什么时候 | 写在哪 |
| --- | --- |
| 建单 | 文件名前缀 + 表头「建单日期」 |
| 每次实质改动（认领、开提案、审查通过、合并） | 表头「最近更新」改成当天；状态跟着改 |
| 做过什么决定、放弃过什么 | 「决策与放弃」表的时间列 |
| 平台上的问题与提案 | 表头写**编号 + 日期**（提出 / 开出、关闭 / 合并）。**不复制正文**——正文会漂移，日期不会 |

**分支名不带日期**：分支是短期对象，合并后就删，日期对它没有意义。它的起止时间记在工作记录
的「分支」一行与平台上的提案记录里（那两处都有时间）。

**「执行者」写身份，不写代词。** 这一格的全部用处只有一个：**这件事该找谁问**。

| 写法 | 为什么不行 / 行 |
| --- | --- |
| 「本次会话」「我」「AI」「助手」 | **不行**。换个人打开这份记录，他不知道那是谁；而这个库会被 fork、会被接手 |
| 手填一个固定人名 | **也不行**。同一个人换机器、换账号、fork 出去，身份就变了，而记录留在版本库里，改动时没人会回来改这一格 |
| 现场取：提交署名 + 平台账号 | 行。两个都从项目自己的权威来源读，换谁跑就指向谁 |

取法（按项目实际有的那几种）：提交署名从版本控制配置读（作者名与邮箱），平台账号从当前
登录状态读。**取不到就写「未署名」并说明原因，不要编一个**——空的含义是「这项事实不存在」，
而编一个会让下一个人去找一个不存在的人。

**别人克隆之后填的应当是他自己的署名，不是原作者的**——这正是它必须现场取、不能写死的
原因。与契约里那条「操作者取值一律现场取」是同一条规则，只是落点在工作记录上。

**发布说明也不带日期**：它是在打标签**之前**写好的，写进正文的日期很可能不是真正发布那天；
日期由标签与发布页承担。规范里要写这一句，否则执行者会「顺手补一个日期」。

**不要为问题（issue）建文件夹**：问题原文在平台上，仓库里只放我们自己的记录。两份副本
一定会漂移，而漂移没人盯得住——需要对应关系时，在记录里写清问题编号与日期。

### 对话不落盘

**聊天记录不是记录**：它会被压缩、会丢，也不是给下一个人读的形态（里面九成是试探、重复与
被推翻的中间结论）。真正留下记录的只有三样：

| 载体 | 回答什么 |
| --- | --- |
| 工作记录 | 这件事做到哪了、为什么这么定、下一步从哪接 |
| 提交信息 | 这次改了什么 |
| 提案与审查评论 | 为什么这么改、谁拦过、拦的理由是什么 |

所以「和 AI 讨论了一下午」本身不会留下任何东西——除非它有结论，而结论进了上面三处之一。
**这也是为什么工作记录不能省**：它是唯一一个「换会话还接得上」的载体。

### 里面至少有什么

骨架从 `templates/work-item.md` 起步。无论怎么改，这五样不能少——**缺任何一样，下一个人
就得重新问一遍**：

| 必须有的 | 回答什么 |
| --- | --- |
| 状态 | 待办 / 进行中 / 待审查 / 已完成 / 阻塞 / 放弃 |
| 目标与验收 | 做成什么样算完成（可验证，不是「做好了」） |
| 计划 | 准备怎么改，分几步 |
| 决策与放弃 | 选了什么、**放弃过什么、为什么**。只追加，被推翻的标「已取代」，不擦掉 |
| 断点 | 下一步从哪接、卡在哪 |

**「放弃的方案」比「选中的方案」更值钱**：下一个人最容易重复的错，正是已经试过的那个。
只写结论不写放弃，等于每次从零开始。

### 写什么、不写什么

| 写 | 不写 |
| --- | --- |
| 结论与判据（为什么这么定） | 聊天记录、逐句对话 |
| 试过并失败的方向，一句话说清为什么失败 | 全部中间产物、大段日志 |
| 下一步从哪接 | 别人的原话（要引就引结论） |

**判据是「下一个接手的人读完能不能继续」，不是「记录得全不全」。** 一份需要读半小时才能接手的
工作记录，会让人宁愿重新问你一遍。

### 和 issue 的分工

| | issue | 工作记录 |
| --- | --- | --- |
| 受众 | 外部（提问题的人、贡献者） | 内部（执行者、下一个接手的人） |
| 写什么 | 问题是什么、讨论结论 | 状态、断点、决策 |
| 存哪 | 平台上 | 仓库里 |

**不双向同步。** 两边受众不同，同步只会产生两份互相漂移的副本，而漂移没人盯得住。
需要的关联只有一个：工作记录里写清关联的 issue 编号，提案里写清关联的工作记录路径。

### 状态不做机器校验

状态是**意图**，不是事实。一旦门禁去判它，就会有人改文字来过门禁——那比状态不准更坏。
机器该判的是**能验证的事实**：门禁绿不绿、有没有回滚点、改动落在哪个目录。

---

## 三、领活：别让两个执行者撞同一件事

**标签不是锁。** 两个执行者可以同时看见「还没有人在做」，然后都开工——工作重复一遍，
两份改动还会互相冲突。

**真要有原子性，载体必须是持久化的**：工作记录自己的状态字段就是。改它要提交，提交会冲突，
**冲突是好事**——它比静默重复劳动好得多。

最小判据三条：

1. 开工前读状态。不是「待办」就不要动，先问。
2. 认领 = 把状态改成「进行中」并提交。提交成功才算领到。
3. 放弃时把状态改回去，并写一句为什么——**否则它会一直显示「进行中」，下一个人不敢接**。

不做「租约」「超时自动释放」这类机制：那是多执行者运行时要解决的问题，而这里的前提是
**仓库里的事实说了算**。人手上的状态过时了，读一眼就知道——文件里写着上次是谁动的手。

---

## 四、审查循环

### 什么时候必须审：三档，缺一不可

**「谁能合」与「谁必须审」是两件事。** 把它们混成一句「高风险必须人合」，就会留下一整个
洞：**一个人合也可能压根没人审**——CI 绿了、门禁过了，改动就被合进去了，而「审查」这一步
从来没发生过。实测过一次：一个 34 文件、动到判定逻辑与模板的改动，执行者看到 CI 绿了就合并，
事后追问「为什么没派审查」，因为规则里确实没写到这一层。

所以先回答**审不审**，再回答**谁能合**：

| 这次改了什么 | 必须独立审查 | 谁能合 |
| --- | --- | --- |
| 落在「高风险路径」表里的任何一处 | **是，没有例外**，包括单人与私有项目 | **人合**（不许自动合） |
| 业务逻辑、测试逻辑、依赖小版本 | 是 | 合完通知到人，留一个可撤销窗口 |
| 注释、文档、新增测试、非关键路径小修 | 否 | 门禁全绿 + 零阻塞 + 有回滚点即自动合 |

**「高风险路径」是项目自己的一张表**，写在项目契约里（`AGENTS.md` 的「## 高风险路径」一节）。
**它不只是说明文字，它同时是那条门禁的判据来源**——`review-record.mjs` 读的就是它。

**本仓库自己没有第二份清单**：那张表在 `AGENTS.md` 里，这里是唯一权威。原先这一段复述了
一份（而且和契约已经差了一条：`.github/workflows/` 与 `.github/`），两份写同一件事，
迟早给出两个答案——而那正是这一节要治的病。

**填那张表的三条要求**（机器靠它判，写错等于没填）：

- 目录写 `src/rules/`，不带尾斜杠也认（会补成前缀形式）；单个文件写 `AGENTS.md`；
- 格子里可以带说明，但路径本身要能被认出来（反引号包着最稳）；
- **认不出来的行会让门禁直接报错**——「认不出来」不等于「没有」，静默跳过正是
  「表填了但门禁永不触发」那个 bug 的形状。

**为什么高风险那一档连单人项目也要审**：单人项目里没人替你看着，这和「没人审」比
「有个人随便看一眼」更接近。审查在这里的作用不是表决，是**换一个上下文重看一遍**——
同一个上下文里再读一次，只会读出「刚才那套没问题」。这件事与项目有几个参与者无关。

**判不出来时按「要审」处理**：多派一轮的代价是几分钟与一点 token；漏审一次的代价是
一个没人看过的判据改动悄悄进了主干，而它出错的方式是**让门禁从此少查一项**。

### 怎么派：主 Agent 开一个新上下文

**审查的人必须是另一个上下文。** 由主 Agent 派出（子代理或新会话），**不复用执行者那一轮**，
也不复用上一轮审查那一轮——带着别人的判断去读，读出来的是复核，不是审查。

**给它一张材料清单，不给一段提示词**（清单见下一节）；只给路径与编号，**不给转述**。
下面三样一律不给：

- 执行者的对话记录与「我的思路」；
- **上一轮审查的结论**（要它重看新一版，就当成第一次）；
- 任何「请确认没问题」式的引导语。

**默认只读。** 它把逐条发现返回主 Agent，由主 Agent 写回提案评论（正文走文件，第九节）；
它自己能写也可以，同样走文件。**写在对话里等于没写**——换会话就没了。

**下一轮重新派一个新的。** 让同一个子代理「再看看」，它已经带着上一轮的结论了，第二轮不会
再真正重看一遍。轮次不是成本，带着偏见的第二轮才是。

**通过之后才动手。** 四条终止条件都满足，主 Agent 才合并、关单、收尾（第五、七节）。
**主 Agent 不能自己充当审查**：同一个上下文里再读一遍，只会读出「刚才那套没问题」。

### 读书单：给什么，不给什么

下面每一行都按**路径或平台编号**给，不给摘要、不给转述——转述已经替它做了一次取舍。

**该读的**（按存在与否动态取，没有的跳过，**不要补一句「暂无」**）：

| 读什么 | 为什么 |
| --- | --- |
| 项目契约（`AGENTS.md`） | 判据基准：这个项目自己的规范 |
| 贡献指南（有才读） | 外部贡献的规则与边界 |
| 发版规范（有才读） | 这一版该不该抬号、说明写哪 |
| 工作记录（有才读） | 目标、验收、放弃过什么 |
| 改动全文 | 判的是代码本身，不是摘要 |
| 门禁结果 | 命令与输出，不是「通过了」三个字 |
| 关联的 issue / 提案原文 | 平台上的一手记录，不是转述 |

**不该读的**——这几样宁可不给：

- 执行者的对话记录与「我的思路」；
- **上一轮审查的结论**。读了它就会倾向于认同，第二轮不会再真正重看一遍。要它重看，
  就把新一版改动当成第一次。
- 任何「请确认没问题」式的引导语。

**范围**：默认读改动涉及的路径，加上契约与门禁结果。**要读改动之外的文件来验证调用链，
允许**，但要把「读了哪些额外文件、为什么」写进报告——否则大仓库里它会淹没在无关文件里，
而报告看不出它到底核了什么。

### 产出：写在三个地方，各一件事

| 写到哪 | 写什么 | 为什么写在这里 |
| --- | --- | --- |
| 提案的评论 | 逐条发现：文件与行、什么问题、标**阻塞**还是**建议** | 下一轮的人要读得到。写在对话里等于没写 |
| 工作记录的断点 | 一句话：卡在哪、下一步从哪接 | 换会话、换人都接得上 |
| 提案正文的「审查记录」一栏 | 一行索引：第几轮、谁审的、结论 | 让人一眼看到「审了几轮、现在什么状态」 |

**评论是痕迹，正文那一栏只是索引。** 这两件事容易混，混掉的后果很具体：如果只填正文那一栏，
「谁审的、发现了什么」这份事后可核对的东西就退化成**执行者自己写的一行字**，而一项独立
审查的全部意义，恰恰在于它不是执行者自己给的。

实测发生过一次：跑完两轮独立审查、所有门禁全绿，而提案上的评论数是 **0**——因为契约里
只写着「写回提案评论」，**没有任何机器判据看评论**。现在有了：判据核两层，索引对不上评论
就是红的（见下面那条）。

**每轮都要写，不是最后补一份总结。** 「最后补」等于把中间几轮的判断丢掉，而下一轮要接的
正是那几轮——它需要知道上一版为什么被打回，不是只知道最终过了。评论按轮写、断点按轮改、
「最近更新」跟着改，这三件事与当轮改动**同一次提交**（写在工作区没提交，等于没写）。

**阻塞与建议必须分开**：不分开，执行者要么全部当阻塞（永远修不完），要么全部当建议（该修的没修）。

**写到哪里和怎么写入是两件事**：上面三处的正文含中文时，一律先写进 UTF-8 文件再提交，
不在命令行里拼。规则与理由见第九节——在审查这条路上，评论正文被吞字是最容易发生也最不容
易发现的一种失败。

### 终止条件：四条，缺一不可

1. **阻塞项为零**。建议项记录即可，不阻塞。
2. **门禁全绿**。审查说通过、门禁红——不算通过。机器判据优先于人的判断，这条没有例外。
3. **阻塞项在减少**。连续两轮卡在同一处、数量不降，说明**方向错了**，不是「再修一轮就好」。
   这时停下，把卡点写进工作记录的断点，升级给能拍板的人——不要继续烧轮次。
4. **记录齐全**。本轮的提案评论写了、工作记录的断点与「最近更新」改了、**而且已经提交**；
   门禁要的那几处文档（README、契约、发版规范）与这次改动对得上。**这一条由审查的人查，
   不是由执行者自称**——它是唯一能挡住「改完就宣布完成、记录还停在上上轮」的那道闸。

**「审过了」必须留下可查的痕迹，不能只是一句自述。** 判据是**同一份提案下有一条来自另一个
上下文的结论行**（通过 / 不通过），加上逐条发现。没有这条痕迹的提案，**无论 CI 多绿都不算
审过**——而「CI 绿了」是最容易被误当成「审过了」的那一个：门禁判的是「现有检查有没有过」，
它不判「这次改动有没有让检查本身变松」。两件事完全正交。

这条要求不是为了留档，是为了**让漏审可以被发现**：一句「我审过了」在事后无从核对，
而一条写着轮次、结论、发现的评论可以。

**这条判据由机器核**，核的是两件事对上：

| 层 | 判什么 | 谁能伪造 |
| --- | --- | --- |
| 索引（提案正文） | 有哪几轮、每轮谁审的、结论是什么 | 执行者自己——所以它**不能单独成立** |
| 痕迹（平台评论） | 每一轮的结论都能在评论里找到对应的一条，且**那一轮的结论与索引里写的一致**。空评论过不了；只写「通过」两个字的**能**过 | 要发一条评论；发没发、结论对不对得上是客观事实。**写得好不好不判**——机器判不了，见下面的边界说明 |

**索引对不上评论，就是红的。** 而且这条对 **issue 同样成立**：别人贴来一段问题，
处理过程要留在那条 issue 的评论里，不是只留在自己的会话里——那条 issue 才是别人看得见的
地方。判据一样：谁认领了、核查了哪几件事、要了什么补充信息、最后怎么处理的。

**这条判据能证明什么、不能证明什么——两件事都要说清**：

| | |
| --- | --- |
| **能证明** | 有一轮审查发生过，结论发成了一条**非空的**公开评论，而且那一轮的结论与索引里写的一致。空评论过不了；**只写「通过」两个字的能过** |
| **不能证明** | 那条评论背后的人真的读了代码、真的发现了该发现的问题 |

**为什么不判「写得够不够清楚」**：试过七种判法，每一种都只能让一批用例过、另一批翻。字数、关键词、顿号列举、句子数、去掉表态词后的剩余量、扩展名白名单——**共同点都是拿「文本的形状」代理「有没有内容」**，而纯附和能换个说法、真结论可以很短。最后砍掉，只判「是不是空的」与「结论对不对得上」。留一条会误伤真结论的判据，比没有更坏：误伤让人以为自己做错了，而真原因（措辞没命中词表）永远发现不了。

**边界写在这里，是因为它和这次改动的其它边界一样，属于「读者该知道」的那一类。**
门禁在这里能做的是把「压根没派审查」和「一派了但什么都没写」都挡掉——那已经是原先
「填一行字就过」的几十倍强度。再往上（「审得对不对」）机器判不了，假装能判就会给出一条
看起来像保证的假痕迹。

这也解释了为什么「审的人不能是执行者」是纪律而不是判据：机器分辨不出一条评论是谁发的
——它只能看到内容。**纪律管机器判不了的那一段，判据管机器判得了的那一段**，两者不能互相
顶替。

**最省事的那种自证挡不住，这一点必须承认**：执行者在同一个会话里改完代码、自己写一条
「说到具体东西」的评论，机器判它是过。要挡它得核评论作者 ≠ 提案作者，而那要求平台接口
与登录态——超出这个 skill 「零依赖、跨平台」的边界。**所以这条纪律只能靠人守，判据守不了。**
写清楚它守不了，比让它看起来守得住有用。

**不写「最多几轮」**：轮次是症状，不减少才是病。写死数字会让它在「还差一点就修好」时被误停，
而在真正卡死时又显得合理。

## 五、能不能合：按风险分级

**分界不是「有没有人看代码」，是「这个改动收不收得回来」。**

**这张表回答「谁能合」，不回答「审不审」**——审不审看上一节那张表。两列都过才算能合：

| 档 | 什么算这一档 | 必须审 | 谁能合 |
| --- | --- | --- | --- |
| **低** | 文档、注释、新增测试、非关键路径的小修 | 否 | 门禁全绿 + 零阻塞 + 有回滚点 → **可以自动合** |
| **中** | 业务逻辑、改测试逻辑、依赖小版本升级 | **是** | 同上，**合完通知到人**，留一个可以撤销的窗口 |
| **高** | 认证、权限、支付、数据迁移、**CI 配置本身**、依赖锁文件、发布配置、密钥相关 | **是，没有例外** | **必须人合**，没有例外 |

**「低档不用审」不等于「低档不用看」**：低档的判据是「收得回来」——文档、注释、新增测试
改坏了，一次反向提交就回到原状，而且不会有人因此在自己的项目里踩到坑。它仍然要过门禁，
只是不需要另一个人格重读一遍。

**为什么高与中两档一定要审**：审查在这里不是表决（高档本来就要求人合），是**换一个上下文
重看一遍**。同一个上下文里再读一次，只会读出「刚才那套没问题」。这条与项目有几个参与者
无关——单人项目里没人替你看着，那正是更需要它的时候。

**为什么高档不能自动合**——和「谁看不看代码」无关，是**这些风险在合并之前就已经不可逆**：

- 凭证泄漏了，合完再回滚**不会让它没泄漏过**；
- CI 配置被弱化（降覆盖率门槛、跳过测试、改必过检查），下一次**就没有东西拦得住**了；
- 数据迁移写错了，回滚脚本本身也可能写错。

这三件事的共同点：**回滚不恢复原状**。所以它们不能靠「反正能回滚」兜。

**对应「使用者不看代码」这个现实**：不看是使用者的权利。正确的回应不是劝他看，而是
**让机器替他把能机器判的都判了**（第五节那三条 + 门禁），只把「收不回来的事」留一道人工闸。
那道闸不是给代码质量设的，是给**不可逆**设的。

### 一条独立的硬规则：弱化门禁的一票否决

改动里出现下面任何一样，**不管风险档、不管审查结论，一律转人工**：

- 跳过或删掉测试、把断言放宽、把测试标记成「预期失败」；
- 降低覆盖率门槛、关掉某条必过检查；
- 改 CI 配置本身（工作流文件、门禁脚本的判定逻辑）；
- 改依赖的锁定文件却没有对应的依赖变更说明。

**为什么单独一条**：这是自动化最容易放过去的一类——它「通过了」，因为**判据被改松了**。
过门禁和改门禁是两件事，后者必须有人看。

## 六、外部贡献：信任分级

### 先判外部还是内部：两种提交路线都合法

「改动怎么进来」有两条都成立的路线，**判据是仓库的可见性与成员范围**，不是习惯：

| 路线 | 什么时候用 | 贡献指南里要写什么 |
| --- | --- | --- |
| **同仓分支 + 提案** | 私有仓库；或者成员都有写权限 | 从主干拉分支、推同仓、开提案 |
| **fork + 提案** | 公开仓库、外部贡献者没有写权限 | fork、改自己的分支、向主干开提案 |

**私有仓库不写 fork 不算缺**：全员同仓是私有仓库的常态，那种仓库里 fork 反而多一层
绕路，而且 fork 出来的副本人人可见。所以贡献指南的门禁判据是**二选一**
（「fork」或「分支 + 提案」），机器不替项目选路线。

### fork 来的提案天然受限，这是安全网

平台对来自 fork 的提案会**把令牌降成只读、扣掉全部密钥**。这是设计出来的保护，
**不要为了「让 CI 跑起来」把它拆掉**。

正确做法是**双工作流**：

| 工作流 | 触发 | 有什么 | 做什么 |
| --- | --- | --- | --- |
| 无特权 | 提案事件 | 只读令牌、无密钥 | 构建、测试、上传产物 |
| 有特权 | 前一个跑完之后 | 有密钥 | **只消费产物**、评论、打标签。**绝不检出提案那边的代码并执行** |

### `pull_request_target` 的判据

这个触发器**能拿到密钥**。它唯一正确的用法是：**只读元数据、只评论打标签，不执行提案那边的内容**。

危险形态很具体，两个特征**同时出现**即是：

- 工作流里用了 `pull_request_target`；
- 并且检出了 `event.pull_request.head` 那一侧（或 `head.sha`、`head.ref`）的代码。

**为什么这两个一起出现才致命**：`pull_request_target` 在**基线**的上下文里跑（所以有密钥），
一旦它把提案那边的代码检出并执行，就等于**让任意陌生人拿你的密钥跑他的代码**。
这类攻击有个名字叫「pwn request」。

**一个特征单独出现都不算**：只用了 `pull_request_target` 来做「给新提案打个标签」，是合法且常见
的用法。所以门禁判的是**配对**，不是单个关键词——单个关键词会误报，误报多了这条判据就没人看了。

### 审外部提案：先只读，再检出

**顺序不能反，因为「检出」之后一次本地安装就可能执行陌生人的代码。**

1. **先只读审 diff**（网页上读，或 `gh pr diff <编号>`），重点看四处：
   - `.github/workflows/`：有没有 `pull_request_target` 与「检出提案那边代码」的**配对**（见上）；
   - **依赖的生命周期钩子**（`preinstall` / `install` / `postinstall` / `prepare` 一类）：
     检出之后，一次本地装依赖就会执行它们；
   - **门禁判据本身**：测试被跳过、断言被放宽、覆盖率门槛被降低、CI 配置被改；
   - **发布与包内容**：发布配置、决定「用户包里有什么」的排除规则、锁文件有没有对应的依赖
     变更说明。
2. 确认没有投毒、也没有弱化门禁，**才**把提案检出到本地跑测试。跑的时候让装依赖的脚本
   不执行（各生态的开关不同，按当前位置的文档查），别给它一次执行的机会。
3. **外部提案一律人合**（见上），合完按第七节收尾。

### 外部提案怎么处置

- **可以审、可以评论**，判据与内部改动一样（第四节）。
- **合并不自动做**。走人合通道：外部改动进主干是**维护者替他承担后果**，这个决定不能代做。
- 他提的改动本身**不需要工作记录**；要长期跟进时由我们接过建单。

## 七、合并之后：顺序不能反

```
合并 → 验证真的合并了 → 关工作记录与关联 Issue → 切回主干并更新 → 删本地分支 → 删远端分支
```

**下面所有命令都以 `gh` 为例——它只是一种通道，不是前提。** 没装它、或团队统一走平台工具
（MCP 一类）与网页时，同样的事按等价动作做：**合并**＝网页的 Merge 按钮或工具里的合并接口；
**回读**＝看页面上是不是 Merged，或工具返回的状态；**查堆叠基底**＝网页上按 base 分支筛，
或工具里的列表查询；**删远端分支**＝网页上的分支列表，或工具里的删除接口。
**通道换了，顺序与回读要求不变**；三种通道怎么发现见 `references/remote-github.md` 第二节。

**每一步做完先验证，再往下**。这不是仪式：合并与清理的可靠性不同，而它们的失败**看起来
一样**——都是「命令报错了」。

```sh
# 1) 合并。不要带「合并并删分支」那种开关——那是两件事（见坑①）
#    网页上点 Merge，或：
gh pr merge <编号> --merge

# 2) 回读验证真的合进去了。不要凭上一条的退出码判断
gh pr view <编号> --json state,mergedAt
#    没有客户端工具时：网页上看到 Merged，或 git log <主干> 里出现这次合并

# 3) 关工作记录与关联 Issue：工作记录状态改「已完成」并写断点；
#    提案正文里写了 Fixes #N 的，平台会随合并自动关闭它——回读确认它真的变成「已关闭」

# 4) 切回主干并更新。必须在删本地分支之前（见坑②）
git checkout <主干>
git pull

# 5) 先删本地分支。用 -d，不用 -D（见坑③）
git branch -d <分支>

# 6) 最后删远端分支。删之前先判在不在（见坑④）
git ls-remote --heads origin <分支>
git push origin --delete <分支>
```

### 四个坑，各有根因

**① 不要用「合并并删分支」一个命令做完**

合并不可逆，清理可恢复。混在一条命令里，失败时你**分不清是「根本没合进去」还是「合进去了
但删分支失败」**——而这两种情况的下一步完全相反：前者要重试合并，后者要补做收尾。更糟的是
远端可能已经合了，报告却像整体失败，于是关单、更新主干全都不做，而本地看上去像没合。

**② 切回主干并更新，必须在删本地之前**

两个原因，缺一个都会报错：还停在那个分支上时，git **不允许删除当前检出的分支**；而不把远端
的合并提交拉回本地主干，`git branch -d` 会认为这条分支**没有**合进主干，于是拒绝删除。
顺序反了，就会掉进「明明合过了却删不掉」的循环。

**③ 先删本地，再删远端**

反过来先删远端，本地分支的上游追踪引用（`origin/<分支>`）就消失了，再跑 `git branch -d` 时
可能因为**无法针对上游确认合并状态**而被拒——逼你用 `-D` 强制删除。而强制删除恰恰丢掉了唯一
那道「万一真没合成功就拦住你」的保护网。**永远不要为了让一条命令通过而升级成强制。**

**④ 平台可能已经替你删了远端分支**

仓库设置里通常开着「自动删除已合并分支」。开了之后，提案一合并，远端分支就被平台删掉，第 6
步直接跑会报 `remote ref does not exist`——**那不是失败，是已经完成了**。所以第 6 步先
`git ls-remote --heads origin <分支>` 判一下在不在，在才删。

### 删分支之前先查三件事（堆叠提案最容易踩）

删一条远端分支，可能**连带关掉别人的提案**——不是删除失败，是平台把它当成「基底没了」。
所以第 6 步之前一律先查，**不靠记得**：

| 查什么 | 怎么查 | 有的话怎么办 |
| --- | --- | --- |
| 有没有**未合并提案以它为基底**（堆叠） | `gh pr list --base <分支> --state open` | 先给那些提案改基底（`gh pr edit <编号> --base <主干>`），或者先留着这条分支；直接删会让它们被自动关闭 |
| 有没有未合并提案**以它为 head** | `gh pr list --head <分支> --state open` | 说明这条分支还在用，不能删 |
| 已合并提案的正文里**链接**了它 | 页面上的链接会 404 | 不影响历史与回滚，不必处理；知道这一点可以避免误判成故障 |

**顺序是「先改基底，再删」**：反过来，下游提案已经被关掉，要重新开一条。
**堆叠不是错**：一层依赖前一个提案是常见做法，所以这条要写进流程，而不是当成意外。
同一条判据也管本地分支：`git branch -d` 会拒绝删除一个还有本地工作树在用的分支，那是保护，
不是故障。

### 合并后的记录

- 工作记录状态改成「已完成」，把**非显而易见的决策**追加进「决策与放弃」；**文件留在原目录**，
  不搬进 `done/` 之类的子目录（见第二节）；
- 发布范围里看得见的改动 → 按项目的发版规范决定要不要抬版本号（那是另一件事，见 `references/publish.md`）；
- 出过问题的话，把「下次怎么避免」写进工作记录——**这是唯一能让同类错误不再来的地方**。

## 八、失败与恢复

| 现象 | 根因 | 怎么办 |
| --- | --- | --- |
| 审查一直不通过，卡在同一处 | 方向错了，不是修得不够 | 停下，卡点写进断点，升级给人 |
| 门禁红但审查说通过 | 审查看得不细，或者判据被改松了 | **以门禁为准**；同时查是不是动了门禁本身 |
| 两个执行者做了同一件事 | 领活没走状态字段 | 保留一份，另一份的结论并进来，删掉多余分支 |
| 提案太大，审不动 | 一件事混了多件事 | 拆；一分支一变更，不是规矩是效率 |
| 合并后发现问题 | 回滚点没写、或写了没用 | 按回滚点退回；把「回滚点怎么写才有用」补进这次的工作记录 |
| 合并后本地分支删不掉 | 还停在分支上，或主干没更新 | 先 `git checkout <主干> && git pull` 再删；**不要**改用 `-D` |
| 删远端报 `remote ref does not exist` | 平台已按设置自动删除 | 这就是完成态，继续下一步，不要重试 |
| 外部提案的 CI 跑不起来 | 保护机制生效了（没有密钥） | **不要去拆那个保护**，让它在无特权工作流里跑 |
| 工作记录断链 | 文件被移动或删除 | 引用判据会报；引用它时写相对路径，别写绝对路径 |

## 九、写回平台：正文一律走文件

**创建或更新 Issue、提案、审查评论时，正文不能经 shell 拼。** 走命令行就用一个 UTF-8 文件
提交（--body-file）；走平台工具或接口时，正文作为参数直接传（本来就不经 shell）。

```sh
# 对：正文在文件里，接口按字节读
gh issue create --title "<标题>" --body-file <文件>
gh pr create --title "<标题>" --body-file <文件>
gh pr review <编号> --comment --body-file <文件>

# 错：正文直接拼进命令行
gh pr create --body "<中文正文……>"
```

**为什么这不是洁癖**：shell 的引用规则与默认编码因平台而异——反引号与 `$` 会被当成语法，
中文与重音字符可能被静默改写；共性是**接口仍然返回成功**，打开页面才看得出字被吞了。

**提交之后回读一次**（`gh pr view --json body` 一类），与源文件逐字比对；比对前把行尾与
末尾空行归一，否则纯格式差异会被误报成「被改写」。不一致就**停下**，不要当作成功。

**那个文件放系统临时目录、用完就删**：不写进仓库（会被提交、也会被门禁当成产物），也不留
`.git/`（不会被提交，但清理时没人敢删）；提交信息、提案正文、评论正文都算这一类。

这条与发版说明那条是同一个规则的两个落点（那边用发送脚本，这边用 `--body-file`）：
**两处不同的只有「用哪个工具」，不是「要不要经 shell」。**

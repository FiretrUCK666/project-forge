# 协作：改动怎么进来、怎么审、怎么收尾

## 何时读本文件

这次要处理「改动怎么落地」时读：判自己该推主干还是拉分支、收别人的 Issue、审 PR、派独立审查、
判谁能合、合并完收尾。**没有远端也读**——独立审查不依赖远端，它依赖「这处改坏了不会当场失败」。

本文件按**相位**排：一至六是「动手之前」，七至九是「diff 出来之后」，十是贯穿全程的记录。
指针一律用**标题名**（`本文件「七、审查循环：怎么才会停」`），不用节号——重排一次，节号就废了。

## 一、先判角色：这一步决定「你能做到哪一步」

| `git.role` | 判据 | 能做什么 |
| --- | --- | --- |
| `maintainer` | 远端就是项目正本 | 可以推主干（能不能推取决于主干保护）。**打标签与发版是另一件事** |
| `contributor-fork` | 这是别人仓库的 fork，或你只是贡献者 | 推自己的分支 + 开 PR。不推主干、不打标签、不发版 |
| `undetermined` | 比不出来（项目没声明源仓库） | **按贡献者处置**。它的意思是「没比出来」，不是「维护者」 |

**判不了时按贡献者走。** 两边的代价不对称：走错贡献者只少做几步（分支推了没人合，补一次 PR 就行）；
走错维护者那一侧，改动会推上一个不该动的仓库，推送撤不回来。角色从 `git.role` 读，不靠推断。

### 还有一格：你是维护者，但这次动的是别人提的东西

角色回答「这是不是你的主场」，不回答「这次改动的作者是谁」。后者决定**能不能要求对方遵守你的流程**：

| 作者 | 能不能要求他走完整流程 | 要不要为他建内部工作记录 |
| --- | --- | --- |
| 维护者自己 | 是 | 要（跨会话或可能换人时） |
| 有写权限的协作者 | 是 | 要 |
| **外部贡献者**（fork 来的 PR、外部账号提的 Issue） | **不能**。只要他说清「解决什么问题、改了什么、怎么验证」且门禁过了，就是有效贡献 | **不建**。上下文就在 Issue 与 PR 里，那是他能看到的地方 |

第三种最容易做错：把内部那套「先开 Issue → 冻结标准 → 建工作记录」当成入场门槛，等于给参与设一道
他并不知道存在、也打不开的门。**「没有关联 Issue」不是退回的理由**；要求先开 Issue 只在确实需要
复现信息时成立，那是提问，不是门槛。反过来，对外部 PR **也不放宽判断**：门禁照跑、审查照做，
只是不要求他交内部格式的产出。

### 独立审查这一条，不随角色变

给别人打审、给外部 PR 打审、审自己在维护者身份下做的改动——**审查者与执行者必须是两个不同的上下文**。
宿主给不了子代理就用新会话，没有新会话就换一个人；**判据是「独立」，不是「用了哪个工具」**。
判不了有没有独立时按「没有独立」处理：自查通过可以合低风险改动，但**高风险路径的改动不许放行**。

### 分档的判据是「能不能撤回」，不是「是不是对外」

把「推送」整个当成需要批准的动作，是这条判据最容易出错的地方：**推自己的分支、开 PR 都能撤回**
（删分支、关 PR 即可），它们是日常；**合并、发版、改可见性、改写历史撤不回来**，这几件才要人点头。

| 动作 | 撤回方式 | 要不要等确认 |
| --- | --- | --- |
| 提交 / 推自己的分支 / 开改 PR | 本地回退、删分支、关 PR | 不要 |
| 合并进默认分支 | 只能反向提交，别人可能已经基于它工作 | **要**（谁能合见「八、谁能合」） |
| 发版（打标签、建发布页、发制品库） | 不能 | **要**，且只有明确说「发版」才做 |
| 改可见性（私有转公开） | 不能，抓走的内容要不回来 | **要** |
| 改写历史 / 强制推送 / 删已发布版本 | 不能 | **永不自动** |

判据只有一条：**出错了能不能当没发生过。** 能，就往前走；不能，就停下来给人看。

这条判据管**所有项目**，包括维护本 skill 自己：维护它同样是「拉分支 → 提交 → 推分支 → 开 PR → 合并」，
不比治理别人的项目多一步确认，也不少一步审查。

### 「维护者」不等于「可以自己决定发版」

| 你看到的 | 该做什么 |
| --- | --- |
| 「改好了推一下」 | 拉分支 → 跑门禁 → 提交 → 推自己的分支 → 开 PR。合并之后**到这里就结束** |
| 「发版」「发个版本」 | 走 `publish.md` 的流程 |
| 攒了几个改动、版本号看着该抬了、上个标签隔得久 | **什么都不做**。这些都不是发版理由 |

## 二、三问定档：决定「开工前必须有什么」

**先问三个问题，不要查表。** 一张「改动规模 → 产物」的表看起来很省事，但它是这三条的**组合结果**——每加一种情形就得
加一行，组合还覆盖不到新情形。三问是判据本身，任何情形都是它的一个实例。

| 问 | 是 → 要做什么 |
| --- | --- |
| **一、这次要过独立审查吗？** | 要 → 动手前冻结验收标准（`C1`、`C2`…，每条能被一条命令或一条断言证明） |
| **二、会跨会话、或存在需要人拍板的设计选择吗？** | 会 → 建工作记录（`templates/work-item.md`），含验收标准与「产物清单」 |
| **三、在这个工作区里改，会动到不属于这次改动的东西吗？** | 会 → 建实施位（见下一节）。**改动改坏了不会当场红**的，另加：派实现子代理 |

外加一条不参与组合的硬规则：**碰高风险路径 → 必须有独立审查**（哪些算高风险，看项目的 `AGENTS.md`）。

**第三问覆盖了「改动大不大」这类模糊判断。** 脏工作区、两件事并行、别人的改动正在这里——都是同一个
问题的实例：**切分支会不会把不属于这次的东西卷进来。** 会就隔离，不会就就地改，不靠「感觉这本书厚不厚」。

**AI 只写草稿，不能自己批准。** 第一条的验收标准、第二条的设计选择，要人点头才算成立。自己判
「标准够了」等于没冻结，而那正是审查要防的事。

### 留痕：分流的结论要写下来

判定完不算完，**结论要落在别人看得到的地方**：首次回复、Issue 评论、或 PR 正文的「实现依据」栏。
写清两件事——这次要走哪几条（要不要审查、有没有记录、要不要隔离），以及为什么其余的不需要。

不留痕的后果很具体：审查的人拿不到「原本说好做什么」，只能凭 diff 猜意图，于是它审的是一份自己
想象出来的需求。占位式的留痕（「按 issue 实现」「见需求」「TBD」）等于没写。

### 门禁分档与证据绑定

同一套门禁不必每次全跑。三档，按改动落在哪些目录选：

| 档 | 跑什么 | 什么时候 |
| --- | --- | --- |
| `fast` | 类型检查、静态检查、编译 | 边改边跑 |
| `affected`（默认） | 加上受影响模块的单元测试 | 提交前 |
| `full` | 加上集成测试、构建、端到端 | 提 PR 前，或动了公共部分 |

**要环境才能跑的门禁，缺环境时记「跳过 + 原因」，不许伪装成通过。** 一条写着「跳过：本机没有
数据库」的记录是有用的；一条什么都没写的绿灯是假的。

**证据绑定提交 HEAD**：门禁跑完之后又改了代码，那份输出就作废了——它证明的是「上一个提交是绿的」。
改过就得重跑，重跑之后才提 PR。这一条不需要工具支持，只需要在 PR 的「怎么验证的」一栏里贴的是
**最后一次**跑出来的东西。

## 三、两个工作位：隔离到什么程度

改动落在两处，用途不同，**属主也不同**。名字与路径固定，这样任何人接手都找得到：

| 位 | 路径 | 检出什么 | 谁能动 | 用来做什么 |
| --- | --- | --- | --- | --- |
| **实施位** | `.worktrees/impl-<短标识>/` | **一条新建的分支** | 实施者（主 Agent 或实现子代理），同一时刻只有一个 | 改代码、提交、推送、开或更新 PR |
| **审查位** | `.worktrees/review-<短SHA>/` | **detached 检出实施 HEAD 那个 SHA** | 审查者（独立上下文），用完即弃 | 故障注入、跑测试、把代码改坏再还原 |

四条规矩是这个模型自己长出来的，不需要另外记：

1. **实施位里一定是新建的分支**，不在默认分支上提交，也不在 detached 上提交——detached 上的提交
   没有引用，切走就成悬空提交，而它看起来像「改动没了」。
2. **审查位永远不检出分支**，所以审查者提交不了、推不了、碰不到实施位。**它改着改着中断了，
   损失的只是一个临时目录；实施分支和 diff 一动没动**，清掉重来即可。这就是隔离要解决的那件事。
3. **故障注入只在审查位做。** 在实施位做就得改完再还原，而「还原」本身会失败。
4. 两个位都建在 `.worktrees/` 下，**该目录必须已被忽略**，否则它会被当成待提交的新文件。

### 建之前先确认，收尾先问

建之前三件事：目标路径没被占用；`.worktrees/` 已被忽略；这次真的满足第二、三问的条件之一。

```sh
git ls-files --error-unmatch .worktrees 2>/dev/null && echo "危险：它被跟踪了"
git worktree add -b <分支> .worktrees/impl-<短标识>          # 实施位：新分支
git worktree add --detach .worktrees/review-<短SHA> <最终HEAD>  # 审查位：detached
git rev-parse HEAD   # 必须等于被审的那个 SHA，不是「刚拉下来的分支」
```

**两个位都不是永久的。** 合并完成时按「九、合并之后」卸掉，且卸之前**先问人**——那是别人的机器，
上面可能有他没提交的东西。

## 四、认领与六个评论节点：状态放哪

**状态放在平台上，不放本地文件。** 因为那是所有参与者（包括外部贡献者）都看得见的地方，
而两份状态必然在某一天给出两个答案。

**没有远端时这一节整节跳过**：不认领、不开 PR，执行者写在工作记录表头，其余规则不变。

### 谁改，谁先认领

动手之前，在 Issue 里留一条评论写明账号与分支。**认领不是仪式**：它回答「这件事现在归谁」，
避免两个人同时改同一处，也让后来的人知道你已经在做了。

### 一次改动 = 一个分支 = 一个 PR

**返工永远在原分支追加提交，更新同一个 PR。** 不新建第二个分支、不新开第二个 PR、不强推。
第一个 PR 还没合并就再开一个，等于把同一件事拆成两份待审内容，而它们互相不知道对方存在。

### 六个必须留评论的节点

评论不是叙事，是**状态同步的唯一出口**。措辞固定，因为读它的人（或机器）要能一遍看懂：

| 节点 | 留在哪 | 说什么 |
| --- | --- | --- |
| 认领 | Issue | 谁认领、用哪条分支 |
| 已提 PR | Issue | PR 链接，以及 `Fixes #N` / `refs #N` |
| 审查退回 | PR **和** Issue | 哪几条标准没过、故障注入记录、这是第几轮 |
| 审查通过 | PR **和** Issue | `fail` 为空、下一棒是谁（谁能合见「八、谁能合」） |
| 返工已提交 | PR **和** Issue | 新 HEAD 短哈希、门禁已重跑、请重新审核 |
| 已合并 | Issue | 合并到哪、这一条关掉了哪几个 Issue |

**「返工已提交」必须在 PR 里留**：审查者靠它知道该复审了，靠里面的 HEAD 知道该 detach 哪个 SHA。

**审查退回与审查通过两边都要留。** 只留一侧时，看 Issue 的人不知道 PR 那边有结论，看 PR 的人
不知道 Issue 那边还有讨论——而两边各自都会以为自己看到的是全貌。

### 各种入场形态

形态很多，但答案都由上面几条推出来，不必另立规则：

| 实际情形 | 走法 |
| --- | --- |
| 只有 PR，没有 Issue | **不要求补 Issue**；验收标准写进 PR 正文；照常独立审查 |
| 只有 Issue，没有 PR | 核四要素 → 缺则进 Issue 追问 → 认领 → 实施 → PR 写 `Fixes #N` |
| Issue 与 PR 互相关联，甚至一对多 | PR 正文列全；**只有 `Fixes` 的才在合并时关闭**，`refs` 的不关 |
| 没有远端的本地仓库 | 不认领、不开 PR；分支 + 提交 + 工作记录；独立审查照做 |
| 外部贡献者的 PR | 门禁照跑、审查照做，**不要求他交内部格式产出**；谁能合见「八、谁能合」 |

## 五、收到别人的 Issue

五步，前一步没做完不进下一步：

1. **核四要素**：期望什么、实际发生什么、怎么复现、在什么环境上。
2. **缺则追问，追问发到 Issue 评论里。** 只留在自己会话里的追问等于没写——作者看不到，
   下一个接手的人也看不到。
3. **领活**（有远端时按上一节留评论；没有远端就写进工作记录表头）。
4. **拉分支，先写能稳定复现的失败测试，同时写一条防误伤的反例**（修好之后它必须仍然绿）。
5. **再改实现**，直到那条失败测试转绿，且反例没被带坏。

**严禁盲猜改代码。** 没复现就动手，改中的概率取决于运气，而改动本身会让人以为问题已处理过。
复现不出来时如实说「按描述复现不出来」并附上试了什么。缺陷报告骨架在 `templates/issue-bug-report.md`。

## 六、审别人的 PR

### 先只读审 diff，不检出

**第一步是读 diff，不是跑起来。** 检出之后一次装依赖就可能执行陌生人的代码（安装生命周期钩子），
而那时你已经在自己的机器上、用你自己的凭据跑过它了。四处重点：`.github/workflows/` 里的门禁
有没有被改松；`preinstall` / `postinstall` / `prepare` 一类生命周期钩子；门禁判据有没有被放宽、
加跳过标记或改成警告；依赖锁文件有没有引入新来源（换 registry、git 地址、tarball 直链）。

跑门禁时**加 `--ignore-scripts` 一类参数**关掉生命周期脚本。要装依赖才能验的部分，
先确认真没有可疑脚本，再装。

### 审查只看「哪几条标准没过」

有效意见指向具体标准：

> 第 2 条（新命令有没有写进 README）没过——脚本加了 `lint`，README 没提。

无效意见给感受：「我觉得这里可以再想想」。它的用途是讨论，不是审查。拿它当阻塞理由，
循环永远收敛不了。**自己审自己也一样**：改完、门禁全绿、看着没问题就合——这个动作里
「看着没问题」正是自审的产物。门禁判「现有检查过没过」，审查判「这次改动有没有让检查本身变松」。

### 高风险改动：独立上下文审查 + 故障注入

高风险改动必须派一个**新上下文**看（子代理或新会话），并给它一份材料清单：

- 目标、冻结的验收标准、**被审的那份 diff 的哈希**、门禁原始输出；
- **PR 里前几轮的审查栏**（只有那几栏，不是执行者的说明）。

**绝不给执行者的思路与上一轮结论。** 给了它只会顺着复核，最后得到一个「同意」。界线要说清：
**前几轮的 `fail: C4` 是记录，不是结论**——它说的是「那一轮这一条没过」，这次过没过要审查者自己判。
不给前几轮记录，审查者就没法知道自己是不是第二轮、「同一条标准连续两轮没过」那条止损也就执行不了。

**为外部贡献者不建内部工作记录。** 外部 PR 的上下文在 Issue 与 PR 里，那是作者和后来的人
都能看到的地方；另建一份内部记录，等于把「为什么这么改」藏进一个他打不开的地方。

具体怎么给结论、几轮之后收窄范围、什么时候该停，全在下一节。

## 七、审查循环：怎么才会停

审查的目的是回答「这次改动可以合了吗」，不是「还能不能找出问题」。后者永远有答案：任何代码都
还能再补一处边界处理，任何命名都还能更贴切。拿它当判据，循环就不会收敛——改一轮、审一轮，
每轮都能挑出真的问题，而其中大多数是第一轮就存在、只是上一轮没扫到的。

下面六条是一套。前五条管「这一次怎么停下来」，第六条管「这一类以后还会不会再漏」。

### 1. 判据只有一份：动手前冻结的验收标准

审查只回答「C1、C7 没过」，不回答别的。标准在工作记录里，动手之前冻结。

**冻结的意思是「改它要留痕」，不是「一个字都不许动」。** 要加或要改，回工作记录正式写一行，
说明为什么——那是一个需要说明的动作，不是审查时顺口一提。标准本身定歪了（拿代理指标当判据）
是真实会发生的事，发现之后改判据是正当的；不正当的是悄悄改，让审查对着一个已经变过的靶子判。

### 2. 结论由字段派生，审查者不宣布「通过」

一轮审查只交四样东西，**一项一项写成字段**（PR 里那四个栏目的名字就是从这里来的）：

```text
审查来源: 子代理 / 新会话 / 另一个人（与执行者不是同一个上下文）
逐条标准状态: fail: C1, C4 / pass: C2, C3, C5, C6
故障注入记录: <删了什么 → 哪条变红 → 还原后是否绿>
止损记录: <触发了哪条，或「未触发」>
```

「通过」不是审查者写的一句话，是 `逐条标准状态` 里没有 `fail`、且 `故障注入记录` 非空时**算出来的**。
按这个规则，任何一个人读完那两栏都能得到同一个结论，不需要理解审查者的措辞。

为什么不能靠声明：结论一旦用自然语言写，读者只能读字面，而中文否定的写法多得数不清
（「不建议不合并」「除 C1 外基本没问题」「不算完全通过」）。要把这些读懂，就得写一套语言解析器，
而它迟早会读错一条——读错的后果是把「没过」当成「过了」。

同理，审查报告里**不写「整体不错」这类评价**。它既不是 fail 也不是 pass，唯一的用途是
让执行者猜该不该改。

### 3. 四条收敛规则

| 规则 | 治什么 |
| --- | --- |
| **第 1 轮看全量**：本 PR 的改动，加上它影响到的地方（调用方、契约、相邻模块） | 前几轮本来就要查全，这个范围是对的 |
| **第 3 轮之后只看新增的那几行**，不再整体重看 | 每轮从头看，必然每轮翻出第一轮就在的旧问题——那些不是这轮改出来的 |
| **同一类问题一次全部指出**：同一个错在五处出现，一次报五处 | 一次只报一处，下一轮又冒出同类，永远收敛不了 |
| **已经提过、还没被改的不重复提** | 重复提让执行者反复应对同一条，也让「还剩几条」看不出变化 |

### 4. 两条止损

| 触发 | 动作 |
| --- | --- |
| **同一条标准连续两轮没过** | 停下。局部卡住说明方向错了，不是再修一轮就好 |
| **轮次超上限**（默认 3 轮全量 + 2 轮增量） | 停下。兜底，防止「每次只差一点」把轮次拖长 |

止损的动作是**停下来交给人**，不是自动再来一轮。交人时给三样：还差哪几条标准、卡在哪里、
你判断的根因是什么。之后由人决定是放宽标准、改方向，还是继续。

**「还差一点」不是继续的理由。** 上限的意义就是不给这句话留口子。

这两条要执行，审查者必须知道两件事：**这是第几轮**、**上几轮哪几条没过**。所以材料清单里
允许给「PR 里的前几轮审查栏」——它给的是记录，不是结论。轮次以 PR 里「一轮一行」为唯一计数处：
数到第几行就是第几轮，这一个人也能算，不靠谁记。

### 5. 打回之后怎么返工

打回（`fail` 非空）之后，**这个提案不得合并**，固定走这一套：

1. **在原分支追加提交**。不新建分支、不新开第二个 PR、不强制推送、不关 Issue。
2. **重跑门禁**，产出绑定新 HEAD 的证据。改过代码之后没重跑的门禁结论是作废的。
3. **更新同一个 PR**，并在 PR 与 Issue 各留一条「返工已提交」评论（新 HEAD 短哈希、请重新审核）。
4. 审查者在新 HEAD 建**新的审查位**重新审一轮，重复直到 `fail` 为空。

**HEAD 没前进就重提，直接拒绝**：拿同一个提交反复送审，等于让审查者重复看一遍一模一样的东西，
而每一轮它都可能报出上一轮没扫到的问题——这正是无限循环最常见的形状。

**已经合并的 PR 不再审、不再打回。** 合并之后才发现的问题按新 Issue 处理，用同一个 Issue
绕过流程再开第二个 PR 是不允许的。

**审查进行中 diff 变了，重判。** 这不是罕见情况：执行者一边改、审查者一边看，中途落一次改动
是常态。规则只有一条：**以你交结论那一刻的 diff 为准**，并在审查栏里记下它的哈希。一句话：
**结论永远绑在一个确定的 diff 上，不绑在「刚才看的那个」。**

**哈希必须可复现，否则它什么也没绑住。** 这一条吃过两次亏，两次都是同一类：一次是把 diff
拼成字符串再求哈希，一次是用会转行尾的重定向写文件——两次都得到一个**别人算不出来**的值。
所以取法要写死成一条，谁跑都是同一个数：

```sh
git diff <基线>...<HEAD> > d.txt      # 重定向，不要经过任何会改编码/行尾的工具
sha256sum d.txt                        # macOS: shasum -a 256 d.txt
```

给哈希的同时给出**字节数**：行尾被改过时字节数会变，而哈希对不上时，字节数能一眼说明是哪一类
差异（差几千字节通常是行尾，差几十字节通常是内容）。**校验方式是让审查者自己跑一遍**——
它算出来的值和你写的不一样，就是这一条没过。

### 6. 漏检要落成回归，不落成印象

审查放过了、后来出事的那个问题，**落一条回归用例**：造一个能复现它的夹具或断言，放进项目
自己的测试里。下次同一类错误再出现时，是门禁先红，不是又一轮审查靠运气碰到。

这条比前五条重要，但见效最慢：前五条让**这一次**停下来，这一条让**下一类**根本进不来。
没有它，止损只是把循环截断——同一个病换个形状再来一次，照样从头审起。

**不写「下次注意」。** 那是一句印象，三个月后没人记得，而它看起来像已经处理过了。

## 八、谁能合：默认由审查者合，只有一类必须人点头

**独立审查通过之后，由那个审查者直接合。** 不再按风险高低分层，也不因为提案来自外部就拦下来。

理由是：**人是不会去读代码的。** 把合并挂到人身上，实际发生的是「点一下同意」，而不是「看一眼
再决定」——那道闸门只增加了等待，没增加判断。真正做出判断的是审查：它拿到了冻结的验收标准、
diff、门禁原始输出，并且做过故障注入。**让它把最后一步做完，闭环才是完整的。**

外部贡献者的 PR 同样如此。防陌生人的那一层不在合并这一步，在**审查之前**：先只读审 diff
（见「六、审别人的 PR」那四处重点），跑门禁时关掉生命周期脚本。那两件事做了，合不合就是技术判断。

### 唯一必须人点头的一类：弱化门禁

| 改动 | 谁能合 |
| --- | --- |
| 普通改动，独立审查 `fail` 为空 | **审查者直接合** |
| 外部贡献者的 PR，同上 | **审查者直接合** |
| **弱化门禁**：删测试、放宽断言、加跳过标记、把检查改成警告、改松 CI | **必须人点头** |
| 触碰项目「高风险路径」的改动 | 审查者合，但**审查必须是独立上下文 + 故障注入** |

**为什么只有这一条。** 它和别的改动不是一类：别的改动做错了，下一次门禁会红；它做错了，
**以后每一次门禁都不会红**——包括这一次。而它的外观是「构建绿了、测试通过」，看起来像一次
正常的改动。这一条闸门拦的不是错误，是**判断力被绕过**。

### 三种永远不自动的动作

合并之外还有三件，与谁审无关：

| 动作 | 为什么 |
| --- | --- |
| 发版（打标签、建发布页、发制品库） | 对外且不可撤回；只有明确说了「发版」才做 |
| 改可见性（私有转公开） | 抓走的内容要不回来，要逐次授权 |
| 强制推送 / 改写已推送历史 / 删已发布版本 | 所有克隆过的人都要重拉 |

### 项目可以收紧

默认按上表。项目要更保守时，在 `AGENTS.md` 的「取舍」里写 `merge-authority: human`，
把「审查者直接合」也收回人手。**这是表态项，不是硬编码**——写与不写都不影响审查照做。

**「独立审查」与「谁能合」是两个问题**，别混：审查者与执行者不能是同一个上下文，这条永远是死的；
谁能按最后那个按钮，按项目表态。

## 九、合并之后

### 固定七步，顺序不能调

1. 合并 PR（**不勾选自动删分支**）
2. 回读确认已合：状态必须是 `MERGED`
3. 更新工作记录与 Issue
4. 切回默认分支并取回合并提交：`git switch <默认分支> && git pull`
5. **先卸 worktree**：`git worktree remove <worktree 路径>`
6. **再删本地分支**：`git branch -d <分支>`（不是 `-D`）
7. 查远端分支还在不在（`git ls-remote --heads origin <分支>`），**确认之后才** `git push origin --delete <分支>`

`<默认分支>` 现场取（勘察的 `git.originHeadBranch`），不写死 `main`。分支名同理。

**第 5 步必须在第 6 步之前。** 一个分支只要还被某个 worktree 检出着，`git branch -d` 就会拒绝
删除它——那时看到的报错是「分支未合并」，而真实原因是它被占用，两个原因的处理方式完全相反。
顺序反了，人就会去用 `-D` 强删，而 `-D` 绕过「这个分支合并了吗」这道检查。

### 删之前先问，这是硬前置

第 5、6、7 步删掉的三样东西**都是不可逆的**，而它们所在的机器不一定是你的。
所以在动第 5 步之前，**把要删的清单列出来问一次**：哪个 worktree、哪条本地分支、哪条远端分支。

清单长这样：

```text
要清掉的：
- worktree  .worktrees/impl-<短标识>、.worktrees/review-<短SHA>
- 本地分支  <分支名>
- 远端分支  origin/<分支名>（先确认没有下游堆叠 PR 以它为 base）
干净的：工作区无未提交改动；这条分支上没有未合并的提交
```

**问到人点头才删。** 没问到人时把清单写进汇报，**不自己动手**——问不到人与他同意是两件事。
「清清爽爽」是目标，但它排在「不删错东西」后面。

### 四个坑

1. **把合并与删分支写在一条命令里**：失败时分不清是哪一步坏的。
2. **不确认状态就删分支**：合并失败时删掉分支，改动就丢了。
3. **用 `-D` 强删**：它绕过「这个分支合并了吗」这个检查，把没合进去的东西一起删掉。
4. **以为删远端失败了**：平台可以设成合并后自动删分支，查不到 = 已经删了，那是完成态。

删远端分支前必查三件事：本地已切回默认分支并 `pull`（否则可能正在删自己唯一那一份）；
这条分支上没有未合并的提交（`git log <默认分支>..<分支>` 为空）；**有没有未合并的下游堆叠 PR
以这条分支为 base**——有就直接删会让平台自动关闭那些 PR，而作者看到的是「我的稿子被撤了」。

### 写回平台

Issue、PR、评论、Release 的正文只要含中文或任何非 ASCII，**一律先写入系统临时目录的 UTF-8 文件**，
再用 `--body-file` / `--notes-file` 提交；提交后回读、归一、比对；用完把文件删掉。

**不在命令行里拼正文。** shell 的编码与引号规则会静默吃掉几个字，而接口仍然返回成功——
只有打开页面才发现少了一句。

平台操作两条路都行：宿主自带的集成工具，或平台的命令行工具。**判据是能不能撤回，不是用哪条路**。

## 十、跨会话的工作记录：一本笔记，不是三份文档

**只在第二问为「会」时建**：跨多次会话、或存在需要人拍板的设计选择。五分钟改完的不建——
建了就要有人读它、维护它，那是一笔真实的成本。

参考做法常把「规格 / 计划 / 待办」拆成三份。好处是表达清楚，坏处是**同一件事的范围要改三处**，
而改漏一处不会有任何东西报错。这里合成**一份**，靠一节「产物清单」补回拆分的好处：

```text
必填  要解决什么 + 验收标准（C1、C2…，动手前冻结）
按需  规格与决策    ← 有需要人拍板的设计选择才建
      计划          ← 要分步才建，每一步后面跟它自己的验证命令
      取舍与放弃    ← 试过走不通的方案
      断点          ← 跨会话才填
必留  产物清单：建了哪几节 + **为什么没建其余几节**（每节一行）
```

**「为什么没建」是这一份里最要紧的一行。** 没有它，「没建规格」和「忘了建规格」长得一模一样；
有了它，审查者一眼就知道这次该有什么、实际缺的是不是真缺。

**谁改**：笔记由**这次改动的执行者**维护（主 Agent 直做就主 Agent 写，派了实现子代理就子代理写）。
**验收标准只能人点头改**，AI 只写草稿。**审查者一个字都不改**——它只读，改了就等于自己给自己
出题再自己判卷。

- **先探既有目录，不搬家**：`docs/work`、`docs/tasks`、`docs/adr`、`todo`、`work`，
  探到哪个用哪个；都没有才建一个。
- **文件名 `YYYY-MM-DD-一句话主题.md`**：日期在最前，写建单那天，之后不改；不带编号（半年后没人
  认得出，编号还会重排、会撞）；不带状态（写进名字就要改名，改名会断掉所有引用）。
- **完成不建 `done/` 子目录**：状态写在表头那一行。建子目录等于把「已完成的」推进一个没人再看
  的角落，同时让所有指向它的链接失效。
- **执行者写身份**：提交署名 + 平台账号，现场取。禁写「AI」「我」「本次会话」。
- **必含「决策与放弃」**：记下试过走不通的方案。它比选中的更值钱。
- 有远端时在表头记 Issue / PR 关联（只写编号，不复制正文）；没有远端就只记分支。
- 骨架在 `templates/work-item.md`。

### 验收标准那一节是审查的入口

- 一条一行，id 用 `C1`、`C2`，指向要判的那条标准。**编号形状不是格式洁癖**：审查写 `fail: C4`，
  标准写成 `1.` 或 `-`，两处就永远对不起来，而那时人只会以为「审查漏看了 C4」。
- 每条必须能被**一条命令或一条断言**证明。「体验更顺」不是一条标准。
- 没有它，审查只能回答「还能不能再找出问题」——而那个问题永远找得到。审查循环不收敛，
  根因就在这里。

## 十一、失败与恢复

| 情况 | 怎么做 |
| --- | --- |
| 合并冲突 | 在**提案那一侧**解决（把默认分支合进来），不在主干预演一遍 |
| 合错了 | `git revert` 造一个反向提交；不改写已推送的历史 |
| 提案被强制推送过 | 重新看一遍 diff——上次审的那份已经不是现在这份了 |
| 审查循环不收敛 | 停下，把「还差哪几条标准」列成清单，往后每轮只判这几条 |
| 同一条标准两轮都没过 | 触发止损，停下交人。不要「再修一轮看看」——那是方向错了的信号 |
| 分支删不掉，报「未合并」 | 先看它是不是还被某个 worktree 检出着；卸掉 worktree 再删，不要直接上 `-D` |
| 两个位都在，但不知道该用哪个 | 要提交的进实施位，要改坏再还原的进审查位。混着用一定会还原失败 |

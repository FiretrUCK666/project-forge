# 协作：别人的改动怎么进来

## 何时读本文件

项目有远端、而这次要处理「改动怎么落地」时读：收别人的 Issue、审 PR、决定谁能合、
合并完怎么收尾，或判断自己这次该推主干还是拉分支。

---

## 一、先判角色：这一步决定「你能做到哪一步」

| `git.role` | 你是谁 | 能做什么 |
| --- | --- | --- |
| `maintainer` | 远端就是项目正本 | 可以直接推主干；能不能推取决于主干保护 |
| `contributor-fork` | 这是别人的仓库的 fork，或你只是贡献者 | **推自己的分支 + 开 PR**。不推主干、不打标签、不发版 |
| `undetermined` | 比不出来（项目没声明源仓库） | **按贡献者处置**。它的意思是「没比出来」，不是「维护者」 |

**判断不了时按贡献者走。** 贡献者的路径在任何情况下都不会造成不可逆后果；
维护者的路径可能直接把改动推上一个不该动的仓库。

---

## 二、再判改动性质（只有维护者这一侧需要）

| 问什么 | 命中的含义 |
| --- | --- |
| 主干受不受保护 | 受保护就不能直推，只能走 PR |
| 会不会有第二个人改 | 有就必须审查；而审查只能发生在合入之前 |
| 改动可不可逆 | 删了拿不回来的（发布链路、门禁、包边界）必须走 PR |

三条都不命中 → **主干直推**：改文件 → 跑门禁 → 确认范围 → 提交 → 推送。

**不要拿「推得上去」当许可。** 主干保护开没开是仓库设置里的事，脚本读不到。它开着时直接
推送会被拒——那是设计，不是故障。

---

## 三、收到别人的 Issue

**不要凭猜测改代码。** 先核实四要素：期望什么、实际发生什么、怎么复现、在什么环境上。

- 信息不够 → 在原处礼貌追问最小复现条件。**不要自己补全然后按猜测改。**
- 能复现 → 先写一个**能稳定复现的失败测试**，再改代码让它通过。顺序反了的话，
  你永远不知道自己修的是不是那个问题。
- 复现不了 → 如实说「按描述复现不出来」并附上你试了什么。这比改一个可能不相关的地方好。

---

## 四、审别人的 PR

### 先只读，再检出

**第一步是看 diff，不是跑起来。** 重点看三处：`.github/workflows/` 有没有被改
（门禁本身被改松是最隐蔽的问题）、`package.json` 的 `preinstall` / `postinstall` 之类钩子
（它们在安装时执行代码）、依赖锁文件有没有引入新来源。

**在本地检出并装依赖之前，先确认真没有可疑脚本。**

### 没有关联 Issue 不是退回的理由

只要 PR 说清了「解决什么问题、改了什么、怎么验证」并且门禁过了，它就是有效贡献。

### 审查只看「哪几条标准没过」

有效的意见**指向具体标准**：

> 第 2 条（新命令有没有写进 README）没过——`npm run lint` 加进脚本了，README 没提。

无效的意见**给感受**：「我觉得这里可以再想想」。后者的用途是讨论，不是审查。
把它当阻塞理由，循环永远收敛不了，因为「还能不能想出问题」的答案永远是「能」。

### 自己审自己也一样

改完、门禁全绿、看着没问题，就合了——这个动作里，「看着没问题」正是自审的产物。
**门禁与审查是两件事**：门禁判「现有检查过没过」，审查判「这次改动有没有让检查本身变松」。

高风险改动（判定逻辑、门禁配置、发布链路、包边界）派一个新上下文看，只给它材料清单
（目标、验收标准、diff、门禁输出），**不给它执行者的理由与上一轮结论**——给了，
它会顺着你的理由往下看。

### 验证测试真的在测东西

关掉刚加的核心逻辑，对应的测试会红吗？不会红就说明它测的是「代码跑起来不崩」，
不是「这件事做对了」。

---

## 五、谁能合：按「收不收得回来」分档

| 档 | 判据 | 谁能合 |
| --- | --- | --- |
| 低 | 不满意可以再改一次就好：文档、注释、新加的测试、独立模块内部实现 | 门禁全绿即可自动合 |
| 中 | 会影响到使用者，但改回来不难：新功能、重构、依赖小版本升级 | 合完要通知人 |
| 高 | **收不回来**：发布链路、门禁配置、包边界、数据迁移、鉴权 | **必须人合** |

**一条独立的硬规则：弱化门禁的改动一票否决。** 删测试、放宽断言、加跳过标记、
把检查改成警告——不管是谁提的，都要人明确点头。

外部来的 PR 一律不自动合，不管门槛多低：你无法为一个陌生人的改动承担后果。

## 六、合并之后

```sh
gh pr merge <号> --merge          # 1. 合并
gh pr view <号> --json state      # 2. 回读确认真的 MERGED
git checkout main && git pull     # 3. 切回主干取回合并提交
git branch -d <分支>              # 4. 删本地分支（用 -d，不用 -D）
git ls-remote --heads origin <分支>  # 5. 查远端分支还在不在
```

### 四个坑

1. **把合并与删分支写在一条命令里**：失败时分不清是哪一步坏的。
2. **不确认状态就删分支**：合并失败时删掉分支，改动就丢了。
3. **用 `-D` 强删**：它绕过「这个分支合并了吗」的检查，把没合进去的东西一起删掉。
4. **以为删远端分支失败了**：GitHub 可以设成合并后自动删分支。查不到 = 已经删了，
   那是完成态，不是错误。

**合并后**：如果项目有工作记录，把状态改成完成并写清实际结果（不是「已完成」三个字）；
如果配了发布链路，判断这次要不要发版（见 `references/publish.md`）。

---

## 七、跨会话的工作记录

**只有需要跨多次会话、或可能换人接手的事才建。** 五分钟能改完的不建——建了就要有人读它、
维护它，那是一笔真实的成本。

要建的话骨架在 `templates/work-item.md`，放在 `docs/work/` 下。里面至少三样：**要解决
什么**（可验证的验收标准）、**做到哪儿了**、**下一步从哪进**。这三样是「换一个人接手能
不能继续」的最小集合。

---

## 八、失败与恢复

| 情况 | 怎么做 |
| --- | --- |
| 合并冲突 | 在**提案那一侧**解决（拉主干进来合），不要在主干预演一遍 |
| 合错了 | `git revert` 造一个反向提交；不要改写已推送的历史 |
| 提案被 force-push 过 | 重新看一遍 diff——你上次审的那份已经不是现在这份了 |
| 审查循环不收敛 | 停下：把「还差哪几条标准」列成清单，每轮只判这几条 |

最后一条值得说透：审查的目的是「这次改动可以合了吗」，不是「还能不能找出问题」。
后者永远有答案，因此**不能用它当判据**。

# 协作：改动怎么进来、怎么审、怎么收尾

## 何时读本文件

这次要处理「改动怎么落地」时读：判断自己这次该推主干还是拉分支、收别人的 Issue、审 PR、
派独立审查、判谁能合、合并完收尾。**没有远端也读**——独立审查不依赖远端存在，它依赖
「这处改坏了不会当场失败」。只自己改自己用、又从不碰高风险路径的项目可以不读。

## 一、先判角色：这一步决定「你能做到哪一步」

| `git.role` | 判据 | 能做什么 |
| --- | --- | --- |
| `maintainer` | 远端就是项目正本 | 可以直接推主干（能不能推取决于主干保护）。**打标签与发版是另一件事**，见下面那一段 |
| `contributor-fork` | 这是别人仓库的 fork，或你只是贡献者 | 推自己的分支 + 开 PR。不推主干、不打标签、不发版 |
| `undetermined` | 比不出来（项目没声明源仓库） | **按贡献者处置**。它的意思是「没比出来」，不是「维护者」 |

**判不了时按贡献者走。** 两边的代价不对称：走错贡献者只少做几步（分支推了没人合，补一次 PR 就行）；
走错维护者那一侧，改动会推上一个不该动的仓库，推送撤不回来。角色从 `git.role` 读，不靠推断。

### 还有一格：你是维护者，但这次动的是别人提的东西

角色回答「这是不是你的主场」，不回答「这次改动的作者是谁」。后者决定**能不能要求对方遵守你的流程**：

| 作者 | 能不能要求他走完整流程 | 要不要为他建内部工作记录 |
| --- | --- | --- |
| 维护者自己 | 是 | 要（跨会话或可能换人时） |
| 有写权限的协作者 | 是 | 要 |
| **外部贡献者**（fork 来的 PR、外部账号提的 Issue） | **不能**。只要他说清「解决什么问题、改了什么、怎么验证」且门禁过了，就是有效贡献 | **不建**。上下文就在 Issue 与 PR 里，那是他能看到的地方 |

第三种最容易做错：把内部那套「先开 Issue → 冻结标准 → 建工作记录」当成入场门槛，等于给参与设一道
他并不知道存在、也打不开的门。**「没有关联 Issue」不是退回的理由**；要求先开 Issue 只在确实需要
复现信息时成立，那是提问，不是门槛。反过来，对外部 PR **也不放宽判断**：门禁照跑、审查照做，
只是不要求他交内部格式的产出。

### 独立审查这一条，不随角色变

给别人打审、给外部 PR 打审、审自己在维护者身份下做的改动——**审查者与执行者必须是两个不同的上下文**。
宿主给不了子代理就用新会话，没有新会话就换一个人；**判据是「独立」，不是「用了哪个工具」**。
判不了有没有独立时，按「没有独立」处理：自查通过可以合并低风险改动，但**高风险路径的改动不许放行**。

### 分档的判据是「能不能撤回」，不是「是不是对外」

把「推送」整个当成需要批准的动作，是这条判据最容易出错的地方：**推自己的分支、开 PR
都能撤回**（删分支、关 PR 即可），它们是日常；**合并、发版、改可见性、改写历史撤不回来**，
这几件才要人点头。

| 动作 | 撤回方式 | 要不要等确认 |
| --- | --- | --- |
| 提交 | 本地回退 | 不要 |
| 推自己的分支 | 删掉那条分支 | 不要 |
| 开 PR / 改 PR | 关掉，或再改一版 | 不要 |
| 合并进默认分支 | 只能反向提交，而且别人可能已经基于它工作 | **要** |
| 发版（打标签、建发布页、发制品库） | 不能 | **要**，且只有明确说「发版」才做 |
| 改可见性（私有转公开） | 不能，抓走的内容要不回来 | **要** |
| 改写历史 / 强制推送 | 不能，所有克隆过的人都要重拉 | **永不自动** |
| 删已发布版本 | 不能 | **永不自动** |

判据只有一条：**出错了能不能当没发生过。** 能，就往前走；不能，就停下来给人看。

这条判据管**所有项目**，包括维护本 skill 自己：维护它同样是「拉分支 → 提交 → 推分支 →
开 PR → 人合并」，不比治理别人的项目多一步确认，也不少一步审查。

### 「维护者」不等于「可以自己决定发版」

角色只回答「这个仓库是不是你的主场」，**它不回答问题「这一版该不该现在发」**。后者要人点头：

| 你看到的 | 该做什么 |
| --- | --- |
| 「改好了推一下」 | 拉分支 → 跑门禁 → 提交 → 推自己的分支 → 开 PR。合并之后**到这里就结束** |
| 「发版」「发个版本」 | 走 `publish.md` 的流程 |
| 攒了几个改动、版本号看着该抬了、上个标签隔得久 | **什么都不做**。这些都不是发版理由 |

这条与「有没有权限」无关，与「能不能撤回」有关：推分支、开 PR 撤得回来，合并、发版收不回来。

## 二、再判改动性质（只有维护者这一侧需要）

三问，命中任一就走 PR：

| 问什么 | 命中的含义 |
| --- | --- |
| 主干受不受保护 | 受保护就不能直推，只能走 PR |
| 会不会有第二个人改 | 有就必须审查；而审查只能发生在合入之前 |
| 改动可不可逆 | 拿不回来的（发布链路、门禁配置、包边界、数据迁移、鉴权）必须走 PR |

三条都不命中 → 主干直推：改文件 → 跑门禁 → 确认改动范围 → 提交 → 推送。

**「三条都不命中」比想象中窄。** 主干保护、会不会有第二个人改、可逆性——只要有一条命中就走分支 + PR。
而仓库只要有保护规则，「主干受保护」这一条就恒为真，于是**所有改动都走 PR**，哪怕它只是
改了一个错别字。这不是流程变重，是判据本来的结论：**能不能撤回**决定推哪一档。

**不要拿「推得上去」当许可。** 主干保护是仓库设置，脚本读不到。它开着时推送会被拒——那是设计，
不是故障。

### 五档分流

先定档，再动手。档位决定「开工前必须有什么」，不是决定「改动看起来大不大」。

| 档 | 判据 | 开工前必须完成的产物 | 谁改 | 允许改代码的时机 |
| --- | --- | --- | --- | --- |
| 纯文档 | 只动 `.md`、注释、模板文字 | 无 | 主 Agent 直接改 | 随时；门禁仍要跑 |
| 局部缺陷修复 | 有能稳定复现的最小用例 | 失败测试 + 一条防误伤的反例 | 主 Agent 直接改 | 测试先红 |
| 局部变更 | 改了行为，没动对外契约 | 冻结的验收标准 + 一句范围说明 | 主 Agent 直接改 | 标准冻结之后 |
| 较大功能或触契约 | 新接口、新配置项、依赖大版本、门禁或流程变化 | 工作记录（含冻结标准）+ 计划 | **派实现子代理** | 工作记录提交之后（提交即领活） |
| 与既有契约冲突 | 要改已公布的接口、格式、命名 | 决策记录 + 弃用与迁移路径 + 用户点头 | 派实现子代理 | 决策被接受之后 |

**「谁改」这一列的判据是「改坏了会不会当场失败」，不是「改动看起来大不大」。** 主 Agent 直接改的
好处是快、上下文连续；代价是改出问题时它顺着自己的思路检查，看不出来。所以一旦这一处坏了不会
当场红（判定逻辑、门禁配置、发布链路、包边界），就得换一个上下文去做，好让审查那一步真的独立。

**AI 只写草稿，不能自己批准。** 第 4、5 档的产物要人点头才算成立。自己判「标准够了」等于没冻结，
而那正是审查要防的事。

### 留痕：分流的结论要写下来

判定完不算完，**结论要落在别人看得到的地方**：首次回复、Issue 评论、或 PR 正文的「实现依据」栏。
写清两件事——这次落在哪一档，以及为什么不需要更重的产物（或需要的产物在哪）。

不留痕的后果很具体：审查的人拿不到「原本说好做什么」，只能凭 diff 猜意图，于是它审的是一份
自己想象出来的需求。占位式的留痕（「按 issue 实现」「见需求」「TBD」）等于没写。

### 门禁分档与证据绑定

同一套门禁不必每次都全跑。三档，按改动落在哪些目录选：

| 档 | 跑什么 | 什么时候 |
| --- | --- | --- |
| `fast` | 类型检查、静态检查、编译 | 边改边跑 |
| `affected`（默认） | 加上受影响模块的单元测试 | 提交前 |
| `full` | 加上集成测试、构建、端到端 | 提 PR 前，或动了公共部分 |

**要环境才能跑的门禁，缺环境时记「跳过 + 原因」，不许伪装成通过。** 一条写着「跳过：本机没有
数据库」的记录是有用的；一条什么都没写的绿灯是假的。

**证据绑定提交 HEAD**：门禁跑完之后又改了代码，那份输出就作废了——它证明的是「上一个提交
是绿的」。改过就得重跑，重跑之后才提 PR。这一条不需要工具支持，只需要在 PR 的「怎么验证的」
一栏里贴的是**最后一次**跑出来的东西。

### 冻结验收标准

**动手之前冻结。** 冻结的意思是：**改它可以，但要留下痕迹**——加一条或改一条都要回工作记录里
正式写，并说明为什么改。不许在审查进行中顺手加减，那等于挪动靶子。

- 一条一行，id 用 `C1`、`C2`，指向要判的那条标准。
- 每条必须能被**一条命令或一条断言**证明。「体验更顺」不是一条标准。
- 没有它，审查只能回答「还能不能再找出问题」——而那个问题永远找得到（任何代码都还能再补一处
  边界处理）。审查循环不收敛，根因就在这里。
- **定歪了要改，就写明理由再改。** 拿一个代理指标当判据（比如「行数下降」，而真正要保证的是
  「结论词不进判定」）是真实会发生的事，发现之后改判据本身是正当的；不正当的是悄悄改。

## 三、收到别人的 Issue

五步，前一步没做完不进下一步：

1. **核四要素**：期望什么、实际发生什么、怎么复现、在什么环境上。
2. **缺则追问，追问发到 Issue 评论里。** 只留在自己会话里的追问等于没写——作者看不到，
   下一个接手的人也看不到。
3. **领活**：把工作记录的状态改成进行中并提交（见第八节，提交即锁）。
4. **拉分支，先写能稳定复现的失败测试，同时写一条防误伤的反例**（修好之后它必须仍然绿）。
5. **再改实现**，直到那条失败测试转绿，且反例没被带坏。

**严禁盲猜改代码。** 没复现就动手，改中的概率取决于运气，而改动本身会让人以为问题已处理过。
复现不出来时如实说「按描述复现不出来」并附上试了什么。缺陷报告骨架在
`templates/issue-bug-report.md`。

## 四、审别人的 PR

### 先只读审 diff，不检出

**第一步是读 diff，不是跑起来。** 检出之后一次装依赖就可能执行陌生人的代码（安装生命周期钩子），
而那时你已经在自己的机器上、用你自己的凭据跑过它了。四处重点：`.github/workflows/` 里的门禁
有没有被改松；`preinstall` / `postinstall` / `prepare` 一类生命周期钩子；门禁判据有没有被放宽、
加跳过标记或改成警告；依赖锁文件有没有引入新来源（换 registry、git 地址、tarball 直链）。

跑门禁时**加 `--ignore-scripts` 一类参数**关掉生命周期脚本。要装依赖才能验的部分，
先确认真没有可疑脚本，再装。

**没有关联 Issue 不是退回的理由。** 只要 PR 说清了「解决什么问题、改了什么、怎么验证」
并且门禁过了，它就是有效贡献。要求先开 Issue 只在你确实需要复现信息时才成立——那是提问，
不是门槛。

### 审查只看「哪几条标准没过」

有效意见指向具体标准：

> 第 2 条（新命令有没有写进 README）没过——脚本加了 `lint`，README 没提。

无效意见给感受：「我觉得这里可以再想想」。它的用途是讨论，不是审查。拿它当阻塞理由，
循环永远收敛不了。

### 自己审自己也一样

改完、门禁全绿、看着没问题就合——这个动作里「看着没问题」正是自审的产物。
**门禁与审查是两件事**：门禁判「现有检查过没过」，审查判「这次改动有没有让检查本身变松」。

再确认一遍测试真的在测东西：关掉刚加的核心逻辑，对应的测试会红吗？不会红，说明它测的是
「代码跑起来不崩」，不是「这件事做对了」。

### 高风险改动：独立上下文审查 + 故障注入

高风险改动（判定逻辑、门禁配置、发布链路、包边界）必须派一个**新上下文**看（子代理或新会话）。

- **只给材料清单**：目标、冻结的验收标准、**被审的那份 diff 的哈希**、门禁原始输出、
  **PR 里前几轮的审查栏**（只有那四栏，不是执行者的说明）。
- **绝不给执行者的思路与上一轮结论。** 给了它只会顺着复核，最后得到一个「同意」。
  这里要说清「给什么」与「不给什么」的界线：**前几轮的 `fail: C4` 是记录，不是结论**——
  它说的是「第四轮的时候这一条没过」，而这次过没过要审查者自己判。
  不给前几轮记录，审查者就没法知道自己是不是第二轮、C4 是不是已经连败两次，
  「同一条标准连续两轮没过就止损」那条规则也就执行不了。
- **判通过必须交一份故障注入记录**：在最终那版代码上删掉一行防御代码，或反转一处判断，
  跑对应用例，**亲眼看到它变红**；再还原，确认变绿。测试全绿有两种可能——代码对了，或者测试
  是空的；只有看到它红过，才排除后一种。
- **为外部贡献者不建内部工作记录。** 外部 PR 的上下文在 Issue 与 PR 里，那是作者和后来的人
  都能看到的地方；另建一份内部记录，等于把「为什么这么改」藏进一个他打不开的地方。

具体怎么给出结论、几轮之后收窄范围、什么时候该停，全在下一节。**审一次就得出「还能再改改」
不是严谨，是把「还能不能再找出问题」当成了判据**——那个问题永远有答案。

## 五、审查循环：怎么才会停

审查的目的是回答「这次改动可以合了吗」，不是「还能不能找出问题」。后者永远有答案：任何代码都
还能再补一处边界处理，任何命名都还能更贴切。拿它当判据，循环就不会收敛——改一轮、审一轮，
每轮都能挑出真的问题，而其中大多数是第一轮就存在、只是上一轮没扫到的。

下面六条是一套。前五条管「这一次怎么停下来」，第六条管「这一类以后还会不会再漏」。缺任何一条，
循环都会往「再来一轮」的方向滑。

### 1. 判据只有一份：动手前冻结的验收标准

审查只回答「C1、C7 没过」，不回答别的。标准在工作记录里，动手之前冻结（见第八节）。

**冻结的意思是「改它要留痕」，不是「一个字都不许动」。** 要加或要改，回工作记录正式写一行，
说明为什么——那是一个需要说明的动作，不是审查时顺口一提。标准本身定歪了（拿代理指标当判据）
是真实会发生的事，发现之后改判据是正当的；不正当的是悄悄改，让审查对着一个已经变过的靶子判。
冻结是为了防止标准被无限扩大，不是为了用一个粗糙的指标把自己锁死。

### 2. 结论由字段派生，审查者不宣布「通过」

一轮审查只交四样东西，**一项一项写成字段**（PR 里那四个栏目的名字就是从这里来的）：

```text
审查来源: 子代理 / 新会话 / 另一个人（与执行者不是同一个上下文）
逐条标准状态: fail: C1, C4 / pass: C2, C3, C5, C6
故障注入记录: <删了什么 → 哪条变红 → 还原后是否绿>
止损记录: <触发了哪条，或「未触发」>
```

「通过」不是审查者写的一句话，是 `逐条标准状态` 里没有 `fail`、且 `故障注入记录` 非空时**算出来的**。
按这个规则，任何一个人读完那两栏都能得到同一个结论，不需要理解审查者的措辞。

为什么不能靠声明：结论一旦用自然语言写，读者只能读字面，而中文否定的写法多得数不清
（「不建议不合并」「除 C1 外基本没问题」「不算完全通过」）。要把这些读懂，就得写一套语言
解析器，而它迟早会读错一条——读错的后果是把「没过」当成「过了」。

同理，审查报告里**不写「整体不错」这类评价**。它既不是 fail 也不是 pass，唯一的用途是
让执行者猜该不该改。

### 3. 四条收敛规则

| 规则 | 治什么 |
| --- | --- |
| **第 1 轮看全量**：本 PR 的改动，加上它影响到的地方（调用方、契约、相邻模块） | 前几轮本来就要查全，这个范围是对的 |
| **第 3 轮之后只看新增的那几行**，不再整体重看 | 每轮从头看，必然每轮翻出第一轮就在的旧问题——那些不是这轮改出来的 |
| **同一类问题一次全部指出**：同一个错在五处出现，一次报五处 | 一次只报一处，下一轮又冒出同类，永远收敛不了 |
| **已经提过、还没被改的不重复提** | 重复提让执行者反复应对同一条，也让「还剩几条」看不出变化 |

收窄范围不会漏掉问题：前几轮已经把改动和它的影响面看过几遍，这时候还剩的多是「这轮新改的
那几行引入的」——那正是重点。

### 4. 两条止损

| 触发 | 动作 |
| --- | --- |
| **同一条标准连续两轮没过** | 停下。局部卡住说明方向错了，不是再修一轮就好 |
| **轮次超上限**（默认 3 轮全量 + 2 轮增量） | 停下。兜底，防止「每次只差一点」把轮次拖长 |

止损的动作是**停下来交给人**，不是自动再来一轮。交人的时候要交三样：还差哪几条标准、卡在
哪里、你判断的根因是什么。交接之后由人决定是放宽标准、改方向，还是继续。

**「还差一点」不是继续的理由。** 上限的意义就是不给这句话留口子。

这两条要执行，审查者必须知道两件事：**这是第几轮**、**上几轮哪几条没过**。所以材料清单里
明写「PR 里的前几轮审查栏」是可以给的——它给的是记录，不是结论。轮次以 PR 里那几行
「一轮一行」为唯一计数处：数到第几行就是第几轮，这一个人也能算，不靠谁记。

### 5. 打回之后怎么返工

打回（`fail` 非空）之后，**这个提案不得合并**，固定走这一套：

1. **在原分支追加提交**。不新建分支、不新开第二个 PR、不 force push、不关 Issue。
2. **重跑门禁**，产出绑定新 HEAD 的证据。改过代码之后没重跑的门禁结论是作废的。
3. **更新同一个 PR**，在 PR 里留言记下新的 HEAD。
4. 审查者在新 HEAD 上重新审一轮，重复直到 `fail` 为空。

**HEAD 没前进就重提，直接拒绝**：拿同一个提交反复送审，等于让审查者重复看一遍一模一样的东西，
而每一轮它都可能报出上一轮没扫到的问题——这正是无限循环最常见的形状。

**已经合并的 PR 不再审、不再打回。** 合并之后才发现的问题按新 Issue 处理，用同一个 Issue
绕过流程再开第二个 PR 是不允许的。

**审查进行中 diff 变了，重判。** 这不是罕见情况：执行者一边改、审查者一边看，中途落一次改动
是常态。规则只有一条：**以你交结论那一刻的 diff 为准**，并在审查栏里记下它的哈希。
你要判的那几条标准如果落在这份新 diff 里，就按新 diff 重判；之前判过的条目不许直接沿用。
一句话：**结论永远绑在一个确定的 diff 上，不绑在「刚才看的那个」。**

### 6. 漏检要落成回归，不落成印象

审查放过了、后来出事的那个问题，**落一条回归用例**：造一个能复现它的夹具或断言，放进项目
自己的测试里。下次同一类错误再出现时，是门禁先红，不是又一轮审查靠运气碰到。

这条比前五条重要，但见效最慢：前五条让**这一次**停下来，这一条让**下一类**根本进不来。
没有它，止损只是把循环截断——同一个病换个形状再来一次，照样从头审起。

**不写「下次注意」。** 那是一句印象，三个月后没人记得，而它看起来像已经处理过了。

## 六、谁能合：按「收不收得回来」分档

| 档 | 判据 | 谁能合 |
| --- | --- | --- |
| 低 | 不满意再改一次就好：文档、注释、新加的测试、独立模块内部实现 | 门禁全绿即可自动合 |
| 中 | 会影响使用者，但改回来不难：新功能、重构、依赖小版本升级 | 合完要通知人 |
| 高 | **收不回来**：发布链路、门禁配置、包边界、数据迁移、鉴权 | **必须人合**，且先跑独立上下文审查 |
**一条独立的硬规则：弱化门禁的改动一票否决。** 删测试、放宽断言、加跳过标记、把检查改成警告
——不管谁提的，都要人明确点头。

**外部来的 PR 一律不自动合**，不管门槛多低：你无法为一个陌生人的改动承担后果。

**「独立审查」与「谁能合」是两个问题。** 低风险档也建议有一次独立审查；高风险档两者都要——先有
独立审查的 `fail` 为空，再有人点头合并。只有一条是死的：**审查者与执行者不能是同一个上下文**。

## 七、合并之后

### 固定七步，顺序不能调

1. 合并 PR（**不勾选自动删分支**）——`gh pr merge <号> --merge`
2. 回读确认已合：`gh pr view <号> --json state`，必须是 `MERGED`
3. 更新工作记录与 Issue
4. 切回默认分支并取回合并提交：`git switch <默认分支> && git pull`
5. **先卸 worktree**：`git worktree remove <worktree 路径>`
6. **再删本地分支**：`git branch -d <分支>`（不是 `-D`）
7. 查远端分支还在不在（`git ls-remote --heads origin <分支>`），**确认之后才** `git push origin --delete <分支>`

`<默认分支>` 现场取（勘察的 `git.originHeadBranch`），不写死 `main`。分支名同理。

**第 5 步必须在第 6 步之前。** 一个分支只要还被某个 worktree 检出着，`git branch -d` 就会拒绝
删除它——那时看到的报错是「分支未合并」，而真实原因是它被占用，两个原因的处理方式完全相反。
顺序反了，人就会去用 `-D` 强删，而 `-D` 绕过「这个分支合并了吗」这道检查。

### worktree：什么时候建，什么时候卸

默认**不建**。只有下面三条有一条成立时才建：

1. 要在最终 HEAD 上做故障注入，而执行者的工作区有未提交改动（改坏它等于破坏执行者的进度）；
2. 同一个仓库要并行做两件事；
3. 审查需要「把代码改坏验证测试会红」，而这处代码不能在被实现者使用的那个目录里动。

建的时候一律 **detached 检出最终 HEAD**，路径放在仓库根的 `.worktrees/<用途>-<短 SHA>/`，
并确认它已被忽略：

```sh
git worktree add --detach .worktrees/review-<短 SHA> <最终 HEAD>
# 校验你检出的就是被审的那一版，而不是「刚拉下来的分支」
git rev-parse HEAD   # 必须等于提案的 head SHA
```

审查结束、合并完成之后**必须卸掉**（第 5 步）。留着它的代价不是「多一个目录」：`.git/worktrees`
里的条目只增不减，`git worktree list` 慢慢变得没法读，磁盘上还留着几份完整检出。**「先留着，
以后再说」的以后不会来。**

### 四个坑

1. **把合并与删分支写在一条命令里**：失败时分不清是哪一步坏的。
2. **不确认状态就删分支**：合并失败时删掉分支，改动就丢了。
3. **用 `-D` 强删**：它绕过「这个分支合并了吗」这个检查，把没合进去的东西一起删掉。
4. **以为删远端失败了**：平台可以设成合并后自动删分支，查不到 = 已经删了，那是完成态。

删远端分支前必查三件事：本地已切回默认分支并 `pull`（否则可能正在删自己唯一那一份）；
这条分支上没有未合并的提交（`git log <默认分支>..<分支>` 为空）；**有没有未合并的下游堆叠 PR
以这条分支为 base**——有就直接删会让平台自动关闭那些 PR，而作者看到的是「我的稿子被撤了」。

### 写回平台

Issue、PR、评论、Release 的正文只要含中文或任何非 ASCII，**一律先写入系统临时目录的 UTF-8 文件**，
再用 `--body-file` / `--notes-file` 提交；提交后回读、归一、比对；用完把文件删掉。

**不在命令行里拼正文。** shell 的编码与引号规则会静默吃掉几个字，而接口仍然返回成功——
只有打开页面才发现少了一句。

## 八、跨会话的工作记录

**只在需要跨多次会话、或可能换人接手时建。** 五分钟改完的不建——建了就要有人读它、维护它，
那是一笔真实的成本。

- **先探既有目录，不搬家**：`docs/work`、`docs/tasks`、`docs/adr`、`todo`、`work`，
  探到哪个用哪个；都没有才建一个。
- **文件名 `YYYY-MM-DD-一句话主题.md`**：日期在最前，写建单那天，之后不改；不带编号（半年后没人
  认得出，编号还会重排、会撞）；不带状态（写进名字就要改名，改名会断掉所有引用）。
- **完成不建 `done/` 子目录**：状态写在表头那一行。建子目录等于把「已完成的」推进一个没人再看
  的角落，同时让所有指向它的链接失效。
- **执行者写身份**：提交署名 + 平台账号，现场取。禁写「AI」「我」「本次会话」——三个月后没人
  知道那是谁，而协作出问题时要找的正是具体的人。
- **必含「决策与放弃」**：记下试过走不通的方案。它比选中的更值钱，是下一个人最容易重复踩的坑。
- **提交状态即领活的原子锁**：把状态从待办改成进行中并提交，这一步成功才算领到。两个人同时改
  时会有一个推送被拒，那正是它该起的作用。
- 骨架在 `templates/work-item.md`。

### 三节按需填，验收标准那一节是审查的入口

工作记录有三节是可填可不填的，另有一节填了就必须守：

| 节 | 什么时候必填 |
| --- | --- |
| 验收标准 | 要走独立审查就必须有。**编号 `C1`、`C2`，每条能被一条命令或一条断言证明** |
| 计划 | 要分几步做时。**每一步后面跟它自己的验证命令** |
| 勾选清单 | 步骤多到要逐条划掉时（可以直接用「计划」那节的勾选框） |
| 决策与放弃 | 试过走不通的方案，任何时候都值得记 |

**编号形状不是格式洁癖**：审查的 `fail: C4` 要能对上标准里的那一条，编号写法一变，两处就对不
起来，而那时人只会以为「审查漏看了 C4」。

## 九、失败与恢复

| 情况 | 怎么做 |
| --- | --- |
| 合并冲突 | 在**提案那一侧**解决（把默认分支合进来），不在主干预演一遍 |
| 合错了 | `git revert` 造一个反向提交；不改写已推送的历史 |
| 提案被 force-push 过 | 重新看一遍 diff——上次审的那份已经不是现在这份了 |
| 审查循环不收敛 | 停下，把「还差哪几条标准」列成清单，往后每轮只判这几条 |
| 同一条标准两轮都没过 | 触发止损，停下交人。不要「再修一轮看看」——那是方向错了的信号 |
| 分支删不掉，报「未合并」 | 先看它是不是还被某个 worktree 检出着；卸掉 worktree 再删，不要直接上 `-D` |

审查的目的是「这次改动可以合了吗」，不是「还能不能找出问题」。后者永远有答案，所以它不能当判据。

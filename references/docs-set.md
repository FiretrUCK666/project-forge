# 文档套装

## 何时读本文件

要写或改项目文档时读：`AGENTS.md`、`README`、`CONTRIBUTING`、`LICENSE`、`RELEASING`、`CHANGELOG`，以及 `.github/` 下的 Issue 与 PR 模板。

## 一、读者是谁，决定怎么写

| 文档 | 读者 | 怎么写 |
| --- | --- | --- |
| `AGENTS.md` | **AI**，每次会话自动读 | 写机制、边界、命令、不变量。要具体值时写「从哪里取」 |
| `README` | **人**，可能第一次听说这个项目 | 可直接复制的命令与地址。第一屏说清「这是什么、怎么跑起来」 |
| `CONTRIBUTING` | **外部贡献者** | 怎么装环境、怎么跑门禁、怎么提改动与反馈 |
| `LICENSE` | **法律意义上的使用者** | 逐字用标准全文，只换年份与版权持有人 |
| `RELEASING` | **要发版的人** | 说明写在哪、分哪几节、按什么顺序发 |

这条区分决定一切：**AI 读的那份写机制与「从哪里取」**，因为它会推理、会自己找；**人读的那份写可直接复制的命令与地址**，因为他是照着做的。写反了的后果不对称：给 AI 写死取值，环境一变就全错；给人写「去清单里读版本号」，他根本不会去读。

### 「永不覆盖」对散文文件是什么意思

**先读，再判断，只补缺的。** 已有的章节不重写；觉得不好就在汇报里说，不直接改。缺的插在合适位置，保持原有标题层级、语气、语言与格式。只有用户明确说「重写」时才整篇替换。散文文件与结构化文件不同：`AGENTS.md` 里带标记的区间归模板管，可以刷新；一篇手写的 `README` 没有标记，它整篇都是人的表达。

### 用户不可达时怎么办

被委派的子代理、无人值守运行都会遇到。判据是：**问不到人不能成为停顿的理由，也不能成为自作主张的借口。** 用安全默认值推进，把决定权留清楚：

| 决定 | 安全默认 |
| --- | --- |
| 可见性 | **私有** |
| 许可证 | **不落**——编一个许可证是替人做法律决定 |
| 收不收外部贡献 | 不落协作模板 |
| 要不要 CI | **默认落**，但只跑项目已有的命令 |
| 署名 | 从环境读（`identity`），读不到就留着缺并说明 |

推进完之后，在汇报里单独列一段「等你回来的三件事」：哪几项用了默认值、默认值是什么、你改的话该改哪个文件。不要混在正文里——混进去的那一段，读的人会跳过。

### 只有用户能定的那几件事

集中一次问完，不要分几次打断。这几件脚本推不出来，也都只在写文档这一步才需要：

| 事 | 为什么不能替你定 | 要不到时 |
| --- | --- | --- |
| 许可证 | 法律决定，后果在别人手里 | 不落，记成待定 |
| 署名来源 | 决定提交记在谁名下、写不写真实邮箱 | 从环境读，读不到就留缺 |
| 可见性 | 公开不可撤销 | 私有 |
| 账号或组织 | 决定推到哪儿 | 当前登录的账号 |
| 收不收外部贡献 | 决定要不要落协作模板 | 不收 |
| 要不要自动发版 | 涉及仓库写权限与凭据 | 不配 |
| 发版说明分几节 | 读者关心的事因项目而异 | 用模板的默认菜单 |

**运行环境最低版本不问。** 直接读勘察的 `artifacts.runtimeRequirements`，照抄进文档。用户随口报的版本与清单里写的对不上，两处就永久漂移，而漂移的那一处总有人照着做。

## 二、必须的只有两件

| 文件 | 必须吗 | 什么时候落 | 骨架 |
| --- | --- | --- | --- |
| `README.md` | **是** | 一直 | `templates/readme.md` |
| `AGENTS.md` | **是** | 一直 | 由 `scripts/compose-agents.mjs` 从 `templates/agents-project.md` 生成 |
| `LICENSE` | 看情况 | 公开项目、可发布项目、用户点名要 | `templates/license-<类型>.txt` |
| `CONTRIBUTING.md` | 看情况 | 要收外部贡献 | `templates/contributing.md` |
| `RELEASING.md` | 看情况 | 要发版 | `templates/releasing.md` |
| `docs/release-notes/<标签>.md` | 看情况 | **明确被要求发版时**，每次发版一份 | `templates/release-notes.md` |
| Issue 模板 | 看情况 | 要收外部报告 | `templates/issue-bug-report.md`、`templates/issue-feature-request.md` |
| PR 模板 | 看情况 | 要收外部改动 | `templates/pull-request-template.md` |
| 工作记录 | 看情况 | 要跨会话 | `templates/work-item.md` |
| CI 流水线 | 看情况 | 要持续集成 | `templates/ci-check.yml`、`templates/ci-release.yml` |

**少一件不是缺陷。** 单语项目不需要翻译，个人项目不需要贡献指南，不发布的项目不需要发版规范。把偏好写成缺口，会让每个项目都欠一笔永远还不完的债，而还债的方式是加一个开关把它压下去——那时文档里就多了一个没人看得懂的状态。

## 三、`AGENTS.md`

### 它是项目契约，不是作者笔记

判断标准：**换一个人接手，这份文件还成立吗？**

| 能写 | 不能写 |
| --- | --- |
| 机制、边界、不变量、硬性规范 | 某个账号的用户名、邮箱 |
| 构建 / 测试 / 发布该做什么、按什么顺序 | 推送目标、发布目标这些**取值** |
| 为什么这样要求 | 一次性的版本号、日期、某人当时的决定 |

### 已经有的怎么办

| 现状 | 动作 |
| --- | --- |
| 不存在 | 生成一份，用勘察事实填能填的部分 |
| 有 `project-forge: begin/end` 标记 | 刷新**还带 `fill` 占位**的区间，标记之外、填好的一律不动 |
| 存在但没有标记 | **不动** |

第三种最容易做错。用户手写的契约里可能有一句「这个项目的 X 永远不许改」，那是他从事故里学来的——自动生成的东西不会知道。真要补，用 `--upgrade`：只**追加**缺的节，每节带自己的标记，已有的字一个不动。

### 生成之后必须填掉占位

生成物里带 `<!-- project-forge: fill <要填什么> -->` 的，每一处都要填。填法是**读代码**，不是猜。填完删掉那一整行标记——**留着它，看起来就像「这里已经填过了」**。一份带空占位的契约比没有契约更糟，因为它让后来的人以为这一段已经交代清楚了。`scripts/review.mjs` 会把未填的占位报出来，这是唯一一个「不填就过不了体检」的文档项。

### 「## 取舍」节

由维护者写，脚本不碰。它是「只有使用者能定的事」的记录处：

```
- `license`：不放，因为这是个人项目
- `no-ci`：不配，本地跑就够了
```

`scripts/review.mjs` 会把记下的项当作已表态，不再报「待定」。**决定写进项目**，不藏在 flag 或隐藏文件里——它是项目事实，该和项目一起被读、被争论、被接手。

### 预算

`AGENTS.md` 每次会话都被注入上下文，所以它**按行付费**。判据：只写「不知道就会改坏」的东西。机制细节指向代码或别的文档，不复述；不写面向终端用户的科普。超长时优先删三类：历史沿革、被否决的方案、当前版本的快照值。

### Monorepo 的子目录 `AGENTS.md`

多包仓库可以每包一份，但它不重复注入通用规则——**只写这个包的特例**，开头一行指回根 `AGENTS.md`。两处都写一遍通用规则，改一次要改两处，而总有一处会忘。

### 建好远端之后必须再跑一次

生成 → 建仓库推上去 → **再跑一次生成**。否则远端相关的那几节永远缺失，而缺的那几节正好是别人接手时最先要看的。

### AI 自维护授权

项目的架构、命令或约定发生了实质变更，导致 `AGENTS.md` 里写的东西不再成立时，**AI 应当直接更新它，并随代码一同提交**。涉及用户可见行为或命令变化时，**必须同步 `README`**。这条授权本身就是机制：没有它，文档只在「第一次生成」那一刻准确，之后每天都更旧一点。

## 四、`README`

### 第一屏三件事

**这是什么**（一句话，不堆形容词）、**为什么用它**（具体的问题，不写「强大」「优雅」）、**怎么跑起来**（一条能复制的命令）。

| 判据 | 反面 |
| --- | --- |
| 每条命令能直接复制执行 | 写 `<你的路径>` 却不说是什么路径 |
| 环境要求照抄 `artifacts.runtimeRequirements` | 凭印象写「需要 Node 18」而清单写着 20 |
| 不承诺没做出来的东西 | 还没发布就写 `npm install <包名>` |
| 示例是最小可运行 | 贴一个要先配五个环境变量的例子 |
| 已有 README 只补缺节、不重排 | 为了一条规范把整篇结构推倒重来 |

### 按语义内容判缺，绝不按标题名判缺

已有 `## 装` 就不缺安装节；已有 `## Getting started` 就不缺「怎么跑起来」。**判据是这一节有没有回答那个问题**，不是标题有没有写成你习惯的样子。按标题名判缺，会把每一份手写 README 都判成缺一整排，然后你会去重排它——那是覆盖，不是补齐。

### 双语 README

只有项目**原本就是双语**、或用户主动要求时才加。单语项目硬加一份翻译，得到的是一份会过期的翻译和一份永远要两边改的负担。真要做，三条：两份**互相指向**对方；**默认语言是权威**，另一份跟着它改；**不机械对译**——命令、术语、链接要按目标读者重写。

### 徽章：200 假绿陷阱

**Shields.io 报 `repo not found` 时，HTTP 状态码仍然是 200。** 用状态码判「徽章能不能显示」永远为真，页面上却是一个灰色破标签。所以写入前必须**打开图片本身看一眼内容**，不是看它返回了几号状态码。

**私有仓库上的 GitHub 系列徽章（星标、许可、发布）全部显示不出来**，同理还有新发布包的下载量徽章。这类不是「永远不写」，是**现在不写**——仓库转公开、包积累一段时间之后它们会自己恢复。

### 多安装来源

项目能从不止一条路装上时（制品库、发布页压缩包、源码直装），给一张对照表，一行一个来源：

| 拿到的是 | 怎么知道有更新 | 适合什么场景 |
| --- | --- | --- |
| 制品库安装 | 包管理器自己会报 | 日常使用 |
| 发布页压缩包 | 自己看发布页 | 不装运行环境、或要固定版本 |
| 从源码直接跑 | `git pull` | 要改代码、或要最新未发布内容 |

### 「怎么更新」这一节必须有

只写怎么装、不写怎么升的 README，会让每一个老用户停在旧版本上——而作者通常以为「装上就会自动更新」。各来源分开写，一条一行命令。

## 五、`CONTRIBUTING`

要收外部贡献时才落。三块：**怎么装环境**、**怎么跑门禁**、**怎么提改动与反馈**。

**门禁命令必须与 `AGENTS.md` 的「构建与验证」节是同一批。** 不一致是最常见的坑：`CONTRIBUTING` 写 `npm test` 而 `AGENTS.md` 写 `node --test`，两边都不报错，但新来的人会跑错一个，然后以为自己环境坏了。

**分流写清两种人**：有写权限的协作者从主干拉分支；没有写权限的外部贡献者 fork 之后在自己的分支上开发，再开 PR。只写一种，另一种人会卡在权限错误上，而那看起来像「仓库坏了」。

**网页铅笔图标只能改文字。** 那条路 GitHub 替你建分支与 PR，方便，但**它跑不了门禁，必须写明不适用于改代码**。不写这一句，会有人用它改一个逻辑，然后没人能验证。

**多生态按 `commandsByEcosystem` 写。** 前后端混合的仓库只写一套命令，另一半的贡献者会以为自己的部分不需要跑。

## 六、`LICENSE`

**选哪个只有用户能定。** 给建议时按项目性质：希望被广泛使用 → MIT 或 Apache-2.0；希望明确专利授权 → Apache-2.0；希望改动必须开源 → GPL 系列（要说清后果）；不想让别人用 → 不放文件。

五条防呆，每一条都对应一种真的会发生的错误：

- **Unlicense 全文没有版权行**，不要往里填年份和占位符——填了就不再是那份许可证。
- **Apache-2.0 / GPL 等长许可证必须取标准全文**，不缩写、不自己写摘要。改过的许可证在法律上可能不成立。
- **持有人读到 `Administrator` / `user` / `root` 时停下追问**，严禁直接落盘。这类署名是系统占位，落进许可证等于宣告一个不存在的人拥有版权。
- **选「保留所有权利」时不落文件。** 没有许可证本身就是「保留所有权利」，多放一份自定义声明只会让下游的合规检查无法识别。
- **双许可（`LICENSE-MIT` 与 `LICENSE-APACHE` 并存）时不补单文件 `LICENSE`。** 那是完整的双许可结构，补一个单文件会让它变成三选一，而选择权本来在用户手里。

落盘时只替换年份与版权持有人，正文一个字符都不改；清单里的 `license` 字段要与文件类型一致。

## 七、`RELEASING`

要发版时才落。它回答三件事：**说明写在哪**、**分哪几节**、**按什么顺序发**。骨架在 `templates/releasing.md`。

**说明目录不写死。** 两种模式并存：`docs/release-notes/` 下按标签分文件的目录模式，或根目录 `CHANGELOG.md` 的单文件模式。用哪个由项目现状决定——看勘察的 `conventions.releaseNotesMode`，不要按自己的偏好新建一处。

分哪几节也由项目自己定：库看接口变化，工具看行为变化，插件看宿主兼容性。**问的是「要回答读者哪几个问题」，不是「照抄哪几节」。**

## 八、`.github/` 下的协作模板

要收外部贡献才落。从 `templates/` 取，不手写——手写会漏要素，而漏掉的要素会让每一份报告都多一轮追问。落完做两件：把占位换成项目真实信息；**删掉模板顶部的说明注释**（不删的话，第一份 Issue 里就会出现「填完请删除本段」）。**要求只写在模板里，不在 `CONTRIBUTING` 里另抄一份。** 两份清单各自维护，改一边就会漂移，而漂移的那一边总是没人读的那一边。

## 九、`CHANGELOG` 什么时候才需要

**默认不建。** 它只是一个放发版说明的位置，而说明已经有位置了。只有三种情况才建：

- 项目**已经在用它**（根目录有 `CHANGELOG.md`，或历史里一直这么发）；
- 用户明确要求单文件承载全部发版说明；
- 要单文件承载全部说明，且不需要按标签分文件。

建了就要**只追加、不重写历史**：新版本加在最上面一段，旧段落一个字都不动——它是记录，不是文档。已有 `CHANGELOG.md` 的项目**不要强迫它改用** `docs/release-notes/`：那是把一个正在工作的机制换掉，换完所有旧链接都会断。

## 十、项目没有门禁命令时

**交付不能被说成「已验证」。** 一个纯文档项目、一个还没有测试的项目，跑不出什么。诚实的说法是：

> 这个项目没有可跑的门禁命令，所以这次只验了结构与文档一致性。

判断依据：**你拿不拿得出实际跑过的输出。** 拿不出就写「未验证」——这比含糊的「看起来没问题」有用得多，因为读的人能据此决定要不要自己再验一遍。

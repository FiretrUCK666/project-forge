# 文档套装

## 何时读本文件

- 需要为项目建立或补齐文档时（`AGENTS.md` / `README` / `CONTRIBUTING` / `LICENSE`）。
- 需要判断「这份内容该写进哪个文件」时。
- 需要判断「这次改动要不要跟着改文档、要不要抬版本号」时。

## 一、一条总原则：读者是谁，决定怎么写

同一个项目里的文档，读者不是同一批人。写错读者，文档就会在该具体的地方含糊、在该
简洁的地方啰嗦。

| 文档 | 读者 | 因此必须 |
| --- | --- | --- |
| `AGENTS.md` | AI 助手 | 写**机制、判据、边界**；需要具体值时写「从哪里取」，让它自己去读项目 |
| `README` | 使用者 | 写**具体、可直接复制**的命令与地址 —— 人要照着做，不能让他去推理 |
| `CONTRIBUTING` | 贡献者 | 同 README：具体命令、明确流程、清晰的反馈渠道 |
| `LICENSE` | 法律意义上的使用者 | **逐字**使用标准文本，一个词都不改写 |

这条原则解释了一个常见的困惑：为什么同一件事（比如仓库地址）在 `AGENTS.md` 里要写成
「从版本控制配置读取」，而在 README 里要写成完整地址？因为它们面向的读者能力不同：
AI 会去读项目、能找到真值；人需要一眼看到能粘贴的东西。

判断口诀：**读者是 AI 就现场取值，读者是人就给现成命令。**

### 「永不覆盖」对散文文件是什么意思

入口的硬不变量要求「已存在的文件先读后合并，永不覆盖」。对配置文件这类结构化文件，
「合并」有机械定义（按条目比对、只补缺失项）；但对 `README` 这种**散文文件**，没有
逐行的机械定义。若不定义清楚，执行者要么整篇重写（覆盖了用户的成果），要么干脆不动
（漏掉了该补的）。

散文文件的合并按这个顺序做：

1. **逐节对照**：读现有文件，列出它已有哪几节、缺哪几节（对照 `templates/readme.md`
   的节结构）;
2. **只补缺失的节**，插在语义合适的位置，不改动已存在的节；
3. **已有的节里若有明显过时或与项目现状矛盾的内容**，指出来给用户看，**由他决定改
   不改**——不要自作主张改写他的表述；
4. **只有在用户明确要求重写时**才整篇替换。

一句话：**结构化文件按条目合并，散文文件按节合并；两者都不整篇覆盖。**

### 用户不在场时怎么办（这一格必须有出口）

上面的第 3 条默认「用户在场、能当场拍板」。但在真实会话里，执行者常常**问不到人**：
被委派的子代理、CI 里的自动运行、批处理任务——此时「指出来给用户看」无处可去，
而第 2 条又要求「只补缺失的节」，两条合起来会稳定产出**自相矛盾的成品**：

```
## 安装
pip install -r req.txt          ← 原有的，文件根本不存在（错的）

## 快速开始
pip install -r requirements.txt  ← 新补的，正确
```

同一件事两套命令并排出现，比只有错的那一套更难判断。**这不是执行偏差，是规则缺少
出口。**

用户不可达时，按这个顺序处理：

1. **不要补齐会产生矛盾的那一节**。宁可少一节，也不要写出一份自相矛盾的文档——
   矛盾会被读者当成「两种都行」，而少一节只是不完整。
2. **把冲突记下来，明确交给用户**：在汇报里逐条列出「哪一节、原文是什么、与实际
   不符在哪、建议改成什么」。这条记录本身是有交付价值的产物。
3. **在 `AGENTS.md` 里留一条可追溯的注记**（如果它在本次范围内）：说明「面向人的
   文档里有 N 处已知过时内容，尚未处理」，并列出位置。**否则下一个会话看到的是一份
   「干净」的契约，不知道还有尾巴**——这条注记是唯一能把未完成事项传递给未来会话的
   载体，而本 skill 的原则是不把快照写进契约，所以注记要写成「待处理事项」而不是
   「某年某月的状态」。

判断「用户是否可达」不需要猜：能问就问（问到了就走第 3 条）；工具返回不可用、
或当前就是无人值守运行时，按上面走。

**同理适用于其它「需要用户拍板」的地方**：G7 的三件事（许可证、署名、环境要求）
在用户不可达时，按各项的「要不到时的做法」处理——**不落盘、不写那一节、不编数字**，
并把这三条列进汇报请用户定夺。少做一件事是可接受的；编一个答案是**不可接受**的。

## 二、文件清单与职责

| 文件 | 回答什么问题 | 必做吗 |
| --- | --- | --- |
| `AGENTS.md` | 这个项目是什么、要求什么、怎么改 | 有 AI 参与开发就必做 |
| `README` | 这是什么、怎么装、怎么用、出问题找谁 | 必做 |
| `CONTRIBUTING` | 怎么提问、怎么提交改动 | 会给别人用就必做 |
| `LICENSE` | 别人能拿它做什么 | 要给别人用就必做 |
| `CHANGELOG` | 每个版本改了什么 | 可选，见下 |
| `.github/` 下的问题与改动模板 | 让反馈一次带全信息 | 会给别人用就建议做 |
| 子目录 `AGENTS.md` | 该子树特有的约定 | 大仓库按需 |

## 三、`AGENTS.md`

它是这个项目与 AI 之间的接口契约。它的价值不在于「给 AI 一些背景」，而在于**把项目
的判据、边界和纪律写下来**，让每一次会话都不必重新交代。

### 结构

分成三段，顺序固定：

| 段 | 内容 | 来源 |
| --- | --- | --- |
| 标题与效力声明 | 一句话说明本文件是什么、被谁读、以什么为完成标准 | 项目自定 |
| **通用内核** | 行事总纲 / 本文件的定位与编辑规则 / 任务编排方法论 | `templates/agents-kernel.md`，**逐字注入** |
| 项目节 | 环境与上下文、项目定位、架构与不变量、构建与验证、硬性规范、版本管理、测试约定 | 本项目特有 |

### 内核必须由脚本注入，不能手抄

```sh
# <本领目录> = 本 skill 自己的位置，与目标项目是两个不同的目录
node "<本领目录>/scripts/compose-agents.mjs" "<项目目录>"          # 生成或刷新
node "<本领目录>/scripts/compose-agents.mjs" "<项目目录>" --check  # 只校验，不一致时退出码 1
node "<本领目录>/scripts/compose-agents.mjs" "<项目目录>" --status # 只看现状，不写入
node "<本领目录>/scripts/compose-agents.mjs" "<项目目录>" --upgrade # 把一份手写的升级为标准结构
```

### 已有的 `AGENTS.md` 是手写的怎么办

项目里已经有一个 `AGENTS.md`、但写得不够好或漏了很多——这是**最常见**的情况，必须
处理好。按文件有没有内核标记分三种，做法完全不同：

| 文件状态 | 脚本行为 |
| --- | --- |
| 不存在 | 生成一份完整的 |
| 有内核标记 | 按节合并刷新（见下） |
| **没有内核标记**（手写的） | **默认只体检、不动文件**，并列出相对标准结构缺哪些节 |

手写文件默认不动，是因为重排别人的文档、把通用样板灌进他组织过的结构里，都属于对他人
成果的改动。默认沉默地改掉比不动更糟。**要升级结构，必须显式加 `--upgrade`。**

`--upgrade` 的行为边界（这是它对使用者的承诺）：

- **只做加法**：插入内核段落、补上**可自动补**的缺失节；
- 需要人写的节**不补**——补进去也只是一堆占位符，不如按项目上下文来写；
- **已有的段落一个字节都不删、不改、不重排**；
- 升级后它成为受管文件，后续刷新走正常路径。

体检报告里每个缺失的节都会标注是「可自动补」还是「需要读代码后自己写」。后者就是
接下来要干的活——读代码，把项目定位、模块结构、关键不变量这些写出来。**别指望脚本
替你写**：它推不出来的，恰恰是这份文件里最值钱的部分。

理由：内核那三段对任何项目都成立，靠手抄必然漂移——改了一处漏了另一处，几个月后各个
项目的「总纲」就各不相同了，而它们本应是同一份东西。脚本把内容收敛成单一来源
（`templates/agents-kernel.md`），并保证注入结果逐字节一致。

脚本的行为边界要记住：

- **已存在的文件按节合并**，不是整篇重写也不是一动不动：
  - **模板说「这里要人写」的节**（带 `pf:author` 标记）→ 保留既有内容，人写的不会被冲掉；
  - **纯生成内容**（提交纪律、发版规则、回滚分档这类）→ 按**当前**项目事实重新求值，
    所以「后来才成立的条件」能补进来。这一点很关键：本 skill 的顺序是 P3（版本管理）
    → P4（文档）→ P5（远端），**生成文档时远端必然还不存在**。若条件只在首次生成时
    求值一次，所有「有远端才有」的内容（发版规则、角色判定）对所有新项目**永远缺席**。
    所以建好远端之后**应当再跑一次**，让它补上；
  - 命令会报告这次重新求值了哪几节、保留了哪几节，可以据此确认。
- **不会自动新增整节**：模板里有、文件里没有的节只**报告**不添加。因为文件可能是手写
  的（本 skill 自己的就是），擅自补进去会灌进一整套与手写内容并列的通用样板。缺节时
  脚本会列出来，由人决定要不要补。
- **不会删除既有节**：文件里有、模板里没有的节一律保留——那可能是作者自己加的，也可能
  是作者刻意换了一种组织方式。
- **顺序与前言沿用既有文件**，不按模板重排：文件一旦存在，作者摆放它的方式就是权威。
- 幂等：没有变化时报告「无需改动」；标记缺失时**报错退出**，不会猜该插到哪里；
- 输出统一换行符、无 BOM。

### 首次生成：脚本填一部分，剩下的必须由你读完代码后来填

新项目第一次跑脚本时，它会做三件事：从项目事实里**填入能填的**（项目名、构建命令、
按事实保留或丢弃条件段落）、**留下填不了的**（标着 `pf:author`）、并**报出还剩几处**。

**关键：那几处不是「留给用户的占位符」，是留给你的作业。**

脚本推不出来的，恰恰是这份文件里最值钱的部分——项目定位、模块结构、关键不变量、
本项目特有的硬性规范。这些只有**读了代码**才写得出来，而它们正是未来会话真正需要的
东西：`AGENTS.md` 存在的意义，是让下一个会话不必重新读一遍代码就知道「哪里不能碰」。

所以首次生成的正确流程是：

1. 跑脚本生成；
2. **读项目代码**，把每一处 `pf:author` 换成真实内容，并删掉该标记；
3. 再跑一次，确认报「待填写 0 处」（此时脚手架注释会自动移除）。

**只做第 1 步就交付，比不生成这个文件更糟**：没有它，未来的 AI 会去读代码；有了它，
AI 会以为自己已经知道了——而文件里全是「请说明本项目……」这类祈使句。一份假装完整的
契约会主动阻止正确的行为。

确实写不出的（需要用户提供信息才能定的），在汇报里**逐条列出**是哪几节、为什么还空着。
宁可交一份标着「还有 3 节待补」的文件，也不要交一份看起来完整的空壳。

### 预算意识

工作区指令在注入会话上下文时有**总字节预算**（当前实现是 64 KB 量级）。超出预算的
部分会被截断——被截断的往往是文件末尾，也就是项目节里最具体的那些内容，而它们恰恰
最有用。

所以：

- **内核只在仓库根放一份**。子目录的 `AGENTS.md` 不要再抄一遍内核，只写该子树特有的
  内容，并指回根文件。同一段文字放多处，是预算被浪费的主要方式。
- 项目节写完量一下总量。脚本每次注入都会报告字节数与占比，超过八成余量就不多了。
- 内容确实多时，**把细节移出去**：`AGENTS.md` 里保留判据与指针，细节放项目内的其他
  文档，需要时再读。指针比重述便宜得多。

### 项目节怎么写

守三条：

1. **写机制，不写会过期的取值**。版本号、日期、「某次决定」都是快照，写进来就是下一个
   坑。需要取值的地方写「从哪里取」。
2. **写判据，不写清单**。清单会腐坏（文件增删、目录改名），判据不会。确需清单时，
   明确写「以目录扫描为准」。
3. **不复述代码**。机制的细节以代码注释和对应文件为准，`AGENTS.md` 只写职责与入口。
   两处都写机制，就一定会有两处不一致的那天。

### 子目录 `AGENTS.md`

大仓库里，离得近的约定应该离得近。判定标准：

- 有一段约定**只对某个子树成立**，且写进根文件会让根文件变臃肿 → 放子目录。
- 放子目录时，开头指回根文件（说明共用约定在那里），之后只写本子树的特例。

## 四、`README`

它是产品的表面：使用者靠它判断「这是不是我需要的」「怎么装」「装了能不能用」。所以
README 里的每一句都应当是**你能兑现的**。

### 已有的 README 不符合规范时怎么办

这是**最常见**的情况：项目已经有 README，但缺了很多东西、或者内容根本不对。处理原则
与「散文文件按节合并」（见第一节）一致，落到 README 上具体是：

**先分清是「缺」还是「错」**，两者的处置完全不同：

| 情况 | 判据 | 处置 |
| --- | --- | --- |
| **缺**（没有安装说明、没有环境要求……） | 现有文件里**找不到这个内容** | **补上**。插在语义合适的位置，不改动已有的节 |
| **错**（命令跑不通、指向不存在的文件） | 与项目实际不符 | **指出，不擅自改**——见下 |
| **结构完全不同**（用的是自己那套标题） | 节名与模板对不上 | **保留他的结构**，只补缺的内容。README 的结构没有标准 |
| **完全过时**（描述的是上一个版本） | 与现状矛盾 | 同上，指出并交给用户 |

#### 「缺」要按**内容**判，不能按**标题名**判

这是最容易做错、而且做错了会直接产出一份更烂的文档的一格。

`## 装`、`## 怎么跑`、`## Getting started` 都是**已经写了**的安装与使用说明，只是标题叫法
不同。若按「模板里有 `## 安装`，文件里没有 `## 安装`」来判断缺不缺，就会**再补一节安装
说明**——同一件事出现两处，而且新旧说法可能不一致。这正是要避免的结果。

正确判据：**这个内容在文件里有没有被讲到**，而不是**有没有这个标题**。
`## 装` 存在时，「安装」这一项**不缺**，不需要补。

同理，「结构完全不同」与「缺」是两件事：作者用自己那套标题把该讲的都讲清楚了，那就
**什么都不缺**，只是标题不同——**不要为了对齐模板去改标题**。

反过来说，模板的节名只是**建议用词**。补新节时用作者已有的用词风格（他写 `## 装`
你就写 `## 更新` 而不是 `## Update`），让整份文档读起来像一个人写的。

#### 「错」为什么不擅自改

那两行可能是作者有意写的（历史命令、迁移期说明）、也可能他正准备改。直接覆盖别人的
表述属于越权，而且改错了没人发现。正确做法是**指出来**——但「指出来」需要有人接
（见第一节「用户不在场时怎么办」）。

**结构完全不同时不要强行对齐模板**。README 没有标准结构：命令行工具、库、数据项目的
合理组织方式各不相同，`templates/readme.md` 只是**建议**。强行重排的代价是把作者想清楚
的顺序打乱，而且会产出一份「看起来规范、读起来别扭」的文档。判据是**内容是否齐全**，
不是**标题是否一致**。

**「缺」与「错」同时存在时**，只补「缺」的部分。补完之后如果同一件事出现了两种说法
（原有的错 + 新补的对），**不要为了好看去删原有那节**——按第一节的出口处理：记进汇报，
交给用户。一份自相矛盾的 README 比只有错的那一份更难判断，但**擅自删改别人的表述更糟**，
两害相权，选择可追溯的那一个。

### 双语 README

项目可能同时有 `README.md` 与 `README.en.md`（或其他语言）。处理规则：

- **两份都是「随包发出的说明」**：都展示在制品库页面上、都在包内，**改任何一份都算
  用户可见变化**（见「版本号」一节）。只改一份却不抬版本号，会出现「仓库里改了、
  制品库上还是旧的」。
- **它们会漂移**——这是双语文档的主要失效方式：一次改动只更新了一份，两份说着不同的
  事，而读者不知道自己看的那份是不是最新的。因此**改一份时必须看另一份**，并在汇报里
  说明另一份是否同步了。
- **不要机械对译**。两种语言的读者关心的问题不同（英文读者更常问「有没有 TypeScript
  类型」「支持哪些平台」，中文读者更常问「国内怎么装」），逐句对译会产出一份读起来像
  翻译腔、又没回答本地读者问题的文档。
- **哪份优先**：默认语言的（通常是 `README.md`）是权威，另一份是它的翻译。两者不一致
  时以权威那份为准，并同步另一份。
- **要不要新增一份**：只在确实有另一语言的读者时才加。**一份没人维护的第二语言 README
  比没有更糟**——它会给读者一个过期的印象，而且没人会去核对。

勘察会在 `docs.readmePair` 里把成对的 README 报出来，并在 `docs.readmeSections` 里给出
主 README 现有的节——那是**事实**，不是「合格不合格」的结论，判断由你来做。

### 写作判据

从 `templates/readme.md` 起步，注意几条判据：

- **徽章只写能显示的**。徽章是可选装饰，但**写错的徽章比没有徽章更难看**：它在页面上
  是一个灰色破标签，会让读者以为项目坏了。而它的失效方式很隐蔽——**图片地址永远返回
  200，图里却写着 `repo not found`**，作者不去看自己的渲染结果就发现不了。
  已经确认会踩的两类：**私有仓库上的 GitHub 系列徽章全部显示不出来**；
  制品库的下载量徽章在新包刚发布时显示 `package not found or too new`。
  **写之前逐个访问一遍**，或用 `scripts/check-badges.mjs` 一次查完：

  ```sh
  node <本领目录>/scripts/check-badges.mjs README.md README.en.md
  ```

  它把每个徽章取回来读渲染出的文字，显示不出来的直接列出来并给出非零退出码。
  注意这不是「永远不写」——仓库转公开、包积累一段时间之后那些徽章会自动恢复可用。
- **章节多时加目录**。它服务于「已经知道要什么、只想跳到那一节」的读者；短 README
  加目录反而累赘。目录由各节标题逐字生成，**锚点必须与标题完全一致**——改标题就要改
  锚点，不一致时那个链接点了没反应。锚点规则：标题原文转小写、空格换连字符、去掉标点，
  **非 ASCII 字符（中文）保留原样**。**不要照抄别人带 emoji 的目录样式**：那种锚点里
  含 emoji，而很多项目的硬性规范禁 emoji，照抄会把规范破掉。
- **有多个语言版本时在标题下加一行语言切换**，且两份**互相指向对方**（中文版指英文版、
  英文版指中文版）。只在一份里加，另一份的读者就找不到回去的路。
- **不写在制品库页面上会变成假话的内容**。写在 README 里的文件会随包分发、会展示在
  制品库页面上，改一个字都算产品变化（见「版本号」一节）。
- **不要写「或更高」这类无法兑现的承诺**。环境要求要给**一个具体的最低版本数字**，
  并说明这个数字的含义——「在这个版本上验证通过，更新的版本预期可用但未逐一验证，
  遇到问题请反馈」。使用者需要一个能判断的数字，而承诺一件做不到的事比不承诺更糟。
- **不要写会过期的快照**。某年某月某版本的对应表、一次性的兼容性结论，写进来就开始
  过期。要写就写判据。
- **多个安装来源要用表格讲清差别**：拿到的是什么、靠什么判断有没有更新、适合什么
  场景。这三列能回答使用者 90% 的疑问。
- **问题反馈渠道要具体**。不要写「欢迎反馈」，要写「到哪提、提的时候附上哪几样东西」
  （版本、环境、完整报错文本）。这一条能把无效问题减少一大半。
- **要有「怎么更新」**。使用者最常问的三件事是「怎么装、怎么用、**怎么升**」。只写
  安装不写更新，等于把第二个问题留给使用者自己去猜。内容要与分发方式一致：不发布
  制品就不要写「用包管理器升级」。

## 五、`CONTRIBUTING`

从 `templates/contributing.md` 起步。要点：

- **把「提问」放在最前面**。绝大多数访客只是想问个问题，让他们一眼看到该去哪。
- 明确**贡献者能做什么、不能做什么**，并且**按有无写权限分开写**：外部贡献者对本仓库
  没有写权限，**推不了分支**——他得先 fork、克隆自己的那份再开发，最后开改动请求。
  协作者才能直接拉分支。（只写「推自己的分支」，外部贡献者会在推送那一步失败，然后
  不知道该干什么。）
- 明确**三类越权动作**：不要推主干、不要打版本标签、不要发布制品。它们属于维护者，
  越权会搅乱项目的版本线。
- 提交前门禁要**具体**：跑哪几条命令、全绿才算完成。
- 硬性规范不要在这里重复维护一份，摘最关键几条，并明确「完整规范以 `AGENTS.md`
  为准」。同一份规范写两处，迟早会不一致。
- 许可条款一句话带过，指向 `LICENSE`。

## 六、`LICENSE`

### 选择

不要替用户拍板。给出判据与常见选项，让用户选。

| 许可证 | 别人可以 | 必须 | 适合 |
| --- | --- | --- | --- |
| MIT / BSD | 几乎任何用途，包括闭源商用 | 保留版权与许可声明 | 想被尽可能广泛使用 |
| Apache-2.0 | 同上 | 同上，另含专利授权与变更说明 | 同上，且在意专利条款 |
| MPL-2.0 | 同上，但改动的**文件**要开源 | 保留声明，公开改动文件 | 想允许更大范围使用、又要求改动回馈 |
| GPL-3.0 | 使用、修改、分发 | 衍生作品也要以同许可开源 | 要求回馈社区 |
| AGPL-3.0 | 同上，且**网络服务**也算分发 | 同上 | 防止被做成闭源服务 |
| Unlicense / 0BSD | 无限制，放弃权利 | 无 | 不在意署名 |
| 保留所有权利 | 什么都不可以 | — | 暂不打算让别人用 |

判据顺序：**你想让别人拿它做什么** → 你是否在意被闭源使用 → 你是否在意专利 → 你是否
要求改动回馈。

不确定时的默认建议：工具库、插件、文档类项目用 MIT 一类的宽松许可；这能最大程度减少
使用者的顾虑。

### 落盘规则（硬性）

- **逐字使用标准文本，一个词都不改写**。改写过就不是那个许可证了，法律上等于没有。
- **短许可证直接取用现成模板**，不要凭记忆写（记忆里的版本常常少一句、错一个词，而
  这类错误不会有人发现）：

  | 许可证 | 模板文件 |
  | --- | --- |
  | MIT | `templates/license-mit.txt` |
  | ISC | `templates/license-isc.txt` |
  | BSD 2-Clause | `templates/license-bsd-2-clause.txt` |
  | BSD 3-Clause | `templates/license-bsd-3-clause.txt` |
  | Unlicense（放弃权利） | `templates/license-unlicense.txt` |

  用法：取模板全文，把 `{{YEAR}}` 与 `{{HOLDER}}` 两个占位符替换成实际值。**除这两个
  占位符外一个字符都别动**。

  **Unlicense 是例外**：它是放弃权利，全文**没有版权行**，因此没有占位符要替换，
  原样落盘即可。这不是模板写漏了——给它加一行 `Copyright (c) ...` 反而与它的性质矛盾。

- **长许可证（Apache、GPL、AGPL、MPL 一类）本 skill 不自带模板**，必须从权威来源取
  全文——它们篇幅长、条款互相引用，凭记忆或摘要写必然出错。取到之后**原样落盘**，
  不要重新排版、不要删掉附录。
- 版权行按标准格式写：`Copyright (c) <年份> <持有人>`。
  - 年份取**当前年份**（从系统时间读，不要写死）。
  - 持有人取**项目自身的权威来源**：仓库元数据里声明的作者/维护者信息，或版本控制
    里配置的署名。**不要凭空编一个名字**。
- **持有人取到占位值时不要直接用**。刚装好的机器上，版本控制的全局署名经常就是操作
  系统默认用户名（形如「Administrator」「user」「admin」这类），它**不是一个人的名字**。
  版权行会随仓库永久分发，写进去之后很难收回。判据是：**这个字符串读起来像不像一个
  真实身份**；不像就回去问用户，不要因为「字段里有值」就当成答案。
- **用户选「保留所有权利」时不要落盘 `LICENSE`**。那一项的含义就是「暂不授权给任何人」，
  此时正确做法是**不写这个文件**，而不是写一份声明保留权利的文本——后者不是标准许可证，
  写了反而会让使用者困惑。汇报里说明「按你的选择没有添加许可证」即可。
- 许可证一旦发布就很难改（已分发的副本收不回来，改动只对未来生效），所以**首次落盘
  前确认一次**。

## 七、`CHANGELOG`（可选）

**默认不建**。理由：维护者是人，人不会记得更新它；而它一旦停更，就变成了误导。

替代方案（更可靠）：

- **版本节点 + 发布说明**：在平台上给每个版本写一段给人看的更新说明。这是使用者真正
  会看的地方，而且写在发布流程里，不容易忘。
- **提交历史**：本身就是逐次变更的记录。

只有一种情况值得建 `CHANGELOG`：项目有外部使用者，且你需要一个**不依赖平台**的变更
记录（例如会分发到多个制品库、或需要离线查阅）。

要建的话守两条：**只追加不修改历史条目**；**每条写「用户能感知的变化」，不写内部
重构细节**。

## 八、写作质量

面向人的文档（`README` / `CONTRIBUTING` / 面向使用者的发布说明）落盘后，用 `oil-tone`
skill 校对一遍，并运行它附带的检查脚本。它检查的是固定的 AI 表达与空泛表述；程序报
`FAIL` 的必须改，`WARN` 的按上下文判断。

**这一步可能不可用，不可用时不要假装做过。** `oil-tone` 是另一个 skill：它可能没装、
它的检查脚本可能需要额外的运行时、也可能在本机根本不适用。任一条件不满足时：

- 直接跳过，**不要**自己凭感觉模仿它的规则去改文风；
- 在汇报里**写明「面向人的文档未做文风校对」**，说清原因（未安装 / 缺运行时）。

理由与密钥门控是同一条：**没做却说做了，比明确说没做危险得多**。使用者据「已校对」
放松检查，实际拿到的是没校对过的稿子。

面向 AI 的文档（`AGENTS.md` 及项目内约定文件）不适用文风规范——它要的是准确和可执行，
不是可读性。

## 九、同步纪律

改完项目之后回头检查一遍文档：

| 你改了什么 | 要检查 |
| --- | --- |
| 对外能力、命令、安装方式 | `README` 是否仍准确 |
| 架构、约定、门禁 | `AGENTS.md` 项目节是否失准 |
| 贡献流程、环境要求 | `CONTRIBUTING` 是否失准 |
| **随包分发**的任何文档 | 是否需要抬版本号（见 `references/publish.md`） |

判断「随包分发」的依据是项目的发布范围声明与实际打包结果，不是文件放在哪个目录。
发布范围声明对**从仓库源安装**同样生效——仓库里有某个文件，不代表使用者手里会有它。

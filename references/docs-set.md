# 文档套装

## 何时读本文件

- 需要为项目建立或补齐文档时（`AGENTS.md` / `README` / `CONTRIBUTING` / `LICENSE`）。
- 需要判断「这份内容该写进哪个文件」时。
- 需要判断「这次改动要不要跟着改文档、要不要抬版本号」时。

## 一、一条总原则：读者是谁，决定怎么写

同一个项目里的文档，读者不是同一批人。写错读者，文档就会在该具体的地方含糊、在该
简洁的地方啰嗦。

| 文档 | 读者 | 因此必须 |
| --- | --- | --- |
| `AGENTS.md` | AI 助手 | 写**机制、判据、边界**；需要具体值时写「从哪里取」，让它自己去读项目 |
| `README` | 使用者 | 写**具体、可直接复制**的命令与地址 —— 人要照着做，不能让他去推理 |
| `CONTRIBUTING` | 贡献者 | 同 README：具体命令、明确流程、清晰的反馈渠道 |
| `LICENSE` | 法律意义上的使用者 | **逐字**使用标准文本，一个词都不改写 |

这条原则解释了一个常见的困惑：为什么同一件事（比如仓库地址）在 `AGENTS.md` 里要写成
「从版本控制配置读取」，而在 README 里要写成完整地址？因为它们面向的读者能力不同：
AI 会去读项目、能找到真值；人需要一眼看到能粘贴的东西。

判断口诀：**读者是 AI 就现场取值，读者是人就给现成命令。**

### 「永不覆盖」对散文文件是什么意思

入口的硬不变量要求「已存在的文件先读后合并，永不覆盖」。对配置文件这类结构化文件，
「合并」有机械定义（按条目比对、只补缺失项）；但对 `README` 这种**散文文件**，没有
逐行的机械定义。若不定义清楚，执行者要么整篇重写（覆盖了用户的成果），要么干脆不动
（漏掉了该补的）。

散文文件的合并按这个顺序做：

1. **逐节对照**：读现有文件，列出它已有哪几节、缺哪几节（对照 `templates/readme.md`
   的节结构）;
2. **只补缺失的节**，插在语义合适的位置，不改动已存在的节；
3. **已有的节里若有明显过时或与项目现状矛盾的内容**，指出来给用户看，**由他决定改
   不改**——不要自作主张改写他的表述；
4. **只有在用户明确要求重写时**才整篇替换。

一句话：**结构化文件按条目合并，散文文件按节合并；两者都不整篇覆盖。**

## 二、文件清单与职责

| 文件 | 回答什么问题 | 必做吗 |
| --- | --- | --- |
| `AGENTS.md` | 这个项目是什么、要求什么、怎么改 | 有 AI 参与开发就必做 |
| `README` | 这是什么、怎么装、怎么用、出问题找谁 | 必做 |
| `CONTRIBUTING` | 怎么提问、怎么提交改动 | 会给别人用就必做 |
| `LICENSE` | 别人能拿它做什么 | 要给别人用就必做 |
| `CHANGELOG` | 每个版本改了什么 | 可选，见下 |
| `.github/` 下的问题与改动模板 | 让反馈一次带全信息 | 会给别人用就建议做 |
| 子目录 `AGENTS.md` | 该子树特有的约定 | 大仓库按需 |

## 三、`AGENTS.md`

它是这个项目与 AI 之间的接口契约。它的价值不在于「给 AI 一些背景」，而在于**把项目
的判据、边界和纪律写下来**，让每一次会话都不必重新交代。

### 结构

分成三段，顺序固定：

| 段 | 内容 | 来源 |
| --- | --- | --- |
| 标题与效力声明 | 一句话说明本文件是什么、被谁读、以什么为完成标准 | 项目自定 |
| **通用内核** | 行事总纲 / 本文件的定位与编辑规则 / 任务编排方法论 | `templates/agents-kernel.md`，**逐字注入** |
| 项目节 | 环境与上下文、项目定位、架构与不变量、构建与验证、硬性规范、版本管理、测试约定 | 本项目特有 |

### 内核必须由脚本注入，不能手抄

```sh
# <本领目录> = 本 skill 自己的位置，与目标项目是两个不同的目录
node "<本领目录>/scripts/compose-agents.mjs" "<项目目录>"          # 生成或刷新
node "<本领目录>/scripts/compose-agents.mjs" "<项目目录>" --check  # 只校验，不一致时退出码 1
node "<本领目录>/scripts/compose-agents.mjs" "<项目目录>" --status # 只看还差几处待填写
```

理由：内核那三段对任何项目都成立，靠手抄必然漂移——改了一处漏了另一处，几个月后各个
项目的「总纲」就各不相同了，而它们本应是同一份东西。脚本把内容收敛成单一来源
（`templates/agents-kernel.md`），并保证注入结果逐字节一致。

脚本的行为边界要记住：

- 只替换一对标记之间的内容，**标记之外一个字节都不动**；
- 幂等，反复执行结果相同；
- 标记缺失时**报错退出**，不会猜该插到哪里；
- 输出统一换行符、无 BOM。

### 预算意识

工作区指令在注入会话上下文时有**总字节预算**（当前实现是 64 KB 量级）。超出预算的
部分会被截断——被截断的往往是文件末尾，也就是项目节里最具体的那些内容，而它们恰恰
最有用。

所以：

- **内核只在仓库根放一份**。子目录的 `AGENTS.md` 不要再抄一遍内核，只写该子树特有的
  内容，并指回根文件。同一段文字放多处，是预算被浪费的主要方式。
- 项目节写完量一下总量。脚本每次注入都会报告字节数与占比，超过八成余量就不多了。
- 内容确实多时，**把细节移出去**：`AGENTS.md` 里保留判据与指针，细节放项目内的其他
  文档，需要时再读。指针比重述便宜得多。

### 项目节怎么写

守三条：

1. **写机制，不写会过期的取值**。版本号、日期、「某次决定」都是快照，写进来就是下一个
   坑。需要取值的地方写「从哪里取」。
2. **写判据，不写清单**。清单会腐坏（文件增删、目录改名），判据不会。确需清单时，
   明确写「以目录扫描为准」。
3. **不复述代码**。机制的细节以代码注释和对应文件为准，`AGENTS.md` 只写职责与入口。
   两处都写机制，就一定会有两处不一致的那天。

### 子目录 `AGENTS.md`

大仓库里，离得近的约定应该离得近。判定标准：

- 有一段约定**只对某个子树成立**，且写进根文件会让根文件变臃肿 → 放子目录。
- 放子目录时，开头指回根文件（说明共用约定在那里），之后只写本子树的特例。

## 四、`README`

它是产品的表面：使用者靠它判断「这是不是我需要的」「怎么装」「装了能不能用」。所以
README 里的每一句都应当是**你能兑现的**。

从 `templates/readme.md` 起步，注意几条判据：

- **不写在制品库页面上会变成假话的内容**。写在 README 里的文件会随包分发、会展示在
  制品库页面上，改一个字都算产品变化（见「版本号」一节）。
- **不要写「或更高」这类无法兑现的承诺**。环境要求要给**一个具体的最低版本数字**，
  并说明这个数字的含义——「在这个版本上验证通过，更新的版本预期可用但未逐一验证，
  遇到问题请反馈」。使用者需要一个能判断的数字，而承诺一件做不到的事比不承诺更糟。
- **不要写会过期的快照**。某年某月某版本的对应表、一次性的兼容性结论，写进来就开始
  过期。要写就写判据。
- **多个安装来源要用表格讲清差别**：拿到的是什么、靠什么判断有没有更新、适合什么
  场景。这三列能回答使用者 90% 的疑问。
- **问题反馈渠道要具体**。不要写「欢迎反馈」，要写「到哪提、提的时候附上哪几样东西」
  （版本、环境、完整报错文本）。这一条能把无效问题减少一大半。

## 五、`CONTRIBUTING`

从 `templates/contributing.md` 起步。要点：

- **把「提问」放在最前面**。绝大多数访客只是想问个问题，让他们一眼看到该去哪。
- 明确**贡献者能做什么、不能做什么**：可以推自己的分支、可以开改动请求；**不要**推
  主干、不要打版本标签、不要发布制品。这三件事属于维护者，越权会搅乱项目的版本线。
- 提交前门禁要**具体**：跑哪几条命令、全绿才算完成。
- 硬性规范不要在这里重复维护一份，摘最关键几条，并明确「完整规范以 `AGENTS.md`
  为准」。同一份规范写两处，迟早会不一致。
- 许可条款一句话带过，指向 `LICENSE`。

## 六、`LICENSE`

### 选择

不要替用户拍板。给出判据与常见选项，让用户选。

| 许可证 | 别人可以 | 必须 | 适合 |
| --- | --- | --- | --- |
| MIT / BSD | 几乎任何用途，包括闭源商用 | 保留版权与许可声明 | 想被尽可能广泛使用 |
| Apache-2.0 | 同上 | 同上，另含专利授权与变更说明 | 同上，且在意专利条款 |
| MPL-2.0 | 同上，但改动的**文件**要开源 | 保留声明，公开改动文件 | 想允许更大范围使用、又要求改动回馈 |
| GPL-3.0 | 使用、修改、分发 | 衍生作品也要以同许可开源 | 要求回馈社区 |
| AGPL-3.0 | 同上，且**网络服务**也算分发 | 同上 | 防止被做成闭源服务 |
| Unlicense / 0BSD | 无限制，放弃权利 | 无 | 不在意署名 |
| 保留所有权利 | 什么都不可以 | — | 暂不打算让别人用 |

判据顺序：**你想让别人拿它做什么** → 你是否在意被闭源使用 → 你是否在意专利 → 你是否
要求改动回馈。

不确定时的默认建议：工具库、插件、文档类项目用 MIT 一类的宽松许可；这能最大程度减少
使用者的顾虑。

### 落盘规则（硬性）

- **逐字使用标准文本，一个词都不改写**。改写过就不是那个许可证了，法律上等于没有。
- 短许可证（MIT、BSD、ISC 一类）可以内置模板；**长许可证（Apache、GPL、AGPL、MPL
  一类）必须从权威来源取全文**，不要凭记忆写——漏一段就等于换了许可证。
- 版权行按标准格式写：`Copyright (c) <年份> <持有人>`。
  - 年份取**当前年份**（从系统时间读，不要写死）。
  - 持有人取**项目自身的权威来源**：仓库元数据里声明的作者/维护者信息，或版本控制
    里配置的署名。**不要凭空编一个名字**。
- **持有人取到占位值时不要直接用**。刚装好的机器上，版本控制的全局署名经常就是操作
  系统默认用户名（形如「Administrator」「user」「admin」这类），它**不是一个人的名字**。
  版权行会随仓库永久分发，写进去之后很难收回。判据是：**这个字符串读起来像不像一个
  真实身份**；不像就回去问用户，不要因为「字段里有值」就当成答案。
- **用户选「保留所有权利」时不要落盘 `LICENSE`**。那一项的含义就是「暂不授权给任何人」，
  此时正确做法是**不写这个文件**，而不是写一份声明保留权利的文本——后者不是标准许可证，
  写了反而会让使用者困惑。汇报里说明「按你的选择没有添加许可证」即可。
- 许可证一旦发布就很难改（已分发的副本收不回来，改动只对未来生效），所以**首次落盘
  前确认一次**。

## 七、`CHANGELOG`（可选）

**默认不建**。理由：维护者是人，人不会记得更新它；而它一旦停更，就变成了误导。

替代方案（更可靠）：

- **版本节点 + 发布说明**：在平台上给每个版本写一段给人看的更新说明。这是使用者真正
  会看的地方，而且写在发布流程里，不容易忘。
- **提交历史**：本身就是逐次变更的记录。

只有一种情况值得建 `CHANGELOG`：项目有外部使用者，且你需要一个**不依赖平台**的变更
记录（例如会分发到多个制品库、或需要离线查阅）。

要建的话守两条：**只追加不修改历史条目**；**每条写「用户能感知的变化」，不写内部
重构细节**。

## 八、写作质量

面向人的文档（`README` / `CONTRIBUTING` / 面向使用者的发布说明）落盘后，用 `oil-tone`
skill 校对一遍，并运行它附带的检查脚本。它检查的是固定的 AI 表达与空泛表述；程序报
`FAIL` 的必须改，`WARN` 的按上下文判断。

**这一步可能不可用，不可用时不要假装做过。** `oil-tone` 是另一个 skill：它可能没装、
它的检查脚本可能需要额外的运行时、也可能在本机根本不适用。任一条件不满足时：

- 直接跳过，**不要**自己凭感觉模仿它的规则去改文风；
- 在汇报里**写明「面向人的文档未做文风校对」**，说清原因（未安装 / 缺运行时）。

理由与密钥门控是同一条：**没做却说做了，比明确说没做危险得多**。使用者据「已校对」
放松检查，实际拿到的是没校对过的稿子。

面向 AI 的文档（`AGENTS.md` 及项目内约定文件）不适用文风规范——它要的是准确和可执行，
不是可读性。

## 九、同步纪律

改完项目之后回头检查一遍文档：

| 你改了什么 | 要检查 |
| --- | --- |
| 对外能力、命令、安装方式 | `README` 是否仍准确 |
| 架构、约定、门禁 | `AGENTS.md` 项目节是否失准 |
| 贡献流程、环境要求 | `CONTRIBUTING` 是否失准 |
| **随包分发**的任何文档 | 是否需要抬版本号（见 `references/publish.md`） |

判断「随包分发」的依据是项目的发布范围声明与实际打包结果，不是文件放在哪个目录。
发布范围声明对**从仓库源安装**同样生效——仓库里有某个文件，不代表使用者手里会有它。

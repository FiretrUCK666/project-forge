# DSH 插件项目

## 何时读本文件

- 勘察判定项目是 `dsh-plugin`（存在 `cordis.patch.yml`，或清单文件里声明了 `dsh.bundle`）时。
- 需要判断「产物要不要提交进仓库」「发布范围怎么写」「包名改了会连带影响什么」时。
- 给一个 DSH 插件配置版本管理、远端或发布链路时。

## 一、DSH 插件是什么

DSH（DeepSeek Harness）的一切都是插件。一个插件是一段以 cordis 插件形态存在的代码，
它可以向宿主贡献能力：注册服务、注册模型工具、注册界面。它不是独立进程，而是被宿主
加载进同一个进程里的模块。

这条性质决定了很多看起来奇怪的约定：

| 因为它被宿主加载 | 所以 |
| --- | --- |
| 宿主从磁盘上的**包**里找入口 | 包要有正确的入口声明与产物文件 |
| 浏览器那一半由宿主供给 | 产物要按宿主的模块加载协议注册自己 |
| 加载失败就是整个宿主启动失败 | 版本兼容性是硬约束，不是建议 |

## 二、两个半区

一个插件通常由两半组成，它们运行在不同的地方：

| 半区 | 运行在 | 负责 | 产物 |
| --- | --- | --- | --- |
| 主进程半区 | 宿主的 Node 进程 | 路由、存储、会话、模型工具、任何需要文件或网络的事 | 一个可被 import 的模块 |
| 浏览器半区 | 网页 | 界面、交互、页面状态 | 一个按宿主协议注册自己的模块 |

两半通过包内**私有的消息通道**通信，只能传无损 JSON。浏览器那一半不能直接读写文件、
不能访问网络——需要这些能力时，由它请求主进程半区代做。

判据：**这段逻辑需要文件系统、网络或宿主的服务吗？** 需要就放主进程半区；只涉及界面
与页面状态就放浏览器半区；两边都要的，界面上那一半只做展示，真正干活的那一半放主进程。

浏览器半区必须注册到宿主提供的**界面插槽**里，不能凭空返回一个界面元素。用哪个插槽
取决于这个界面要出现在哪里——侧边栏、设置页、会话面板各有各的插槽。

## 三、插件标识与包名是两个身份

这是这类项目**最容易出错、后果最难查**的一处。两个身份各自独立：

| 身份 | 由什么决定 | 影响什么 |
| --- | --- | --- |
| **插件 id** | 配置文件里那一行的 `id`，通常与项目目录名一致 | 加载与数据的身份：路由前缀、设置命名空间、存储单元、界面插槽标识、本地存储键 |
| **包名** | 清单文件里的 `name` | 安装标识：依赖键、安装命令、浏览器产物的注册标识 |

关键结论：

- **改包名不影响插件 id**。加作用域、换提交范围，动的是包名，路由、设置命名空间、
  存储单元、界面插槽、本地存储键**一个都不许跟着改**——那些是用户数据的地址，改了
  就等于把已有用户的数据丢掉。
- **浏览器产物的注册标识必须等于包名**，不是插件 id。宿主按包清单给产物定键，注册成
  别的名字会被拒绝加载。没有作用域时两者恰好相同，一旦加了作用域就会分叉，因此构建
  配置里的那个字符串**必须是包名**。
- 无作用域时两个身份相同，是这种错误最常见的潜伏期——等到加作用域那天才暴露。

自检办法：构建后检查浏览器产物里注册标识的那个字符串，与清单文件的包名逐字比对；
并真实执行一次加载握手，而不只是看文件是否存在。

## 四、产物必须入库（与常规做法相反，这是对的）

一般项目的编译产物不进版本库。**DSH 插件的产物必须进**，理由只有一条：

> 安装这个包的人**不会**替它跑一次构建。

安装路径（无论从制品库装、从仓库源装、还是被宿主按路径加载）都只做「取文件、放到位、
加载」，没有任何一步会运行构建。所以产物不存在，插件就是加载失败。

这条与「依赖目录永远不进库」并不矛盾——判据是同一条：

| 东西 | 拿到的人能自己生成吗 | 结论 |
| --- | --- | --- |
| 依赖目录 | 能（装一次依赖就有） | 不进库 |
| 插件产物 | 不能（安装流程不构建） | **必须进库** |

推论：

- 源码与产物**必须同一次提交**。产物是构建出来的，源码改了产物没改，使用者拿到的就是
  旧行为；反过来产物改了源码没改，下次构建又会被覆盖。两者分开提交，等于在历史里
  埋下「某个提交的产物与源码不一致」的状态。
- 持续集成里应当有一条检查：**重新构建一次，产物必须与提交的产物逐字节一致**。这是
  唯一能自动发现「忘了重新构建」的手段。

## 五、构建可复现（跨机器必须一致）

因为产物入库、且持续集成会在另一台机器上重建比对，构建结果**不能依赖构建机的任何
特征**。已经确认会出问题的两类：

**一、绝对路径。** 不要把绝对路径交给「会把它写进产物、或用来派生标识」的工具。典型
是 CSS 处理器的类名哈希取自传入的文件名——传绝对路径会让同一份样式在不同目录下编译
出不同的类名，产物于是永远无法在别的机器上复现。构建脚本一律传**相对于仓库的路径**。

**二、行尾。** 如果产物里内嵌了源码原文（源码映射、生成的代码、快照），工作区里残留
的另一套行尾会被原样写进去，而别的机器检出时用的是另一套，于是产生大量差异。

对策是**先声明文本属性，再做首次提交**（见 `references/version-control.md`）。如果属性
声明加晚了、工作区已经被写脏，正确的修正是**按属性重新检出**后再重建，而不是提交
「本机能过」的产物。

自检办法：把仓库复制到另一个绝对路径，装依赖、构建，产物应当逐字节相同。

## 六、发布范围

发布范围声明（清单文件里的白名单字段）**对从仓库源安装同样生效**。这在这类项目里
后果特别明显：

- 源码目录通常可以包含（它们是给人读的，不是运行必需的）；
- **产物必须包含**，否则装上去加载失败；
- 插件的配置文件（那行声明）必须包含，否则宿主找不到要加载什么；
- 面向人的说明文档可以包含（会展示在制品库页面上）。

发布前**必须**用「只打包不发布」的手段核对一次实际文件清单，确认产物、配置、说明都
在里面。等到用户装不上再回头查，代价高得多。

## 七、依赖版本必须跟随实际运行的宿主

这类项目的依赖版本有一个特殊性：**它们是宿主的一部分**。版本不匹配会直接表现为加载
失败。

规则：

- **跟随版本**（构建与类型检查所对的版本）必须与**实际运行的宿主**一致。每次宿主升级
  都要重新对齐，且**逐个包确认目标版本确实存在**——同一个发布批次里，个别包可能停更，
  不能用「同号」的假设蒙过去。
- **出版方的「最新版本」标记不可信**。有些包的这个标记会停在很旧的版本，而实际已有
  更新的版本。因此不要用「查最新版本」的单值命令判断，要取完整版本列表，从末尾找。
- **最低支持版本**是另一回事：只在真不兼容时上移，且兼容性声明与面向使用者的说明文档
  必须一起改。细则见 `references/publish.md`。

## 八、平台与模块表

浏览器半区能直接引用的那些模块，是**宿主界面的模块表**的镜像：表里有的走外部引用，
表里没有的必须内联进产物。这张表与真实宿主不符时会在运行时出错，两个方向都危险：

- 列了一个已经被移除的模块（宿主换实现时这类模块会消失）；
- 少列了一个新增的。

因此**每次宿主升级都要重新核对**这张表。核对办法：在宿主的界面产物里找模块加载器
附近的种子对象，那份清单就是真值。

## 九、本地挂载与发布挂载是两条路

开发时用「指向本地目录」的方式挂载，改完刷新或重启即可生效；给别人用时走安装命令。
两条路的差别：

| | 本地开发挂载 | 正式安装 |
| --- | --- | --- |
| 内容来源 | 你当前的工作目录 | 制品库或仓库源的快照 |
| 改完生效 | 刷新页面 / 重启宿主 | 需要装新版本 |
| 适合 | 开发与调试 | 日常使用 |

用户在文档里最需要看清的就是这个差别（见 `docs-set.md` 里关于安装来源表格的要求）。

生效规则：**主进程半区的改动要重启宿主；浏览器半区的改动刷新页面即可。**

## 十、这类项目的建库检查清单

在给它配版本管理之前确认：

- [ ] 产物目录会被提交（检查忽略规则里没有把它排除掉）
- [ ] 依赖目录被忽略
- [ ] 文本属性已声明，且早于首次提交
- [ ] 构建配置里的注册标识字符串等于包名
- [ ] 发布范围包含产物、配置文件与说明文档
- [ ] 仓库根目录就是插件目录，不要把一个更大的目录纳入进来

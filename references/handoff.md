# 交棒：把自己留下的痕迹清干净

## 何时读本文件

用户说「这个项目以后不用这个 skill 了」「把痕迹清掉」「交棒」，或项目配完、你在汇报里提出这件事、
用户点头之后读。目标项目不需要清理时不读。

## 一、痕迹是看得见的

本 skill 在别人项目里留下的每一处都带标记，**就写在文件里**：

```
<!-- project-forge: begin 构建与验证 -->   ...   <!-- project-forge: end 构建与验证 -->
<!-- project-forge: fill 项目定位 -->
```

YAML 文件里是 `#` 注释的等价形式。人和 AI 都能 grep 到，也能手工删掉。

**为什么用可见标记，而不是一份藏起来的账本。** 账本记的是「我写过哪些字节」，撤除能精确到字节；
代价是用户项目里多一个他不知道存在、删了会让工具退化成「什么都不认」的目录。标记把同一件事从
「推断」变成「读取」：有没有痕迹，打开文件就能回答，不依赖工具还记得。代价是**撤除不再是纯字节
操作**——用户在受管区间里改过东西的话，删区间就是连他改的一起删，所以第四步要求先给 diff 再问。

## 二、三档，处置完全不同

| 档 | 是什么 | 处置 |
| --- | --- | --- |
| `marker` | 标记行本身（`generated`、`begin` / `end`） | **纯减法**：删标记行，正文保留 |
| `placeholder` | 还没填的 `fill` | **不是减法**：这里缺的是内容。先填上，再删标记 |
| `legacy` | 旧版留下的东西 | 各不相同，见第六节 |

**最容易搞错的是第二档。** 看到 `<!-- project-forge: fill 项目定位 -->` 就把它删掉，得到的是
「一节空着的契约」——看起来像有，实际什么也没说。正确动作是先读代码把它写出来。

## 三、交棒还是撤销

拆之前先问一个问题：**这个项目还做不做？** 两种答案，动作几乎相反。

| | 交棒（毕业） | 撤销（放弃） |
| --- | --- | --- |
| 前提 | 项目继续做，只是不再用本 skill | 项目不做了，要回到介入之前 |
| 保留什么 | 全部成果：文档、CI、约定、能力目录 | 只保留本来属于这个项目的东西 |
| 删什么 | 只删标记行与旧版残留 | 标记行 + 本 skill 带来的文档与流程 |
| 顺序 | 先填占位，再剥标记，最后复扫 | 先确认没有别人在依赖它，再逐项撤 |

**顺序不可反，且严禁把交棒做成撤销。** 交棒时把 `AGENTS.md`、CI、贡献指南一起删掉，是把用户
积累下来的成果当成了痕迹——那些文件现在是他的了，标记只说明来历。撤销更要小心：先确认没有下游
在用（分支、发布、外部引用），否则撤掉的是别人正在依赖的东西。

## 四、两步走：先看，再问

### 第一步：扫描（不改任何东西）

```sh
node "<本 skill 目录>/scripts/handoff.mjs" "<项目目录>" --scan
```

它列出三档各有什么、在哪一行。**它不删任何东西**——删除不可逆，脚本不该有这权力。这条分工不是
保守：一个能自动删的脚本，迟早会在没人看着的时候被跑一次。

### 第二步：报告，等用户确认

报告要说清三件：一共几处、分别在哪；哪些是纯减法、哪些要先填内容；**项目里还有哪些东西看起来
像痕迹但不是**（第七节那张表）。报告就是这次的 diff——用户看的是「删掉之后会少什么」，不是
「你打算跑哪条命令」。然后**等用户明确说「删」**。不是「他没反对」，是他说的。

## 五、拆的顺序：先搬承重墙，再拆脚手架

0 到 6 步，顺序不能跳。前一步没做完，后一步删掉的可能是别人正在依赖的东西。

**第 0 步：填清所有 `fill` 占位。** 逐条读代码，把缺的内容写出来。这一步在删任何东西之前——
占位一旦被当成标记删掉，那节内容就永远缺了，而契约看起来还是完整的。

**第 1 步：给规则找新家。** 扫一遍文档与工作流，找**悬空指针**：指向
`references/<本 skill 的参考文件名>.md`，或指向 skill 目录下的 `scripts/`，而项目自己并没有
那个目录。那些地方写的规则现在挂在一个即将消失的位置上。**先把规则搬进项目自己的文档或脚本**，
搬完才算这一处可以拆。

**第 2 步：删悬空指针。** 搬完就删。留着它的后果是下一个人顺着链接去找，什么也找不到。

**第 3 步：剥标记。** 跑 `compose-agents.mjs --clean`，它只删标记行、正文保留。同一批里清掉
`.tmp-<pid>` 一类临时文件（写文件时被杀留下的半截产物），它们不会被当成痕迹报出来，但确实是
本 skill 留下的。

**第 4 步：排同名不同物**（dangling-name-collision）。清完之后可能有一个名字，在两个地方指的是
两样东西——旧指针指向的那个、和项目自己那个。逐个确认留下哪个，不要按「哪个新」判。

**第 5 步：清工作流里的注释残留。** 骨架顶部那些「按 TODO 替换后删掉本注释块」的说明、被注释
掉的旧命令，都在 CI 文件里。它们不影响运行，但会让后来的人以为那些步骤还生效。

**第 6 步：复扫**（第八节）。这一步是唯一的完成判据。

## 六、旧版留下的东西

这一档是 `--verify` 判「还有东西」的常见原因，而用户往往不知道为什么——他没写过这些。

| 路径或形状 | 是什么 | 怎么处置 |
| --- | --- | --- |
| `.project-forge/` 目录 | 旧版归属账本 | 删前先看一眼：它记的是「写过哪些字节」，不是项目配置 |
| `review-record.mjs`（在项目的 `scripts/` 下） | 旧版拷进项目的审查脚本 | **先 grep 工作流目录确认没有流水线在调它**，再删 |
| `project-forge:kernel:start` / `end` | 旧版内核注入标记 | 删标记行，正文保留 |
| `pf:todo` / `pf:author` / `pf:if` / `pf:endif` / `pf:include` 等 | 旧版条件与待填标记 | 同样只删标记行；它们已经不参与任何求值 |

第二行要特别小心：项目自己的 CI 里如果有一整步在跑它，删掉会让那条流水线断，而断的时候看起来
像「CI 坏了」，不是「我删了一个文件」。

## 七、不许误伤

下面这些**看起来像痕迹，其实是项目自己的**：

| 东西 | 为什么不是痕迹 |
| --- | --- |
| 文档的**正文** | 剥标记只删标记行，不动正文 |
| `skills/`、`.dsh/skills/` 下的能力目录 | 项目自己带的能力，不是本 skill 装的 |
| 与 `templates/` 里某份骨架相似的文件 | **相似不等于来源**。从这里起步、后来改写过的，就是项目自己的 |
| `.gitignore` 里的条目 | 通用条目，删掉会放进不想进的东西 |
| `LICENSE` | 见第十节 |

**判断依据只有一条：文件里有没有标记。** 不要用「形状相似度」判定——那会把 `{{ title }}` 这类
正常的模板语法判成「没填完」，照着处置就是删掉使用者自己的代码。

## 八、拆完验收

```sh
node "<本 skill 目录>/scripts/handoff.mjs" "<项目目录>" --verify
```

**四档退出码**：

| 退出码 | 含义 |
| --- | --- |
| `0` | 干净：一处标记都没有 |
| `1` | 还有痕迹，跑 `--scan` 看清单 |
| `3` | 扫描因深度或大文件被截断——**严禁把 3 当成干净** |
| `4` | 不适用：目标是这套 skill 自己的源码仓库 |

第三档是「没查完」，第四档是「不该查」。两者都不是干净，但处置完全相反：前者换个方式再扫一遍，
后者根本不要动它。**把 4 当成 0 就会去删 skill 自己的语法**，把 4 当成 1 就会让人去删一个
删不掉的东西。

拆完再跑一次交付体检（`review.mjs`），它应当只剩项目本身的问题，不该有任何一条提到本 skill。

## 九、特殊情况

- **已经交过棒**：再扫一遍。干净就说干净；不干净说明上次漏了，或后来又跑过一次。
- **目标本身就是这套 skill 的源码仓库**：`--scan` 会认出来（判据是「目标目录就是脚本所在的
  skill 根」，一条结构性事实，与它叫什么名字无关），并在报告里说明「这一趟不适用于它」。
  理由：交棒是「把一个项目从这套流程里摘出来」，而这个仓库**就是**这套流程——它的
  `templates/` 与 `references/` 里的标记是语法与讲解，删掉会把工具弄坏。
  **正确回答是「不适用」，不是「干净」，也不是「还有 N 处痕迹」。**
  要清理的它的产物，指的是清到**别的项目**里去的那些东西。
- **项目本来就没有文档**：`AGENTS.md` 可能整个都是产物，但删整份文件仍然不可逆——用户可能已经
  在里面写了东西。给完整内容，让他自己决定删哪些。
- **用户想留下**：完全可以。痕迹不删也只是几行注释。**交棒是选项，不是义务。**
- **无人值守时不要拆。** 把「有几处、在哪、要不要清」写进汇报，等用户回来定。问不到人与他同意
  是两件事，一台无人值守的机器不等于一份授权。

## 十、不许做

- **用户明确确认之前不删任何东西。**
- **不删没有标记的文件**，哪怕它看起来很像。
- **不删 `LICENSE`**：许可证的来历不影响它的效力，而删掉一份已发布的许可证是不可逆的法律问题。
- **不把「清洁」当目标**：痕迹留着的代价是几行注释，误删的代价是一个文件。

# 交棒：把本 skill 留下的痕迹清干净

**G9 的全文。** `SKILL.md` 的硬门控表把 G9 指向本文件——拆除本 skill 在目标项目里留下的
痕迹之前（交棒或撤销），先读完这一节。

`SKILL.md` 的 G1–G8 管的是「动项目之前该读什么」，本文件是 **G9**，专管「拆之前」——两件事
不是一回事，所以它自带条件。

**扫描归脚本，判断归本文。** `scripts/handoff.mjs` 只读地找出痕迹并给出分类与依据；本文件
给交棒与撤销的判据、顺序与验收。两者分开是因为它们失败的方式不同：脚本可能读漏，但读漏了
不会删错；本文件可能漏项，但拿它去删错东西比不删更糟。

## 何时读本文件

**要读**：

- 收尾汇报之后，要向用户提出「要不要把本 skill 留下的痕迹清掉」时；
- 用户已经说了「清掉 / 交棒 / 别留工具痕迹 / 这个技能以后不用了」时；
- 要判断该交棒还是该撤销时；
- 要动手拆之前——哪怕只拆一处。

**不用读**：

- 正在给项目配版本管理、文档、远端、发布，还没到收尾；
- 用户在改项目本身的代码，与痕迹无关；
- 只是想知道这个 skill 怎么用（那是 `SKILL.md` 的事）。

---

## 一、什么时候走这条路

**交棒是常规收尾，不是「用户想起来才做」。**

收尾汇报之后**主动问一次**：「要不要把本 skill 留下的痕迹清掉？」不问就收工，
等于把痕迹永久留在项目里——那不是交付。

**这是第一问，问的是「去不去痕迹」。** 用户说「清掉」，**先按交棒理解**：成果（版本管理、
远端、CI、许可证、面向人的文档）全都留下。是不是要做成撤销，要等第二问（下一节）——
项目不继续做了，才改成撤销。

**问不到人时不执行。** 被委派的子代理、批处理、无人值守运行——此时**一个字节都不许拆**，
把待确认项写进汇报，等人回来定。

自作主张拆掉是错的：痕迹留着最多是难看，拆错了是把项目的门禁撤掉了。

---

## 二、先分清：交棒还是撤销

**用户说「清掉」之后还有第二问**：这个项目还要继续做吗？

- **还要继续做** → **交棒**：成果全留，只去掉标识符；
- **不继续做了** → **撤销**：连我们加的那些一起撤掉，尽量恢复成跑之前的样子。

**两问的顺序不能颠倒**：先问要不要清痕迹（第一问，在收尾汇报里问）；用户要清，再问这个
项目还要不要继续做（第二问）。反过来问会得到相反的结果——用户以为在清痕迹，你以为在撤项目。

**两种都叫「把东西清掉」，做法几乎相反。搞混了会把做完的项目毁掉。**

| | **交棒（毕业）** | **撤销（放弃）** |
| --- | --- | --- |
| 什么时候 | 项目还要继续做，规范已经到位 | 没做完，或用户改主意不想要了 |
| `AGENTS.md` | **留**，只去掉标识符 | 我们生成的那份整份删掉；合并进已有文件的，撤掉我们加的节 |
| 面向人的文档 | **留** | 逐项问用户：删还是留 |
| CI 与远端 | **留** | 逐项问；撤远端是另一个决定，单独确认 |
| 验收 | 项目不依赖本 skill，门禁绿 | 尽量回到跑之前的样子 |

**判据只有一句**：问用户「这个项目还要继续做吗」。要 → 交棒；不要 → 撤销。**不要替他猜。**

下面正文按**交棒**写。撤销时读第六节（找新家）与第九节（特殊情况），其余按上表右列执行。

### 撤销没有机器依据（这条必须诚实说明）

本 skill **不记录**哪些文件是它新建的、哪些是它合并进已有文件的。所以撤销时能拿到的边界
只有三类：

| 依据 | 怎么用 | 边界 |
| --- | --- | --- |
| 版本控制的提交历史 | 从零锻造的项目，第一个提交就是边界 | 已有历史的项目分不出来 |
| 与本 skill 模板的相似度 | `templates/readme.md`、`templates/contributing.md`、`templates/ci-check.yml`、`templates/ci-release.yml`、许可证模板 | 相似不等于我们写的——作者自己照着同一份骨架写也像；相似度是**提问的起点，不是判决** |
| 文件名与落点路径 | 工作流与模板固定的落点 | 路径不证明作者是谁 |

**拿不到的部分必须逐项问用户，不许猜。** 猜错的方向通常是「删」——删掉的是别人的成果，
而删掉的东西不会自己回来。

**撤远端仓库与撤版本历史是不可逆且对外的动作**，要单独确认、单独给清单，按
`references/remote-github.md` 建仓那节的做法走。

## 三、三类东西，处置完全不同

看起来都是「skill 装进来的」，其实不是一类。

| 类别 | 是什么 | 交棒时 |
| --- | --- | --- |
| **技能痕迹** | 标识符、未替换的模板占位符、注入残留、指向本 skill 的悬空指针 | **删** |
| **项目基础设施** | 版本管理、远端、CI、许可证、面向人的文档 | **留**——它们现在归项目，不归 skill |
| **文档正文** | `AGENTS.md` 里的内核正文与项目节、面向人文档里的内容 | **留**——这才是产物本身 |

**第二类最容易误删。** 它们长得像 skill 装进来的零件，其实是项目现在的质量网。删了等于把
安全网撤掉，而且**不会有任何东西报警**——它本来就不在运行。

判据一句话：**凡是「删了之后，项目就没有任何机制能发现同类问题」的东西，都是基础设施，
要留。**

## 四、痕迹清单

**下面这份清单是判据，不是待办。** 逐条对照目标项目的实际情况处理，不在清单里的东西不要
顺手删。

| 痕迹（括号里是脚本报的 `kind`） | 在哪 | 是什么 | 交棒时怎么处置 |
| --- | --- | --- | --- |
| `<!-- project-forge:kernel:start -->` / `<!-- project-forge:kernel:end -->`（`kind=kernel-start` / `kernel-end`） | `AGENTS.md` | 圈定「通用内核」区的边界 | **去掉这两个标记，保留它们之间的正文**——正文是项目自己的契约，留着有价值 |
| `<!-- project-forge:managed -->`（`kind=managed`） | `AGENTS.md` | 标记「这份文件的节结构由脚本决定」 | 删掉；文件转为作者编排型，之后不再被脚本刷新 |
| `<!-- project-forge:upgraded -->`（`kind=upgraded`） | `AGENTS.md` | 标记「结构已按模板升级过」 | 删掉，同上 |
| `<!-- pf:author: 说明 -->`（`kind=author-placeholder`，**单独成一组**） | `AGENTS.md` | 残留说明**这一节还是待填写的占位** | **不是「skill 的痕迹」，是「交付没做完」**：交棒前必须先补齐**内容**，再**手工删掉**该标记——标记不会自己消失，**删掉标记不等于填了内容** |
| `<!-- pf:if ... -->` / `<!-- pf:endif -->` / `<!-- pf:scaffold -->` / `<!-- pf:endscaffold -->`（`kind=inject-control`，**四种各报各的名字**） | `AGENTS.md` | 正常注入后不残留；残留说明注入被中断 | 删掉。脚手架标记整块处理，条件标记要逐段核对事实 |
| **缺节**（机器认不出，没有 `kind`） | `AGENTS.md` | 标准结构里的若干节整个不在文件里 | **不是「skill 的痕迹」，是「交付没做完」**：补齐那几节。**它没有标识符，扫描器看不出来**——跑一次 `--status` 才看得到（见第七节第 0 步） |
| 模板占位符（`{{TOKEN}}` 形态，`kind=placeholder`） | 任意文件 | 模板没填完 | 填掉或删掉。**只在本 skill 从模板落下来的那些位置才算**——用户自己模板语言里的 `{{ }}` 不是本 skill 的痕迹 |
| `AGENTS.md.tmp-<数字>`、`README.md.tmp-<数字>`、`README.en.md.tmp-<数字>`（`kind=tmp-file`） | 仓库根 | 本 skill 的脚本原子写入中途被杀留下的半截文件 | 删掉。**只有本 skill 写入留下的才算痕迹**（它写的就这几个文件：注入脚本写 `AGENTS.md`，目录同步脚本写 README）——别的工具留下的同形态临时文件（`kind=tmp-file-suspect`）不是，别删 |
| **发布说明草稿**（`<标签>-notes.md` 一类，`kind=notes-draft`） | 目标项目任意位置 | 本 skill 起草、没写完的发布说明 | 确认是本 skill 起草的，就**连整个草稿文件一起删**。**用户要留时怎么办**：那一类命中**不计入干净判定**，所以留它不影响验收——把决定写进汇报，等用户回话即可 |
| **注释里的本 skill 名字**（`kind=skill-name-in-comment`） | `.github/workflows/` 下的工作流文件 | 模板落盘时带的头部注释块，**首行含本 skill 的名字** | 删掉注释块，机制不动。正文里提到本 skill 的名字不算这一类 |
| **指向本 skill 的悬空指针**（`kind=dangling-rule` / `dangling-script-in-automation` / `dangling-name-collision`） | 目标项目的任意文件（契约正文、工作流、配置都算） | 引用了本 skill 自己的 `references/`、`templates/`、`scripts/` 顶层里的文件，而那个路径在目标项目里**不存在** | 前两类：规则搬进项目之后，删掉指针句子（第六节那张表）；第三类是同名不同物，机器判不出，**不计入干净判定**，由人判读 |

**机器读 `kind`，人查行。** 报告里每组下面有一行指到本文件的对应位置（第四节这张表、
第六节那张表、或第七节第三步的某一步）。**处置一律以本文件为准**：脚本只给事实——
位置、原文、`kind`、是什么、挡不挡验收——**不给处置**。两边各写一份处置会漂，而那种
漂没人盯得住。

### 一条不许搞反的：与模板相似的文件不是痕迹

扫描器会报出**与本 skill 模板内容相似的文件**（`kind=template-similar`，`templates/readme.md`
一类）。那是**撤销时的证据**，不是交棒时要删的东西——面向人的文档恰恰是产物本身。

交棒时它们一律**留在原地**。撤销时它们是提问的起点，不是判决：作者照着同一份骨架写出来
的文件一样相似。**相似度只能用来缩小要问的范围，不能用来替用户决定删。**

### 必须排除，不许误伤

- `<!-- toc:start -->` / `<!-- toc:end -->`：通用目录标记，不专属本 skill，别处也在用。
  **交棒时不动。**
- `pf:needs-summary`、`<!-- pf:claims ... -->`、`<!-- <scope>-verified: ... -->`（`kind=needs-summary`
  / `claims` / `freshness-marker`）：正常只出现在本 skill 自己的文件里，出现在目标项目属
  异常——**报出来、计入「不干净」，但标为「疑似」，删之前先问用户**，它可能说明这个文件是
  从别处搬来的。
  其中 `pf:needs-summary` 出现在一份发布说明草稿里时，确认是本 skill 起草的，就**连整个
  草稿文件一起删**——那是一份没写完的草稿，不是项目的文件。
- **同名不同物**（`kind=dangling-name-collision`）：路径与本 skill 的某个文件同名，但说的是
  目标项目自己的东西（例如另一个项目自己的 `scripts/zip.mjs`）。**那不算悬空指针，别删。**
  判据是看那句上下文指向的是不是本 skill——同名只是同名。**这一类不计入干净判定**，
  所以留它不影响验收。
- **别的工具留下的临时文件**（`kind=tmp-file-suspect`）：不是本 skill 的写入方式留下的
  `*.tmp-<数字>`。**不计入干净判定**，别删。
- **用户自己的发布说明草稿**（`kind=notes-draft`）：**不计入干净判定**——用户可以决定
  保留，它不会让验收卡住。
- **用户自己模板语言里的 `{{ }}`**：那是用户项目的一部分，不是本 skill 没填完的占位符。
  **别当成占位符删掉。**

### 机器查得到什么，人还要做什么

| 类别 | 谁来查 | 怎么查 |
| --- | --- | --- |
| 标识符、未完成的占位、占位符、注入残留、临时文件、注释里的名字、与模板相似的文件、悬空指针 | `scripts/handoff.mjs` | 跑 `--scan`（人读）或 `--scan --json`（机器读） |
| **缺节**（标准结构里少了几节） | **机器判不了** | 跑 `compose-agents.mjs <项目目录> --status`（只报告，不写入） |
| **悬空指针的「搬成什么」** | **人读原文** | 扫描器报出「哪个文件的哪一行、指向本 skill 的哪个文件」；**这条规则该搬进目标项目的哪里、搬不搬得动，只能读原文才知道** |

悬空指针组（报告里标 `[F]`）的判定口径：候选取自本 skill 自己的文件树（`references/`、
`templates/` 与 `scripts/` 顶层，**允许子目录**——`references/plugins/dsh.md` 一类也查得出），
名字里的尖括号按通配算；出现在围栏代码块里的一律不算——文档里举例说明不是引用。判定悬空
要看两处：相对项目根、相对引用它的那个文件所在目录，**两处都没有才算数**——目标项目在
自己子目录里有同名文件时不算悬空。

**它按「引用出现在哪儿」分成三种 kind**，分界是扩展名（`.md` / `.markdown` / `.rst` /
`.txt` / `.adoc` 算文档，其余算机器会照着跑的配置）：

| kind | 是什么 | 处置查哪一行 |
| --- | --- | --- |
| `dangling-rule` | 指向 `references/`、`templates/` 的判据文档 | 第六节「指向本 skill 文件的指针」那一行 |
| `dangling-script-in-automation` | 指向 `scripts/` 的可执行脚本，**且引用出现在机器会照着跑的文件里** | 第六节「对某个发布脚本的调用」那一行 |
| `dangling-name-collision` | 指向 `scripts/` 的脚本，**但引用出现在文档里** | 同名不同物，机器判不出，**由人判读**；不计入干净判定 |

每条命中给的是：文件相对路径、行号、被引用的路径原文、`kind`、它指向本 skill 的哪个文件
（Markdown 取一级标题，脚本取顶部注释里的用途那半句——因此能看出**缺的是哪一段判据**），
以及一句「目标项目里没有承接这段判据，读者按它去读会走到空处」。**指向多个文件时只报
「几个文件」**：一处指针可能欠一整族判据，摘其中一个标题会让人以为只欠一份。

**处置不在报告里。** 报告每组标题下有一行指到本文件的对应位置——机器给 `kind`，人查行。
脚本只给事实（位置、原文、`kind`、是什么、挡不挡验收），**不给处置**：两边各写一份处置
会漂，而那种漂没人盯得住。

机器可读的一路，命中按 `groups` 分组给出：`markers`、`unfinished`、`placeholders`、
`residue`、`templateSimilar`、`stateDir`、`dangling`。顶层另有 `project`、`mode`、`clean`、
`findings`（**命中总数**，含与模板相似的那一组）、`blocking`（**挡着干净判定的那些**的条数，
不含相似那一组）与 `scanned`（本次没能扫到的东西各计多少，外加已扫过的文件与目录数）。

**`findings` 与 `blocking` 是两件事，别混。** `findings` 是命中总数，`blocking` 才是挡验收
的那些——**验收看 `blocking`**。不计入 `blocking` 的有：与模板相似的那一组、疑似且机器判
不准的那几类（同名不同物、别的工具留下的临时文件、用户自己的发布草稿）。

状态目录一组（`kind=state-dir`）指的是**目标项目里以本 skill 名字命名的状态目录**（形如以
skill 名加前缀的隐藏目录）——本 skill 的更新状态实际写在系统临时目录里，不落在项目内；
但目标项目里若存在这样一个目录，它就是痕迹，**整个删掉**。

**`scanned` 这一层决定报告怎么读。** 「没发现痕迹」有两种含义：一种是扫过了、确实干净；
另一种是有一批东西没被扫到（超大的文件、二进制文件、读不出来的目录、超过深度上限的目录、
遍历被上限截断），所以没发现。**只看「没发现」而不看跳过了什么，就会把「没扫到」读成
「扫过了、很干净」。** 跳过的东西不为零时，按 `scanned` 里列的种类与数量补扫。`scanned`
里那个 `partial` 为真，表示**目标给成了文件而不是目录**——只扫了那一个文件，结论行会
明说「本次没扫到全部」。

**扫描器报干净，不等于处理完了。** 它给得出位置与「指向本 skill 的哪个文件」，因而能看出
缺的是哪一段判据；给不出的是**「这条规则该搬进目标项目的哪里、搬不搬得动」**——
**这一类不许因为扫描器说干净就跳过。**

### 悬空指针为什么值得单独查

注入到目标项目里的契约，正文里带着几处指向本 skill 自己的引用——版本号抬不抬的判据、
发布说明怎么写、可见性怎么改，都写着「详见某某文件」。那些文件在目标项目里**不存在**。

所以每一处悬空指针同时是三件事：一处**痕迹**（项目提到了本 skill 的内部文档）、一处
**坏链**（读者按它去读会走到空处）、一处**待搬的规则**（它指向的判据是项目需要的）。

纯文档类项目可能一处都没有；要发布或有远端的项目通常有几处。**不要预设数量，按实际扫
出来的处理。**

**脚本能定位它，但定位不等于搬运。** 定位回答「哪里有」，搬运回答「搬成什么」；后者只能
由人读原文决定，机器给不了。

## 五、铁律：先能拆，再拆

拆之前必须证明：**拆完之后，项目不依赖本 skill 的任何东西，也能跑、门禁也能绿。**

拆到一半比不拆更糟——门禁还在，但它读的数据没了，于是开始误报，而人会以为「这项目本来
就有问题」。

**具体到本 skill，有两处会让人误判：**

- **本 skill 的交付门禁在拆完之后会报红。** 它要的就是内核标记在（`scripts/review.mjs`
  会说「`AGENTS.md` 缺少内核标记」）。那是**本 skill 对目标项目的门禁**，交棒之后它不再
  适用于那个项目——项目自己的门禁是项目自己声明的那些命令。**不要为了让本 skill 的门禁
  变绿而把标记留着**（那是没拆），**也不要因为它变红就以为项目坏了**。
- **拆完之后不要对这个项目再跑注入脚本。** 没有内核标记的文件会被当成手写文件，默认不动
  它；但**带升级参数重跑会把内核重新灌回去**，把刚拆干净的项目变回有围栏的样子。

---

## 六、拆之前：先给规则找新家

**删掉一个记录，就等于删掉它承载的那条规则。规则不能因为记录没了就悄悄失效。**

拆之前逐条过一遍「现在靠什么才成立的规则」，给它新载体。

本 skill 留下的东西里，真正承载规则的不多，但每一处都要有去处：

| 现在靠什么才成立 | 交棒后靠什么 |
| --- | --- |
| 内核标记圈定的那两段正文 | 留在 `AGENTS.md` 里。标记只是围栏，正文本来就是项目的契约——去掉围栏，规则一条不少 |
| **指向本 skill 文件的指针**（`kind=dangling-rule`） | **规则本身搬进项目自己的文档**（写成项目的话），然后删掉指针句子。脚本能告诉你「哪里悬空、指向本 skill 的哪个文件」，**不能告诉你「这条规则该搬进目标项目的哪里、搬不搬得动」**——后者只能读原文与问人 |
| **对某个发布脚本的调用**（`kind=dangling-script-in-automation`） | 那个脚本必须留在项目里，或调用方改写成项目自己的做法。**删了脚本而留着工作流，就是门禁还在、数据没了**。留在项目里的脚本**要改掉里面属于本 skill 的名字**（标识串、User-Agent、路径前缀一类）——脚本已经归项目，名字也该换掉 |
| **同名不同物**（`kind=dangling-name-collision`） | **没有规则要搬**——那句话说的是目标项目自己的东西。机器判不出，**由人判读**：既别删那句话，也别造个同名文件骗过检查。这一类**不计入干净判定** |
| 工作流顶部的模板注释块 | 删掉注释块，机制不动。首行含本 skill 的名字，**机器只认注释里的**，正文里提到名字不算 |
| 按项目事实取舍的条件段落 | 已经在正文里了。删标记时逐段核对——**条件成立与不成立两种事实，在项目里都要写对** |
| 许可证模板里的年份与持有人占位符 | 填成真实值；用户选择不授权的，整个文件不写 |

**找不到新载体的规则，要当场告诉用户它会失去守护**，让他决定：换个载体（项目自己的文档、
提交前钩子、另一条检查），还是接受这条不再有保障。**不许静默丢掉。**

## 七、三步走

### 第一步：勘察（不改任何东西）

跑一次扫描，拿到完整痕迹清单：

```sh
node "<本领目录>/scripts/handoff.mjs" "<项目目录>" --scan
```

`<本领目录>` 指本 skill 自己所在的位置，`<项目目录>` 指被处理的项目，两者通常不同。
需要程序接着处理时用 `--scan --json`。扫描是只读的，**扫完不确认就动手，等于凭印象删**。

悬空指针由扫描器一并报出（见第四节）；**手工再扫一遍是交叉核对**——脚本告诉你哪里悬空，
**它不告诉你这条规则该搬进目标项目的哪里、搬不搬得动**。

同时要答几个**只有人能答**的问题。**答不出来就不许进下一步**：

| 问题 | 为什么只有人能答 |
| --- | --- |
| 这个项目还要继续做吗？ | 决定交棒还是撤销 |
| 待填写的那几节，谁来写？ | 那是项目的内容，不是工具的 |
| 悬空指针指向的规则，搬进项目哪个文件？ | 只有项目自己知道规则该落在哪 |
| 要不要连自动化与远端一起撤？ | 那是另一个决定（第九节） |
| 撤销时逐项：面向人的文档、CI、远端、本地仓库，各自留还是删？ | 撤销没有机器依据 |

### 第二步：报告，等用户确认

给一张表，三列：**删什么 / 留什么 / 为什么**。

**必须等用户明确说「可以」。** 「你觉得呢」「应该没问题」「应该没影响」都不算确认。

报告里要写清两件事：

- 拆完之后，**项目不再依赖本 skill 的任何东西**——包括脚本、文档与门禁；
- 拆完之后，**再跑这个 skill 也不会动这个项目的文档**——它找不到自己的标记了。

### 第三步：按顺序拆

顺序是承重的，反了就红：

0. **补齐交付**：把没写完的那几节写实。**未完成有两种形态**，两种都要处理：
   - **待填写的占位**（带 `pf:author` 标记的节）：扫描器把它报在「未完成」那一组里。把内容
     写实，**再手工删掉那个标记**——标记不会自己消失，**删掉标记不等于填了内容**；
   - **缺节**（标准结构里的若干节整个不在文件里）：**机器判不了**——节名清单在模板里，
     脚本里再抄一份模板结构正是要消灭的东西。跑一次下面这条才看得到：

     ```sh
     node "<本领目录>/scripts/compose-agents.mjs" "<项目目录>" --status
     ```

     报出缺失的节数不为零，就是缺节。**手写起来的 `AGENTS.md` 走的就是这条路**——
     升级成标准结构之后缺的节，只在 `--status` 里看得见。

     扫描报告里常驻一句提醒（形态是标记还是缺节）。**别把「扫描没报缺节」读成「不缺节」。**
1. **给规则找新家**：按第六节那张表，规则搬进项目。**载体没定，不许往下走。**
2. **删悬空指针**：规则搬完之后再删指针。**反过来做，那条规则在项目里彻底消失，且没人知道
   它存在过。**
3. **删工作流里的注释块**（`kind=skill-name-in-comment`）与对本 skill 脚本的依赖：脚本留在
   项目里（并改掉里面属于本 skill 的名字），或工作流改写成项目自己的做法。
4. **删标识符**：内核标记对（**保留中间的正文**）、受管标记、已升级标记。
5. **删注入残留**：条件标记、脚手架标记（**四种各报各的名字**）。
6. **删占位符与临时文件**：占位符填掉或删掉；**本 skill 留下的**半截临时文件删掉——
   别的工具留下的同形态文件（`kind=tmp-file-suspect`）别动。
7. **复验**：见第八节。

**第 1→2 步是承重的，反了就红。** 先搬规则再删指针，反过来做，那条规则在项目里彻底消失，
且没人知道它存在过。

**第 0 步放在第 4 步之前，是为了让待补的那几节在还能被识别的状态下补齐**——先拆了围栏，
那一节就不好认了。**但机器不强制这个顺序，靠人**：把第 4 步提到第 0 步之前，产物与正序
一样。真正危险的不是顺序，是**删了标记却不补内容**——那会得到一份「干净但空」的契约，
机器还判它干净。

第 4 步与第 5–6 步之间没有承重关系，但都要在复验之前。

**不可逆动作单独确认**：撤远端仓库、撤本地版本历史，单独给清单、单独确认，不夹在这一批里。

## 八、拆完验收

- [ ] `node "<本领目录>/scripts/handoff.mjs" "<项目目录>" --scan` 的 **`blocking` 归零**
      （**`blocking` 才是挡验收的那些**，`findings` 是命中总数——与模板相似的那一组只进
      `findings`，不进 `blocking`，交棒时不动它；标着「不计入干净判定」的那几类同理）
- [ ] `node "<本领目录>/scripts/handoff.mjs" "<项目目录>" --verify` 判定干净（退出码 0）
- [ ] 项目**自己**的门禁命令全绿（按项目契约里声明的那些命令，贴输出）
- [ ] 目标项目里没有指向本 skill 的悬空指针（扫描器那一组归零，且按第四节手工交叉核对过一遍——它给不出「搬进哪里」的判据）
- [ ] 工作流与发布通道不依赖本 skill 的任何脚本（逐个确认；留在项目里的那些已改掉里面的名字）
- [ ] **整个项目搜本 skill 的名字（名字从 `SKILL.md` 的 `name` 取），零命中；而项目里的规范
      一条没少**——契约里的判据、面向人的文档、CI 与远端都还在

**`findings` 与 `blocking` 别混。** 验收看 `blocking`（`blocks` 为真的那些条数）；`findings`
是命中总数，含与模板相似的那一类。**说「零命中」是不对的**——那一类永远会被报出来，而它
恰恰是交棒时一个字节都不该动的东西。

最后一条是总判据：**项目里不再有任何东西知道这个 skill 存在过，但规范一条没少。**

文档留下的是规范，不是「某个工具生成的产物」。

## 九、特殊情况

### 已经交过棒了

再跑一次扫描，`blocking` 归零。**这不是错误**：结论行说「已经是干净状态」就结束。

与模板相似的那一组仍会被列出来，报告末尾也会补一句「[D] 组列出的模板衍生物交棒时一律不动」
——那是正常的，那一组不参与干净判定。

**不许为了走流程建个空目录再删掉它**——那是在制造它本来要清理的东西。

### 结论行说「本次没扫到全部」时

目标给成了一个文件（而不是目录）、或者扫描被上限截断、有目录读不出来时，结论行**不说**
「已经干净状态」，而是「**没有发现痕迹（本次没扫到全部，见上面的提示）**」。

**那不是「干净」，是「没扫到」。** 按报告里的提示补扫之后再判断——**别拿它当验收通过**。

### 项目本来就没有文档

没有契约可拆，也就没有围栏可去。只处理其余痕迹：占位符、临时文件、悬空指针、工作流里的
注释块。

**报告照走**——用户要知道删的是什么、删完还剩什么。

### 目标是关于本 skill 的项目，或 fork 它做二次开发

这一类项目里，本 skill 的名字与标记**是内容，不是痕迹**——那份契约谈的就是这个工具，
它的文档里当然会出现它的名字。

**照样要扫**，只是判读方式不同：每一处命中都要人重新判读「这是内容还是痕迹」，不能按
「凡是命中就是痕迹」处理。

**先确认用户是不是真的要拆**——多数情况下不是：用户是要改这个工具，不是要把它从自己的
文档里抹掉。

### 用户连自动化也不要

有的用户连自动化也不要，想回到「一个干净的项目」。**那是另一个决定，要单独问、单独确认。**

如果确认，额外做：删掉检查与发布工作流；撤远端（不可逆且对外，按
`references/remote-github.md` 的确认清单做法单独确认）；本地版本库要撤同样单独确认——里面
的历史撤掉就没有了。

**必须把后果说给用户听**：

> 从此这个项目没有任何自动检查。规范还在文档里，但**没人守**——
> 下一个改代码的人可以随便写死一个值，而不会有任何东西变红。

说完等他再确认一次。

### 目标是本 skill 自己的仓库

那份契约里的内核是该仓库的正式构成，不是待清理的痕迹。**先确认用户是不是真的要拆**，再
决定走不走本流程。

## 十、无人值守时怎么推进

问不到人时，**唯一可以自己决定的是：一个字节都不改**。

- 可以做：跑只读扫描；把痕迹清单与「只有人能答的问题」写进汇报；
- 不可以做：删任何文件、删任何标记、撤远端、撤历史。

理由：拆除是不可逆的，而痕迹留着只是难看。**把待确认项留在汇报里，等人回来定**——这比
自作主张安全得多。

汇报里要写清「待确认项」是什么，让接手的人一眼知道下一步做什么。

## 十一、不许做

| 不许 | 为什么 |
| --- | --- |
| 用户没明确确认就拆 | 那不是收尾，是擅自破坏 |
| 问不到人时自作主张拆 | 痕迹留着最多难看，拆错了是把门禁撤了 |
| 把「交棒」做成「撤销」 | 一字之差，结果相反：交棒留成果，撤销删成果 |
| 把面向人的文档、许可证、CI、远端当痕迹删掉 | 它们是项目的安全网，删了没有任何东西会报警 |
| 删内核标记时连中间的正文一起删 | 正文是项目自己的契约，最值钱的就是它 |
| **删掉待填写的标记却不补那一节的内容** | 得到一份「干净但空」的契约，而且机器还判它干净——最难发现的一种坏 |
| **把缺节当成没有这回事** | 缺节没有标识符，扫描器看不见；不补齐就拆围栏，交出去的是半份契约 |
| 先拆围栏再补待填写的节 | 得到一份「干净但空」的契约，比原来更糟 |
| 只删指针不搬规则 | 那条规则在项目里彻底消失，且没人知道它存在过 |
| **删了工作流依赖的脚本却留着工作流** | 门禁还在、数据没了，于是开始误报 |
| **删掉别的工具留下的临时文件** | 同形态的临时文件不只本 skill 会留；只有本 skill 写入留下的那些才是痕迹 |
| **把用户自己模板语言里的 `{{ }}` 当占位符删掉** | 那是用户项目的一部分，不是本 skill 没填完的占位符 |
| **把与本 skill 同名、但说的是目标项目自己东西的路径当成悬空指针处理**（`kind=dangling-name-collision`） | 删掉用户自己的一句话，或造个同名空文件骗过检查——两种都错 |
| **把用户自己的发布说明草稿删掉** | 那是用户的文件；确认是本 skill 起草的才删 |
| 拆到一半停下 | 半拆比不拆更糟 |
| 为了让本 skill 的门禁变绿而留着标记 | 那是没拆；而且那个门禁交棒后不再适用 |
| 拆完又对这个项目跑注入脚本的升级参数 | 它会把内核重新灌回去 |
| 撤远端仓库或版本历史不做单独确认 | 不可逆且对外，别人可能已经克隆过 |
| 扫描没跑就动手 | 凭印象删，会删掉不该删的 |
| 拿「你觉得呢」当确认 | 必须是明确的「可以」 |
| 拆完不跑复验就宣布完成 | 拆本身就是一次改动，一样要验 |
| 为了走流程建个空目录再删掉它 | 那是在制造它本来要清理的东西 |

# 交棒：把自己留下的痕迹清干净

## 何时读本文件

用户说「这个项目以后不用这个 skill 了」「把痕迹清掉」「交棒」，或者项目配完、你在汇报里
提出这件事、用户点头之后读。

---

## 一、痕迹是看得见的

本 skill 在别人项目里留下的每一处都带一个标记，**就写在文件里**：

```
<!-- project-forge: begin 构建与验证 -->   ...   <!-- project-forge: end 构建与验证 -->
<!-- project-forge: fill 项目定位 -->
```

YAML 文件里用 `#` 注释的等价形式。人和 AI 都能 grep 到，也能手工删掉。

早先版本不是这样：它靠藏在 `.project-forge/` 里的哈希账本倒推「这段是不是我写的」。
那能精确到字节，代价是用户项目里多一个他不知道存在、删了会让工具退化成「什么都不认」的
目录。**拿掉账本之后，同一件事从「推断」变成了「读取」。**

代价也要说清：**精确到字节的撤除没有了**。用户在受管区间里改过东西的话，删区间就是连他改
的一起删。所以下面第二步要求先给 diff。

---

## 二、三档，处置完全不同

| 档 | 是什么 | 处置 |
| --- | --- | --- |
| `marker` | 标记行本身 | **纯减法**：删标记行，正文保留 |
| `placeholder` | 还没填的 `fill` | **不是减法**：这里缺的是内容。先填上，再删标记 |
| `legacy` | 旧版留下的东西 | 各不相同，见第四节 |

**最容易搞错的是第二档。** 看到 `<!-- project-forge: fill 项目定位 -->` 就把它删掉，
得到的是「一节空着的契约」——看起来像有，实际什么也没说。正确动作是先读代码把它写出来。

---

## 三、两步走：先看，再问

### 第一步：勘察（不改任何东西）

```sh
node "<本 skill 目录>/scripts/handoff.mjs" "<项目目录>" --scan
```

它列出三档各有什么、在哪一行。**它不会替你删任何东西**——删除不可逆，脚本不该有这权力。

### 第二步：报告，等用户确认

报告要说清三件：一共几处、分别在哪；哪些是纯减法、哪些要先填内容；
**项目里还有哪些东西看起来像痕迹但不是**。

然后**等用户明确说「删」**。不是「他没反对」，是他说的。

---

## 四、旧版留下的东西

早先版本往目标项目里塞过两样东西，它们**不是**这个项目的资产：

| 路径 | 是什么 | 怎么处置 |
| --- | --- | --- |
| `.project-forge/` | 旧版归属账本 | 删前先看一眼——它记的是「本 skill 写过哪些字节」，不是项目配置 |
| `review-record.mjs`（在 `scripts/` 下） | 旧版落到项目里的审查脚本 | 先 grep 一遍项目的工作流目录确认没有流水线在调它，再删 |

后者要特别小心：如果项目自己的 CI 里有一步在跑它，删掉会让那条流水线断。

---

## 五、不许误伤

下面这些**看起来像痕迹，其实是项目自己的**：

| 东西 | 为什么不是痕迹 |
| --- | --- |
| `README` / `CONTRIBUTING` / `LICENSE` / `AGENTS.md` 的**正文** | 剥标记只删标记行，不动正文 |
| `skills/`、`.dsh/skills/` 下的能力目录 | 项目自己带的能力，不是本 skill 装的 |
| 与 `templates/` 里某份骨架相似的文件 | **相似不等于来源**。从这里起步、后来改写过的文件，就是项目自己的 |
| `.gitignore` 里的条目 | 通用条目，删掉会放进不想进的东西 |

**判断依据只有一条：文件里有没有标记。** 没有标记就不是痕迹，不管它长得多像。

这一条是从错误里学来的：早先版本用「形状相似度」判定，结果是 `{{ title }}` 这种正常的
模板语法被判成「没填完」——照着处置就是删掉使用者自己的代码。

---

## 六、拆完验收

```sh
node "<本 skill 目录>/scripts/handoff.mjs" "<项目目录>" --verify
```

干净时退出 0，还有东西时退出 1。**「干净」的定义是「一处标记都没有」**，包括未填的占位。
宽一点说「差不多干净了」没有意义——那等于把「还有东西」读成「干净」，而这是个不可逆动作
的最后一道关。

拆完还要确认项目还能用：跑一遍 `review.mjs`，它应当只剩「项目本身的问题」，
不该有任何一条提到本 skill。

---

## 七、特殊情况

**已经交过棒了**：再扫一遍。干净就说干净；不干净说明上次漏了或后来又跑过一次——
后者常见于「交棒之后又想配点什么」。

**目标本身就是关于本 skill 的项目**（fork 它做二次开发）：那时 `project-forge` 出现在
文件里是**内容**，不是痕迹。报告里每一处都要人重新判读。

**项目本来就没有文档**：那 `AGENTS.md` 可能整个都是产物——但删整份文件仍然不可逆，
用户可能已经在里面写了东西。给完整内容，让他自己决定删哪些。

**用户想留下**：完全可以。痕迹不删也只是几行注释。**这不是「必须清干净才算交付」**——
交棒是选项，不是义务。

---

## 八、无人值守时怎么推进

**不要拆。** 把「有几处痕迹、分别在哪、要不要清」写进汇报，等用户回来定。

不是保守，是「问不到人」和「他同意」是两件事。一台无人值守的机器不等于一份授权。

---

## 九、不许做

- **用户明确确认之前不删任何东西。**
- **不删没有标记的文件**，哪怕它看起来很像。
- **不删 `LICENSE`**：许可证的来历不影响它的效力，而删掉一份已发布的许可证是不可逆的
  法律问题。
- **不把「清洁」当目标**：痕迹留着的代价是几行注释，误删的代价是一个文件。

# 各宿主硬判据

## 何时读本文件

目标是插件类项目（宿主加载代码的扩展）时读。判定流程与三态分流在
`references/skill-project.md`，这里只写会在发布或安装时**拦住你、或悄悄让用户装不上**的硬判据。
遇到本文件没有的宿主，回那一份的「没有专章时怎么办」走五步查证。

## Obsidian 插件

1. **识别**：仓库根的 `manifest.json` 含 `minAppVersion`。没有这个字段的不是这个宿主的插件。

2. **严苛字段红线**：`id` 禁含 `obsidian`、禁以 `plugin` 结尾、全局唯一（**提交审核时才校验**）；
   `name` 禁含 `Obsidian` / `Plugin` / emoji；`description` 以句号结尾、禁以 `This is a plugin`
   开头。这几条在本地跑得通，只在审核那一刻拦你。

3. **产物铁律**：`main.js` **绝不进 Git 库**（写进忽略规则），必须作为发布页的**独立附件**上传。
   三件套是 `main.js`、`manifest.json`、可选的 `styles.css`，**禁打成 zip**。
   只打标签不传附件，用户装不上——而且**失败很安静**：标签有了、目录页也有了，装的时候就是没有。

4. **最致命的标签陷阱**：Git 标签必须与 `manifest.json` 的 `version` **完全一致且严禁带 `v`
   前缀**（`1.2.3`，不是 `v1.2.3`）。npm 一类工具默认建 `v1.0.1`，这是该生态最高频的翻车点。
   **CI 触发行必须从 `v*` 改成 `[0-9]*`**，否则永远不触发——工作流看着配了，一次都没跑过。

5. **社区目录读默认分支的最新提交**：`manifest.json` 改了没提交、或提交在别的分支，审核看到的
   是旧版。发布前确认它在默认分支上。

6. **稳定通道的 `version` 只认 `x.y.z`**。带后缀（`-beta`）只能走测试通道；而装过后缀版的用户
   **收不到同号正式版的更新**——他的版本号已经「更高」了。

7. **`versions.json` 的映射要跟着改**（`version` → `minAppVersion`）。它决定老版本能不能被解析，
   漏改的表现是旧版用户升不上来。预发布只走测试通道，不进稳定通道。

8. **目录侧有缓存**。新版没被收录时先手动触发重扫，不要连发几个新版硬撞——撞出来的是一堆没人
   装的版本，而原因在缓存。

9. **手动安装时文件夹名要与 `id` 一致。** 宿主按目录建配置与数据的位置，而插件按 `id` 报自己的
   身份。两者不一致的表现是「设置存了、但读不到」，用户会以为插件坏了。

10. **`isDesktopOnly` 该置 `true` 就置。** 用了 Node 或桌面端能力的插件在移动端会装上然后崩，
    而崩的时候没有提示指向这个字段。

## VS Code 扩展

1. **识别**：`package.json` 含 `engines.vscode`（或 `contributes`）。

2. **必填四字段**：`name`、`version`、`publisher`、`engines.vscode`。**`engines.vscode` 严禁填
   `*`**——打包工具直接拒绝，这是硬校验不是风格建议。写清最低版本（如 `^1.85.0`）。

3. **扩展 ID 是 `${publisher}.${name}`，不可变。** 它与宿主侧的数据、设置、命令命名空间绑定；
   改任一半，老用户装上新版之后所有配置都失联。

4. **`name` 与 `displayName` 都要求市场唯一。** 撞名是发布失败，平台**不会自动加后缀**——
   而这一步通常在打包成功之后才发现。

5. **`categories` 只能填官方枚举值，`keywords` 有数量上限。** 填错**不给模糊提示**，报的是
   一个看不出所以然的字段错误。

6. **双入口**：`main` 是 Node 宿主（桌面），`browser` 是 Web 宿主。**Web 入口禁用 Node 的 `fs`、
   子进程、原生模块**——那里没有这些能力。同一份源码支持双环境必须显式处理，不能靠运行时判断。

7. **`.vscodeignore` 裁剪与打包预演**：`vsce package` 出一份清单，确认运行时需要的文件在、
   测试与源码不在。打包体积超限时平台直接拒收。

8. **扩展间依赖用 id 声明**（`extensionDependencies`）。改 `name` 或 `publisher` 会连带影响下游
   ——那些扩展装的是一个再也解析不到的地址。

9. **激活事件要与实际能力对上**（`activationEvents`）。写错时扩展装了、看着是启用状态，就是
   一个命令都不响应；而用户分不清「没装好」和「没生效」。

10. **`contributes` 里声明的命令必须在代码里注册。** 两处不一致时命令出现在命令面板里，
    点下去报「未找到」——这比不出现更让人困惑。

11. **发布用 `vsce publish`（或对应的市场发布命令），不是把 `.vsix` 传到仓库。** 市场读的是
    发布动作带来的元数据；只传附件的项目在市场上没有版本记录。

## DSH 扩展

1. **三态识别与 `exports` 对齐**：bundle 补丁（`package.json` 的 `dsh` 字段里声明补丁文件）、
   配置文件补丁（`cordis.patch.yml` 一类）、客户端半区（`platform: "web"`）。`exports` 里要能
   解析到每一处被引用的子路径，缺一条就是安装时找不到模块。

2. **`engines.dsh` 是硬闸门。** 安装与启动都按它（未声明时按对等依赖的范围）检查运行版本，
   不兼容要求用户明确豁免。范围写错的表现是「装了但启动不起来」，而错误信息未必指向这一行。

3. **补丁层按顺序叠加**：上游组合包的补丁在前，profile 自己的补丁在后，最后是用户覆盖层，
   后叠加的赢。新增行要写进自己这一层，不要指望改上游。顶层改写只对**已存在**的 id 有效；
   要给上游没有的东西加行，必须走 `insert` 一类显式新增语法——对不存在的 id 做顶层改写是
   静默空操作，装上也不报错。

4. **补丁 `name` 写错只告警不生效。** 行看着在、就是不做事。`config` 缺字段走 schema 默认值，
   因此**覆盖某一行时必须把该行需要的键重述全量**——只写要改的那一个键，其余会被默认值填掉。

5. **行 `id` 改名不报错**，只会作为新控件并列多出来。同一件东西出现两次时，先查 id 是不是被
   改过，不要去查渲染逻辑。

6. **别拿注册表的 `latest` 当宿主版本。** 它可能落后于本机装着的预发布版。宿主版本一律以
   `dsh --version` 为准，对等依赖的范围也要按它写。

7. **`whenToUse` 与 `metadata` 不进模型目录**，别把路由押在它们上面——它们不会让模型知道这个
   能力存在。真正决定「会不会被读到」的是目录摘要里的那句话。

8. **浏览器半区必须以「装进 profile」验收**，开发叠加层不算。开发模式下能出的界面，走一遍正式
   安装可能因为 `exports`、平台字段或产物缺失而完全不来。

9. **`peerDependencies` 里要写宿主侧的那几个包**（连接、界面插槽、基础组件一类），并放进
   `devDependencies` 供本地类型检查。写进 `dependencies` 会装出第二份宿主副本，故障表现是随机
   的初始化失败，而不是一条明确的报错。

10. **`files` 白名单要包含源码与补丁文件。** 只要产物不要源码时，二次开发与调试都没法做；
    而漏了补丁文件的表现是「装上了但一行都没生效」——宿主找不到那个 YAML，不会报错。

11. **改宿主侧行的 `id` 前先确认没有别处按它引用。** 存储键、路由、配置项都可能由它派生，
    改名之后旧数据还在、新代码读不到，而两边都没有错误信息。

12. **打包后要在一个干净 profile 里验一遍完整链路**：装上、重启、看那一行真的生效、关掉再看
    它真的不生效。只验「装上了」不够——装上了不做事是这个宿主最常见的失败形状。

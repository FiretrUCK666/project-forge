# 插件类项目

## 何时读本文件

- 勘察判定项目是**插件类**（如 `dsh-plugin`、`vscode-extension`、`obsidian-plugin` 等），
  或你从项目形态上认出它是「被某个宿主加载的扩展」时（无专章的生态见第九节）。
- 需要判断「产物要不要提交进仓库」「发布范围怎么写」「改标识会连带影响什么」时。
- **遇到一个没有专章的插件生态时**——先读本文件，它给出的是判定协议与生长规则，
  不依赖任何具体生态。

## 一、这一类项目的共同点：宿主加载你的代码

不管宿主是编辑器、笔记应用、浏览器还是某个 Agent，插件类项目都满足一条性质：

> **它不是独立程序，而是被另一个程序加载进自己的进程（或受限环境）里的模块。**

这条性质推出一整串看起来奇怪的约定。它们**不依赖任何具体生态**，所以对每一种插件
都成立：

| 因为宿主加载你的代码 | 所以 |
| --- | --- |
| 宿主从磁盘上的**包**里找入口 | 包必须有正确的入口声明，且入口指向的文件必须真实存在 |
| 宿主决定运行环境 | 你能用的能力是宿主给的，不是语言的全部 |
| 加载失败 = 宿主启动失败或功能缺失 | 版本兼容性是硬约束，不是建议 |
| 安装你的人**不会替你构建** | 产物必须随包分发（见第三节） |
| 宿主按自己的标识认你 | 那个标识是**数据地址**，改名会丢用户数据（见第四节） |

**这五条是本文件的骨架**，下面逐个展开。各生态的专章只补「在这个生态里具体长什么样」，
不重复这些结论。

## 二、判定协议：先查清这六件事

遇到任何插件类项目（**包括没有专章的**），都要先查清这六件事。它们对每一种生态都有
答案，只是取值不同——所以「查什么」是固定的，「答案是什么」由项目自己决定。

| # | 要查什么 | 为什么必须查 | 从哪查 |
| --- | --- | --- | --- |
| 1 | **清单文件是哪个** | 宿主靠它认识你的项目，它的位置与格式决定了后面一切 | 项目根目录里那个「描述项目、声明入口、声明对宿主版本要求」的文件 |
| 2 | **宿主侧的标识是什么** | 它是**数据地址**（用户数据存在哪个键下），改名会丢数据 | 清单里那个被宿主当作唯一名的字段；通常与目录名一致 |
| 3 | **分发侧的标识是什么** | 安装标识与宿主标识是两件事，混淆会导致「装上了但加载不了」 | 制品库上的包名 / 发布者账号下的名字 |
| 4 | **宿主加载什么文件** | 决定产物入不入库、发布范围怎么写 | 清单里的入口字段；以及宿主文档里「安装时下载哪些文件」 |
| 5 | **宿主版本约束写在哪** | 决定依赖跟随与最低支持版本的规则 | 清单里声明「需要宿主哪个版本」的字段 |
| 6 | **怎么本地调试、怎么正式分发** | 两条路差别很大，而且这是使用者最需要看清的 | 宿主文档的「开发扩展」与「发布扩展」两节 |

**这六件事查清了，一个新生态就已经被正确处理了**——剩下的只是把答案写下来。

### 查不到的怎么办

**不要猜，也不要凭「插件一般都这样」填空。** 按这个顺序退：

1. 先在项目自己身上找证据（清单文件的字段名、依赖里有没有宿主 API 包、构建配置里
   有没有打包命令、`.gitignore` 里排除了什么——这些都能反推出宿主的加载方式）。
2. 再查该宿主的官方文档。文档里通常有「开发扩展」与「发布扩展」两节，那两节就是答案。
3. 还查不到，**如实说明哪一项没查出来、以及它对结论有什么影响**，然后请用户确认。
   例：「我没能确认这个宿主安装时会下载哪些文件，所以无法判断产物是否必须入库——
   这一项会影响第一次提交，建议先确认。」

**不清楚就说不清楚**，比给一个看起来合理的答案好：错的答案会被照着执行，而不确定的
答案会被核实。

## 三、产物必须入库（与常规做法相反，这是对的）

一般项目的编译产物不进版本库。**插件类的产物必须进**，理由只有一条：

> 安装这个包的人**不会**替它跑一次构建。

安装路径（从制品库装、从仓库源装、被宿主按路径加载）都只做「取文件、放到位、加载」，
没有任何一步会运行构建。产物不存在，插件就是加载失败。

这条与「依赖目录永远不进库」并不矛盾——判据是同一条：

| 东西 | 拿到的人能自己生成吗 | 结论 |
| --- | --- | --- |
| 依赖目录 | 能（装一次依赖就有） | 不进库 |
| 插件产物 | 不能（安装流程不构建） | **必须进库** |

推论：

- 源码与产物**必须同一次提交**。两者分开提交，等于在历史里埋下「某个提交的产物与源码
  不一致」的状态。
- 持续集成里应当有一条检查：**重新构建一次，产物必须与提交的产物逐字节一致**。这是
  唯一能自动发现「忘了重新构建」的手段。
- 少数生态是例外：宿主只加载**源码**（例如纯 Markdown 声明的扩展、或宿主自己会编译），
  此时产物不适用。**判据仍然是第 2 节第 4 问**——宿主到底加载什么文件。

## 四、两个标识：宿主侧的那个是数据地址

这是这类项目**最容易出错、后果最难查**的一处。两个标识各自独立：

| 标识 | 决定什么 | 改名的后果 |
| --- | --- | --- |
| **宿主侧标识** | 宿主认你的名字，也是**用户数据的地址**（配置键、存储单元、界面挂载点） | **丢用户数据**——已有用户的设置与数据找不到宿主了 |
| **分发侧标识** | 安装标识：包名、发布者账号下的名字 | 换安装命令；旧版本不会被自动替换 |

关键结论：

- **改分发标识不影响宿主标识**。加作用域、换发布者、改包名——动的都是安装标识；路由、
  配置命名空间、存储键、界面挂载点**一个都不许跟着改**。
- **反过来也一样**：改宿主标识是**破坏性变更**，会让已有用户的配置与数据失联。真要改，
  必须同时提供数据迁移，或者明确告知用户会丢什么。
- **无作用域时两者恰好相同**，是这种错误最常见的潜伏期——等到加作用域那天才暴露。
- 有些生态里宿主标识被写进了**分发的名字本身**（例如发布者名 + 扩展名拼成的 id），
  此时两者看似同一个，但**改的仍然是安装标识那一半**，宿主数据键不能动。

自检办法：构建一次，检查产物里注册标识的那个字符串，与清单文件的声明逐字比对；
并真实执行一次加载握手，而不只是看文件是否存在。

## 五、构建可复现（跨机器必须一致）

因为产物入库、且持续集成会在另一台机器上重建比对，构建结果**不能依赖构建机的任何
特征**。已经确认会出问题的两类：

**一、绝对路径。** 不要把绝对路径交给「会把它写进产物、或用来派生标识」的工具。典型
是 CSS 处理器的类名哈希取自传入的文件名——传绝对路径会让同一份样式在不同目录下编译
出不同的类名，产物于是永远无法在别的机器上复现。构建脚本一律传**相对于仓库的路径**。

**二、行尾。** 如果产物里内嵌了源码原文（源码映射、生成的代码、快照），工作区里残留的
另一套行尾会被原样写进去，而别的机器检出时用的是另一套，于是产生大量差异。

对策是**先声明文本属性，再做首次提交**（见 `references/version-control.md`）。如果属性
声明加晚了、工作区已经被写脏，正确的修正是**按属性重新检出**后再重建，而不是提交
「本机能过」的产物。

自检办法：把仓库复制到另一个绝对路径，装依赖、构建，产物应当逐字节相同。

## 六、发布范围

发布范围声明（清单文件里的白名单字段一类）**对从仓库源安装同样生效**。这在这类项目里
后果特别明显：

- 源码目录通常可以包含（它们是给人读的，不是运行必需的）；
- **产物必须包含**，否则装上去加载失败；
- **清单/配置文件必须包含**，否则宿主不知道要加载什么；
- 面向人的说明文档可以包含（会展示在制品库页面上）；
- 有些生态**根本不从制品库装**，而是从「仓库的某个发布」里下载固定的几个文件——
  此时「发布范围」不是清单里那个字段，而是**你往发布里附了哪些文件**。这是第 2 节
  第 6 问的一部分，专章里会写明。

发布前**必须**用该生态的「只打包不发布」手段核对一次实际文件清单，确认产物、清单、
说明都在里面。等到用户装不上再回头查，代价高得多。

## 七、依赖版本必须跟随实际运行的宿主

这类项目的依赖有一个特殊性：**宿主提供的 API 是你运行时的一部分**。版本不匹配会直接
表现为加载失败。

规则：

- **跟随版本**（构建与类型检查所对的版本）必须与**实际运行的宿主**一致。每次宿主升级
  都要重新对齐，且**逐个包确认目标版本确实存在**——同一个发布批次里，个别包可能停更，
  不能用「同号」的假设蒙过去。
- **出版方的「最新版本」标记不可信**。有些包的这个标记会停在很旧的版本，而实际已有更新
  的版本。因此不要用「查最新版本」的单值命令判断，要取完整版本列表，从末尾找。
- **最低支持版本**是另一回事：只在真不兼容时上移，且兼容性声明与面向使用者的说明文档
  必须一起改。细则见 `references/publish.md`。
- 具体查法（去哪里读运行宿主的版本、怎么确认目标版本存在、客户端模块表怎么核对）按生态而定，
  见各专章；没有专章时按第二节第六问现场查宿主文档，不要凭记忆拼命令。

## 八、本地挂载与正式分发是两条路

开发时用「指向本地目录」的方式挂载，改完刷新或重启即可生效；给别人用时走安装或分发。
两条路的差别：

| | 本地开发挂载 | 正式分发 |
| --- | --- | --- |
| 内容来源 | 你当前的工作目录 | 制品库或仓库快照 |
| 改完生效 | 刷新 / 重启宿主 | 需要装新版本 |
| 适合 | 开发与调试 | 日常使用 |

**这个差别必须写进面向使用者的文档**（见 `docs-set.md` 里关于安装来源表格的要求）：
「我改了代码为什么没生效」是这类项目最常见的问题，而答案就是这个差别。
有些生态里叠加层只能验证其中一半（如只验 host 不验界面），正式验证必须走安装路径，
见各专章；不要用开发链接代替隔离安装的验证。

## 九、没有专章时怎么办（这一节是防遗漏的关键）

专章是**生长**的，不是一次写全的。所以「遇到一个没有专章的生态」不是异常，
是**正常路径**。按这个顺序处理：

1. **通用结论照用**。第一、三、四、五、七、八节的结论对任何插件生态都成立——它们是从
   「宿主加载你的代码」推出来的，不是从某个生态观察来的。**这六节不需要专章也不会漏。**
2. **按第二节的六个问题去查**。查清了，这个生态就已经被正确处理。
3. **查到的答案沉淀成一份新专章**（按下面的模板），这样下一次不用再查一遍。
   **这是把「一次性排查」变成「能力」的唯一动作**，不做的话下次还要从头查。
4. 查不到的项，如实说明并请用户确认——**不要猜**。

### 新增专章：模板与要求

放在 `references/plugins/<生态名>.md`，用下面的骨架。**只写该生态特有的事实，
不重复通用结论**（重复会产生两处不一致，而通用结论只有一个真相源）：

```markdown
# <生态名> 插件

## 何时读本文件
- 勘察判定项目是 `<kind>` 时。
- <其他触发条件>

## 一、怎么认出这类项目
<清单文件的文件名与位置；判定用的字段>

## 二、清单里必须有什么
<逐字段：哪些是宿主要求的、哪些是分发要求的>

## 三、两个标识分别是什么
<宿主侧标识在哪个字段、分发侧标识是什么、改名的后果>

## 四、宿主加载什么文件
<入口字段；安装时下载哪些文件——这一条决定产物入不入库>

## 五、宿主版本约束
<声明字段名；跟随与下限分别写在哪>

## 六、怎么打包、怎么发放
<本地调试方式；正式分发的动作；发布范围由什么决定>

## 七、这个生态特有的坑
<只写「与通用结论不同」或「通用结论在这里有个陷阱」的地方>

## 八、事实来源（必填）
<官方链接 + 核实日期/方式 + 对照的宿主版本号；版本事实过期即按此重核>
<!-- <scope>-verified: date=<当天日期> -->（scope 与文件名对应，末尾附，格式见 AGENTS.md「外部事实保鲜」节）
```

**写作要求**：事实必须来自**核实过的来源**（该生态的官方文档，或在本机实际跑通一次）。
标注来源与核实方式，写在文件末尾的「事实来源」一节。**不要凭印象写**——专章里的内容
会被照着执行，而错的事实比没有专章更糟：没有专章时执行者会去查，有专章时他会直接信。

## 十一、建库检查清单

给插件类项目配版本管理之前确认：

- [ ] 发布路线已定：成品包路线还是源码直装路线（决定产物目录忽略还是跟踪，见各专章第四节一类判据）
- [ ] 依赖目录被忽略
- [ ] 文本属性已声明，且早于首次提交
- [ ] 产物里的注册标识 == 分发标识（见第四节）
- [ ] 发布范围包含运行时、清单、补丁与说明文档（以打包预演清单为准）
- [ ] 仓库根目录就是插件目录，不要把一个更大的目录纳入进来

## 十二、仓库本地 skills（通用协议，不止 DSH）

目标仓库里可能自带一套本地 skills（目录含 `SKILL.md`，位置以勘察为准，当前收三处：
`.agents/skills/*`、`.claude/skills/*`、包内 `skills/*`）。它们是仓库源码的一部分，不是外部模板；每个项目的名单完全不同，不写死名单。

- **先盘点再动手**：位置、目录名与 `name` 是否一致、`description` 触发语是否具体、是工作流还是知识、是否含 `scripts/` 与 `references/`、与本次任务是否相关。只读盘点，不自动删改；损坏的 `SKILL.md` 标出来，不中断。
- **两套都要留**：scaffold 与 align 必须同时保留目标仓原有 skills 与模板自带 skills；清理占位符时排除 skills 内的通用示例；禁止全局替换 skills 内的示例名；禁止把 skills 当产物删。
- **个人目录不算**：家目录与外部 checkout 的 skills 不读不写；文档里不写个人路径。
- **只收顶层三处**：嵌套子包里的 skills 当前不收，需要时手工盘点并记进汇报，不装作扫过。
- **扫描边界**：只收 `.agents/skills/*`、`.claude/skills/*`、包内 `skills/*` 三处；
  家目录、企业下发、插件市场、其他宿主布局不在 scope 内，缺了不算漏。空数组是正常结果。

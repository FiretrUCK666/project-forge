# DeepSeek Harness 插件

## 何时读本文件

- 勘察判定项目是 `dsh-plugin`（清单里声明了 `dsh.bundle`，或存在 `cordis.patch.yml`）时。
- 给一个 DSH 插件配置版本管理、远端或发布链路时。
- 插件加载失败、配置不生效、包名与补丁对不上，需要按层排查时。
- 目标仓库带有一套本地开发 workflow（例如 `.agents/skills/` 下的插件专属 skills）时，先读本文件再读通用协议（见 `references/plugin-project.md` 本地 skills 一节）。

通用结论（产物判据、两个标识、构建可复现、宿主版本跟随）见
`references/plugin-project.md`，本文件只写这个生态特有的事实。
模板仓库只是其中一种实例，不升格为规则；实例与规则冲突时以判据为准。

## 一、怎么认出这类项目

| 证据 | 说明 |
| --- | --- |
| `package.json` 里的 `dsh.bundle` 字段 | 声明「这是一个 DSH 插件，补丁文件在哪」。它是对象里的单个字符串路径（`dsh.bundle.patch`），不是数组 |
| `cordis.patch.yml` | 插件挂载声明：一个行 id 加一个包名 |
| `package.json` 里的 `dsh.client` 字段 | 声明「这个包还有浏览器半区」。有它才有界面，无它就是纯 host 行为 |
| `package.json` 里的 `dsh.profile` 字段 | 这是 profile 自身的声明（有序 bundle 列表），不是插件作者分发的东西 |

两者通常同时存在。只有配置文件、没有 JS 清单的项目也算这类。

`dsh.bundle` 之外的未知 `dsh.*` 字段只报名字，不解释语义。宿主未来加新声明时，静默忽略等于装懂；语义按 `references/plugin-project.md` 六问现场查，不要猜。

## 二、形态三态：先定是 host-only、client-only 还是双面

不要默认每个包都有浏览器面。按清单事实判定：

| 形态 | 判据 | 要验什么 |
| --- | --- | --- |
| host-only | 有 host 入口（`exports["."]` 或 `main`），无 `dsh.client` 且无 `./client` 入口 | Loader 导出形状、schema 默认、行为、disposal（见第九节）、伴生（见第六节） |
| client-only | 有 `./client` 入口与 `dsh.client` 声明，无 host 入口 | 客户端入口、ModuleLoader 包装、slot 注册与 disposal |
| 双面 | 两边都有 | 两边各验，外加两半之间的消息契约（只传可结构化数据，浏览器半区不直写持久真相） |

判据打架时（例如有 `./client` 入口却无 `dsh.client` 声明，或反过来）先停下对齐，不猜哪边是对的。目录布局不固定：`src/index.ts`、`src/config.ts`、`src/runtime.ts`、`src/invariant.ts` 只是常见分工，大包可用能力命名模块替代；判据是职责归属是否清晰，不是目录名是否照抄模板。

## 三、两个标识分别是什么

| 标识 | 在哪 | 影响什么 |
| --- | --- | --- |
| **插件 id** | `cordis.patch.yml` 那一行的 `id`（稳定小写短横线风格，发布后不改） | 路由前缀、设置命名空间、存储单元、界面插槽标识、浏览器本地存储键 |
| **包名** | `package.json` 的 `name` | 安装标识；浏览器产物的注册标识也用它 |

包名可带作用域也可不带，不推导前缀。选中之后六处逐字一致：清单 `name`、补丁行 `name`、invariant 注册名、exports、测试、文档。模板占位符残留在其中任何一处即未完成；但 skills 目录内的通用示例不算身份归属，清理占位符时排除它们。

**插件 id 派生的一切是数据地址**：加作用域、换发布者、改包名只动安装标识，这些一个都不许跟着改。改宿主标识是破坏性变更，会让已有用户的配置与数据失联，真要改必须同时给迁移或明确告知会丢什么。

**发现载体行**：补丁里保留一行 `name` 等于包名自身的行。缺了这一行，包明明装上了，浏览器半区或 bundle 激活也不会被发现。勘察只做文本包含判断，供人复核，不做硬结论。

## 四、产物与分发：按消费者判，不写死入库与否

“git 里有”与“包里有”是两套集合，不要混为一谈：

| 问题 | 判据 |
| --- | --- |
| 消费者拿到什么 | 成品包（制品库、Release 附件、本地 tgz）则消费现成构建，不跑安装时构建；源码直装（Git 地址且无构建步骤）则才要求跟踪成品或另写源码构建约定 |
| git 里放什么 | 防历史膨胀：可再生成物默认忽略；刻意跟踪成品时必须配逐字节一致检查 |
| 包里放什么 | `files` 白名单说了算：含了则 ignore 拦不住，缺了则 git 有也白搭；`files` 写了但文件不存在不告警，必须用打包预演发现 |

做法：

- 成品路线：构建产物目录（如 `lib/`）可忽略，但必须进 `files`；无安装时构建钩子；发前用只打包不发布的手段核对完整文件清单，要求 `main`、`types`、`exports`、`files` 承诺的每个运行时与声明文件都在包里，`cordis.patch.yml` 在声明 bundle 时也在包里；发后到隔离环境装发布位验证，不用开发链接代替。
- 源码路线：确认为源码直装时，成品必须跟踪并与源码同一次提交；CI 重建比对逐字节一致。
- 时机：先抬号再构建，顺序颠倒会产出旧号包；构建号进包前确认清单版本号已更新。

## 五、清单矩阵：从项目自身读，不编造

| 项 | 从哪读 | 错了什么症状 |
| --- | --- | --- |
| 包名与版本 | 清单 `name`、`version` | 包名撞名发不出去；版本与标签对不上导致自动化对不上 |
| 入口 | `exports`（`.` 必有，按形态有 `./client`、`./invariant`）、`main`、`types` | 入口指向的文件不存在即加载失败 |
| 发布范围 | `files` 白名单 | 仓库有但包里无，或包里混入凭据与缓存 |
| 宿主运行时 | `peerDependencies`（消费方提供的 Cordis 与宿主 API） | 宿主运行时被打进包或缺失导致加载失败 |
| 开发源 | `devDependencies`（构建与测试时可达的注册表来源） | 类型检查与测试在换机器后失准 |
| 自带运行时 | `dependencies`（插件自己拥有并提供的库） | 该自带的没带导致消费者缺依赖 |
| 可发布开关 | `private` | 未就绪公开导致误发；该发的没发导致消费者拿不到 |
| 运行环境下限 | `engines` 一类声明 | 声明与实际不一致导致装上跑不起来 |

宿主提供的运行时不进 `dependencies` 或捆绑依赖，只做 peer；本地 `link:`、`file:` 依赖与出仓引用一律拒绝；每个新依赖必须有生产导入对应。

## 六、Bundle 与伴生

`package.json` 用 `dsh.bundle.patch` 指向已发文件；`cordis.patch.yml` 只做行插入与覆盖，不改宿主源码、编译配置、目录与启动代码。

- `insert` 加行：稳定行 id 加包名原文；伴生行按包名派生子路径，不脑补前缀。
- id 寻址覆盖：替换整单 `config`，保留字段必须重述，不指望深合并。
- `!!js` 只许在插件 `config` 与 `disabled` 下；Loader 元数据（`id`、`name`、`disabled`）保持静态。
- 空补丁非法：故意空用空列表写法，不留空文件或纯注释文件。
- 凭据不出补丁，只放引用名或环境变量名。

伴生 `./invariant` 是语义件，不是工具链标记：有包独占的事件或数据关系才写非空检查，并配正反两路测试；无则保留精简解释，不编造检查。普通 profile 不提供 `invariants` 服务时不插伴生行，缺服务导致 pending 是预期行为，不是缺陷。

## 七、Bundle 层语义（最容易写错的一节，先读宿主当前实现再动手）

补丁是按 `id` 寻址的修改单，不是完整树。生效树按层叠加，后层赢：各 bundle 按 profile 清单列表序加 profile 自身补丁加家目录级补丁加单次启动叠加加预设与遥测开关。根组合每次启动重建，真实组合完全由补丁层组成。

三条硬约束：`config` 整单替换；`name` 失配只告警后跳过；补丁语法里**没有 `replace` / `ignore` 这类动词**——覆盖就是按 id 直接写键，写进去的键整值替换，没写的键保持原样。

**别把第三条读成「没有替换语义」**：整值替换是真的（见第一条），第三条说的是**语法**——键直接写，不需要（也没有）动词来声明意图。

覆盖已有行之前，先看目标组合当前行，把该行需要的键完整重述一遍。热更新边界按宿主当前实现确认：`live` 只监听 profile 自身补丁与家目录级补丁这两份文件，**bundle 级补丁与 `--patch` 覆盖层不在监听范围内**，改它们要重启。版本号一律现场取，不把插件的依赖范围当成宿主版本。

## 八、本地开发 workflow 与补丁目录（可选，有则按契约，无则不强求）

- 仓库本地 workflow（如 `.agents/skills/` 下的插件专属 skills）是仓库源码的一部分：生成时保留、按事实对齐时只审计（只读盘点，不自动删改），清理占位符时排除其中的通用示例。盘点方法见通用协议，不在这里复述名单。
- `patches/` 缺席是正常态。有则分两类：依赖补丁（精确到版本、声明理由、上游修复即删）与宿主补丁（自包含 diff、有 pin 快照、可再生、可幂等应用、不进包）。无补丁计划时不建目录、不留空配置与补丁专用脚本。

## 九、构建、测试与发布

构建、测试、打包按仓库声明的命令跑，不编造第二套：

- 静态检查：类型感知，警告即失败；只查源码与测试，不查产物与依赖。
- 测试：Loader 真实解包形状、schema 默认与拒绝、observable 行为、注册与 fiber disposal、伴生正反（非空才要反例）、产品可见行为的真实组装测试、稳定可见输出的 keyless 快照。覆盖率数字与“跑过即过”不算行为证据。
- 打包：构建后逐个导入公开运行时入口；用完整文件清单核对 `main`、`types`、`exports`、`files`；到隔离 profile 装发布位验证激活与有效行，不只看包管理器退出码。
- 发布：按仓库政策走（分支驱动附件发布或标签驱动 Release 皆可，以仓库文档为准）；打标签、建 Release、上传附件、改远端、发制品库均为用户授权动作，不默做；同版重推是否刷新以仓库政策为准，不推断。

## 十、这个生态特有的坑

- 包名与插件 id 不可互相推导；加作用域只动包名。
- 补丁 `name` 写错只告警不生效：行没起作用时先对 `id` 与 `name`。
- 模块 `inject` 必须是数组；未声明的服务不防御性直读。
- `config` 缺字段走 schema 默认：覆盖行必须重述全量。
- 叠加层只能验 host 半区：浏览器面必须走 profile 安装验证。
- 构建传仓库相对路径；产物内嵌源码时先声明文本属性再重检出后重建。
- 模板占位符残留只查身份归属，不查 skills 通用示例。

## 事实来源

本文件的通用结论来自 Cordis 官方教程与宿主实现的逐点核对：函数插件命名导出、Service 三形态、`inject` 就绪语义、`ctx.effect` 可逆回收、`cordis.yml` 基座与 patch 层叠加。构建与包管理事实来自对应工具的官方文档：`files` 白名单语义、构建器 ESM 与声明输出、包管理器 workspace 与构建授权。

**第七节至第九节的核对方法与证据**（版本号一律现场取，不把插件的依赖范围当成宿主版本）：

- 层叠顺序与组合入口：宿主安装目录 `README.zh.md` 的 Profile 一节列出层序，`node_modules/@deepseek-ai/dsh-app-boot/lib/index.js` 里 `composeEntries` 的注释说明「profile 的 patch 层在所有 bundle 层之后」，层组装函数按 `dsh.profile.bundles` 顺序逐层取各 bundle 的补丁。
- 三条硬约束：同一文件的补丁应用函数里，按 id 命中后对补丁携带的每个键做**顶层整值赋值**（所以 `config` 整单替换、没写的键保持原样），`name` 失配走告警后 `skipping`，顶层特殊键只有 `id` / `insert` / `name` 三个。
- 热更新边界：`lib/profile-boot-*.js` 里 `patchReload === "live"` 成立时才装载 HMR，随后对 profile 补丁路径与家目录补丁路径各调用一次监听函数——因此监听范围就是这两份文件，bundle 级补丁与 `--patch` 覆盖层不在其中。

上面一行是机器可读的核对标记，格式固定不要改。两个键的含义与纪律：

- **`host=` 是「上次核对时本机实际运行的那套宿主版本」**——不是兼容下界，也不是某个目标项目锁定的版本。宿主升级后把它改成本机实际版本、`date=` 改成当天日期，然后把第七节至第九节逐条对照新版宿主重核一遍。**两个键必须同批改**：只改版本号不改日期，机制会喊「一致」，而日期还标着上一次的核对日——那是最难发现的一种假绿。版本号一律现场取（问宿主自己要，佐以它自己的安装元数据），不把插件的依赖范围当成宿主版本。
- **它能被自动核对**：`preflight` 会拿它对本机实际运行的宿主比对——能取到就比，取不到就报「未核对」并说明原因，**只提示不失败**（换台机器校验、宿主回滚、同机多份宿主都会造出「不同」，脚本层判不了罪）。取值途径按宿主各自登记，没登记就是「未核对」。**「没比」与「比过且一致」是两回事**，看到「未核对」不要读成通过。
- 另有一条**不同性质**的提示：某个目标项目在清单里声明了宿主兼容范围时，`compose-agents.mjs` 会把该范围与本标记对照并提示。那是**跨机兼容性提示**，不是本标记的核对结果，两者不要混读。

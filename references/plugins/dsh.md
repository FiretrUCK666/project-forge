# DeepSeek Harness

## 何时读本文件

- 勘察判定项目是 `dsh-plugin`（清单里声明了 `dsh.bundle`，或存在 `cordis.patch.yml`）时。
- 勘察判定项目是 `skill`（被这个宿主当能力目录加载）时——它是插件类之外、被同一套宿主加载的另一形态，契约见第九节。
- 给一个被这个宿主加载的扩展配置版本管理、远端或发布链路时。
- 加载失败、配置不生效、包名与补丁对不上，需要按层排查时。
- 目标仓库带有一套本地开发 workflow（例如 `.agents/skills/` 下的插件专属 skills）时，先读本文件再读通用协议（见 `references/plugin-project.md` 的「仓库本地 skills」一节）。

通用结论（产物判据、两个标识、构建可复现、宿主版本跟随）见
`references/plugin-project.md`，能力目录形态的通用结论见 `references/skill-project.md`，
本文件只写这个宿主特有的事实。
模板仓库只是其中一种实例，不升格为规则；实例与规则冲突时以判据为准。

## 一、怎么认出这类项目

| 证据 | 说明 |
| --- | --- |
| 清单里的 `dsh.bundle` 字段 | 声明「这是一个 DSH 插件，补丁文件在哪」。`dsh.bundle.patch` 接一个文件路径或一组有序文件路径，按列出的顺序施加为同一层；每个文件里的相对插件路径按该文件所在目录解析。声明形状以宿主 `dsh-app-boot` 包里 `bundlePatchFiles` 的校验为准，不是「路径或路径列表」即抛错 |
| `cordis.patch.yml` | 插件挂载声明：一个行 id 加一个包名 |
| 清单里的 `dsh.client` 字段 | 声明「这个包还有浏览器半区」。有它才有界面，无它就是纯 host 行为。它是对象不是开关：`platform` 必填字符串，`inject` 与 `external` 是可选字符串数组，`immediately` 是可选布尔；字段存在而形状不对，扫到即抛。逐字段校验在宿主 `dsh-client-modules` 包的 `parseDshClient` |
| 清单里的 `dsh.profile` 字段 | 这是 profile 自身的声明（有序 bundle 列表），不是插件作者分发的东西 |
| 清单里的 `dsh.manifestVersion` | 声明的**清单格式版本**（本机当前声明值为 `1`）。它与包版本号、与会话格式版本是三件不同的东西，同名不同物，别互相替换 |
| 清单里的 `engines.dsh` | 声明宿主兼容范围（SemVer 范围，可填精确的预发布版本），与 `engines.node` / `engines.npm` 并列。**这一项只作声明**：安装器与加载器都不强制执行它，声明一个不兼容的范围照样装得进、加载得起来。真正拦人的闸门在第五节 |
| 清单里的 `package.json.icon` | 展示图标（图片 data URL）。0.2.x 起**子路径插件不再单独读自己的清单**，展示文字与图标必须走对应的子路径导出，否则读不到 |
| 宿主内部字段（如会话格式迁移声明） | 本机多个包在用、由启动器读取；它不属于公开作者字段，公共类型也不暴露它。插件作者不要写它，它出现时也不用管 |

上面的证据通常同时存在。只有配置文件、没有 JS 清单的项目也算这类。

**公开的作者字段就是那几个**（格式版本、bundle、profile、client），另有宿主内部的字段不由插件作者控制。既不在这两类里、又以 `dsh.` 开头的键**只报名字，不解释语义**——宿主未来加新声明时静默忽略等于装懂；语义按 `references/plugin-project.md` 的判定协议现场查，不要猜。

## 二、形态三态：先定是 host-only、client-only 还是双面

不要默认每个包都有浏览器面。按清单事实判定：

| 形态 | 判据 | 要验什么 |
| --- | --- | --- |
| host-only | 有 host 入口（`exports["."]` 或 `main`），无 `dsh.client` 且无 `./client` 入口 | Loader 导出形状、schema 默认、行为、disposal（见第十一节） |
| client-only | 有 `./client` 入口与 `dsh.client` 声明，无 host 入口 | 客户端入口、ModuleLoader 包装、slot 注册与 disposal |
| 双面 | 两边都有 | 两边各验，外加两半之间的消息契约（只传可结构化数据，浏览器半区不直写持久真相） |

判据打架时（例如有 `./client` 入口却无 `dsh.client` 声明，或反过来）先停下对齐，不猜哪边是对的。目录布局不固定：`src/index.ts`、`src/config.ts`、`src/runtime.ts` 只是常见分工，大包可用能力命名模块替代；判据是职责归属是否清晰，不是目录名是否照抄模板。

## 三、两个标识分别是什么

| 标识 | 在哪 | 影响什么 |
| --- | --- | --- |
| **插件 id** | `cordis.patch.yml` 那一行的 `id`（稳定小写短横线风格，发布后不改） | 补丁行寻址：后续层按 `id` 命中并覆盖。其余命名空间由插件按 id 自行派生，属插件自己的约定，宿主不强制统一命名 |
| **包名** | 清单的 `name` | 安装标识；浏览器 roster 的键也用它 |

包名可带作用域也可不带，不推导前缀。选中之后这几处要逐字一致：清单 `name`、补丁行 `name`、exports、测试、文档。模板占位符残留在其中任何一处即未完成；但 skills 目录内的通用示例不算身份归属，清理占位符时排除它们。

**插件 id 派生的一切是数据地址**：加作用域、换发布者、改包名只动安装标识，这些一个都不许跟着改。改宿主标识是破坏性变更，会让已有用户的配置与数据失联，真要改必须同时给迁移或明确告知会丢什么。

**发现载体行**：浏览器 roster 由 node 半区遍历**已挂载的行**建出——每行的 `name` 要能解析到一个声明了 `dsh.client` 的包。行的 `id` 不参与发现，roster 的键是**包名**；`name` 写子路径也行，只要能解析回本包。缺了这一行，包明明装上了，浏览器半区或 bundle 激活也不会被发现。勘察只做文本包含判断，供人复核，不做硬结论。

## 四、产物与分发：按消费者判，不写死入库与否

「git 里有」与「包里」是两套集合，不要混为一谈：

| 问题 | 判据 |
| --- | --- |
| 消费者拿到什么 | 成品包（制品库、Release 附件、本地 tgz）则消费现成构建，不跑安装时构建；源码直装（Git 地址且无构建步骤）则才要求跟踪成品或另写源码构建约定 |
| git 里放什么 | 防历史膨胀：可再生成物默认忽略；刻意跟踪成品时必须配逐字节一致检查 |
| 包里放什么 | `files` 白名单说了算：含了则 ignore 拦不住，缺了则 git 有也白搭；`files` 写了但文件不存在不告警，必须用打包预演发现 |

做法：

- 成品路线：构建产物目录（如 `lib/`）可忽略，但必须进 `files`；无安装时构建钩子；发前用只打包不发布的手段核对完整文件清单，要求 `main`、`types`、`exports`、`files` 承诺的每个运行时与声明文件都在包里，补丁文件在声明 bundle 时也在包里；发后到隔离环境装发布位验证，不用开发链接代替。
- 源码路线：确认为源码直装时，成品必须跟踪并与源码同一次提交；CI 重建比对逐字节一致。
- Git 直装只拿到源码，不跑 `build`。这一路的正确做法是作者发一个自包含的 `prepare` 脚本（不假设同级 monorepo 等仅开发期上下文），用户侧放行构建——放行怎么批准见第八节。把 git 依赖钉到具体提交：放行等于允许该包在装的时候于本机执行代码。
- 时机：先抬号再构建，顺序颠倒会产出旧号包；构建号进包前确认清单版本号已更新。

## 五、清单矩阵：从项目自身读，不编造

| 项 | 从哪读 | 错了什么症状 |
| --- | --- | --- |
| 包名与版本 | 清单 `name`、`version` | 包名撞名发不出去；版本与标签对不上导致自动化对不上 |
| 入口 | `exports`（`.` 必有，按形态有 `./client`）、`main`、`types` | 入口指向的文件不存在即加载失败 |
| 发布范围 | `files` 白名单 | 仓库有但包里无，或包里混入凭据与缓存 |
| 宿主运行时 | `peerDependencies`（消费方提供的 Cordis 与宿主 API）；宿主侧 DSH 包另受版本闸门约束，见下 | 宿主运行时被打进包或缺失导致加载失败 |
| 开发源 | `devDependencies`（构建与测试时可达的注册表来源） | 类型检查与测试在换机器后失准 |
| 自带运行时 | `dependencies`（插件自己拥有并提供的库） | 该自带的没带导致消费者缺依赖 |
| 可发布开关 | `private` | 未就绪公开导致误发；该发的没发导致消费者拿不到 |
| 运行环境下限 | `engines` 一类声明 | 声明与实际不一致导致装上跑不起来 |
| 清单格式版本 | `dsh.manifestVersion` | 与包版本、与会话格式版本混用；写错等于没写 |
| 宿主兼容范围声明 | `engines.dsh`（范围符号原样保留，可填精确预发布版本） | **它不拦任何东西**：装与加载都不执行这个声明。误以为声明了就有闸门，兼容性就会在运行期才炸 |

宿主提供的运行时不进 `dependencies` 或捆绑依赖，只做 peer；本地 `link:`、`file:` 依赖与出仓引用一律拒绝；每个新依赖必须有生产导入对应。

**宿主版本闸门**与上面那个 `engines.dsh` 声明是两回事：闸门是宿主真的执行的检查，只校验清单 peer 里落在宿主命名空间下的那批包（本机安装的 `dsh` 主包，以及 `@deepseek-ai/dsh-` 前缀的那批）。范围不含本机**实际运行**的版本时，这个 bundle 加载时会被跳过或安装被拒，用户侧要显式豁免才能继续。四个要点：

- 范围按语义版本比较，**预发布参与比较**——写一个只覆盖稳定版的上界会把自己挡在门外；
- 指向当前工作区（`workspace:` 开头的那几个 range 写法）解析为「本机运行时版本」，本地开发因此天然自洽，这也是**随包各包把这类 peer 钉死到精确版本**、并另列一份开发期依赖的原因；
- 豁免写在 profile 目录里一份独立文件 `compatibility.json`（常量 `PROFILE_COMPATIBILITY_FILENAME`），与清单、profile 补丁并列，把精确的 `包名@版本` 映射到精确的宿主版本列表；
- 豁免**不继承**：插件升级与宿主升级都不带着它走，两边都要重新授权。

判据在宿主 `dsh-app-boot` 包的 `evaluatePluginCompatibility`。宿主也提供命令与工具来装包、启停组合包、增删豁免——**先查宿主有没有命令，别手搓**。

## 六、Bundle

`package.json` 用 `dsh.bundle.patch` 指向一个或一组补丁文件，顺序即施加顺序；`cordis.patch.yml` 只做行插入与覆盖，不改宿主源码、编译配置、目录与启动代码。

- `insert` 加行：稳定行 id 加包名原文。
- id 寻址覆盖：替换整单 `config`，保留字段必须重述，不指望深合并。
- `!!js` 出现在 `config` 树内任意深度、或 `disabled` 上，由 Loader 在该行注入就绪后求值（`config` 走整棵树的递归求值，`disabled` 单独判定）；`id` / `name` / `insert` 是静态元数据，不接受 `!!js`。
- 空补丁非法：故意空用空列表写法，不留空文件或纯注释文件。
- 凭据不出补丁，只放引用名或环境变量名。

随安装提供的一组实验性 bundle 默认关闭、由用户开启、永不可卸载，也**不被任何随配模板选中**——看到模板列表里没有它们是正常的，不是模板缺项。

## 七、Bundle 层语义

这一节最容易写错。动手前先读宿主当前实现，不要凭印象。

补丁是按 `id` 寻址的修改单，不是完整树。生效树按层叠加，后层赢：`dsh.profile.bundles` 里各 bundle 的补丁（按清单顺序）→ profile 自身的补丁 → 家目录级补丁 → `--patch` 指定的覆盖层 → 遥测开关。根组合每次启动重建，真实组合完全由补丁层组成。

三条硬约束：`config` 整单替换；`name` 失配只告警后跳过；补丁语法里**没有 `replace` / `ignore` 这类动词**——覆盖就是按 id 直接写键，写进去的键整值替换，没写的键保持原样。

**别把第三条读成「没有替换语义」**：整值替换是真的（见第一条），第三条说的是**语法**——键直接写，不需要（也没有）动词来声明意图。

覆盖已有行之前，先看目标组合当前行，把该行需要的键完整重述一遍。

**免重启体检**：三条命令不启动宿主就能打出组合后的结果，是验证补丁层的正确手段——比反复重启快，也比重启准。

| 命令 | 打什么 |
| --- | --- |
| `--dump-default-config` | 只有 bundle 层。**不接受 `--patch`** |
| `--dump-config` | 再加上 profile 家目录层与 `--patch` 覆盖层 |
| `--dump-config-schema` | 打 schema，不是取值 |

三条互斥，一次只能给一条。把 dump 结果与「你以为的层序」逐层对照，层序或字段错在哪一层一眼可见。

**Node 侧与浏览器侧是两回事。** `dsh-hmr` 负责 Node 半区的热重载，监听 profile 目录的 `package.json`、profile 自身补丁、家目录级补丁这三处——**bundle 级补丁与 `--patch` 覆盖层不在监听范围内**，单独改它们不触发重载。`dsh-client-hmr` 是另一回事：它是独立的浏览器产物重载包（事件走一条 SSE 通道，两类帧，固定轮询间隔）。插件作者不需要为它额外做任何事，**但「改了没生效」的排查必须知道它存在**：浏览器半区没刷新时，先确认是不是它在等下一轮。只有 Web 形态走这条路。

## 八、安装、启停与豁免

宿主自带包管理器入口：`dsh plugin --profile <profile> <pnpm 参数>`。除 profile 之外，其余参数**原样转发**给包管理器——增、删、查因、更新等子命令都照常。宿主自己另出三条与包操作无关的命令，只管版本豁免：

| 命令 | 作用 |
| --- | --- |
| `version-exemptions` | 列出 profile 现有的授权 |
| `allow-version <包名@版本> --dsh-version <精确版本> --accept-risk` | 授权一个精确组合 |
| `revoke-version <包名@版本> --dsh-version <精确版本>` | 撤销一个授权 |

授权只认精确的「包名@版本」与精确的宿主版本，**不接受范围、标签与前缀**。四条规则：

| 规则 | 说明 |
| --- | --- |
| 只放行，不改动 | 写豁免不改变依赖、bundle 选择与补丁层，它只是让闸门放行 |
| 要显式接受风险 | 授权必须带显式确认，不是默默生效 |
| **不继承** | 插件升级与宿主升级都不带着它走，两端都要重新授权（第五节闸门那段的要点之一） |
| 损坏不致命，但挡住了改授权 | 文件坏了只警告不致命；**必须先修好**才能改授权 |

**安装规格**接受注册表包名、git 地址、tarball 与**绝对路径**四种形态；相对路径不接受，要指本地目录就先自己解析成绝对路径。

**注册表回退**：配置的 `registry` 不可达、或它上面没有该包副本时，依次去问 `fallbackRegistries` 里的源。集合外的私有源**只问自己**——私有源不会掉到公共源，这条防止凭据与包内容意外外泄，不要绕。

**构建批准**：包管理器拦下的依赖构建脚本，按**包名**记进 profile 工作区配置的 `allowBuilds`。只能批准当前待批的那个名字，已有的拒绝与通配规则不会被新条目覆盖。批准等于允许该包在装的时候于本机执行代码。

**没有官方市场。** 官方发现渠道是 GitHub 上 `dsh-plugin` 这个 topic；生态里流通的第三方市场只是普通插件包，看它等于看第三方账号，权威性由那个账号自己承担。

**什么改动要重启**（其余编辑走热更新，边界见第七节）：

| 改动 | 需要重启吗 |
| --- | --- |
| `dsh.profile.bundles` 列表的成员变更（加、删、调顺序） | **要** |
| 已安装包的版本替换 | **要** |
| 编辑补丁文件 | 不要，走热更新 |

插件管理器里的直接操作不等文件事件——它自己就是那个变更源，不要再等一次监听。

**profile 模板**：内置的一组模板首次使用自动初始化。`--from-default-profile <名字>` 能用一个没被用过的、非内置的名字创建；有一个名字保留给桌面应用，命令行会拒绝启动它，也拒绝为它做配置转储。宿主还会把自己不再携带的 bundle 从 profile 的 bundle 列表里移除——这是对账结果，不是误删。

**组合清单调和**：包操作成功后，profile 的 bundle 列表按已安装状态对账——依赖被移除才移除对应条目；新装的 bundle **追加到列表末尾**（追加会改变配置优先级，所以位置有后果，不只是顺序问题）；显式停用的选择被保留。

## 九、作为能力目录被加载时

宿主扫磁盘上的能力目录（入口文件加同级目录），解析元数据，把它们编成模型可见的目录。这套契约与插件那几节**互不相关**：没有清单字段参与，能力目录要么放磁盘由宿主扫，要么由插件代码注册——**公开清单字段里没有 `dsh.skill` 这一项**。

**发现**。扫描根按 rank 排序，**低 rank 胜出**：

| 顺序 | 根 |
| --- | --- |
| 1 | `<项目根>/.dsh/skills` |
| 2 | `<项目根>/.agents/skills` |
| 3 | 自定义目录 |
| 4 | `<宿主家目录>/skills` |
| 5 | `<agents 家目录>/skills` |
| 6 | 随包提供的根 |

项目根 = 最近一个含 `.git` 的祖先目录，没有就用当前目录。家目录级根会跳过它自己的 `.system` 子目录。**具体 rank 值随宿主版本变**，要写自定义根时按 `roots()` 现场读。

**形状**只有两种：`<根>/<名字>/SKILL.md`（目录形态）或平铺的 `<根>/<名字>.md`。**深度只有一层**——嵌在子目录里的同名入口文件**刻意不被发现**，这不是 bug。入口文件名**大小写敏感**。

**元数据**：必填 `name`（形状 `^[a-z0-9]+(?:-[a-z0-9]+)*$`，纯小写短横线）与非空 `description`；可选 `whenToUse`、`metadata`、`disable-model-invocation`、`user-invocable`。调用类布尔值接受 YAML 布尔，也接受不区分大小写的 `true/false`、`yes/no`、`on/off`、`1/0`。

**宿主不校验 `name` 与目录名是否一致**。目录名只是定位用的，`name` 才是路由与覆盖的依据。勘察脚本会报两者不一致，那是**项目自己的约定问题**，不是宿主规则——照实标注，别冒充宿主要求。

**失败对模型不可见。** 模型拿不到逐个目录的诊断，**分不清「不存在」与「不合法」**：三类情形会让整个目录随警告丢弃——缺必填字段、名字形状非法、调用或可见性键非法（驼峰旧写法 `modelInvocable` / `userInvocable` / `disableModelInvocation` 被直接拒绝）。调用布尔值拼错或不是布尔值，同样丢整个目录，**不会静默放行某一个接口**。

**模型侧两套同时在**：追加到会话的目录消息，加一个名为 `skill` 的工具（单个必填参数 `name`）。用户手打 `/名字` 走同一渲染路径——**这是唯一能让「禁止模型调用」的目录被加载的入口**。

**摘要与正文是两条不同的生命周期**。描述按空白归一化之后的长度截断（本机当前上限 500，可配，最小 3），超出的部分等于不存在；**指令正文没有长度上限**。摘要里哪些字段真正参与路由由宿主自己定义（`whenToUse`、`metadata` 被解析，但**不进模型目录**，别指望它们影响路由）。

**重载**：深度 1，只认三类事件——根下目录增删、根下 `*.md` 增删改、`<名字>/SKILL.md` 增删改。改 `references/` 之类不触发目录刷新，但**每次加载都重读正文**，所以照样生效。

**相对资源只是提示**：宿主只给一句「这个能力目录的基准目录是 …」，不枚举、不附带任何文件，模型要自己再去读。`references` / `templates` / `scripts` / `assets` 这些名字**宿主一个都不认**——它们只是普通子目录，不因名字获得任何待遇。

**重名裁决**：更近的层直接遮蔽更远的层；同一层内按 rank、提供方注册顺序、提供方本地顺序依次裁决，输掉的记警告并隐藏。运行期注册的同名目录先到先得。

## 十、本地开发 workflow 与补丁目录（可选）

- 仓库本地 workflow（如 `.agents/skills/` 下的插件专属 skills）是仓库源码的一部分：生成时保留、按事实对齐时只审计（只读盘点，不自动删改），清理占位符时排除其中的通用示例。盘点方法见通用协议，不在这里复述名单。
- `patches/` 缺席是正常态。有则分两类：依赖补丁（精确到版本、声明理由、上游修复即删）与宿主补丁（自包含 diff、有 pin 快照、可再生、可幂等应用、不进包）。无补丁计划时不建目录、不留空配置与补丁专用脚本。

## 十一、构建、测试与发布

构建、测试、打包按仓库声明的命令跑，不编造第二套：

- 静态检查：类型感知，警告即失败；只查源码与测试，不查产物与依赖。
- 测试：Loader 真实解包形状、schema 默认与拒绝、observable 行为、注册与 fiber disposal、产品可见行为的真实组装测试、稳定可见输出的 keyless 快照。覆盖率数字与「跑过即过」不算行为证据。
- 打包：构建后逐个导入公开运行时入口；用完整文件清单核对 `main`、`types`、`exports`、`files`；到隔离 profile 装发布位验证激活与有效行，不只看包管理器退出码。
- 发布：按仓库政策走（分支驱动附件发布或标签驱动 Release 皆可，以仓库文档为准）；打标签、建 Release、上传附件、改远端、发制品库均为用户授权动作，不默做；同版重推是否刷新以仓库政策为准，不推断。

## 十二、这个生态特有的坑

- **包名与插件 id 不可互相推导**；加作用域只动包名。
- **补丁 `name` 写错只告警不生效**：行看着在、就是不做事。先对 `id` 与 `name`。
- **`config` 缺字段走 schema 默认**：覆盖行必须把该行需要的键重述全量，否则你以为设了的值是默认来的。
- **叠加层只能验 host 半区**：浏览器面必须走 profile 安装验证，开发叠加层验不出来。
- **构建传仓库相对路径**；产物内嵌源码时先声明文本属性再重检出后重建。
- **行 id 变了**：composer 的统计条目从 `stats` 拆成 `activity` 与 `usage` 两个扩展条目。替换过 `stats` 的插件必须改注册 id，否则注册不上。
- **改了 bundle 列表或换了包版本却没生效**：这两类都要重启，不等热更新（边界见第八节那张表）。
- **拿注册表的 `latest` 当宿主版本**：那个标签可能落后于本机正在跑的预发布版。读宿主版本一律以 `dsh --version` 为准。
- **`whenToUse` 与 `metadata` 不进模型目录**：它们被解析，但不影响模型怎么选你。别把路由押在上面。
- **能力目录的驼峰调用键**：写法不对整个目录被丢弃，而模型分不清「不存在」与「不合法」，症状就是「好像没装上」。
- **模块 `inject` 写数组**（服务名列表）；要带 intercept 语义时写映射对象（服务名 → intercept 配置），类继承写法亦可。未声明的服务不防御性直读。
- **模板占位符残留**只查身份归属，不查 skills 通用示例。

<!-- dsh-verified: host=0.2.1-alpha.1 date=2026-10-04 -->

上面一行是机器可读的核对标记，格式固定不要改。两个键的含义与纪律：

- **`host=` 是「上次核对时本机实际运行的那套宿主版本」**——不是兼容下界，也不是某个目标项目锁定的版本。宿主升级后把它改成本机实际版本、`date=` 改成当天日期，然后**重核第一节至第九节**。**两个键必须同批改**：只改版本号不改日期，机制会喊「一致」，而日期还标着上一次的核对日——那是最难发现的一种假绿。
- **它能被自动核对**：`preflight` 会拿它对本机实际运行的宿主比对——能取到就比，取不到就报「未核对」并说明原因，**只提示不失败**（换台机器校验、宿主回滚、同机多份宿主都会造出「不同」，脚本层判不了罪）。取值途径按宿主各自登记，没登记就是「未核对」。**「没比」与「比过且一致」是两回事**，看到「未核对」不要读成通过。
- 另有一条**不同性质**的提示：某个目标项目在清单里声明了宿主兼容范围时，`compose-agents.mjs` 会把该范围与本标记对照并提示。那是**跨机兼容性提示**，不是本标记的核对结果，两者不要混读。

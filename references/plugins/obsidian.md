# Obsidian 插件

## 何时读本文件

- 勘察判定项目是 `obsidian-plugin`（根目录有 `manifest.json`，且含 `minAppVersion`）时。
- 给一个 Obsidian 插件配置版本管理、远端或发布链路时。

通用结论见 `references/plugin-project.md`，本文件只写这个生态特有的事实。

## 一、怎么认出这类项目

根目录的 **`manifest.json`**。判定字段是 `minAppVersion`（只有 Obsidian 插件用它）。
次要证据：依赖里有 `obsidian` 这个包、或存在 `versions.json`。

注意与 VS Code 的区别：VS Code 用 `package.json`，Obsidian 用独立的 `manifest.json`
——**同一个「插件项目」在不同生态里清单文件完全不同**，这正是本生态需要专章的原因。

普通网页应用的同名 `manifest.json`（不含 `minAppVersion`）不是本类，勘察已按此守卫，
不要凭文件名硬认。

## 二、清单里必须有什么

`manifest.json` 的字段（官方 `PluginManifest` 接口）。类型与必填按官方文档，
不要凭记忆补：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 是 | 插件标识。只许小写字母与连字符；不能含 `obsidian`；不能以 `plugin` 结尾；全生态唯一。本地开发时与插件文件夹同名，否则部分设置回调不会触发 |
| `name` | string | 是 | 显示名。短而描述性，优先英文与 Basic Latin；标点只许连字符/加号/括号；禁 emoji；禁含 `Obsidian` 及其变体；禁单独使用核心功能名；插件名禁含 `Plugin` 一词；全生态唯一 |
| `version` | string | 是 | 只支持 `x.y.z` 三段格式，需符合语义化版本；预发布后缀不进社区稳定通道 |
| `minAppVersion` | string | 是 | 能运行本插件的最低宿主版本；不知道填什么就填最新稳定版号 |
| `description` | string | 是 | 以动作语句开头，不以 `This is a plugin` 开头；不超 250 字符；以句号结尾；禁 emoji；遵官方 style guide |
| `author` | string | 是 | 作者名 |
| `isDesktopOnly` | boolean | 是 | 是否仅桌面端。用了 Node/Electron 能力必须填 `true`；不用也要显式声明 `false`，不要省略 |
| `authorUrl` | string | 否 | 作者主页 |
| `fundingUrl` | string 或对象 | 否 | 打赏链接。单个用字符串，多个用对象（标签为键、地址为值）；不接受捐赠就删掉该字段，不要留空 |

`id` 的全局唯一性由作者自己保证：撞名、违规在提交审核时被拒，而不是自动加后缀。
老插件里带 `obsidian-` 前缀的是规则收紧前的产物，新插件不许再带。

## 三、两个标识分别是什么

| 标识 | 是什么 | 约束 |
| --- | --- | --- |
| **插件 id** | `manifest.json` 的 `id` | 全生态唯一、只许小写字母与连字符、不能含 `obsidian`、不能以 `plugin` 结尾；是用户数据的地址 |
| **分发标识** | 仓库地址（见第六节——这个生态没有包制品库） | 用户在社区目录里按插件名找到它 |

要点：

- **`id` 是数据地址，发布后不要改**：改了等于换了一个插件，已有用户的配置与数据失联。
- 这个生态**没有包制品库**——分发靠「仓库 + 发布」，所以「发布范围」的含义与前文不同，
  见第六节。

## 四、宿主加载什么文件

**这一节是本生态最特殊的地方，也是决定产物入不入库的关键。**

用户安装时，宿主会**从你仓库的某个发布（GitHub Release）里下载固定的文件**，
不是从制品库装整个包：

| 文件 | 仓库根（版本控制） | 发布附件 | 是否必需 |
| --- | --- | --- | --- |
| `manifest.json` | 必须提交（目录读默认分支最新提交的那一份判最新版本） | 必须附（安装时下载的那份，两处版本必须一致） | 必需 |
| `main.js` | **不提交**（官方模板的忽略规则明确忽略它；它只进发布附件） | 必须附（插件本体，编译产物） | 必需 |
| `styles.css` | 有样式才有（源码提交、构建产出）；无样式则两处都可省略 | 可选，有才附 | 可选 |
| `versions.json` | 仓库根文件（旧宿主回退用），不是三件套之一 | 不必附 | 按需 |

因此：

- **`main.js` 只进发布附件，不进版本库**——与常规插件「产物必须入库」相反。
  仓库里有它属于污染（与官方模板的忽略规则冲突）；发布里缺它才是断链
  （`Failed to install` / 404 / 装上无法启用）。
- 仓库里 `manifest.json` 与发布里的 `manifest.json` 版本必须一致；社区目录读的是**默认分支
  最新提交**里的那一份，所以提交要先生效，改了没提交或提交在别的分支上，审核看到的都是旧的。
- 附件名必须精确为 `main.js`、`manifest.json`、`styles.css`（小写、无版本号、无哈希）。
  改名、打包成压缩包、大小写错一律断链。
- 提交社区前仓库根还必须有 `README.md`（用途与用法，目录页摘录展示）与 `LICENSE`
  （决定他人使用方式）。缺它们提交前即被打回。
- 如果宿主只加载仓库里的源码而不需要构建（例如纯样式的主题），产物规则不适用——
  但插件的 `main.js` 是编译产物，属于必须进附件那一类。

核对办法：发布后**回读一次**，确认该发布的附件列表里有必需文件，且 tag 与两处
`manifest.json` 的版本三方一致。

## 五、发布与版本：标签必须与清单一致

这是本生态**最容易出错的一处**，因为它的分发流程对版本一致性有硬要求：

1. 先把 `manifest.json` 的 `version` 更新为符合 `x.y.z` 的新版本并提交到默认分支；
2. 建一个**发布**，其**标签名必须与 `manifest.json` 里的 `version` 完全一致（不带 `v` 前缀，例如 `1.2.3` 而非 `v1.2.3`）**；
3. 把 `main.js`、`manifest.json`（以及可选的 `styles.css`）作为**附件**上传到该发布；
4. 发布必须点 Publish（一直 Draft 用户收不到更新）；后续更新发新发布即可，无需重新提交目录。

**标签与清单版本不一致 = 装不上**。这不是「后续自动化对不上」那种隐患，是立即失败。

三个配套机制：

- **npm 的 `v` 前缀陷阱**：包管理器的版本命令默认建 `v` 前缀的标签（如 `v1.0.1`），
  推上去宿主认不出。必须手动建裸标签并推送，或把带 `v` 的标签删改后再推。
  模板仓库用版本同步脚本在版本钩子里同步 `manifest.json` 与清单版本号，
  但 tag 前缀问题仍需作者自己保证，这是最高频翻车点之一。
- **`versions.json`**：JSON 对象，键为插件版本、值为该版本要求的最低宿主版本
  （如 `{"0.12.0":"1.1.0"}`）。宿主版本低于 `minAppVersion` 的用户靠它回退到兼容旧版。
  **只在 `minAppVersion` 变化时才需更新它**，不必罗列每次发布。
- **Release 的标题与说明文字随意**，宿主只认 tag 名，不用它判断版本。

## 六、发布范围在这个生态里是什么意思

因为这个生态分发的是「发布里的附件」而不是「包」，所以：

- **发布范围 = 你往那个发布里附了哪些文件**。少附一个必需文件，用户就装不上。
- 制品库白名单那一套在这里**不存在**——不要去找清单里的白名单字段。
- README 之类的说明文档放在仓库里（社区目录与仓库页面展示），不需要进发布附件。

## 七、自动化：官方模板的工作流机制

官方模板仓库的发布工作流只覆盖「标签驱动写发布附件」，机制不要改，只换取值：

- 触发：推任何标签即跑；tag 名必须事先等于 `manifest.json` 的 `version`（裸版本，无 `v`）。
- 权限：建发布传附件要 `contents: write`；构建来源背书要 `id-token: write` 与背书权限。
  仓库设置里工作流权限需开读写，否则传附件失败。
- 构建：装依赖后跑构建产出 `main.js`（与可选的 `styles.css`）；有无样式要自动检测，
  无样式时跳过样式附件与背书对应行，不要硬传不存在的文件。
- 背书：对 `main.js`（与有时的 `styles.css`）做构建来源背书，提交审核时加分。
- 建发布时 tag 原样透传；正文写完后到发布页补说明并点 Publish。
- 版本同步脚本在版本钩子里同步 `manifest.json`、清单版本号与 `versions.json`，
  并暂存改动；tag 仍需手动推送。

本 skill 的通用发布模板默认 `v*` 触发器。Obsidian 项目落盘时必须按本节把触发器改成
裸版本形状，否则推上去的标签宿主认不出。`review.mjs` 会按触发器形状卡这一项。

## 八、测试通道与本地调试

- 官方目录外不提供 beta 通道，推荐用社区的测试分发工具在提交前分发给测试者。
  测试发布同样建一个发布（可标预发布）并附三件套；此时**不要把 bump 后的
  `manifest.json` 提交到默认分支**，否则目录会当正式版收录。
- 预发布后缀（`-preview`、`-alpha` 一类）只走测试通道，不进社区稳定通道：
  装过后缀版的用户收不到同号正式版的自动更新，必须等下一个裸版本号才重新触发。
  结论：稳定通道永远用裸 `x.y.z`。
- 本地调试时把构建产物指向本地仓库的插件目录挂载，改完按宿主生效规则验证；
  给别人用时走目录安装。**不要用开发链接代替附件齐备的验证**——缺附件的失败
  在本地永远不复现。

## 九、这个生态特有的坑

- **`version` 只支持 `x.y.z`**，不接受预发布后缀。想发候选版走测试通道，
  不要往稳定版本号里塞额外标记——那会让标签对不上。
- **发布必须带附件**。只打一个标签、不附文件，用户装不上，而且这个失败很安静
  （标签看起来是对的）。
- **`id` 不能含 `obsidian`**、不能以 `plugin` 结尾、只许小写字母与连字符，
  且要全局唯一——提交审核时才校验，早查早改。
- **社区目录读默认分支的最新提交**：`manifest.json` 改了但没提交（或提交在别的分支上），
  审核会看到旧的那份。
- **目录侧有缓存**：tag 与附件全对仍报版本对不上时，先用管理页的手动触发重扫，
  确认 tag 无 `v` 且附件齐，再走社区支持渠道，不要连发新版硬撞。
- **用户宿主过低**：报无可用版本时，先查 `minAppVersion` 与 `versions.json` 回退，
  让用户升级宿主或补回退映射。

## 事实来源

`manifest.json` 的字段集合与命名限制、`version` 只支持 `x.y.z`、发布标签必须与清单版本
一致且不带 `v`、安装时下载 `main.js` / `manifest.json` / `styles.css`、社区目录读取默认分支
最新提交的 `manifest.json`、`versions.json` 的作用、官方模板的忽略规则与工作流机制、
测试通道的后缀陷阱，均来自官方开发者文档的提交、版本、动作、测试、目录管理各节与官方模板仓库

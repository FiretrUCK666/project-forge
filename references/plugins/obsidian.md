# Obsidian 插件

## 何时读本文件

- 勘察判定项目是 `obsidian-plugin`（根目录有 `manifest.json`，且含 `minAppVersion`）时。
- 给一个 Obsidian 插件配置版本管理、远端或发布链路时。

通用结论见 `references/plugin-project.md`，本文件只写这个生态特有的事实。

## 一、怎么认出这类项目

根目录的 **`manifest.json`**。判定字段是 `minAppVersion`（只有 Obsidian 插件用它）。
次要证据：依赖里有 `obsidian` 这个包、或存在 `versions.json`。

注意与 VS Code 的区别：VS Code 用 `package.json`，Obsidian 用独立的 `manifest.json`
——**同一个「插件项目」在不同生态里清单文件完全不同**，这正是本生态需要专章的原因。

## 二、清单里必须有什么

`manifest.json` 的字段（官方 `PluginManifest` 接口）：

| 字段 | 说明 |
| --- | --- |
| `id` | 插件标识。**在所有已发布插件里必须唯一，且不能包含 `obsidian` 这个词** |
| `name` | 显示名 |
| `version` | 版本号。**只支持 `x.y.z` 三段格式**，需符合语义化版本 |
| `minAppVersion` | 能运行本插件的最低宿主版本 |
| `description` | 说明 |
| `author` | 作者 |
| `authorUrl` / `isDesktopOnly` | 可选：作者主页；是否仅限桌面端 |

## 三、两个标识分别是什么

| 标识 | 是什么 | 约束 |
| --- | --- | --- |
| **插件 id** | `manifest.json` 的 `id` | 全生态唯一、不能含 `obsidian`；是用户数据的地址 |
| **分发标识** | 仓库地址（见第五节——这个生态没有包制品库） | 用户在社区目录里按插件名找到它 |

要点：

- **`id` 是数据地址，发布后不要改**：改了等于换了一个插件，已有用户的配置与数据失联。
- **`id` 的全局唯一性由你自己保证**：撞名会在提交审核时被拒，而不是自动加后缀。
- 这个生态**没有包制品库**——分发靠「仓库 + 发布」，所以「发布范围」的含义与前文不同，
  见第六节。

## 四、宿主加载什么文件

**这一节是本生态最特殊的地方，也是决定产物入不入库的关键。**

用户安装时，宿主会**从你仓库的某个发布（GitHub Release）里下载固定的三个文件**，
不是从制品库装整个包：

| 文件 | 是否必需 |
| --- | --- |
| `main.js` | **必需**——插件本体，编译后的产物 |
| `manifest.json` | **必需** |
| `styles.css` | 可选 |

因此：

- **`main.js` 必须提交进版本库**（它是构建产物，而安装你的人不会替你构建），
  **并且必须作为附件上传到发布里**——这两件事都要做，缺一个都装不上。
- 仓库里 `manifest.json` 与发布里的 `manifest.json` 要一致；社区目录读的是**默认分支
  最新提交**里的那一份，所以提交要先生效。
- 如果宿主只加载仓库里的源码而不需要构建（例如纯样式的主题），产物规则不适用——
  但插件的 `main.js` 是编译产物，属于必须入库那一类。

## 五、发布与版本：标签必须与清单一致

这是本生态**最容易出错的一处**，因为它的分发流程对版本一致性有硬要求：

1. 先把 `manifest.json` 的 `version` 更新为符合 `x.y.z` 的新版本；
2. 创建一个**发布**，其**标签名必须与 `manifest.json` 里的 `version` 完全一致**；
3. 把 `main.js`、`manifest.json`（以及可选的 `styles.css`）作为**附件**上传到该发布；
4. 提交到社区目录。目录读的是默认分支最新提交里的 `manifest.json`，
   **所以它必须已经提交且准确**。

**标签与清单版本不一致 = 装不上**。这不是「后续自动化对不上」那种隐患，是立即失败。

`versions.json`（放在仓库根）用于旧版宿主：当用户的宿主版本低于 `minAppVersion` 时，
宿主会去读它来挑一个兼容的旧版本。

## 六、发布范围在这个生态里是什么意思

因为这个生态分发的是「发布里的附件」而不是「包」，所以：

- **发布范围 = 你往那个发布里附了哪些文件**。少附一个必需文件，用户就装不上。
- 制品库白名单那一套在这里**不存在**——不要去找清单里的白名单字段。
- README 之类的说明文档放在仓库里（社区目录与仓库页面展示），不需要进发布附件。

核对办法：发布后**回读一次**，确认三个文件都在该发布的附件列表里。

## 七、这个生态特有的坑

- **`version` 只支持 `x.y.z`**，不接受预发布后缀之类的其他形式。想发候选版要走别的办法，
  不要往版本号里塞额外标记——那会让标签对不上。
- **发布必须带附件**。只打一个标签、不附文件，用户装不上，而且这个失败很安静
  （标签看起来是对的）。
- **`id` 不能含 `obsidian`**，且要全局唯一——提交审核时才校验，早查早改。
- **社区目录读默认分支的最新提交**：`manifest.json` 改了但没提交（或提交在别的分支上），
  审核会看到旧的那份。

## 事实来源

`manifest.json` 的字段集合、`id` 的唯一性与命名限制、`version` 只支持 `x.y.z`、
发布标签必须与清单版本一致、安装时下载 `main.js` / `manifest.json` / `styles.css` 三个文件、
社区目录读取默认分支最新提交的 `manifest.json`、以及 `versions.json` 的作用，
均来自 Obsidian 官方开发者文档的「Submit your plugin」与「Reference > Versions」两节
（https://docs.obsidian.md/Plugins/Releasing/Submit+your+plugin ，核实于本文件写入时）。

社区目录的提交流程界面与审核细则可能变化——**以官方文档为准**。

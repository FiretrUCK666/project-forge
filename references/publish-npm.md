# npm 专章

> 发布总纲见 `references/publish.md`（版本语义、发布通道的取舍、"发布"这个动作的一般模型）。本文件只讲 npm 这一条通道，不重复总纲内容。

## 何时读本文件

出现下列任一情况时读全文：

- 用户提到 npm、包、发布、装依赖，或要求"把这个项目配起来"；
- 项目里已经存在清单文件（`package.json`），或需要判断它该不该存在；
- 需要决定一个**非 JavaScript 项目**要不要引入 npm 工具链；
- 需要解释 npm 与 TypeScript、与其他语言生态的关系；
- 需要核对"哪些文件会被分发出去"，或排查"仓库里有、装完却没有"的问题。

读完后应能独立回答：这个项目该不该用 npm、用到哪一层、从当前状态出发缺哪几步。

## 先把 npm 这个词拆开

`npm` 这一个词在日常对话里指四件不同的东西。把它们混在一起，就会得出自相矛盾的结论——一个人说"npm 什么都能发"，另一个人说"npm 只能给 JS 用"，两句都对，只是说的不是同一件事。理解本文件的前提是先把四件事分开：

| 职能 | 是什么 | 依赖 Node 吗 |
| --- | --- | --- |
| 制品库（registry） | 一个存放与分发包的**服务**，按名字与版本存取，对外提供查询与下载 | 不依赖（它是网络服务，与你的项目无关） |
| 命令行工具（CLI） | 输入包管理器命令时运行的那个程序，负责打包、上传、下载、解析 | 依赖（它本身就是一个 Node 程序） |
| 依赖解析与锁文件 | 读清单文件里的依赖声明，算出完整依赖树并锁定版本 | 依赖 |
| 任务运行器 | 清单文件里 `scripts` 那一段定义的命名命令，起个名字代指一串命令 | 依赖工具链本身；但**被它调用的脚本可以是任何语言**（见下） |

**结论先行**：npm 的「制品库」是一个基本不挑文件类型的通用存储服务；而「工具链」那部分需要 Node 才能运行。二者的适用范围不一样，后面所有"能不能用"的困惑都来自这一条。

需要精确表达时，用「制品库」「命令行工具」「清单文件」这些词，不要笼统说"npm"。

## 基础操作：从头到尾

下面是一条完整链路。每一步都说明：**在做什么、产出什么、为什么需要**。顺序即执行顺序。

### 一、前置：确认运行环境

包管理器通常**随运行环境一起安装**，不需要单独装一个。先确认两件事：

| 要确认的 | 怎么取 | 判断 |
| --- | --- | --- |
| 运行环境是否可用及其版本 | 取运行环境自身的版本输出 | 版本过低会让清单文件里的新写法失效 |
| 包管理器是否可用及其版本 | 取包管理器自身的版本输出 | 版本过低会让锁文件格式、工作区能力失效 |
| 清单文件是否声明了要求的运行环境版本 | 读清单文件的 `engines` 字段 | 声明与实际不一致时，install 可能只是警告而不会拦（见下） |

`engines` 只是一个**声明**，不是强制门禁：默认行为常常是警告后继续，而不是拒绝执行。所以它写的是"这个项目期望的环境"，不能当成"环境不对就装不上"。真正的守门要另配（例如在工作流里显式校验），不要指望这个字段。

**不要为这一步单独安装运行环境**。若环境确实缺失，那是"这台机器还没有这个工具链"，属于要用户决策的事（这会引入一整套语言运行时），不是照着步骤往下敲就能解决的。

### 二、清单文件：项目身份与元数据的唯一权威来源

清单文件（`package.json`）是这个生态里**关于项目是什么、怎么引用、发布什么**的唯一权威来源。工具链读它，制品库页面展示它，下游据此判断能不能用。凡是要描述项目身份的地方，都从它读，不要在别处重复写。

字段分三组看：**身份与呈现**、**入口与产物**、**依赖与运行环境**。

#### 身份与呈现

| 字段 | 作用 | 要点 |
| --- | --- | --- |
| `name` | 包的唯一标识 | 决定别人用什么名字安装它。**在制品库的可见范围内全局唯一**，被占用就只能换名。小写、可用连字符与点、不得有空格与大写。命名规则与命名空间的含义见下 |
| `version` | 当前版本 | 语义与递进规则见总纲；这里只需知道制品库按"名字 + 版本"寻址，同一组合只能存在一份 |
| `description` | 一句话说明 | 会展示在制品库页面上，也是被检索到时的摘要。不是注释，是给陌生人的第一句话 |
| `private` | 禁止发布 | 设为真值后，发布动作会直接失败。**这是防误发开关**，任何不打算发布的项目都该打开 |
| `license` | 授权条款 | 不写会让下游的合规检查无法判断，很多组织因此不允许引入。常见做法是写标识符，并在仓库里放对应的许可证全文 |
| `keywords` | 检索关键词 | 影响**可发现性**，不影响功能。填真正描述用途的词，不要堆砌无关热词 |
| `repository` / `homepage` / `bugs` | 源码、主页、反馈渠道 | 制品库页面据此提供跳转，也是排查问题时找到源码的唯一线索。键名与地址都要与实际一致（各平台的写法不同，以该平台文档为准） |

#### 命名与命名空间

`name` 有两种形态，差别是**权限与可见性**，不是装饰：

| 形态 | 含义 | 何时需要 |
| --- | --- | --- |
| 无命名空间 | 占用制品库的全局名字池 | 名字还没被占用时优先用；更短、更好记 |
| 带命名空间（`@…/…`） | 归属某个账号或组织，只在命名空间内唯一 | 全局名字已被占用；或需要把一批包归到一个组织下统一管理 |

带命名空间的包**默认是私有的**，要公开发布必须显式声明公开——这正是 `publishConfig` 存在的原因之一（见下）。不知道自己的命名空间是什么、有没有登录，就现场查账号登录状态与组织归属，不要假设。

#### 入口与产物

这三个字段回答的是"别人 `import` 它时，实际加载哪个文件"：

| 字段 | 作用 | 要点 |
| --- | --- | --- |
| `type` | 声明这个包的模块格式约定 | 决定同一后缀的文件按哪种模块语义解析。写错会让下游以错误的语义加载，报错往往离现场很远 |
| `main` / `module` | 传统入口声明 | 前者多用于旧式加载路径，后者多用于打包器。二者都属于历史演化出的约定 |
| `exports` | **现代入口声明** | 显式列出对外暴露的路径与对应文件，并**同时约束外部可见范围**：没列出的路径，外部引用会被拒绝 |

**`exports` 是现代做法**，优先用它：它把"对外暴露什么"从隐式约定变成显式契约，同时管住子路径访问。用它的代价是约束更严格——若项目内部有依赖深层路径引用的代码，迁移时可能暴露出来，这是好事，属于设计问题浮出水面。

#### 发布范围：`files` 白名单

**这是全文最需要讲透的一个字段，因为它有一条最反直觉的规则。**

| 问题 | 答案 |
| --- | --- |
| 它决定什么 | **哪些文件会被分发出去**——它是一份白名单，不是排除表 |
| 不写会怎样 | 有一整套默认规则：常见的说明与许可证、清单本身、入口指向的文件通常会被带上；而依赖目录、版本控制元数据、常见临时文件会被排除。默认规则覆盖得了常见情况，但**它是一份隐式约定**，看代码的人要凭经验推断，容易漏 |
| 它与忽略文件的关系 | 另有一份忽略配置可以反向排除。**两者同时存在时，白名单优先**——白名单里明确列出的，忽略配置排不掉 |
| 它是白名单还是黑名单 | 建议当**白名单**用：写"要发什么"，不写"不要发什么"。黑名单的失效模式是静默的（漏排一个新文件就发出去了），白名单的失效模式是可见的（漏加一个必需文件，预演时就看出来） |

**最关键的一条**：`files` 白名单**对「从仓库源安装」同样生效**。

也就是说，即使某个文件已经提交进版本库，只要它不在白名单覆盖范围内，别人装这个包时**拿不到它**。安装工具会按同一套规则对拿到的内容做筛选，不是"仓库里有什么就给什么"。

实际后果，必须写进判断里：

- **"仓库里有"不等于"用户手里有"**。这两件事是两个不同的可见集合，白名单是二者共同经过的那道闸门；
- 仓库能正常构建、能跑通测试，**完全不能证明**发布出去的包是可用的——从仓库源安装的人可能缺文件，从制品库安装的人一定缺；
- 典型翻车：产物目录没进白名单、声明为入口的文件被默认规则排除、运行时需要的模板或静态资源被漏掉。这些在开发机上永远不复现，因为开发机上文件就在那里。

建议做法：

1. **显式声明白名单**，不依赖默认规则。默认规则可以兜底，但契约要写出来；
2. 凡是**运行时需要**的文件（产物、入口、模板、资源、必要的说明与许可证）都要在白名单覆盖范围内；
3. 发布前用预演手段核对实际清单（见第六步），把"白名单是否覆盖了全部必需文件"变成一次可验证的检查，而不是靠记忆；
4. 包体积异常偏大时，先怀疑白名单写得太宽（把源码、测试、样例数据一起发了出去）。

#### 依赖声明：三种依赖的区别

| 字段 | 含义 | 装在哪 | 典型用法 |
| --- | --- | --- | --- |
| `dependencies` | **运行时要装** | 使用者安装时自动装上 | 代码在运行期真的会加载的库 |
| `devDependencies` | **只有开发时要装** | 只有在本仓库里开发、构建、测试时才装 | 构建器、测试框架、类型定义、命令行工具 |
| `peerDependencies` | **由使用方提供** | 不由本包安装，期望使用者的项目里已存在 | 插件与其宿主：宿主由使用者选版本，本包声明兼容范围 |

**放错字段的后果不对称，所以拿不准时偏向 `devDependencies`**：

- 把只用于开发的工具放进 `dependencies` → 所有使用者替你多装一份，且是**运行期不必要的攻击面**；
- 把运行期真正需要的库放进 `devDependencies` → 在本仓库能用（因为本地都装了），使用者装完直接报错。这个错误在本地无法复现，只会发生在下游。

`peerDependencies` 的用途是把"宿主版本由使用者决定"这件事显式化。它的关键词是**兼容范围**：写下你能接受的范围，而不是当前开发用的那一个版本。

#### 运行环境与引用

| 字段 | 作用 |
| --- | --- |
| `engines` | 声明期望的运行环境版本范围。是声明而非强制（见前置一节） |
| `scripts` | 命名命令表，见"构建与测试的挂载"与下一节 |

#### 发布相关配置

`publishConfig` 放发布行为本身需要的配置，常见两类：

- **访问级别**：带命名空间的包默认不公开，要公开发布就在这里声明公开。把它写进清单，比依赖"每次发布时记得加一个参数"可靠——参数会被忘，清单不会；
- **发布目标**：发布到哪个制品库、用哪个标签。默认目标是公共制品库；要在私有制品库或企业内部镜像发布时在这里声明。

**原则是：凡是"每次都要记得加"的东西，都搬进清单文件。** 靠人记住的命令行参数，迟早会漏。

### 三、本地开发与依赖安装

安装动作做两件事：**按清单解析出完整依赖树并下载到本地依赖目录**，同时**生成或更新锁文件**。

| 概念 | 是什么 | 该怎么对待 |
| --- | --- | --- |
| 本地依赖目录 | 装下来的依赖文件的落地位置 | **永远不进版本库**。它是可重建的派生物，体积大、平台相关、内容随解析结果变 |
| 锁文件 | 记录这次解析出的**精确**依赖版本与来源 | **必须进版本库**。清单写的是范围，锁文件钉的是确定的树 |
| 清单文件里的范围 | 表达兼容意愿（例如允许打补丁的版本） | 它有意留出弹性，所以不同时间解析可能得到不同结果 |

**为什么锁文件必须进版本库**：它保证不同机器、不同时间、包括持续集成环境，装出**同一棵树**。没有它，别人拿到你的项目后装出来的依赖版本可能与你不同；由此产生的故障最难排查——报错出现在别人机器上，而你的机器永远复现不了。这不是"可有可无的缓存"，是**可复现性的载体**。

**为什么依赖目录永远不进版本库**：它是锁文件的产物，可以被完整重建；提交它会把体积、平台差异和大量噪声带进历史，让每次改动都无法审阅。是否忽略它，也可以反过来当作判据——看到一个项目的依赖目录被提交，说明它的工程约定还没建立。

**依赖变化后要重新安装**，而不是手改依赖目录。手改目录不会更新锁文件，于是"我这儿好了"与"别人那儿"再次分叉。

### 四、构建与测试的挂载

把构建、测试、校验这些动作挂到清单文件的 `scripts` 上，让**"怎么跑这个项目"只有一个入口**。

| 好处 | 说明 |
| --- | --- |
| 协作者不必记长命令 | 记住几个名字就够，参数与顺序封装在一处 |
| 自动化（持续集成、发布钩子）可以复用同一条命令 | 否则自动化里会抄一份命令，慢慢与本地不一致 |
| AI 助手能自我定位 | 读到清单文件就知道该跑什么，不必猜这个项目用什么构建器 |

悬挂原则：**命名要表达意图**（构建、测试、校验、类型检查各一个），**不要**把多个不相关动作塞进一个名字里。同一个意图只留一个入口，出现第二个就说明职责没划清。

对非 JavaScript 项目，这一节同样适用——见"适用范围"。

### 五、发布前预演

大多数生态都提供"**只打包、不发布**"的手段，用来**先看清将要发出去的文件清单与体积**。

**这一步不可跳过。** 它是唯一能在发布前发现"发出去的东西不对"的检查点；发布之后再补救只能靠新版本，而某些错误（例如把不该公开的东西发了出去）是补不回来的。

预演输出该看四件事：

| 看什么 | 异常信号 |
| --- | --- |
| 文件数 | 远多于预期：白名单太宽，源码、测试、样例数据被一起发了出去 |
| 有没有混入不该有的 | 凭据、环境配置、本地路径痕迹、构建缓存、依赖目录 |
| 有没有漏掉必需的 | 产物缺席、入口文件缺席、运行时模板或资源缺席——**白名单最常见的失效方向** |
| 包体积 | 与内容明显不符时，通常是打包了数据或缓存；体积同时影响使用者的安装成本 |

预演也应能反映**白名单对从仓库源安装同样生效**这一事实：把预演结果当"用户最终拿到的东西"来审，而不是当"上传前的一次预览"。

### 六、发布

发布动作本身是"把预演出的那份内容上传到制品库，登记为某个名字的某个版本"。

认证方式有两条路：

| 方式 | 怎么工作 | 适用场景 | 代价 |
| --- | --- | --- | --- |
| 交互式验证码 | 由账号持有人在其终端确认一次性验证码，随发布动作一起提交 | 手工发布、首次发布、本地一次性发布 | 必须有账号持有人在现场；无法用于无人值守 |
| 基于身份令牌的自动发布 | 由持续集成环境用短时身份凭证证明"我来自这个仓库的这条工作流"，制品库据此授权 | 由流水线自动发布 | 需要**在制品库侧预先登记**发布者身份，配置不改就无法发布 |

**优先自动发布（可信发布）**：短时凭证不可窃取、不能离线复用，且发布记录能追溯到具体哪次构建。**不要长期把长期有效的令牌放在仓库配置里**——它一旦泄漏就能冒充你发布任意内容，且无从追溯。若已经在用长期令牌，迁移方向就是换成可信发布（见"场景应用"）。

官方迁移顺序：先登记可信发布者并验证能用，再收紧发布访问（禁传统令牌），最后吊销不再需要的旧令牌。
**没登记就切，流水线会在发布步骤失败。**

### 构建来源背书（provenance）

可信发布 + 公开仓库 + 公开包 → 默认自动生成并发布构建来源背书，无需额外 flag；
私有仓库一定不生成。手动背书路径才需要显式 flag，且要求较新的包管理器版本、
仓库地址大小写一致、云构建机、首发声明公开。第三方发布工具可用等价的环境变量、
清单字段或配置文件三选一声明。首版实战里有人报告不加显式声明发不出去、加了就通——
把显式声明留在命令或清单里无害（一劳永逸），模板注释已写。

### 发布构建不用缓存的原因

模板要求发布构建关缓存，完整原因是两层：旧缓存会改变发出去的东西，**且中毒的缓存
可把凭据（含短时身份令牌）暴露给攻击者控制的代码**——包管理器在清单声明包管理器时
会自动开缓存，发布构建必须显式关掉。防的不仅是产物不一致，更是凭据泄露。

#### 可信发布接线步骤（带着用户在浏览器里填，约 3 分钟）

登记动作只能由账号持有人在 npm 网站上做，AI 碰不了——但 AI 要把每一项要填什么讲清楚，
否则用户面对表单只能猜。路径：包页面 → `Settings` → `Trusted Publisher`：

| 项 | 填什么 | 填错的后果 |
| --- | --- | --- |
| 组织或用户名 | 包作用域的所有者（与 `package.json` 的 `name` 作用域段逐字一致） | 大小写都敏感，错一个字符即无权 |
| 仓库名 | 源码仓库名 | 同上 |
| 工作流文件名 | 仅文件名（如 `release.yml`），且该文件必须真实存在于仓库 `.github/workflows/` 下 | 不存在即无权 |
| Environment 名 | 仅用部署环境做保护时填；填了则发布身份必须带该环境 | 不一致即无权 |
| 允许的动作 | 是否同时允许直接发布，可选（新建默认可能仅走分阶段发布） | 没勾直接发布时报无权 |
| 允许发布 | 勾选直接发布（不勾则只能走预发布通道） | 发布步骤报无权 |

五条必须提前说的现实：

- npm 保存时**不校验**这几项，填错只在发布那一刻爆错，且错误信息不区分“无权”与“目标不存在”
  （常被误判成包名写错）——对照 `templates/ci-release.yml` 与包名逐字核对，而不是重填碰运气；
- **`package.json` 的仓库地址必须与源码仓库精确一致**（含大小写；fork 没改这个字段会失败）；
- 工作流里要声明 `permissions: id-token: write`（签发短时身份用），且 Node 自带的 npm 版本
  可能过旧（可信发布要较新的 npm 大版本，推荐与较新的 Node 配对，见模板注释）；
- 校验的是**调用方**的文件名：被复用调用的工作流配了也白配，父子两边都要给短时身份权限；
- 仅支持云构建机，自建构建机不支持。
- 接线验证不用真发一版：手动触发一次该工作流（`workflow_dispatch` 携带的也是同一个工作流身份），
  若卡在“版本号已占用”而不是认证失败，说明线是通的。注意被触发的文件须在默认分支上，
  否则点触发没反应不是“坏了”。

两个必须提前知道的现实：

- **发布后短时间内查询可能返回不存在，这属于正常延迟。** 制品库在收录新版本时会做安全扫描与索引处理，期间对外查询可能查不到。**不要在"刚发完就查不到"时重复发布**——重复发布是无效动作（同名同版本不能再发），还会把排查方向带偏。等一段时间再确认；
- **"命令成功了"与"制品库上有了"是两件事，只有后者算发布完成。** npm 在收录期间就可能成功退出（并打印 `+ 包名@版本`），所以人工排查要查制品库、自动流程要写回读（见「七、发布后确认」）。反过来说，**重新发布同一个号一定会被拒**（`You cannot publish over the previously published versions`）——若回读说"不存在"而重发被拒，说明第一次其实已经上去了，只是当时还没可见；
- **已经在用别的包管理器时，不要混用发布命令**。用什么包管理器管理这个仓库，就用它对应的发布路径；两套工具混用会造成锁文件与制品库状态不一致。

### 七、发布后确认

按顺序确认，从"制品库承认了"到"内容真的是我打包的那份"。

**自动发布时，这条回读必须写进流水线，不能留给人事后核对。** npm 会在包「还在处理、对外尚不可见」时就成功退出并打印 `+ 包名@版本`——**退出码 0 不等于制品库上真的有这一版**。发布走 CI 时没人在看输出，一次没真正落地的发布会以「全绿」的样子过去，直到有人去 npm 页面核对才发现。回读不必问"最新版本是哪个"，只查那一个版本的地址即可（见 `templates/ci-release.yml` 的发布后回读步骤）。

| 确认项 | 怎么确认 | 期望 |
| --- | --- | --- |
| 版本已登记 | 查该包在制品库上的版本列表或该版本的地址（**不是**查询"最新版本"那一个字段，某些包的"最新"标记可能不跟随实际发布；也**不是**看发布命令的输出） | 目标版本出现在完整列表里 / 该版本地址返回 200 |
| 发布内容正确 | 查该版本的**文件列表** | 与预演结果一致：该有的都在、不该有的一律不在 |
| 元数据正确 | 查该版本的清单与说明 | 名称、描述、授权、源码入口都对 |
| 真实可安装 | 在一个**隔离的、干净的环境**里安装刚发布的版本并实际加载一次 | 能装、能引用、能跑起来。**不要用指向本地目录的安装方式替代**——那样验证的是本地文件，绕过了白名单这道闸门，等于没验证 |

最后一项是唯一能同时验证"白名单覆盖是否完整"和"产物是否真的可用"的手段，不能省。

### 八、发布前钩子

把"构建 + 测试 + 自检"挂到发布前钩子上：清单文件的 `scripts` 里有一组以发布相关事件命名的钩子，它们在打包或发布前自动触发（`prepublishOnly` 是其中最贴合这个用途的一个，其余同名家族成员的触发时机各不相同，用之前先确认它到底在哪个环节触发）。

**钩子里要调用已经存在的脚本名，而不是抄一遍命令**。抄一遍就有了两份定义，迟早不一致；正确的结构是一处定义、多处引用。

**目的是让某类错误在机制上不可能发生**，而不是靠人记得按顺序执行：

| 钩住什么 | 挡住的错误 |
| --- | --- |
| 构建 | 忘了重新构建就发布：制品库里是旧产物，而仓库里是新源码——这是发布通道最典型的"看起来成功了"的错误 |
| 测试 | 明知不绿的版本被发出去 |
| 自检（体积、凭据、路径痕迹等） | 把不该公开的内容发出去；这类错误发布后不可撤回 |

**判据**：凡是"上一次靠人记得、下一次不记得就会错"的步骤，都应该变成钩子。钩子是清单文件的一部分，跟着项目走、跟着接手者走，不依赖任何人的记忆。

## 场景应用：各种既有状态怎么接

**总原则：先勘察现状，再补缺口，永远不要假设项目是白纸。**

勘察的固定动作：读清单文件是否存在及其内容 → 读版本库现状（有没有远端、有没有提交）→ 看有没有锁文件与工作区配置，**从锁文件的种类就能判断这个仓库已经在用哪个包管理器** → 查账号登录状态与包的归属。这四步做完，起始状态就确定了，再对照下表决定动作。

| 起始状态 | 判断依据 | 动作 | 容易踩的坑 |
| --- | --- | --- | --- |
| 完全没有清单文件 | 目录里没有清单文件 | 先判断要不要用 npm（见"适用范围"），要用再从零开始：建清单、填身份、定白名单、挂脚本 | 环境没确认就开始；把 `private` 忘了，之后误发布 |
| 已有清单文件，从未发布过 | 有清单，但制品库上查不到这个名字 | 只补发布相关的缺口：身份是否唯一且合规、白名单、钩子、访问级别、预演 | 直接跳到发布，跳过预演与隔离安装验证 |
| 已发布过，但没有自动化 | 制品库上有版本，但发布靠人工敲命令 | 先把完整链路（构建 → 测试 → 预演 → 确认）固化成脚本与钩子，再考虑改造成流水线发布 | 先上自动化再补流程，把人工步骤原样搬进流水线，等于把隐患自动化 |
| 已发布过，已有自动化，但用长期令牌 | 自动化配置里存着可直接发布的长期凭证 | 迁移到基于短时身份凭证的可信发布 | 迁移需要**先在制品库侧登记发布者身份**；没登记就切，流水线会在发布步骤失败，且**失败信息可能不区分"没有权限"与"目标不存在"**，容易误判成名字写错 |
| 已在用别的包管理器（pnpm / yarn / bun 等） | 仓库里有别的锁文件或工作区配置，锁文件与工作区文件名即所用包管理器（各家的文件名互不相同） | **沿用现有的，不要换**：认准锁文件与工作区文件的名字，之后所有安装与发布动作都走同一套 | 换包管理器会产生**第二个锁文件**，让依赖树分叉：本地与流水线各按一份锁文件装出不同的树，故障隐蔽且难以归因。**不要为了统一而换掉既有选择**——已经形成的约定优先于个人偏好 |
| 多包仓库（工作区 / 单体仓库） | 工作区配置里列了多个子包，或目录下有多份清单 | 每个包**各有自己的身份与版本，独立发布**；先决定版本策略再动手 | 见下 |
| 只想把清单当任务运行器用 | 项目不打算发布，只是想要统一入口 | 只做 `scripts` 那一段；**不要填发布相关字段**（名称的唯一性、授权、仓库地址、访问级别都不需要），并打开 `private` | 顺手填了发布字段，让人误以为这是个要发布的包 |
| 非 JavaScript 项目想借用任务运行器 | 项目主语言不是 JS/TS，但已有或愿意引入运行环境 | 见"适用范围"的判据 | 为了"统一"而在完全没有 Node 环境的项目里引入整套运行时 |
| 私有包（只给内部用） | 使用者限于组织内部 | 两种模式选一种：仓库内私有（`private`，根本不发布）或发布到私有制品库并配访问控制 | 把两种"私有"混为一谈，见下 |
| 想发布但不想公开源码 | 只希望别人拿到产物 | 白名单只放产物，入口指向产物 | 以为"没有白名单就会自动只发产物"，实际上默认规则可能带上源码；必须显式声明并预演核对 |

### 几个场景的展开

**从零开始**：不要先建一堆配置再想目的。顺序是「先确定这个项目属于哪个生态 → 再确定要不要发布 → 再决定发布到哪 → 最后才填字段」。反过来的顺序会产生一堆填了却无用的字段，而且容易在没想清楚"给谁用"的情况下把东西公开出去。

**多包仓库的版本策略**：两种做法各有取舍，**先选一种并写进约定**，不要混用。

| 策略 | 做法 | 好处 | 代价 |
| --- | --- | --- | --- |
| 版本联动（统一版本） | 所有包共用同一个版本号，一起升 | 兼容性一目了然：同一个版本号的包互相兼容 | 会产生大量"内容没变但版本号变了"的版本；发布体积与噪声大 |
| 独立版本 | 每个包各自按自己的改动升号 | 版本号忠实反映各包的改动 | 需要额外机制或工具来记录"哪几个版本互相兼容"，否则使用者要自己试 |

**私有包要区分两种"私有"，混了就会得出错误结论**：

| "私有"的两种含义 | 机制 | 后果 |
| --- | --- | --- |
| 仓库内私有：只是一个项目，不对外发布 | 清单文件的 `private` 开关 | 发布动作直接失败。**这是防误发，不是权限** |
| 制品库上的私有：发布出去，但只对特定范围可见 | 制品库的可见性与访问控制（命名空间归属、组织成员、访问令牌） | 真的发出去了，因此**必须有可见性配置与令牌管理**，否则很可能默认公开或默认无人可用 |

`private` 开关**不能**用来保护已发布内容的可见性——它拦的是"发布这个动作"，不是"发布之后谁能看"。

## 适用范围：能不能用、该不该用

这是最容易糊在一起的问题。用**三个层次**回答"能不能用"——每往下一层，答案的适用范围就窄一截：

| 层次 | 问题 | 答案 |
| --- | --- | --- |
| 第一层：**能装** | 这个制品库能不能存我的东西？ | **能，基本不挑文件类型。**任何文件都能作为包内容分发，它对外提供的就是"按名字与版本存取"的通用存储服务 |
| 第二层：**有意义** | 装在别人机器上之后，别人能用起来吗？ | **只有当消费者处在 Node 生态、或至少有 Node 运行环境时才有意义。**要让别人真的能用起来，通常需要运行环境来加载或执行它 |
| 第三层：**该用哪个** | 这是不是这类项目该用的分发渠道？ | **看消费者在哪个生态。**各生态有自己的制品库，不要混用——用错渠道的代价是使用者要跨生态装依赖，且拿不到该生态的惯例（版本策略、依赖声明、文档呈现） |

三层是递进关系：**"能装"永远成立，"有意义"和"该用哪个"要看消费者**。多数关于"能不能用"的争论，其实是在不同层次上各说各话。

### 制品库是不是专门给 JavaScript 用的

- **制品库本身不是"只给 JS 用"的**：它是一个通用分发服务，包内容是什么都行——配置文件、资源、数据、命令行工具都能装在里面；
- **但整个工具链是围绕 JS/Node 生态设计的**：依赖解析、入口声明、模块格式、生命周期钩子，默认的消费者模型就是"一个 Node 项目在装依赖"。脱离这个生态，你只是在用一个通用文件分发服务，而**它并不是为此优化的**（没有该生态的依赖解析能帮你，也没有该生态的惯例能帮使用者）；
- 因此正确说法是：**不存在"用不了"的项目，只存在"发到 npm 没意义"的项目**。判断"有没有意义"的判据是第二、三层——消费者是谁、他们用什么装东西。

### TypeScript 与包管理器的关系

先把概念掰正，这里混了三个不同层级的东西：

| 是什么 | 属于哪一类 | 与 npm 的关系 |
| --- | --- | --- |
| TypeScript | 一种**编程语言**（以及实现它的编译器） | 不是包管理器，与 npm **不是同一类东西**——不存在"TS 用不用 npm"这种层面的对立 |
| 包管理器 | 负责依赖解析与分发的工具 | 它管的是"怎么把东西装下来、怎么把东西发出去"，不管语言本身 |
| 编译器 | 把一种语言转成另一种语言的程序 | 它本身也是一个普通程序，可以经由制品库分发 |

真实的关系是一条链：

```
TypeScript 编译器（作为普通包分发在制品库上）
  → 用包管理器把它装下来
  → 用它的编译器把 TS 编译成 JS
  → 运行环境执行的是编译产物（JS），不是 TS 源码
```

所以 npm 在这里的角色是「**分发与安装渠道**」，不是「TypeScript 的运行方式」。TypeScript 的运行方式是"先编译、再运行产物"，与用什么把它装下来无关——换成任何别的分发方式，这一步都不变。

两点补充：

- **浏览器不认识 TypeScript**，所以编译这一步是必需的，不是可选的工程习惯。运行环境有能力直接执行 TypeScript 属于**特例**（需要专门的加载支持），不要把它当常态，也不要据此省掉编译与产物检查；
- **用包管理器装下来的东西不一定是 JS 库**。编译器、命令行工具、构建器、甚至字体与数据集都可能以包的形式分发。判断一个包"是不是 JS 库"要看它的**内容和消费者**，不是看它从哪个渠道装下来。

### 清单文件的 `scripts` 是不是只能跑 JS

**不是。** `scripts` 本质是一个**与语言无关的命名命令表**：它只是把"一串命令"起了个名字，然后把那串命令交给系统的 shell 去执行。被执行的命令是什么语言写的、调用了什么工具，它不关心也不检查。

因此：Python、Rust、Go 项目也能用一份清单文件，把"构建 / 测试 / 检查"统一成一个入口，让协作者与 AI 助手不必记住一堆长命令、也不必猜这个项目用什么工具链。

但代价与边界要说清楚：

| 维度 | 说明 |
| --- | --- |
| 前提 | 这样做**需要 Node 运行环境**（工具链要从它来）。这是为便利额外引入的一层依赖，不是白得的 |
| 必要性 | 对纯 Python 这类项目，这是**额外便利而非必需**——它的生态有自己的等价机制（自己的任务定义方式与项目元数据），不引入 npm 也完全能组织好工程 |
| 判据 | **项目本来就有 Node 环境**（例如前端与后端在同一个仓库里），或**确实需要跨语言统一入口**（多种语言混在一个仓库，希望一个命令跑完所有检查）→ 值得用；**项目完全在另一个生态里，且对方已有成熟工具** → 不要为了"统一"而引入额外依赖，那只会给使用者增加一道装环境的门槛 |

**决策原则是"减少总门槛"，不是"统一到我喜欢的那一个"。** 让使用者少装一套运行时，比让命令看起来整齐更重要。

### 各生态对照

| 语言 / 生态 | 默认公共制品库 | 备注 |
| --- | --- | --- |
| JavaScript / TypeScript | npm 制品库 | 同一制品库还有别的包管理器客户端在用，它们共用同一份制品库与锁文件语言 |
| Python | PyPI | 有独立的打包与项目元数据规范，与 npm 的概念一一对应但不同名 |
| Rust | crates.io | 构建工具兼包管理器，清单与锁文件都由它管理 |
| Go | 模块代理（默认取公共代理与源码仓库） | **没有中心化的上传动作**，见下 |
| Java / JVM | Maven Central 等 | 多仓库并用常见（公共库 + 企业私服），发布到公共库通常有较严的准入要求 |
| Ruby | RubyGems | 与 npm 的模型最接近：集中式、按名与版本发布 |
| PHP | Packagist | 元数据集中，包内容多托管在源码仓库（发布是"登记"而非"上传内容"） |
| .NET | NuGet | 集中式，工具链与构建系统深度集成 |

**Go 需要特别说明，不要强行套用"上传一个包"的模型。** Go 的模块**没有中心化的上传动作**：所谓"发布"就是给源码仓库打一个**版本标签**，模块代理据此去源码仓库取内容并提供分发的加速与校验。这带来两个与 npm 根本不同的性质：

- **收录有延迟，不是即时生效**：标签打上去后，需显式触发一次代理收录（约一分钟可用；
  打标签前被请求过的路径缓存更久）。刚推送就查不到属正常延迟，先触发后回读，不要重发——
  详见 `references/publish-go.md`；
- **分发范围与源码仓库的可见性绑定**：仓库私有，模块就取不到；也没有"白名单决定发什么"这一层——**仓库里有什么，取用的就是什么**（除去版本控制自身的忽略规则）。这与 npm 的 `files` 白名单形成了鲜明对比，也解释了为什么"仓库里的东西会被筛选后才给使用者"这条经验不能跨生态照搬。

## 常见误解与决策清单

| 常见说法 | 实际情况 |
| --- | --- |
| npm 只能装 JS 库 | 制品库里什么文件都能存；能不能用取决于消费者是否处在 Node 生态（见"三个层次"）。用包管理器装下来的编译器、命令行工具、字体都属常见 |
| TypeScript 用 npm 运行 | TypeScript 是语言与编译器，npm 是分发渠道。运行的是**编译产物**；npm 只负责把它装下来，不参与运行方式 |
| 装不上就是不能用 | "装不上"通常是环境缺失、名字或版本写错、网络或代理问题、权限或可见性配置问题——**都是可修的工程问题**，不是"这个项目用不了 npm"。真正的判据是消费者生态，不是某次安装的成败 |
| `node_modules` 要提交进仓库 | 绝对不能。它是锁文件的产物，可由安装动作完整重建；提交它只会带进体积与平台差异。要提交的是**锁文件** |
| 发布了就不能改了 | 部分正确，且**关键部分正是不可逆的那一半**：已发布的版本号不能重复使用，已发布的内容不可删除，只能发新版本修正。因此"发布前预演 + 隔离安装验证"是唯一有效的防线，发布后再发现错误只能靠新版本补救 |
| 私有包也要公开权限 | 取决于"私有"指哪一种：仓库内私有用 `private` 开关（防误发，不需要任何权限）；真正发布出去的私有包需要制品库侧的可见性与访问控制。**由权限控制的可见性不能被 `private` 开关替代** |
| 从仓库装和从制品库装拿到的东西一样多 | **两者都不是"仓库里有什么就给什么"。** 发布范围白名单对两者**都生效**；从仓库源安装时，拿到的是仓库里的内容**经过同一套规则筛选后**的结果，从制品库安装时则是那份已发布内容的展开。差别在**渠道与时机**：制品库上的内容是发布那一刻的冻结快照，仓库源则随提交变化。**唯一可靠的判断依据是显式声明白名单并预演核对，而不是"它已经在仓库里了"** |

## 决策清单

照着走，每一步都只回答一个问题：

1. **这个项目属于哪个生态？** 看主语言与消费者。不是 Node 生态的话，先回到"三个层次"判断**该不该**用 npm，而不是先动手配。
2. **要发布吗？** 不发布 → 打开 `private`，只做 `scripts` 与工程文档，跳过其余全部发布配置。发布 → 继续。
3. **发布到哪个制品库？** 公共还是私有。私有需要可见性配置与访问控制，公共需要确认名字可用与授权条款。
4. **名字确定了吗？** 查制品库上是否已被占用。被占用则改用命名空间，并注意带命名空间的包默认不公开，需显式声明公开。
5. **白名单确定了吗？** 列出运行时真正需要的文件；不依赖默认规则；记住它**对从仓库源安装同样生效**。
6. **依赖字段分对了吗？** 运行时要装的、只有开发时要装的、由使用方提供的，三者不要放错——**放错的后果是不对称的**（见上文）。
7. **入口声明清楚了吗？** 优先用 `exports` 显式声明对外暴露的路径。
8. **构建与测试挂到 `scripts` 了吗？** 让"怎么跑这个项目"只有一个入口，且自动化能复用同一条命令。
9. **预演过了吗？** 看文件数、看混入、看遗漏、看体积。**不看就不发。**
10. **发布前的钩子挂了吗？** 构建、测试、自检都在钩子上——让"忘了构建就发布"在机制上不可能。
11. **认证方式选对了吗？** 优先短时身份凭证的可信发布；用长期令牌的，规划迁移。迁移前先在制品库侧登记发布者身份。
12. **发布后确认了吗？** 查版本列表（**不是**"最新版本"那一个字段）、查文件列表、并在**隔离的干净环境**里真实安装与加载一次。刚发完查不到属正常延迟，**不要重复发布**。
13. **既有约定动过吗？** 若仓库本来就在用别的包管理器，**已经形成的约定不要换**；多包仓库则确认版本策略只有一种。

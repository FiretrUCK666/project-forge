# Rust 专章

> 发布总纲见 `references/publish.md`（版本语义、发布通道的取舍、“发布”这个动作的一般模型）。本文件只讲 Rust（crates.io）这一条通道，不重复总纲内容。

## 何时读本文件

出现下列任一情况时读全文：

- 用户说发到 crates.io、发个 crate、发新版；
- `Cargo.toml` 发布相关字段报错或缺失，要补齐；
- 需要配置或排查自动发布（可信发布、API token）、预演或打包清单；
- 发布超时、撞号、服务端拒绝，要找修正路径；
- 需要撤回坏版本（yank）或发私有 registry。

读完后应能独立回答：缺哪几个字段、预演哪两步、走哪条认证、报错后先查什么。

## 清单：发布前必须齐的字段

权威来源是 `Cargo.toml` 的 `[package]`：

| 字段 | 要求 |
| --- | --- |
| `name` | 先到先得，被占只能换名；只许 ASCII 字母数字与连字符下划线，非空，有长度与保留名上限 |
| `version` | 三段数字语义化版本；预发布用 `-` 后缀，构建元数据用 `+` 后缀（后者仅信息用途，构建工具忽略） |
| `edition` | 不强制、可发布，但应填（当前新建默认较新的版本；缺省等于用旧语义编译） |
| `license` 或 `license-file` | 必填其一：标准许可写 SPDX 表达式（支持与/或/例外组合，斜杠分隔多许可是废弃写法），非标准改用许可文件（相对清单路径，发布时强制包含） |
| `description` | 必填（纯文本，不是 Markdown） |
| `documentation` | 应填（缺省自动链到文档站对应页，需文档站已构建） |
| `homepage`、`repository`、`readme` | 应填：前两个找得到源码与主页，`readme` 进包并按 Markdown 渲染（缺省自动探测常规文件名，显式关闭亦可） |
| `keywords`、`categories` | 可选但强烈建议：**各至多 5 个**，超了服务端拒绝；前者 ASCII 与长度字符集都有限制，后者必须逐字命中官方分类表 |
| `authors` | 已废弃，只为兼容保留；新包不填 |

防误发开关：`package.publish = false` 禁止一切发布；不发布的包打开它，发布动作直接失败。不要靠“记得不发”来防误发。

包体积有硬上限（约 10MB 量级，超了服务端拒绝）：发前看构建输出目录下产物的大小。

## 发布范围：白名单语义与 npm 不同但同样要验

- `exclude`/`include` 是 gitignore 风格；一旦写 `include` 即覆盖 `exclude`，要排除再用取反。
- 没写 `include` 时自动跳过版本控制忽略的文件；写了则不应用忽略规则。
- 无论如何一定排除含清单的子包目录与根构建输出，一定包含包自身清单、最小化锁文件与指定许可文件。
- 打包副作用：补丁与替换节从发布的清单里剥离；本地路径依赖必须带版本号（发布时忽略路径）；
  符号链接压平；生成版本控制信息文件（脏树记脏标记，溯源变弱）。
- 核对手段：`cargo package --list` 看完整文件清单；包体积有上限，超了发不出去。

## 预演：两步缺一不可

```sh
cargo publish --dry-run   # 只校验加打包，不上传
cargo package --list      # 核对将要发出去的文件清单
```

预演只做校验与打包：产物在构建输出目录下，解包重编验证默认会跑（脏树、跳过验证各有显式开关，按需用）。**跳过预演是最典型的翻车**：范围写错漏发运行时文件，或带上大资源超体积，或依赖写了仅本地路径、通配符、跨 registry 而被服务端拒绝。

两个开关的风险定语（正式发布禁用，只用于本地验证）：

- 脏树打包允许把未提交代码发出去，版本信息记脏，溯源变弱；
- 跳过验证会跳过“解包重编”与构建脚本改源检查——本地能编不等于解包后能编
  （漏文件、生成代码未进包、构建副作用），发出去即坏包。

锁文件由工具维护、不手改；发包总是带上它（除非明确知道自己在做什么才排除）。

## 发布：超时先查，不要重发

```sh
cargo publish
```

- 默认发公共索引；发私有 registry 加对应参数并先登录一次存好凭据。
- 服务端会再检一次；客户端轮询等索引出现，**可能超时——超时不代表失败，
  上传多半已成功**。先查索引上有没有这个版本：有则按已发布处理（补标签与说明即可），
  无则修掉原因后用**同一版本号**重发，**不要改版本号重试**
  （改号会留下一个永远占位的空号；只有确认要发新内容时才抬号）。
- 版本永不可覆盖：撞号只能往前发新号，旧号已有锁定与缓存，删不掉也盖不掉。
  发新版时建议手写变更记录、打版本标签，复杂项目可用发布自动化工具。

## 认证：可信发布优先，长期 token 次选

| 方式 | 怎么工作 | 前提 |
| --- | --- | --- |
| 可信发布（OIDC） | CI 用短期身份换 30 分钟有效的发布凭据（用完自动吊销） | 已手动发布过一次、操作者为所有者；在 crate 设置页登记仓库、workflow 文件名（逐字一致，可选 environment）；job 声明短时身份签发权限，用官方认证 action 换凭据后发布 |
| API token | 长期有效的密钥 | 在网站建好复制一次（离页即不可再见）；存本地凭据文件或钥匙串，不进仓库不进聊天；CI 用环境变量覆盖；泄漏立即吊销 |

### 可信发布接线步骤（带着用户在浏览器里填）

登记动作只能由所有者在 crate 设置页做，AI 碰不了——但 AI 要把每一项要填什么讲清楚。
主流托管平台填拥有者、仓库名、工作流文件名（逐字一致）与可选 environment；
工作流里发布 job 声明短时身份签发权限，用官方认证 action 换出令牌后以环境变量传给发布命令。
触发器收敛到标签或受保护分支，可配审批环境缩攻击面；另有 staging 地址可先演练。

两种可并存过渡：验通可信发布后删掉旧长期 token。**不要把“能自动发布”误解为账号操作全自动化**：撤销、改权限这类仍走人工。

## 修正：yank 不是删除

- `cargo yank` 只把版本从索引移除、不删代码：新解析不再选用，已有锁文件继续可用，直接下载链接仍有效。
- 正确顺序：**先发兼容修复版，再 yank 坏版**——否则精确 pin 旧版的下游直接报错；
  解 yank 可逆。只在误发、意外破坏兼容、严重不可用时用；安全漏洞优先走安全通告流程。
- 制品里混入凭据：先吊销凭据再发新版；yank 拦不住已锁文件与直接下载的扩散，旧副本收不回。
- 版权、许可、个人信息问题 yank 不够，按制品库政策联系官方处理。
- 删除整包另有严格自助条件（发布时间、下载量、无人依赖三者），不满足需特批；
  不要把 yank 当删除——删掉的名字会被他人占用。

## 私有 registry

在 cargo 配置里声明替代索引地址（稀疏协议按需拉元数据，省时省带宽；否则走完整克隆），
依赖按名称加 registry 标注，登录一次存凭据后用对应参数发布。公共索引不接受依赖外部 registry 的包——要发公共的，先把依赖收敛到公共。
私有凭据放本地凭据文件分表或大写环境变量，不进仓库不进聊天。

## 常见翻车对照

| 现象 | 根因 | 处置 |
| --- | --- | --- |
| 报版本已存在 | 改完没抬 `Cargo.toml` 的号 | 抬号发新版 |
| 发布超时 | 索引轮询超时（上传多半已成功） | 先查有无该版，有则按已发布处理，无则修因同号重发 |
| 服务端拒绝 | 元数据缺字段、范围带错文件、依赖写法不合规 | 按缺字段、清单、依赖三处逐项修 |
| 发完用户装到旧版 | 依赖要求默认排除预发布，或下限声明挡人 | 检查预发布写法与兼容下限 |
| 可信发布换不到令牌 | workflow 文件名与登记不一致、缺短时身份权限、未先手动发过一次、操作者非所有者 | 逐字对文件名、补权限、补首次手动发布、查所有者 |
| yank 后下游全断 | 先 yank 后补兼容版 | 先发兼容修复版再 yank，可逆解 yank |

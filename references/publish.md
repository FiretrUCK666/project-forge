# 发布

## 何时读本文件

要配发布通道、要发第一个版本、要发新版，或者发布失败要排查时读。只在自己用、或明确不发布的
项目上，不读。

## 先回答四个问题

按顺序，前一个没答完不答下一个：

1. **该发吗？** 见「一、该不该发」。**「不发布」是正常结果，不是失败。**
2. **发到哪？** 看生态，见「二、发到哪、版本号从哪来」。
3. **版本号从哪来？** 只能有一个权威来源（清单字段）。见「二、发到哪、版本号从哪来」。
4. **发出去的到底是什么？** 先看清文件清单，再按发布键。见「六、怎么安全地发」。

四个问题里前三个是**判断**，由人做；自动化只覆盖第四个动作。期望「自动化帮我判断该发哪个版本」，
得到的是一个会发错版本的系统。

## 一、该不该发

**这一节回答两个问题，顺序不能反：先「要不要发」，再「能不能发」。**

### 先问：有人让你发吗

**没有明确要求，就不发。** 发版是**不可撤回的动作**——标签推上去之后别人会拉、会装、会依赖，
而它收不回来。所以它和「改个文件推一下」不是同一类事：

| 你看到的 | 该做什么 |
| --- | --- |
| 用户说「改好了推一下」 | 拉分支 → 跑门禁 → 提交 → 推自己的分支 → 开 PR。**完** |
| 用户说「发版」「发个版本」「发布」 | 走 `docs/release-notes/`（或 `CHANGELOG.md`）顺序：先写说明、提交推送、再打标签 |
| 攒了好几个改动、版本号看着该抬了 | **什么都不做**。攒得多不是发版理由 |
| 上一个标签隔了很久 | **什么都不做**。时间间隔不是发版理由 |
| 用户说「随便你」「你觉得该发就发」 | 先把「发什么版本号、说明写什么、影响谁」讲清楚，等人点头 |

**分档的判据是能不能撤回，不是「是不是对外」。** 推自己的分支、开 PR、改 PR 都能撤回
（删分支、关 PR），属于日常，不必等人点头；合并进默认分支由独立审查通过后审查者直接收尾
（涉及弱化门禁须人点头）；而**发版**、把私有仓库转公开、改写历史撤不回来，这几件才停下让人拍板。

**「该发版了」这个判断不属于执行者。** 理由很实在：什么时候把一个版本交给使用者，
取决于发布节奏、兼容承诺、下游有没有在等——这些只有项目所有者知道。

### 再问：这个形态能发吗

判据不是「这是个什么项目」，是**别人能不能把它装走用起来**：

| 形态 | 能发吗 | 发到哪 |
| --- | --- | --- |
| 库 / 包（有导出接口） | 能 | 对应生态的制品库 |
| 命令行工具 | 能 | 制品库，或单文件发布页 |
| 服务 / 应用 | **不发制品库** | 部署是另一条路，不在本 skill 范围 |
| 纯文档 | **不发** | 仓库本身就是产物 |
| 能力目录 | **不发制品库** | 克隆或发布页压缩包分发 |
| 插件 | 能 | 宿主市场 / 发布页附件 |
| Go 模块 | 「发布」= 推标签 | **没有上传动作** |

清单里写了 `"private": true` 的，一律不发。那是防误发开关，不是待办。

### 发版策略 5 选 1 菜单（建制与重入决策）

具备可发布形态且配置发布通道前，由用户从以下 5 种策略中拍板（不默认强推自动化发版）：

| 策略 | 适用项目 | 默认鉴权与配置要点 |
| --- | --- | --- |
| 1. **不配置发版流水线** | 内部工具、实验项目或仅自用仓库 | 不生成发布工作流，在 `AGENTS.md`「## 取舍」记 `no-release` |
| 2. **沿用已有工具** | 已含 `.changeset/`、`release-please-config.json`、`.releaserc*`、`.goreleaser*` | 严格 `preserve` 原有工具链，只在 `AGENTS.md` 对齐该工具实际流转 |
| 3. **纯手动发版** | 低频发版仓库 | 按需人工执行 `gh release create`（仍先提交推送发布说明） |
| 4. **Tag 自动发布页（默认零额外 Secret 路线）** | 大多数需要标准 GitHub Release 页面的项目 | 复制 `templates/ci-release.yml`：默认用工作流内置 `GITHUB_TOKEN` + `permissions: contents: write`，**无需额外建个人密钥** |
| 5. **联动下游或推送制品库（按需增强路线）** | 须连锁触发下游 CI、回写受保护分支或上传 npm/PyPI/crates.io | 按下方「`RELEASE_TOKEN` 与 OIDC 接线」配置最小权限 Fine-grained PAT 或各生态 Trusted Publishing（OIDC） |

## 二、发到哪、版本号从哪来

| 生态 | 制品库 | 版本号的权威来源 |
| --- | --- | --- |
| Node / TypeScript | npm（或自建 registry） | `package.json` 的 `version` |
| Python | PyPI | `pyproject.toml` 的 `version`（在 `dynamic` 里时按后端取值） |
| Rust | crates.io | `Cargo.toml` 的 `version` |
| Go | 模块代理（无上传） | git 标签 |
| Java | Maven Central / Gradle Portal | `pom.xml` `<version>` / `build.gradle*` `version` |
| 插件 / 能力目录 | 宿主市场 / 发布页附件 | 清单文件的 `version` / `SKILL.md` `metadata.version` |

**版本号只有一个来源，标签是它的副本。** 两者对不上时，自动化会取到其中一个，而结果看起来像
「发了但没生效」——这类故障最难查，因为它两头都是「成功」。`templates/ci-release.yml` 内置从标签树读取唯一清单做单源版本号对齐门禁，并对 `workflow_dispatch` 空输入 `tag` 立即报错拦截。

## 三、版本号语义

| 档 | 什么时候抬 |
| --- | --- |
| 主版本 | 有不兼容的变化：删了导出、改了参数含义、改了配置格式 |
| 次版本 | 新增能力，向后兼容 |
| 修订版本 | 只修缺陷，不动接口 |

三条不变量：

- **同一个版本号只存一份。** 覆盖式发布会让锁文件失去意义。
- **已发布的版本不可修改也不可删除。** 别人的依赖锁定文件里可能已经写了那个号，删掉会让他们的构建坏掉。
- **预发布版本默认不会被装上。** 它是给愿意尝鲜的人用的，不是给所有人的。
- **支持跨多版本跳跃与自定义目标版本号。** 长周期多轮迭代后允许直接指定跨越多个小/大版本的自定义号（例如 `v1.0.0` 后直接发布 `3.0.0` 或 `v4.0.0`），不假设每次只能单步递进；新号只要未占用且清单权威字段与 Git 标签一致即可。

抬不抬的判据是**使用者会不会察觉**：改了导出、行为、配置格式、最低运行版本 → 抬；只改注释、
内部重构、测试 → 不抬，进下一个版本，不单独占一个号。

## 四、跟随版本与最低支持版本

| 概念 | 例子 | 怎么走 |
| --- | --- | --- |
| **跟随版本** | `devDependencies`、测试与构建用的依赖 | 跟着实际上游版本走，每次升级都跟 |
| **最低支持版本** | `engines`、`requires-python`、`rust-version`、Go 的 `go` 指令、插件的 `minAppVersion` | **只上移、不下移、默认不动** |

最低支持版本只在两种情况上移：真用上了新版独有的 API，或旧版实测失败。**上移必须同时改清单与
README 的环境要求节**——只改一处，另一处就开始说假话。

**不要用「查最新版本」的单值命令判断。** 要取**完整版本列表**从末尾找，并逐个确认目标版本确实存在。

## 五、各生态要点

| 生态 | 必填字段 | 预演命令 | 修正手段 |
| --- | --- | --- | --- |
| **npm** | `name`、`version`、`license`、入口（`exports` / `main` / `bin`） | `npm pack --dry-run` | 删不掉，只能发新版或 `deprecate` |
| **PyPI** | `[build-system]`、`[project]` 的 `name`、`version`、`description`、`readme`、`license`、`requires-python` | `python -m build` + `twine check dist/*` | 只能发新版 |
| **crates.io** | `[package]` 的 `name`、`version`、`edition`、`description`、`license`、`repository` | `cargo package --list` + `cargo publish --dry-run` | `yank` 不是删除 |
| **Go** | `go.mod` 的模块路径与 `go` 指令；v2+ 要带 `/vN` | `go build ./... && go test ./...` | 标签不可变，只能发新版 |

**详细硬判据见 `references/publish-ecosystems.md`**——本表只够判断「大体上要注意什么」，
真正会在发布时拦住你的字段约束、校验规则、烧号规则与 OIDC 细节都在那一份里。

## 六、怎么安全地发

### 发布前 4 项最小核对

1. **清单**：必填字段齐、版本号已抬、白名单对。
2. **预演**：跑过预演命令，把清单**贴进汇报**。判据是运行时必需的文件在；测试夹具、内部脚本、本地配置、凭据**不在**。
3. **认证**：发布凭据只存在于运行环境或仓库 Secrets 中——不进代码库、不进聊天记录。
4. **回读**：发布之后从发布页与制品库读回版本、正文与文件清单，确认与说明一致。

### 跨多版本变更采集与人类可读去噪规范

- **全区间采集防漏**：始终从**上一个可达发布标签到 `HEAD`**（首发无标签时覆盖全量提交史）完整汇总；写说明前先运行 `.agents/skills/dev-govern/` 下的 `govern-audit.mjs release-prep [--from <基线>] [--version <目标号>]`（兼容浅克隆警告并聚合多子包版本），核对最低运行版本升降信号、已实现规格及有变更的公开入口是否遗漏。
- **面向人类读者的严格过滤**：只写最终用户或接入方**明显能感知的变化**，合并同类提交为清晰人话；**严禁倾倒内部重构、测试/夹具增删、CI 微调、文件搬移流水账、内部编号、分支名或晦涩源码符号**。
- **双标题格式与零空节**：`templates/ci-release.yml` 既支持 `docs/release-notes/<标签>.md`，也支持 `CHANGELOG.md` 下的 `## [v1.2.3]` 与 Keep a Changelog 常见的 `## [1.2.3]`；空节整节删去。

### `RELEASE_TOKEN` 配置与可信发布（OIDC）分步接线

1. **何时需要配置 `RELEASE_TOKEN`**：策略 4（仅创建/编辑 GitHub Release 并挂附件）**默认零额外 Secret**，直接使用工作流内置 `GITHUB_TOKEN`（须声明 `permissions: contents: write`）。仅当走策略 5 需要**联动触发下游工作流**或**向受保护分支回写**时，才配置 `RELEASE_TOKEN`：
   - 在 GitHub 账号 Settings -> Developer settings -> Fine-grained tokens 生成令牌，Repository access 仅选当前目标仓库；
   - Permissions 仅勾选最小所需：`Contents: Read and write`（如需触发工作流再加 `Workflows: Read and write`，禁止给全账号通配令牌）；
   - 写入仓库 Settings -> Secrets and variables -> Actions -> `New repository secret`，名称固定为 `RELEASE_TOKEN`；
   - **401/403 刷新排障**：若 Release 工作流报错 401/403（`Bad credentials` / `Resource not accessible`），检查该 Secret 是否已过期或权限不足，立即在原地更新 Secret 后重跑 `workflow_dispatch`（切记填写 `tag` 参数）。
2. **可信发布（OIDC）分步操作**（向 npm / PyPI / crates.io 推送制品库首选，免长期静态 Secret）：
   - 在制品库那一侧登记「哪个仓库的哪个工作流可以替我发」：**仓库名（完整 `<owner>/<repo>` 大小写一致）、工作流文件名（含路径与扩展名）、环境名（`environment:` 字符串）三处逐字对上**；
   - 在发布 job 声明 `permissions: id-token: write`（若用独立环境须配 `environment: <名>`）并关闭不必要缓存；
   - 若从长期静态令牌迁移到 OIDC：① 先在制品库登记信任关系；② 在有效期内完成首次 OIDC 成功发布；③ 收紧或移除旧 Secret 与多余权限。顺序反了会中途断发。

### 预发布版本与未知生态

- `alpha` / `beta` / `rc` 必须**显式指定预发布通道**（如 npm `--tag next`），严禁默认顶掉 `latest`。
- 遇到未覆盖的制品库，现场核查 6 问（入口清单 / 版本号字段 / 发布范围 / 预演命令 / 认证方式 / 修正手段）并按 `references/publish-ecosystems.md` 沉淀卡片。

## 七、失败与中断

| 现象 | 第一动作 |
| --- | --- |
| 401 / 403 无权或未授权 | 若配置了 `RELEASE_TOKEN`，立即核查是否过期并刷新 Secret；OIDC 则逐字重核制品库登记项，不要盲目重试 |
| 版本已存在 | 换一个号；该号已被占用，重试永远失败 |
| 包名被占 | 换名，或改发到自己的命名空间 |
| 字段非法 | 对照该生态的必填字段清单逐条核，报错通常只点出第一个 |
| 超时无响应 | **先回读查有没有发出去**，再决定要不要重发 |

| 中断场景 | 怎么做 |
| --- | --- |
| 收录与扫描延迟 | 等，不要盲目重发 |
| Monorepo 多包部分失败 | **逐包回读**，只补发没成功的那些 |
| 制品里混进了凭据 | **第一步去平台吊销那个凭据**，再发一个补丁版 |

## 八、发布后的修正路径

| 情况 | 能做什么 |
| --- | --- |
| 说明写错了 | 改发布页正文，制品不受影响 |
| 代码有问题 | 发一个新的修订版，**不改已发布的版本** |
| 发错了包名 | 发一个新包，把旧包标记为弃用 |
| 想让某版不被选中 | Rust 用 `yank`；npm 用 `deprecate`；Go 用 `retract` |

## 九、汇报纪律

发布完成**只报版本号与去哪看**，不复述流程细节。失败时报三件：卡在哪一步、报错原话、下一步建议。

## 事实来源

本文件涉及的外部事实会随平台/宿主版本变化，动手前查官方文档，本文件写的是判定流程而不是字段快照。

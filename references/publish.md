# 发布总纲

## 何时读本文件

本文件是**发布决策的总纲**，跨技术栈通用。凡任务涉及「把项目交出去」，都读本文全文：

- 用户说「发版」「发出去」「发布这个项目」「让别人也能装」；
- 要判断一次改动该不该抬版本号；
- 要判断最低支持版本（兼容性下限）要不要跟着上游一起升；
- 要配置或排查自动发布通道、凭据与发布前检查；
- 发布已经出错，要找修正路径。

本文只管**决策与通用规则**。某一个具体制品库的命令、字段、场景化接入，见文末
「与其他文件的关系」指向的专章。**判断与执行分开**：读完本文应先能回答「发不发、发到哪、
发什么号」，再去查那个生态的具体操作。

## 先回答四个问题

**总原则：发布不是一个动作，是一个决策链。**

这条链有四问，必须按顺序回答；前一问的答案决定了后一问还成不成立。

| 顺序 | 问题 | 一句话判据 | 答错的代价 |
| --- | --- | --- | --- |
| 1 | 能不能发？ | 有没有一个「别人可以拿去用」的边界 | 给本就该自用的项目套上长期维护义务 |
| 2 | 该发到哪？ | 目标消费者在哪个生态 | 发到了没有消费者的地方，等于没发 |
| 3 | 版本怎么走？ | 这次改动使用者会不会看到 | 使用者收不到更新，或收到无意义的更新 |
| 4 | 怎么安全地发？ | 凭据从哪来、谁能代表账号发布 | 凭据泄露、发到错误身份、污染版本号 |

**跳过前三问、直接执行第四问，是发布事故的主要来源。** 因为第四问是整条链上唯一产生
不可逆副作用的动作：一旦上传或推送，版本号就被占用、制品就公开可下载。前三问都是纯推理，
成本极低，省掉它们的代价却要发布之后来承担。**先想清楚，再动手。**

下面各节按这四问展开：第 3、4 节回答前两问，第 5、6、7 节回答第三问，
第 8、9 节回答第四问。

## 能不能发：可分发形态

**判据：项目里有没有一个「别人可以拿去用」的边界。**

边界的含义是：存在一样东西，能被与本项目无关的人在**不了解你的内部约定**的前提下拿走
并使用。有边界 → 可发；没有边界 → 不可发。

可分发形态的典型样子（不限于此）：

| 形态 | 别人拿去做什么 | 边界是什么 |
| --- | --- | --- |
| 可被依赖的库 | 在自己的代码里调用 | 公开的接口 |
| 可执行的工具 | 在自己的环境里运行 | 命令行契约 |
| 可安装的扩展 / 插件 | 装进宿主程序里启用 | 宿主约定的接入点 |
| 可被引用的数据集 / 文档包 | 在自己的材料里引用 | 稳定的标识与版本 |

反例（这些**通常不该发布**）：

- **纯应用 / 服务**：别人是来用你的服务，不是来装你的包。它的交付物是运行中的服务，
  需要操心的是部署与运维，而不是制品库。
- **私有脚本集合**：内容与本机环境、私人路径、私人凭据强绑定，拿出去就跑不起来。
- **只有作者知道怎么跑的研究目录**：没有可复现的入口，别人拿到也复现不了。

**结论：「不发布」是正常且常见的结果，不是失败。** 判断为不可发时说清理由即可收工；
不要为了「有一个发布流程」而硬套一层分发外壳——那是需要长期维护却没人受益的负担。

**从仓库源获取与从制品库获取是两条不同的分发路径**，不要混为一谈：

| | 从仓库源获取 | 从制品库获取 |
| --- | --- | --- |
| 方式 | 克隆仓库，或直接从仓库地址安装 | 用包管理器从制品库安装 |
| 前提 | 仓库可读即可 | 必须先把版本发到制品库 |
| 更新感知 | 比提交 | 比版本号 |
| 适用 | 想跟最新代码、参与开发的人 | 想要稳定版本、不想跟源码的人 |

所以**「没有发布」不等于「别人拿不到」**：只要你推送了，从仓库源获取的人就已经拿到了。
「这个项目还没发过版」本身不是必须发布的理由。

## 该发到哪：生态对照

**判据：目标消费者在哪个生态，就发到那个生态的制品库。** 先确定「谁是使用者」，
再选制品库；不是先挑一个制品库，再看它能装什么。

| 语言 / 生态 | 默认的公共制品库 | 发布动作的本质 |
| --- | --- | --- |
| Python | 官方包索引（PyPI） | 上传一个制品（源码包或轮子） |
| JavaScript / TypeScript | npm 公共制品库 | 上传一个包 |
| Rust | crates.io | 上传一个 crate 制品 |
| Go | **无中心上传动作**，由模块代理按版本标签取 | **打一个版本标签**，不需要上传 |
| Java / JVM | Maven Central 一类中央仓库 | 上传构件（含坐标与元数据） |
| Ruby | RubyGems | 上传一个 gem |
| PHP | Packagist | 登记包，由版本控制标签驱动 |
| .NET | NuGet | 上传一个包 |
| 无语言归属的通用资产 | 随形态而定：制品库的通用仓库、发布页附件、容器镜像仓库 | 上传一个带版本的制品 |

**特别提醒：不要强行把所有生态套进「上传一个包」的模型。** 有的生态没有中心化的上传
动作，它的「发布」就是**在版本控制里打一个版本标签**，由生态的模块代理或索引去取；
也有的生态以版本控制标签为唯一真相，制品库页面只是它的镜像。判断方法很简单：
**问「发布这个动作最终改变了什么」**——是某个库里多了一个制品，还是版本控制里多了一个
标签。两者的自动化方式、可撤销性、以及「发错了怎么办」都不相同。

**跨生态分发**（例如把非 JavaScript 的东西发到 npm 一类生态）技术上常常可行，
但**只有在你确实想触达那个生态的使用者时才有意义**。若使用者本来就在原生态里，
跨发只会制造一个需要同步维护的第二份制品与第二套版本号。

各生态对「三档版本语义对应哪一段数字」「版本标签叫什么形状」有自己的约定，
**从该生态的惯例与项目的清单文件里确认**，不要跨生态套用。

## 版本号语义

版本号是**给使用者的承诺**，不是内部流水账。它只回答一个问题：
**从上一个版本到这个版本，使用者要付出什么代价。**

### 三档语义

| 档 | 判据：消费者会不会被迫改自己的代码 | 为什么要如实标注 |
| --- | --- | --- |
| 破坏性变更 | 会——不改就用不了，或行为变了 | 不标出来，使用者的构建会在某次自动升级后突然坏掉 |
| 新增 | 不会，但多了能力 | 旧的用法原样有效，使用者可以选择用新能力 |
| 修补 | 都不会——行为与接口对使用者完全等价 | 修缺陷、内部调整 |

**判据只有一条：消费者会不会被迫改自己的代码。** 不要用「改了多少行」「花了多久」来衡量：
改动规模与版本档位无关——一行删除可能砸掉别人的调用，几百行重构可能对使用者完全透明。

### 三条不变量

- **单调递增，永不复用**：同一个版本号不能发第二次。用掉的号是历史，不是可回收资源。
- **已发布的版本通常不可删除**，只能发新版本修正。原因不是平台苛刻：**别人的依赖锁定
  文件里可能已经写了这个号**，删掉会让他们的构建在毫无改动的情况下无故坏掉。
- **版本号的唯一权威来源是项目清单文件里的那一个字段**。不要在文档、脚本、代码里各写
  一份——多写一处就多一处会漂移的副本，而版本号一旦漂移，使用者拿到的判断依据就是错的。
  打标签时**标签名要与该字段一致**：形状按生态惯例，数值必须同源。

## 什么时候该抬版本号

**判据：使用者会不会因此看到变化。** 看得到 → 抬；看不到 → 不抬。

| 要抬 | 不抬 |
| --- | --- |
| 行为、界面、交互、报错文案 | 重构 |
| **随包发出去的说明文档**（会展示在制品库页面上，也随包分发） | **不进包的内部文档**（只给协作者、给 AI 看的那些） |
| 面向使用者的兼容性声明变化 | 测试、构建脚本 |

### 最容易判错的一行：两种「文档」

同样叫「文档」，它们的读者完全不同：

- **随包分发的那种是产品的表面**：使用者按它判断这个包能不能用、怎么装、怎么配、
  有什么限制。改一个字都算用户可见——因为它本身就是使用者看到的产品说明。
- **只存在于仓库里的内部文档**：使用者根本接触不到，它服务的是协作者与 AI。

所以前者必须抬版本，否则会出现**「仓库里的说明已经改了，制品库页面上还是旧的」**：
使用者照着旧说明装，装出问题还找不到原因。后者不抬，因为它不进包，制品库上本来就没有它。

### 反过来也要提醒：看不到的改动硬抬，是噪音

用户看不到的改动（重构、测试、构建脚本）如果也抬版本，会在制品库上多出一个**内容与
上一版完全相同的版本**。使用者收到更新提示、下载安装，然后发现没有任何变化——
几次之后就不再相信更新提示了。**版本号的信用，是靠「每次跳动都对应真实变化」积累的。**

### 三个地方各自怎么感知更新

| 渠道 | 靠什么判断「有更新」 |
| --- | --- |
| 从制品库安装的人 | 比版本号 |
| 从仓库源获取的人 | 比提交 |
| 版本节点 / 发布说明 | 看标签与说明——想知道「这版改了什么」的人读它 |

**结论：抬版本号主要是给制品库渠道用的。** 仓库渠道在你推送的瞬间就已经拿到新代码，
它不需要版本号来通知——这也解释了为什么「没抬版本」不等于「别人拿不到」。

## 跟随版本与最低支持版本（两个不同的概念）

这是极易混淆、后果严重的一节。两者都是「版本」，都写在清单文件附近，
但回答的是完全不同的问题。

| | 跟随版本 | 最低支持版本 |
| --- | --- | --- |
| 是什么 | 构建与测试所依赖的宿主 / 依赖版本 | 使用者的环境还能不能跑起来的最低下限 |
| 写在哪 | 开发依赖声明 | 兼容性声明 + 面向使用者的说明文档 |
| 何时变 | 每次上游升级都跟上去 | **只在真不兼容时上移** |
| 谁看得到 | 只有开发者 | 使用者 |

### 关键规则

- **最低支持版本只上移、不下移，且默认不动。** 下移等于向使用者承诺一个你没有验证过的
  环境；默认不动，则是因为**升级上游并不会自动抬高下限**。
- **升级上游之后，项目在新版上照常工作、甚至继续在新版上开发，恰恰说明旧的下限依然
  成立。** 这时**不要动它，也不要问要不要改成最新版**：「我能跑在新版上」与「我要求新版」
  是两件事——前者是开发者的便利，后者是使用者的门槛，抬高门槛只会挡住本可使用的人。
- **只有两种情况才上移**：
  1. 采用了只有新版才有的能力——旧版没有这个符号或接口，加载即失败；
  2. 在旧版上**实测**失败。

  除此之外的理由（「新版更好」「保持一致」「反正没人用旧版」）都不成立。
- **上移时两处必须一起改**：兼容性声明里的下限，与面向使用者的说明文档里的那一行。
  它们是**同一事实的两种表达**，漏改一处就会出现「文档说支持、装上去却报错」的错配，
  而这种错配使用者无法自行诊断。
- 面向使用者的那行**必须写具体版本号**：使用者需要一个能拿来对照自己环境的数字。
  「最新版」「较新版本」这类模糊说法等于没写。

## 怎么安全地发

按优先级排序：能用自动发布通道就用；不能再用长期令牌；人工验证码只作为最后的交互式兜底。

| 方式 | 机制 | 前提 | 定位 |
| --- | --- | --- | --- |
| 基于身份的自动发布（OIDC / 可信发布） | 构建平台在运行时**签发一次性凭据**，用完即废 | 在制品库平台上登记「哪个仓库的哪个工作流可以代表我发布」 | 首选 |
| 长期令牌 | 一个长期有效的密钥 | 必须只放在**环境变量或平台的机密存储**里 | 次选 |
| 人工验证码（双因素） | 账号持有人在自己的终端输入一次性验证码 | 需要人在场 | 交互式兜底 |

**长期令牌绝不进版本库**：不写进文件、不写进配置、不写进提交信息，也不贴进对话。
一旦进了版本库，它就成了历史的一部分，删掉某个提交并不能让它失效——
**正确的处置是立即在平台上吊销并重新签发**。

**人工验证码属于交互式操作**，需要账号持有人在自己的终端执行。自动化流程**不该依赖
它**：依赖它的「自动化」在无人值守时一定会断，而断的那一刻通常正是你在赶一个紧急修复。

### 能力边界：自动发布通常只覆盖「发布」这一个动作

这一点最容易被误解。自动发布通道打通之后，**能自动做的只有「发布」**；下面这些通常
仍然需要人工验证码或网页操作：

- 撤销发布、删除或废弃某个版本；
- 修改包的权限、协作者、可见性；
- 修改账号设置，或调整发布者登记本身。

所以**不要把「已经能自动发布」误解为「所有账号操作都自动化了」**。规划回滚与应急流程时，
要按「这些操作需要人在场」来设计，否则真出事时会发现退路比预想的窄。

### 发布前的最后一道检查：看清要发出去的到底是什么

大多数生态都提供**预演手段**：只打包不发布，并列出将要包含的文件。发布前跑一次，
**逐个确认清单里的每一项都是你打算公开的东西**。

要专门提醒一条：**发布范围声明对「从仓库源安装」的场景同样生效**。也就是说，
**仓库里存在某个文件，不代表装到使用者机器上会有它**——范围声明会把它排除掉；
反过来，范围声明之外的东西也不会因为「它在仓库里」就自动跟着走。这一条同时解释了两类
事故：使用者抱怨「装了却没有那个文件」，以及你把不该公开的东西发上了制品库。

### 发布后的确认

发布动作返回成功之后，**去制品库上确认新版本确实出现了**，并核对它的元信息
（版本号、说明、文件清单）与你预期的一致。

注意一个正常现象：**有些制品库在发布后会先做一轮安全扫描，短时间内查询可能返回
「不存在」，这属于正常延迟，不是发布失败。** 遇到这种情况先等一会儿再查，不要立刻重发——
重发通常会因为版本号已被占用而失败，或者更糟：让你误以为需要换一个号。

## 发布后的修正路径

发布不可逆，但**可以往前修正**。总原则是：**只用新版本修，不回改历史。**

| 情况 | 可行手段 | 限制 |
| --- | --- | --- |
| 刚发布就发现问题 | 尽快发一个修正版本 | 版本号必须继续往前；不要试图覆盖已发布的号 |
| 某个版本有严重缺陷 | 把那个版本标记为「已废弃」，让使用者看到警告 | **不要删除**：删掉会让已经锁定了这个号的使用者构建失败 |
| 版本号发错了（发成了不该发的号） | 只能继续往前发 | 那个号已被占用，无法回收；后续版本按正确语义继续递增 |
| 制品内容里混入了不该有的文件 | 发新版本，并从发布范围里排除它 | 若混入的是凭据，**先吊销凭据**再发新版本；旧版本的下载记录无法收回 |

两条通用纪律：

- **优先「告知」而不是「抹除」**：废弃标记让使用者知道该升级了，删除则让他们无从判断。
- **撤不回来的东西按撤不回来处理**：已经公开的凭据一律视为泄露，吊销并重发是一条独立于
  版本号的动作，不要指望靠发一个新版本把它盖掉。

## 汇报纪律

发布完成后向用户汇报，**只报版本号**——用户在已安装列表或制品库页面上看的就是这个号，
过程的复述对他们没有信息量。

同时说明**「用户能在哪里看到这次更新」**：包管理器的更新提示、制品库的版本页面、
仓库的版本节点或发布说明。用户需要知道去哪里确认，而不是听一遍过程。

若本次发布伴随使用者可见的变化，用一句话说清变化是什么；不要把提交记录抄一遍。

# 发布

## 何时读本文件

要配发布通道、要发第一个版本、要发新版，或者发布失败要排查。

---

## 先回答四个问题

按顺序，前一个没答完不答下一个：

1. **该发吗？** 纯文档、明确私有的、内部工具、能力目录——都不经过制品库。
   **「不发布」是正常结果，不是失败。**
2. **发到哪？** 看生态。
3. **版本号从哪来？** 只能有一个权威来源。
4. **发出去的到底是什么？** 先看清文件清单，再按发布键。

---

## 一、该不该发

判据不是「这是个什么项目」，是**别人能不能把它装走用起来**：

| 形态 | 能发吗 | 发到哪 |
| --- | --- | --- |
| 库 / 包（有导出接口） | 能 | 对应生态的制品库 |
| 命令行工具 | 能 | 制品库，或单文件发布页 |
| 服务 / 应用 | **不发制品库** | 部署是另一条路，不在本 skill 范围 |
| 纯文档 | **不发** | 仓库本身就是产物 |
| 能力目录 | **不发制品库** | 克隆或发布页压缩包分发 |
| 插件 | 能 | 宿主市场 / 发布页附件 |
| Go 模块 | 「发布」= 打标签 | 没有上传动作 |

最后一类最容易搞错：Go 的发布就是推一个符合语义化版本的标签，模块代理自己去抓。
**不要再去找上传命令**——没有那个命令。

---

## 二、发到哪、版本号从哪来

| 生态 | 制品库 | 版本号的权威来源 |
| --- | --- | --- |
| Node / TypeScript | npm（或 GitHub Packages） | `package.json` 的 `version` |
| Python | PyPI | `pyproject.toml` 的 `version`（或动态版本的来源） |
| Rust | crates.io | `Cargo.toml` 的 `version` |
| Go | 模块代理（无上传） | git 标签 |
| 插件 | 宿主市场 / 发布页附件 | 清单文件的 `version` |

**版本号只有一个来源。** 标签是它的副本，不是第二个来源。两者对不上时，自动化会取到其中
一个，而结果看起来像「发了但没生效」。

---

## 三、版本号语义

| 档 | 什么时候抬 |
| --- | --- |
| 主版本 | 有不兼容的变化：删了导出、改了参数含义、改了配置格式 |
| 次版本 | 新增能力，向后兼容 |
| 修订版本 | 只修缺陷，不动接口 |

三条不变量：同一个版本号只能存在一份；已发布的版本不可修改，只能向前；预发布版本默认不会
被装上。

### 什么时候该抬

**判据是「使用者会不会察觉」**，不是「改了几行代码」：

- 改了导出、行为、配置格式、最低运行版本 → **抬**；
- 只改注释、内部重构、测试、与使用者无关的实现细节 → **不抬**（进下一个版本，
  不单独占一个号）。

最容易判错的一行：**文档算不算变化？** 分两种——README 里讲的安装方式、命令参数变了，
那是使用者能察觉的，抬修订版；只改错字或排版的，不抬。判断标准是「照着旧文档做会不会失败」。

**反过来也要提醒**：看不到的改动硬抬版本号是噪音。使用者每看到一个新版就要判断一次
「要不要升」，而升级是要付成本的。为一个内部重构发一个版本，是把你的整理成本转嫁给他们。

## 四、各生态要点

| 生态 | 必填字段 | 预演 | 修正 |
| --- | --- | --- | --- |
| **npm** | `name`、`version`、`license`、入口（`exports` / `main` / `bin`） | `npm pack --dry-run` | 删不掉，只能发新版 |
| **PyPI** | `[build-system]`、`[project]` 下 `name`、`version`、`description`、`readme`、`license`、`requires-python` | `python -m build` + `twine check dist/*` | 同上 |
| **crates.io** | `[package]` 下 `name`、`version`、`edition`、`description`、`license`、`repository` | `cargo package --list` + `cargo publish --dry-run` | `yank` 不是删除 |
| **Go** | `go.mod` 的模块路径与 `go` 指令；v2+ 要带 `/vN` | `go build ./... && go test ./...` | 标签不可变，只能发新版 |

三条通用纪律：

- **npm 要写 `files` 白名单**：不写的话默认会把一堆没用的东西打包进去。
- **不打算发布的 npm 项目写 `"private": true`**：发布动作会直接失败，这是防误发开关。
- **crates.io 的 `keywords` / `categories` 有数量上限**（以官方文档为准）。

## 五、怎么安全地发

### 能力边界：自动化只覆盖「发布」这一个动作

抬版本号、写发布说明、判断该不该发——这三件是**判断**，由人（或按本文件的判据）做。
自动化只负责把已经决定好的东西投递出去。期望「自动化帮我判断该发哪个版本」，
得到的是一个会发错版本的系统。

### 发布前最后一道检查

跑一次预演，把清单**贴进汇报**。判据：运行时必需的文件在（入口、编译产物、类型声明、
README、LICENSE）；测试夹具、内部脚本、本地配置、凭据**不在**；文件数与预期一致
（差得多个数就说明白名单没写对）。

### 可信发布接线

三个生态做法相近：在制品库那一侧登记「哪个仓库的哪个工作流可以替我发」；工作流里给发布
job 加 `id-token: write`；**仓库名、工作流文件名、环境名这三处要逐字对上**。

第三点是绝大多数失败的原因，而报错通常只说「未授权」。

## 六、失败与中断

| 现象 | 第一动作 |
| --- | --- |
| 无权 / 未授权 | **重核制品库那一侧的登记**，不要重试 |
| 版本已存在 | 换一个号；该号已被占用，重试永远失败 |
| 包名被占 | 换名，或改发到自己的命名空间 |
| 字段非法 | 对照该生态的必填字段清单逐条核 |
| 超时无响应 | **先查有没有发出去**（回读），再决定要不要重发 |

最后一条最容易出事：超时不等于失败。急着重发会得到「版本已存在」，而这时真正的问题是
「它其实发成功了，只是我没看见」。

---

## 七、发布后的修正路径

| 情况 | 能做什么 |
| --- | --- |
| 说明写错了 | 改发布页正文（制品库不受影响） |
| 代码有问题 | 发一个新的修订版，**不要试图改已发布的版本** |
| 发错了包名 | 发一个新包，把旧包标记为弃用 |
| 想让某版不被选中 | Rust 用 `yank`；其他生态各有弃用机制 |

**没有「删掉重发」这条路。** 制品库的不可变性是整个生态的信任基础——如果已发布的包能被
换掉，锁文件就没有意义了。

## 九、汇报纪律

发布完成后**只报版本号与去哪看**，不要复述流程细节。失败时报三件：卡在哪一步、
报错原话、下一步建议。

## 事实来源

本文件涉及的外部易变事实：各制品库的必填字段、数量上限、认证方式的名字与配置路径。
它们会随平台改版变化。**动手前若拿不准，查官方文档对应那一节**；本文件写的是「上次核对时
的样子」，不是永久保证。

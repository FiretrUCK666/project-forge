# 发布

## 何时读本文件

要配发布通道、要发第一个版本、要发新版，或者发布失败要排查时读。只在自己用、或明确不发布的
项目上，不读。

## 先回答四个问题

按顺序，前一个没答完不答下一个：

1. **该发吗？** 见「一、该不该发」。**「不发布」是正常结果，不是失败。**
2. **发到哪？** 看生态，见「二、发到哪、版本号从哪来」。
3. **版本号从哪来？** 只能有一个权威来源（清单字段）。见「二、发到哪、版本号从哪来」。
4. **发出去的到底是什么？** 先看清文件清单，再按发布键。见「六、怎么安全地发」。

四个问题里前三个是**判断**，由人做；自动化只覆盖第四个动作。期望「自动化帮我判断该发哪个版本」，
得到的是一个会发错版本的系统。

## 一、该不该发

**这一节回答两个问题，顺序不能反：先「要不要发」，再「能不能发」。**

### 先问：有人让你发吗

**没有明确要求，就不发。** 发版是**不可撤回的动作**——标签推上去之后别人会拉、会装、会依赖，
而它收不回来。所以它和「改个文件推一下」不是同一类事：

| 你看到的 | 该做什么 |
| --- | --- |
| 用户说「改好了推一下」 | 拉分支 → 跑门禁 → 提交 → 推自己的分支 → 开 PR。**完** |
| 用户说「发版」「发个版本」「发布」 | 走 `docs/release-notes/` 的经验：先写说明、提交推送、再打标签 |
| 攒了好几个改动、版本号看着该抬了 | **什么都不做**。攒得多不是发版理由 |
| 上一个标签隔了很久 | **什么都不做**。时间间隔不是发版理由 |
| 用户说「随便你」「你觉得该发就发」 | 先把「发什么版本号、说明写什么、影响谁」讲清楚，等人点头 |

**分档的判据是能不能撤回，不是「是不是对外」。** 推自己的分支、开 PR、改 PR 都能撤回
（删分支、关 PR），属于日常，不必等人点头；合并进默认分支由独立审查通过后审查者直接收尾
（涉及弱化门禁须人点头）；而**发版**、把私有仓库转公开、改写历史撤不回来，这几件才停下让人拍板。

**「该发版了」这个判断不属于执行者。** 理由很实在：什么时候把一个版本交给使用者，
取决于发布节奏、兼容承诺、下游有没有在等——这些只有项目所有者知道。

### 再问：这个形态能发吗

判据不是「这是个什么项目」，是**别人能不能把它装走用起来**：

| 形态 | 能发吗 | 发到哪 |
| --- | --- | --- |
| 库 / 包（有导出接口） | 能 | 对应生态的制品库 |
| 命令行工具 | 能 | 制品库，或单文件发布页 |
| 服务 / 应用 | **不发制品库** | 部署是另一条路，不在本 skill 范围 |
| 纯文档 | **不发** | 仓库本身就是产物 |
| 能力目录 | **不发制品库** | 克隆或发布页压缩包分发 |
| 插件 | 能 | 宿主市场 / 发布页附件 |
| Go 模块 | 「发布」= 推标签 | **没有上传动作** |

Go 那一行最容易搞错：推一个符合语义化版本的标签，模块代理自己来抓。**不要去找上传命令**
——没有那个命令。

清单里写了 `"private": true` 的，一律不发。那是防误发开关，不是待办。

## 二、发到哪、版本号从哪来

| 生态 | 制品库 | 版本号的权威来源 |
| --- | --- | --- |
| Node / TypeScript | npm（或自建 registry） | `package.json` 的 `version` |
| Python | PyPI | `pyproject.toml` 的 `version`（在 `dynamic` 里时按后端取值） |
| Rust | crates.io | `Cargo.toml` 的 `version` |
| Go | 模块代理（无上传） | git 标签 |
| 插件 | 宿主市场 / 发布页附件 | 清单文件的 `version` |

**版本号只有一个来源，标签是它的副本。** 两者对不上时，自动化会取到其中一个，而结果看起来像
「发了但没生效」——这类故障最难查，因为它两头都是「成功」。

## 三、版本号语义

| 档 | 什么时候抬 |
| --- | --- |
| 主版本 | 有不兼容的变化：删了导出、改了参数含义、改了配置格式 |
| 次版本 | 新增能力，向后兼容 |
| 修订版本 | 只修缺陷，不动接口 |

三条不变量：

- **同一个版本号只存一份。** 覆盖式发布会让锁文件失去意义。
- **已发布的版本不可修改也不可删除。** 别人的依赖锁定文件里可能已经写了那个号，删掉会让他们的
  构建坏掉——而他们的构建坏掉时，报错指向的是他们自己。
- **预发布版本默认不会被装上。** 它是给愿意尝鲜的人用的，不是给所有人的。
- **支持跨多版本跳跃与自定义目标版本号。** 长周期多轮迭代后允许直接指定跨越多个小/大版本的自定义号（例如 `v1.0.0` 后直接发布 `3.0.0` 或 `v4.0.0`），不假设每次只能单步递进；新号只要未占用且清单权威字段与 Git 标签一致即可。

抬不抬的判据是**使用者会不会察觉**：改了导出、行为、配置格式、最低运行版本 → 抬；只改注释、
内部重构、测试 → 不抬，进下一个版本，不单独占一个号。

**文档算不算变化？分两种。** README 里讲的安装方式、命令参数变了，那是使用者能察觉的，抬修订版；
只改错字或排版，不抬。判断标准是「照着旧文档做会不会失败」。

**反过来也要提醒：看不到的改动硬抬版本号是噪音。** 使用者每看到一个新版就要判断一次「要不要升」，
而升级要付成本。为一个内部重构发一个版本，是把整理成本转嫁给他们。

## 四、跟随版本与最低支持版本

两个概念必须分清，混在一起的后果是「一升级就再也装不上」或「明明没用到新 API 却要求新版」。

| 概念 | 例子 | 怎么走 |
| --- | --- | --- |
| **跟随版本** | `devDependencies`、测试与构建用的依赖 | 跟着实际上游版本走，每次升级都跟 |
| **最低支持版本** | `engines`、`requires-python`、`rust-version`、Go 的 `go` 指令、插件的 `minAppVersion` | **只上移、不下移、默认不动** |

最低支持版本只在两种情况上移：真用上了新版独有的 API，或旧版实测失败。**上移必须同时改清单与
README 的环境要求节**——只改一处，另一处就开始说假话，而读者会照着那份假的做。

**不要用「查最新版本」的单值命令判断。** 发布方给某个版本打的「最新」标记可能停在很旧的版本上
（尤其是长期维护的旧分支）。要取**完整版本列表**从末尾找，并逐个确认目标版本确实存在。

## 五、各生态要点

| 生态 | 必填字段 | 预演命令 | 修正手段 |
| --- | --- | --- | --- |
| **npm** | `name`、`version`、`license`、入口（`exports` / `main` / `bin`） | `npm pack --dry-run` | 删不掉，只能发新版或 `deprecate` |
| **PyPI** | `[build-system]`、`[project]` 的 `name`、`version`、`description`、`readme`、`license`、`requires-python` | `python -m build` + `twine check dist/*` | 只能发新版 |
| **crates.io** | `[package]` 的 `name`、`version`、`edition`、`description`、`license`、`repository` | `cargo package --list` + `cargo publish --dry-run` | `yank` 不是删除 |
| **Go** | `go.mod` 的模块路径与 `go` 指令；v2+ 要带 `/vN` | `go build ./... && go test ./...` | 标签不可变，只能发新版 |

三条通用纪律：npm 写 `files` 白名单（不写会把一堆没用的东西打进去）；不打算发的项目写
`"private": true`；crates.io 的 `keywords` / `categories` 有数量上限。

**详细硬判据见 `references/publish-ecosystems.md`**——本表只够判断「大体上要注意什么」，
真正会在发布时拦住你的字段约束、校验规则、烧号规则都在那一份里。

## 六、怎么安全地发

### 发布前 4 项最小核对

1. **清单**：必填字段齐、版本号已抬、白名单对。
2. **预演**：跑过预演命令，把清单**贴进汇报**。判据是运行时必需的文件在（入口、编译产物、类型
   声明、README、LICENSE）；测试夹具、内部脚本、本地配置、凭据**不在**；文件数与预期一致
   （差得多个数就是白名单没写对）。
3. **认证**：发布凭据在运行环境里，仅此而已——不进仓库、不进聊天、不写进任何文件。
4. **回读**：发布之后从制品库读回版本与文件清单，确认它真的在那儿。

### 跨多版本变更采集与人类可读去噪规范

- **全区间采集防漏**：始终从**上一个可达发布标签到 `HEAD`**（首发无标签时覆盖全量提交史）完整汇总；写说明前先运行 `.agents/skills/dev-govern/` 下的 `govern-audit.mjs release-prep [--from <基线>] [--version <目标号>]`，核对最低运行版本升降信号、已实现规格及有变更的公开入口是否遗漏。
- **面向人类读者的严格过滤**：只写最终用户或接入方**明显能感知的变化**（重点新能力、不兼容变更与升级动作、修掉的可见问题、兼容性下限变化），合并同类提交为清晰人话；**严禁倾倒内部重构、测试/夹具增删、CI 微调、文件搬移流水账、内部编号、分支名或晦涩源码符号**。
- **结构定制与零空节**：可按项目习惯自由增删小节或沿用既有 `CHANGELOG.md`，没有条目的节直接删去，绝不留「无」字空节。

### 可信发布（OIDC）接线纪律

做法一致：在制品库那一侧登记「**哪个仓库的哪个工作流**可以替我发」；工作流里给发布 job 加
`id-token: write`。**仓库名、工作流文件名、环境名这三处要逐字对上。**

| 项 | 填什么 | 填错后果 |
| --- | --- | --- |
| 仓库 | 完整 `<owner>/<repo>`，大小写逐字一致 | 报「未授权」，与「不存在」同一个错误 |
| 工作流文件名 | 含扩展名的文件名，含子目录路径 | 同上：静默不匹配 |
| 环境名（若要求） | 工作流里 `environment:` 的那一个字符串 | 同上；这一条是绝大多数失败的原因 |

三个坑都表现为「未授权」，而错的可能只是其中一个字符串。所以失败时**先逐字重核登记项**，
不要重试——重试一万次也是同一个答案。

**验证 OIDC 线通没通，用一个「版本已占用」的号去发。** 如果报的是「版本已存在」，说明认证已经
过了、请求已经到达制品库；如果报「未授权」，问题还在登记项上。这个手法比读日志快得多。

### 从长期令牌迁到 OIDC 的四步

1. 在制品库登记信任关系（仓库 + 工作流 + 环境）。
2. 在**登记有效期内**完成第一次成功发布，让这条线真的跑通过一次。
3. 收紧权限：删掉多余的写权限，只留发布需要的那几项。
4. 吊销旧的长效令牌。

顺序反了会中途断发：先删令牌再登记，中间那段时间谁也发不出去。

### 预发布版本

`alpha` / `beta` / `rc` 必须**显式指定预发布通道**（npm 一类是 `--tag next`）。**严禁默认顶掉
stable / latest 指针**——那会让所有执行普通安装的人拿到一个未完成的版本，而他们并不知道。

### 未知生态怎么办

遇到本节没有覆盖的制品库，现场核查 6 问：入口清单叫什么 / 版本号写在哪个字段 / 发布范围怎么
声明 / 预演命令是什么 / 认证方式是什么 / 修正手段是什么。答案从那个平台的官方文档里取，不猜。
拿到答案后按 `references/publish-ecosystems.md` 的写法沉淀成一张卡。

## 七、失败与中断

| 现象 | 第一动作 |
| --- | --- |
| 无权 / 未授权 | **逐字重核制品库那一侧的登记**，不要重试 |
| 版本已存在 | 换一个号；该号已被占用，重试永远失败 |
| 包名被占 | 换名，或改发到自己的命名空间 |
| 字段非法 | 对照该生态的必填字段清单逐条核，报错通常只点出第一个 |
| 超时无响应 | **先回读查有没有发出去**，再决定要不要重发 |

超时不等于失败。急着重发会得到「版本已存在」，而这时真正的问题是「它其实成功了，只是我没看见」。

### 发布中断与恢复

| 情况 | 怎么做 |
| --- | --- |
| 收录与扫描延迟（接口说成功，搜索页还搜不到） | 等，不要盲目重发。重发的代价是一个多余的号 |
| Monorepo 多包部分失败 | **逐包回读**，只补发没成功的那些。整批重跑会撞上已成功的那几个 |
| 制品里混进了凭据 | **第一步去平台吊销那个凭据**，再发一个补丁版。换版本号不会让泄露消失 |

## 八、发布后的修正路径

| 情况 | 能做什么 |
| --- | --- |
| 说明写错了 | 改发布页正文，制品不受影响 |
| 代码有问题 | 发一个新的修订版，**不改已发布的版本** |
| 发错了包名 | 发一个新包，把旧包标记为弃用 |
| 想让某版不被选中 | Rust 用 `yank`；npm 用 `deprecate`；其他生态各有弃用机制 |

**没有「删掉重发」这条路。** 制品库的不可变性是整个生态的信任基础——如果已发布的包能被换掉，
锁文件就没有意义了。

## 九、汇报纪律

发布完成**只报版本号与去哪看**，不复述流程细节。失败时报三件：卡在哪一步、报错原话、
下一步建议。

## 事实来源

本文件涉及的外部事实会随平台/宿主版本变化，动手前查官方文档，本文件写的是判定流程而不是字段快照。

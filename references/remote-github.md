# 远端仓库

把本地仓库接到托管平台（以 GitHub 为主），并把与远端相关的配套设施一次配到位：仓库本体、
首次推送、平台元数据、版本节点与发布说明、协作模板、持续集成骨架。本文只写「怎么做、按
什么顺序、依据什么判断」，不写任何具体取值；凡需要具体值的地方，一律说明从哪里现场读。
平台与 shell 均不写死，涉及 shell 差异处会明确标注。

---

## 何时读本文件

出现以下任一情况，必须完整读本文件再动手：

- 项目还没有远端仓库，需要把本地仓库推上托管平台；
- 已有远端，但要补推送、改可见性、改名、换远端地址或调整默认分支；
- 需要建版本节点（tag）、写发布说明（Release），或配仓库描述与主题标签等平台侧元数据；
- 需要新增 Issue 模板、PR 模板、贡献指南入口或持续集成骨架；
- 推送失败、认证失败、Release 更新报「不存在」等远端相关故障需要排查。

只改本地代码、不碰远端时不必读本文件。

## 一、凭据纪律（先读，最容易出事）

平台凭据是本文里唯一「一旦泄露就无法收回」的东西。以下各条无例外。

**来源**：只从当前运行环境读取——环境变量、平台凭据管理器、既有登录态（命令行工具的认证
存储）。取值方式见对应通道的说明，不要为了图快把值抄到别处。**四条禁止**：绝不写入项目里
的任何文件（配置、脚本、文档、示例、测试夹具都不行）；绝不写进版本库（曾经提交过又删除也
不行——历史里的凭据等同于仍处于泄露状态）；绝不写进文档或报告（包括只留前几位的脱敏写法）；
绝不写进脚本源码（脚本应读环境变量，而不是内嵌字面量）。

**不要拼进命令行**：把凭据作为命令行参数会同时进入三处——shell 历史、进程列表、各类日志
与错误上报。正确做法是让它经由环境变量或标准输入进入工具，不出现在参数里。

**万一出现在输出里**：立即停止后续动作；告知用户该凭据已暴露、需在平台吊销并重新签发；
检查是否已落进文件或提交；确认后再用新凭据继续。不要「先做完再处理」。

**提交前扫描**：与版本管理那份文档的提交前检查是同一件事，此处不重复展开，按那份执行。

## 二、通道发现（动手前先探测）

实际环境里不保证装了某个命令行工具，也可能只有助手自带的集成工具，或只有原始 HTTP 接口。
**先探测有哪些通道可用，按下面的优先级顺序尝试，选中一条就沿用它**，并在最终报告里说明
实际用了哪一条。

**「部分可用」是常态，不是异常。** 三种通道的能力并不重合，最常见的组合是「能建仓库
但推不了代码」（有平台接口凭据，但本地推送认证没配），或反过来「能推已有仓库但建不了
新的」。因此探测要**分别回答两个问题**，不要只回答「远端能不能用」：

| 问题 | 决定什么 |
| --- | --- |
| 能**建仓库**吗？（平台侧写权限） | 是否需要先创建远端仓库 |
| 能**推代码**吗？（本地推送认证） | 内容能否送达 |

- 两个都能 → 按流程走完。
- **只有一个能 → 只做那一半，把另一半明确列为「需要你来做」**：写清缺的是平台凭据
  还是推送认证，以及补上之后执行哪一条命令即可继续。**不要因为做不全就整条停下**，
  也不要假装做成了。
- 两个都不能 → 如实报告「本次无法操作远端」。**本地部分（版本管理、文档）照常完成**，
  不要跟着一起停——它们与远端无关。

| 优先级 | 通道 | 何时优先 | 能力边界 |
| --- | --- | --- | --- |
| 1 | 助手自带的平台集成工具（MCP 一类） | 探测到即优先 | 通常覆盖建仓库、改元数据、建 Release、读写文件；能否推代码视实现而定，不能替代版本控制工具的推送能力 |
| 2 | 官方命令行工具 | 已安装**且已登录** | 覆盖最全，推送与仓库管理都有；未登录或凭据失效时失败，先做登录或改走第 3 条 |
| 3 | 直接调用平台 HTTP 接口 | 前两条不可用，或只差某一项能力 | 覆盖平台接口暴露的管理能力（建仓库、元数据、Release）；推代码需另行具备带凭据的远端地址 |

**探测判据**：集成工具看当前会话已注册的工具清单里有无该平台条目，以实际列出的为准，不要
凭记忆假定某个工具一定存在；命令行工具先看是否可执行、再看登录态——**已安装不等于已登录**，
两件事分别确认；HTTP 接口确认有可用凭据来源并确认网络可达，接口路径与请求格式以平台当前
的公开契约或内置文档为准，不要沿用记忆里的旧路径。

**按「要做的事」选通道**：建仓库与改可见性、描述、主题标签，第 1、2、3 条通道都能做；
建 tag 与 Release，第 2、3 条通道都能做；**推代码只有第 2 条通道能直接做**——集成工具能否
推代码视其实现而定，HTTP 接口本身不推代码，需另行具备带凭据的远端地址。

**发现失败要如实报告**。三条通道都不可用时，不要假装成功、不要用占位符凑出一份「已完成」
的报告，也不要擅自改用未经用户同意的其他平台。正确做法：说明探测了哪几条、各自失败在什么
环节（未安装、未登录、无凭据、网络不可达），把剩下的动作整理成用户可自行执行的清单，然后
停下等待指示。

## 三、建仓库之前的确认

### 3.1 可见性：默认私有

**默认新建为私有**。改成公开必须由用户明确点头，且要把「公开意味着什么」说清楚：任何人可
搜索、可克隆、可被第三方索引与抓取；历史里的敏感内容一经公开即等同于泄露，**删除也收不回**
（已被克隆、缓存、镜像或被搜索引擎收录）；许可、凭据、内部地址、个人信息在公开前都要先
清理。用户说「开源」「发出去」不等于授权公开某个具体仓库，需要落到明确的一次确认。

**建之前先探测**，不要上来就建：目标账号或组织下是否**已存在同名仓库**（存在则不要重复
创建，见第十一节幂等要求）；是否已存在一个**空仓库**准备接收这次推送（有则直接推给它，
省掉创建）。探测结果连同下面的清单一起给用户，等确认后再执行：

| 项 | 内容 |
| --- | --- |
| 仓库名 | 规范化后的最终名称，以及它的来源 |
| 可见性 | 私有 / 公开，公开需用户明确点头 |
| 平台与归属 | 建在哪个平台、哪个账号或组织下 |
| 分支 | 将推送哪个分支，以及它是否是默认分支 |
| 内容 | 大致范围：代码、文档、产物、配置；有无需要排除的目录或文件 |
| 地址形式 | HTTPS 或 SSH，以及选用理由 |
| 本次跳过 | 本次不做的动作（不发布、不改可见性、不动已有标签） |
| 署名确认 | 若之前用的是临时署名，此处必须已修正（推送后永久；与 SKILL.md G4 清单第六项是同一项） |

### 3.2 可见性变更（公开一个已存在的私有仓库）

这是**最容易造成不可逆泄露的一步**，比新建公开仓库更危险——因为仓库里已经有历史了。
新建时内容还没推上去，还能先清理再公开；改可见性时，**整个历史会一次性暴露**。

因此改可见性前必须按顺序做完这三件事，一件都不能省：

1. **扫描整段历史，不只是当前版本**。当前工作区干净不等于历史干净：早期提交里可能有
   后来才删掉的凭据、写错提交的内部地址、被强推掩盖过的旧提交、以及已删除分支上仍被
   引用的对象。清理当前文件对历史毫无作用。手段：用 `git rev-list --all` 重扫整段历史，
   命中按版本管理「历史里已有凭据」分层处置。
   - 判据：凡是**曾经提交过**的敏感内容，都要当作已泄露处理（见版本管理那份文档）。
   - 真的在历史里发现了凭据：**先轮换那些凭据**，再考虑公开；只把文件从历史抹掉是不够
     的，因为它已经被至少一个地方（你本地、可能还有别的克隆）读到过。
2. **确认授权是逐次的**。用户之前同意「公开某个仓库」不构成对**这个**仓库的授权，说
   「开源」「发出去」也不等于授权。改之前落到一次针对该仓库的明确确认，并在确认里说明
   第 3 点的后果。
3. **说明不可撤销**。公开之后：任何人都能克隆、平台会保留可达性、第三方可能已经索引
   或缓存。**把它改回私有，已经流出去的内容不会回来**。这句话必须让用户听到，而不是
   我们自己知道就好。

**改回去也救不了**：可见性开关是可逆的，泄露不是。因此这一步的默认答案是「不做」，只有
用户明确要求、且上面三步都走完时才执行。

改完后回读确认可见性确实变了；若平台需要额外操作（例如组织的策略限制、需要管理员批准），
如实报告，**不要假定改成功了**。

**仓库名规范化**：从**项目目录名**推导，但要处理平台不允许的形式，推导后**把最终名称告知
用户**，不要默默改名。规范化只在**平台侧仓库名**上做，本地目录名不必跟着改。

| 要处理的 | 处理方式 |
| --- | --- |
| 空格 | 替换为允许的分隔符（连字符或下划线），不要留空格 |
| 非 ASCII 字符 | 见下方「非 ASCII 目录名」——**不要停在「与用户确认」**，先给一个可用的默认值 |
| 大写字母 | 统一转为小写，避免不同系统与链接解析出的差异 |
| 平台保留字与非法字符 | 去掉或替换，以平台当前的命名规则为准 |
| 前导、尾随、连续分隔符 | 收敛为单个，去掉首尾 |

#### 非 ASCII 目录名

中文、日文这类没有规范转写的名字（`订单对账工具`）落不到「转写」这一步，若规则只写
「无法转写时与用户确认」，执行者每次都会卡在这里——而这是在**命名一个仓库**，不是
不可逆的决定，不值得为它中断流程。

按这个顺序做：

1. **优先用项目自己的标识**。清单文件里声明的名字（`name` 字段一类）通常已经是合法的
   ASCII 标识，而且比目录名更权威——目录名往往是随手起的。
2. 项目也没有声明时，**按语义译成一个简短英文名**（`订单对账工具` → `order-reconciler`），
   并**在汇报里说明这个名字是你起的**，请用户确认或替换。
3. 名字只是**平台侧的仓库名**：本地目录名不必跟着改，用户不接受时改名成本很低
   （平台上改一次 + 更新远端地址）。

**关键是不中断**：给出一个合理的默认值、说明它的来源、请用户事后确认——比停下来等
一个命名决定更符合「先做完再对齐」的节奏。真正的不可逆动作（推送、发布、公开）仍然
必须停在确认上，但**命名不是**。

## 四、首次推送

**先确认本地有提交**：推送的前提是本地存在提交——没有任何提交时先做首次提交（内容范围、
提交信息、署名规则按版本管理那份文档）；已有提交但不完整时按用户意图补提交，不要替用户
决定提交边界。

**远端地址形式：HTTPS 与 SSH**

| | HTTPS | SSH |
| --- | --- | --- |
| 前置条件 | 一次认证，之后由凭据管理器记住 | 需要先生成密钥、把公钥登记到平台 |
| 对新手 | 省事，走一遍登录即可 | 多出密钥生成与登记两步，易卡住 |
| 凭据形态 | 平台令牌（不要用账号口令） | 私钥留在本机，不外发 |
| 常见故障 | 令牌过期或权限范围不足 | 密钥未登记、agent 未加载、权限位不对 |

**默认选 HTTPS**，理由是它把「认证」交给凭据管理器，用户只需完成一次登录，不必理解密钥
体系。已经配好 SSH 的环境直接沿用现状，不必改。选择结果要与用户说明。**不要在文档或脚本
里写死地址形式**：远端地址是现场读出来的事实，随环境而变。

**推送与上游跟踪**：首次推送时**设置上游跟踪**，让之后的推送与拉取不必重复指定远端和分支；
默认分支名称以项目现状为准，不要强行改名。大仓库首次推送慢是正常的：对象多，压缩与上传都
需要时间。**不要因为耗时长就判定失败，更不要中途重试或换方式重推**——并行重推会造成重复
对象与混乱；要观察就看进度输出，不看耗时。

**推送后回读校验**——**不要只看命令退出码**：退出码为 0 只说明命令自己认为完成了，不说明
远端收到了什么。校验方式：读取本地当前提交的标识，再读取远端对应分支的提交标识，两者一致
才算成功。不一致时不要重推了事，先查明远端是否领先（见第十节）。

## 五、仓库元数据

元数据决定「别人能不能找到、一眼能不能看懂」，应当**一次配齐**，配完回读确认。

| 元数据 | 内容 | 判断依据 |
| --- | --- | --- |
| 描述 | 一句话说明这是什么项目 | 面向第一次看到它的人，不要写内部代号与缩写 |
| 主题标签 | 若干关键词 | 见下 |
| 主页 / 文档地址 | 可访问的项目页或文档站 | 仅当确实存在；没有就不填，不要填占位地址 |

**主题标签怎么选**：主题标签有两个作用——被平台的专题页或话题页收录，以及被站内与站外的
搜索发现。选择判据只有三条，按项目自身的事实回答：**项目实际是什么**（语言、框架、形态
——插件、库、应用、工具）；**面向什么生态**（它接进哪个生态、随谁一起被使用）；**解决什么
问题**（领域与用途）。**不要堆砌不相关的热门标签**：蹭热标签带来的错误流量会让真正需要它
的人找不到它，也会让项目看起来不可信；宁少勿滥，每个标签都要能指着项目的某个事实说
「就是这个」。**私有仓库的标签通常不会被公开专题页收录**，这不影响标签在仓库设置里的作用，
但不要向用户暗示「加了标签就会出现在公开话题页上」——那需要仓库本身是公开的。

**回读确认**：描述、标签、主页都要**读回来核对**，确认平台侧真的保存了，而不是只提交了
请求。做完整项目交付时，元数据应与其他设施在同一次流程里配齐。

## 六、版本节点（tag）与发布说明（Release）

这是**两件不同的事**，先分清，再看它们各自显示在平台的什么位置。

**tag——不可变的版本节点**：给某个提交起一个版本名，形成一个不再移动的版本节点。命名用
`v<版本号>` 的形式，**且必须与项目清单文件里的版本号一致**——不一致会让后续自动化对不上，
按清单版本取产物、按 tag 取源码的人会拿到两份不同的东西。它在平台的代码浏览与提交历史里
可见，围绕代码。

**Release——给人看的更新说明**：在某个 tag 之上写一段给人看的说明——这次改了什么、影响谁、
要不要动手。它是用户点开某个版本时在平台发布页面上看到的东西。**Release 依附于 tag；有 tag
不一定有 Release**，所以只打 tag 的项目，发布页面上是空的。

### 6.1 含非 ASCII 正文的硬规则
**正文含非 ASCII 字符时，绝不经 shell 拼接命令行，也绝不由 shell 拼请求体。**

理由是平台无关的：不同 shell 的引用规则与默认编码各不相同，同一条命令在不同系统上行为
不同，中文、日文、重音字符都可能被静默改写。而这类损坏的共性是——**接口仍然返回成功状态
码**。命令成功、退出码为 0、日志干净，只有真的打开页面才看得出内容已变成乱码；任何「先发
了再说」的做法都会把这个错误藏到很久以后。

正确做法：把正文写进一个 **UTF-8 文件**（由程序写入，不经 shell 转义）；由脚本**按字节
读取**该文件并作为请求体发送，不经过任何 shell 插值；发送后**回读比对**，把远端保存的正文
读回来与源文件逐字比对；不一致就**报错并停下**，不要当作成功。

同一条规则也适用于正文为纯 ASCII 的情况，理由相同：少一条需要分平台验证的路径。

**更新已存在的 Release**：**先按 tag 查出它的标识**，再用该标识去改。直接按 tag 去改会返回
「不存在」——「按 tag 查询」与「按标识更新」是两组不同的接口能力，不要因为一次失败就认定
Release 不存在。

**完成判据**：tag 指向的提交与预期一致；Release 正文与源文件逐字一致（回读比对通过）；
Release 关联的是同一个 tag，不出现「tag 已更新、Release 还挂在旧提交上」。

想让“推 tag 即自动建 Release”：用 `templates/ci-release.yml` 落盘（先建 `RELEASE_TOKEN`），
配完走第八节末的核对表——日常攒提交、发版打标签，标签不再碎。

## 七、协作基础设施（当项目可能接受外部贡献时）

**判据**：项目还只有作者一个人用 → 可以先不建，避免空模板带来的形式主义；**一旦要给别人
用、或已经开源 → 应当建**。

**Issue 模板**解决的是「让提问者一次把必要信息给全」，不必来回追问，也避免维护者收到
「用不了」这类无法处理的报告。应包含的字段——缺哪一项这份报告就无法处理：项目版本（或
提交标识）；运行环境（平台与版本、相关运行时版本）；复现步骤（从干净状态开始，能照着走一
遍）；期望结果与实际结果；**确切的报错文本**（不要转述、不要把截图当唯一证据）；已尝试过的
做法。可直接用的骨架：

```markdown
缺陷报告

版本：（项目版本或提交标识）
环境：（平台与版本、相关运行时版本）
复现步骤：
1.
2.
期望结果：
实际结果：
报错文本：（原样粘贴完整输出，不要转述）
已尝试：
```

**PR 模板**解决的是「让提交者说明改了什么、为什么、怎么验证」，让审查者不必从改动内容反推
意图。骨架要点：变更摘要与动机 → 关联的 Issue → 验证方式（跑过哪些检查、结果如何）→ 有无
破坏性变更或需要同步的文档。

**贡献指南**本身由文档套装那份文档负责生成，这里只说它在平台侧的位置与作用：放在仓库根
目录的约定文件名上，平台会在发起 Issue 与 PR 时自动把它呈现给贡献者。本文件不重复它的
内容，也不在这里另写一套与文档套装不一致的流程。

## 八、持续集成骨架

**解决的问题**：把「在我本机能过」变成「换一台机器、换一个系统也能过」，并在每次推送时
自动检查——本机通过只证明本机装了该装的东西，不证明项目本身是完整的。

**最小骨架的结构**（不绑定具体语言，四步足够）：装依赖（从清单文件装，不用本机缓存）→
构建（从源码产出该产出的东西）→ 测试（跑项目自带的检查）→ 校验产物（确认产物存在，且是
这次构建产生的）。

**一条容易被忽略的检查**：如果项目把**生成产物提交进了版本库**，CI 必须验证「重新构建得到
的产物与提交的产物**逐字节一致**」。否则产物迟早会和源码脱节——有人改了源码忘了重建，或
构建结果依赖了构建机（绝对路径、行尾、平台差异），而所有测试仍然全绿；这类问题一旦漏过去，
使用者拿到的就是与源码不符的产物。

**触发时机**：推送与拉取请求都要触发。只挂推送会漏掉外部贡献的检查；只挂拉取请求会让直接
推送的分支没有回退保护。

**保持轻量**：私有仓库的自动构建有额度限制，超额后构建会停止。因此骨架尽量轻——优先放
秒级的自检（格式、产物一致性、关键单元测试），耗时长的全量测试留到确有必要时再挂，或只在
特定分支与标签上跑。

### 从模板落盘，不要手写

骨架每次都长一样，所以不要现场手敲——从模板复制，按 TODO 替换取值，删掉注释块：

| 模板 | 落到哪里 | 什么时候拿 |
| --- | --- | --- |
| `templates/ci-check.yml` | 目标项目的 `.github/workflows/check.yml` | 任何要 CI 的项目都要 |
| `templates/ci-release.yml` | 目标项目的 `.github/workflows/release.yml` | P2 判定可发布、且用户要自动写发布说明时 |

手写 CI 是目标项目自动化遗漏的主要来源（上次漏的就是英文版校验），模板把“有哪些节”固定下来，
AI 只填取值，漏不掉。

### 发布自动化的人工部分（自动化做不了，照着做只要 5 分钟）

`templates/ci-release.yml` 用的凭证在仓库 Secrets 里，名叫 `RELEASE_TOKEN`：细粒度 token，
仅 Contents 读写、仅本仓库、90 天过期（以平台当前上限为准）。建成后验证三件事：推一个 `v*` 标签 → `release` job 变绿 →
Releases 页出现该版本。token 过期或换人时只换 Secrets 里那一个值，代码不动。

### 配完后的核对表（给目标项目配完自动化，逐项打勾）

| 核对项 | 怎么确认 |
| --- | --- |
| CI 跑的命令与本地门禁是同一批 | 逐条对照 `AGENTS.md` 构建与验证节 |
| 产物入库的项目有逐字节一致检查 | 看 CI 里有没有重建比对那一步 |
| 打标签能触发 Release | 推一个测试标签或看 `release` job 历史 |
| Secret 已建且名字 exactly `RELEASE_TOKEN` | 看仓库 Settings → Secrets（只看有没有，不看值） |
| npm 包要自动发布：可信发布已登记 | 按 `references/publish-npm.md` 接线步骤逐项核对（组织/仓库/文件名逐字一致） |
| 标签形状与清单/专章一致 | npm 一类 `v*`；Obsidian 与 `manifest.json` 完全一致 |

有一项没勾，自动化就不算配完——宁可当时多看一眼，不要等用户装不上再回头查。

## 九、推送之后的三处状态

本地仓库、远端仓库、制品库是**三个独立的地方，互不自动同步**。一次动作只推进其中一处，
不要以为做了一处其他两处会跟上。

| 动作 | 效果 | 谁能感知 |
| --- | --- | --- |
| 推送 | 远端仓库更新 | 从仓库源安装 / 克隆的人，推送后立刻能拿到 |
| 打 tag + 建 Release | 产生版本节点与更新说明 | 打开平台发布页面的人 |
| 发布到制品库 | 制品库上的版本更新 | 从制品库安装的人 |

**未发布不等于别人拿不到**：从仓库源获取的人，在你推送的瞬间就拿到了最新代码——即使还没
打 tag、还没建 Release、还没发制品库。反过来说，只有推送而没有版本节点，使用者无法判断
「我拿到的这份是哪个版本」，所以三者要按需分别推进，而不是只做推送。

## 十、失败与恢复

| 情况 | 处置 |
| --- | --- |
| 推送被拒绝（远端有本地没有的提交） | 先取回远端改动，再合并或变基到本地历史之上；**不要强推** |
| 认证失败 | 检查凭据是否存在、是否过期、**权限范围**是否覆盖要做的操作（只读范围不能推） |
| 推错了内容 | 按版本管理那份文档的回滚分档处理，**已推送的历史不改写** |
| 平台限流或接口暂时不可用 | 退避后重试，间隔递增并设上限；不要连续重打，也不要并行重试 |

通用原则：**失败先停，把实际状态读回来**（远端当前提交、远端当前元数据、远端当前
Release），再决定下一步。凭想象重试是这类故障里最常见的二次伤害。

### 10.1 仓库改名

改名会**同时牵动两处**：平台上的仓库名，和本地远端地址指向的路径。

顺序取决于平台行为，**不要凭直觉决定**：

- 主流平台在改名后会**把旧地址重定向到新地址**，因此「先改平台名」是安全的——那段
  时间里的推送会被转到新位置，不会失败；
- 反过来先改本地地址、再改平台名，中间那段时间本地指向的是一个**还不存在的仓库**，
  推送会真的失败。

所以稳妥顺序是：**先改平台上的名字 → 确认重定向生效 → 再改本地远端地址 → 最后回读
两处都对了**。本条依据平台文档而非本地实测，执行前请核对目标平台的当前说明；不同平台
可能不同。

两个容易被忽略的后果：

- **旧名字被重新占用后，重定向会失效**。改名之后如果又把旧名拿去建了别的仓库，那么
  所有还指向旧地址的克隆都会静默地拉到另一个仓库——这是很隐蔽的事故，改名后不要急着
  复用旧名。
- **自动化配置里写死的仓库名会失效**。例如工作流里 `uses:` 引用了本仓库（或任何指向
  旧路径的地方），改名后会以「repository not found」失败。改名后搜一遍这些引用。

另外两点：

- 改名**影响所有克隆过这个仓库的人**——他们的远端地址要自己更新。有外部使用者时，
  这属于对外可见的变更，提前说明。
- **包名与仓库名是两件事**，改一个不影响另一个。发布过的项目尤其要注意：改了仓库名，
  制品库上的名字、依赖它的项目写的地址，都不会跟着变。

### 10.2 归档与模板仓库

- **归档**：把仓库标记为只读，表达「不再维护但保留可查」。适合已停止演进、但仍有人
  会来看的项目。它是**对外可见的信号**——做了要说清楚，别悄悄归档，否则使用者会以为
  只是暂时没更新。归档前确认没有未处理的改动请求。
- **模板仓库**：让新项目从现成结构起步。只适合「结构稳定、每次新建都要照抄」的场景；
  内容还在频繁变动时不要转，否则基于它建出来的项目一开始就是旧的。

### 10.3 协作与权限

仓库一旦给别人用，就要处理「谁能做什么」：

| 角色 | 通常给什么 | 说明 |
| --- | --- | --- |
| 只读使用者 | 无需设置 | 公开仓库人人可看；私有仓库需要显式邀请 |
| 外部贡献者 | **不需要授予权限** | 靠 fork 加改动请求参与。**不要为了收贡献而给写权限** |
| 协作者 | 写权限 | 能推分支、能开与合并改动请求。**谨慎给出**——写权限意味着能改动主干 |
| 维护者 | 管理权限 | 能改设置、能发布、能删除 |

两条要点：

- **收贡献不需要给写权限**，这是最常见的越权来源。贡献指南也要按这个前提写：先 fork
  再提请求；只有协作者才「直接拉分支」。
- **需要钥匙的 job 只挂 tag 与手动触发，不挂拉取请求**：fork 过来的拉取请求默认拿不到
  任何 Secrets（平台保证，不是配置项），所以建 Release、发包这类步骤天然跑不起来——
  这是安全的反面：贡献者的 PR 只跑检查不跑发布，既不会泄钥匙，也不会被钥匙卡住。
  配 CI 时就把两类 job 的触发路径分开，不要事后打补丁。
- **权限属于平台设置，不是仓库内容**：给出去不留任何仓库内记录，历史里查不到「某人
  曾经有写权限」。所以给之前想清楚，并定期复核。
- 私有仓库邀请别人之前，先确认**历史里没有不该被看到的内容**——理由与公开前扫历史
  相同，只是范围小一些。

## 十一、幂等要求

本文件描述的流程会被重复执行（换会话、换助手、用户再说一次）。重复执行时的行为：

| 现状 | 应当怎么做 |
| --- | --- |
| 已有远端 | 只校验地址、分支、上游跟踪与提交是否一致，**不重建** |
| 已有 tag / Release | **更新说明，而不是重复创建**；更新前先按 tag 查出标识 |
| 元数据已正确 | 不动，不要为了「确保生效」再写一遍 |
| 发现冲突（同名仓库内容不同、tag 指向与预期不符、远端领先且无法自动合并） | **报告并停下**，交回用户决定；不要自行覆盖、改名或强推 |

判断「已正确」靠回读：把平台侧的实际值与预期比对，而不是假设上次成功过就一直正确。

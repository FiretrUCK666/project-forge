# 远端仓库（GitHub）

## 何时读本文件

要把本地仓库推上 GitHub、建仓库、配仓库元数据、接 CI 与发布自动化，
或推送失败要排障。

---

## 一、凭据纪律（先读，最容易出事）

推送与 API 是**两条独立的通道**，互不替代：

| 通道 | 干什么 | 凭什么 |
| --- | --- | --- |
| **git 传输** | `git push` / `fetch` / `ls-remote` | SSH 私钥，或 HTTPS 凭据（凭据助手、`gh auth setup-git`） |
| **GitHub API** | 建仓库、改元数据、发 Release、读写 Issue | `gh` 的登录态，或环境变量里的令牌 |

**只通了其中一条时说清缺的是哪一条**，不要笼统报「认证失败」——那会让用户去重装一个
本来没问题的东西。凭据只从运行环境读，**绝不写进项目里的任何文件**；报告里也不打印值，
只报「有没有」。

---

## 二、动手前先探测

| 要确认的 | 怎么查 | 判据 |
| --- | --- | --- |
| 能推吗 | `git.auth.https`（加 `--probe-auth`） | `available` 直接推；`no-credential` 才需要用户动手 |
| 能建仓库吗 | `gh auth status` | 决定「建仓并推送」还是「让用户先建」 |
| 远端指向谁 | `git.remoteUrls` | 决定这是正本还是 fork（见 `git.role`） |

---

## 三、建仓库之前

**不可逆与对外的动作，动手前给一份清单让用户过目**：仓库名、可见性、归属账号或组织、
要推的分支。用户已明确说过的不再问。

**默认私有。** 理由不是保守，是**公开不可撤销**：一个仓库被公开的下一秒就可能被爬虫抓走。
私有转公开随时可做，被抓走的内容要不回来。

```sh
gh repo create "<owner>/<repo>" --private --source=. --remote=origin --push
```

已有远端时不重建：只补缺的，然后推。

**改可见性最危险**，默认答案是「不做」。

---

## 四、首次推送

推送前确认三件：署名配了、没有凭据要进历史、`.gitattributes` 在首次提交之前就位。

| 现象 | 大概率原因 | 怎么查 |
| --- | --- | --- |
| `Permission denied (publickey)` | SSH 密钥没配到 GitHub | 查 `~/.ssh` 里有没有对应公钥 |
| `could not read Username` | HTTPS 缺凭据 | 问凭据助手（`auth`） |
| `Repository not found` | 仓库名错，或没权限 | 核对 `remoteUrls` 与实际仓库 |
| `protected branch hook declined` | 主干受保护 | **这是设计，不是故障**：改走 PR |

最后一条特别容易误判成故障。被主干保护挡住，说明流程对了，只是走错了路。

---

## 五、仓库元数据

```sh
gh repo edit --description "<一句话简介>" --add-topic "<topic1>,<topic2>"
gh repo view --json name,visibility,description,repositoryTopics
```

**回读确认**：描述、标签、主页都读回来核对。接口返回成功不等于它记下了——这类「返回 200
但其实没生效」的情况，只有回读能发现。

---

## 六、版本节点与发布说明

### 正文的单一来源：版本库里的一个文件

说明写在版本库里（默认 `docs/release-notes/<标签>.md`），由自动化原样贴到发布页。
**不在命令行里拼、不在网页上现写**——那份有历史、能评审、能改；网页上那份只有当下。
而且中文正文直接拼进命令行会被 shell 的编码规则静默吃掉几个字，接口仍返回成功，
只有打开页面才看得出。

### 顺序：说明先到远端，标签才触发发送

写说明 → **提交并推送** → 打标签并推送 → 等自动化 → 回读确认。

顺序反了，自动化读不到文件，发版直接失败。失败时**补推说明后用 `workflow_dispatch` 手动
触发**——不要重打标签，也不要挪标签（标签不可变是它的价值所在）。

### 每个项目一份发版规范

不同项目的读者关心的事不同：库看接口变化，工具看行为变化，插件看宿主兼容性。
所以分哪几节**由项目自己定**，落一份 `RELEASING.md` 说明。**问的是「要回答读者哪几个
问题」，不是「照抄哪几节」。**

### 含非 ASCII 正文的硬规则

Release / Issue / PR / 评论，只要正文里有中文、多行 Markdown、反引号或 `$`，
**一律先写成 UTF-8 文件再按文件提交**：

```sh
gh release create "<tag>" --title "<tag>" --notes-file "docs/release-notes/<tag>.md"
gh pr create --title "<标题>" --body-file "/tmp/pr-body.md"
```

**提交后回读比对**：编码层、代理、平台的规范化都可能改写它，而它们都不报错。

### 更新已存在的 Release

重跑会用文件内容覆盖正文。**发布页上有人工改写时不要重跑**——那会抹掉人的编辑。
完成判据是回读：正文与文件一致、附件在、版本号对。

## 七、持续集成

骨架在 `templates/ci-check.yml`。落盘后三件事：按生态保留一块环境准备步骤（其余删掉）、
把占位命令换成项目里真能跑的命令（与 `AGENTS.md` 的构建与验证节同一批）、删掉模板顶部的
说明注释。

第二件最容易漏：留着 `<安装命令>` 那种占位的工作流不报错，它跑一次然后红，
而红了以后看上去像「代码坏了」。

### 安全红线：`pull_request_target`

`pull_request` 是安全默认值：fork 来的提案自动降成只读令牌、扣掉全部密钥。

**绝不要在 `pull_request_target` 下检出提案那边的代码。** 那个触发器拿得到密钥，而它执行
的又是提案里的代码，等于让任意陌生人拿你的密钥跑他的代码（这类攻击叫 pwn request）。

需要「有密钥的步骤」时拆成两个工作流：一个无特权的跑检查并上传产物，另一个等它跑完
只消费产物。

**判据是配对**：用了这个触发器 + 检出了提案代码才是危险形状。只用它打标签、评论是合法
用法，按单个关键词判会误报。

### 发布自动化

发布 job 要显式声明 `permissions: contents: write`。**这一行不能只写在注释里**——
删掉它，门禁会一直报待配。

## 八、失败与恢复

| 情况 | 怎么做 |
| --- | --- |
| 仓库改名 | GitHub 保留旧地址的重定向，但**别依赖它**：本地远端要改，文档里的地址也要改 |
| 推送被拒（non-fast-forward） | 先 `git pull --rebase`，不要 `--force` |
| 标签推错了 | 删远端标签重推，**仅当没人基于它发布过**；已发布就只向前补一个新版 |
| 自动化没跑 | 查 Actions 页面的开关状态——它可能被整个禁用了（脚本读不到这个设置） |
| Release 正文乱码 | 说明没走文件。改成 `--notes-file` 重发，并检查源文件编码 |

---

## 九、幂等

已有远端不重建；已有元数据只在缺的时候补，不覆盖用户写过的描述；已有的工作流先读再合并，
不整份覆盖（里面可能有这个项目自己的门禁）；重复建标签会失败，那是正确行为。

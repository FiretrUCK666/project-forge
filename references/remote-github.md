# 远端仓库（GitHub）

## 何时读本文件

要把本地仓库推上 GitHub、建仓库、改仓库元数据、接 CI 与发布自动化，或者推送失败要排障时读。

## 一、三条通道，两条轨道

**这是最容易出事的一节，先读完再动手。** 推送与平台操作走的是两套完全不同的凭据，两条轨道互不替代：

| 轨道 | 干什么 | 凭什么 |
| --- | --- | --- |
| **轨道 A：git 传输** | `git push` / `fetch` / `ls-remote` | SSH 私钥，或 HTTPS 凭据助手 |
| **轨道 B：GitHub 平台 API** | 建仓库、改元数据、发 Release、读写 Issue 与 PR | 平台登录态，或环境变量里的令牌 |

轨道 B 有三条通道，**按优先级降级**，前面的能用就不要装后面的：

1. **宿主自带的 GitHub 集成工具**（MCP 一类）。会话里已经能调，就不用装任何东西、不用碰任何凭据——它自带授权。
2. **`gh` CLI**。判据是 `gh auth status`，它判的是**登录态**，不是「有没有装」：装上了但没登录时，每条命令都以统一的方式失败，看起来像网络问题。
3. **`curl` 直连 `https://api.github.com`**，带 `GITHUB_TOKEN` 或 `Authorization: Bearer`。前两条都不通时才走这条。

**半通原则：轨道 A 通、轨道 B 不通时，先把能做的做完。** 把代码推上去，再把建仓库、发 Release 这些需要轨道 B 的命令**列给用户**，绝不整条停摆。整条停摆的代价是「用户什么也没得到」，而缺的那几步他心里有数。

**凭据只从运行环境读**，绝不写进项目里的任何文件；报告里也不打印值，只报「有没有」。打印一次就进了日志和聊天记录，而它们删不掉。

## 二、动手前先探测

| 要确认的 | 怎么查 | 判据 |
| --- | --- | --- |
| 能推吗 | 勘察的 `git.auth`（加 `--probe-auth`） | `available` 直接推；`no-credential` 才需要用户动手；`undetermined` 说「未确认」 |
| 能建仓吗 | 按上面的优先级试一条轨道 B | 通就直接做；不通就把命令列给用户 |
| 远端指向谁 | `git.remoteUrls` 与 `git.role` | 决定这是正本还是 fork，以及能不能推主干 |

**`git credential fill` 必带 `path`。** 输入三行：`protocol=https`、`host=github.com`、`path=<owner>/<repo>.git`。漏掉 `path` 时凭据助手查的是按主机存的条目，而凭据往往是按路径存的——症状是「登录了却推不上去」，所有报错都说认证失败。

## 三、建仓库之前

**不可逆与对外动作，动手前给一份清单让用户过目**：仓库名、可见性、归属账号或组织、要推的分支。用户已明确说过的不再问。

**默认私有。** 理由不是保守，是**公开不可撤销**：一个仓库被公开的下一秒就可能被爬虫抓走。私有转公开随时可做，被抓走的内容要不回来。

**目录名不是 ASCII 时，转写三步走，不要卡在等用户起英文名上**：

1. 优先取项目清单里声明的 `name`——那是作者自己定的名字。
2. 没有声明就按语义译成一个简短的英文名，**作为默认建议写进汇报里说明「我按这个建，要改告诉我」**。
3. **只作远端仓库名，不改本地目录名**。改本地目录会让所有已有路径失效，而这件事跟本次任务无关。

**私有转公开的三步铁律**（这是整个文件里最不能跳的一段）：

1. 先用 `git rev-list --all` 扫**整段历史**，确认没有遗留的凭据。只看当前文件不够——删掉的东西还留在历史里。
2. **逐次单独授权**。不要说「上次同意过公开另一件事」，那是另一件事。
3. **明示不可逆**：公开的那一秒起，内容就可能已被复制。

**改可见性最危险，默认答案是「不做」。** 用户主动要求时才做，且走完上面三步。

## 四、首次推送

推送前确认三件：**署名配了**（见 `references/version-control.md` 的「提交署名」）、**没有凭据要进历史**、**`.gitattributes` 在首次提交之前就位**。这三件在推之前都还能免费改，推之后都要动历史。

| 现象 | 大概率原因 | 怎么做 |
| --- | --- | --- |
| `Permission denied (publickey)` | SSH 密钥没配到平台，或没加载 | 查本机现有公钥，把它加到账号；不要重新生成一对覆盖旧的 |
| `could not read Username` | HTTPS 缺凭据，且没有可用的凭据助手 | 用 `gh auth setup-git` 或系统凭据管理器接上助手 |
| `Repository not found` | 仓库名错、没权限，或**令牌的作用域不覆盖它** | 先核对 `remoteUrls` 与实际仓库名，再查令牌权限 |
| `protected branch hook declined` | 主干受保护 | **这是设计，不是故障**：改走分支 + PR |
| Windows 上两个 ssh 冲突（系统自带与 Git 自带的互相抢） | 两者都在 `PATH` 里，推到一半握手失败 | 配 `git config core.sshCommand` 指定其中一个的绝对路径 |
| Windows 上私钥权限被拒 | `chmod 600` 在那儿不起作用 | 用 `icacls` 收紧到当前用户，并移除继承 |
| 22 端口被网络封掉 | 防火墙只放行 443 | 在 `~/.ssh/config` 里配 `Host github.com` + `Hostname ssh.github.com` + `Port 443` |
| macOS 每次都要输密码短语 | 钥匙串没接上 | `~/.ssh/config` 里加 `IgnoreUnknown UseKeychain` 与 `UseKeychain yes` |
| 推送成功但内容不对 | 推的是另一个远端或另一个分支 | 比对本地 `HEAD` 与远端 `ls-remote` 的 SHA，两个 SHA 相同才算推到了 |

**最后一行是通用验收动作**，任何推送都该做一次：命令返回 0 只说明「我认为我成功了」。

## 五、仓库元数据

```sh
gh repo edit --description "<一句话简介>" --add-topic "<topic1>,<topic2>"
gh repo view --json name,visibility,description,repositoryTopics
```

**回读确认。** 描述、标签、可见性都读回来核对。接口返回成功不等于它记下了——这类「返回 200 但没生效」的情况，只有回读能发现。

**仓库设置里有几项脚本读不到，必须提醒用户手工看。** 不要假装查过：

| 要看 | 在哪 | 为什么重要 |
| --- | --- | --- |
| **合并需审批（Require approvals）** | 分支保护规则 | **单人项目千万不要开**：自己提的 PR 没人能批，仓库会被锁死，而唯一的出路是关掉保护规则 |
| **必需状态检查的名字** | 分支保护规则 | 名字必须与实际报上来的检查**逐字相同**。工作流用了矩阵时，每个 job 报的是 `名字 (取值)`，而保护规则里写的是裸名字——对不上，那个必需检查永远不会出现，PR 会一直停在 `BLOCKED`，看起来像「还在跑」 |
| 默认分支名 | 仓库设置 | 与本地 `conventions.defaultBranch` 对不上时，文档里的每条命令都指向不存在的分支 |
| Actions 是否被启用 | Actions 页面 | 被整个禁用时，工作流不报错、不运行，看起来像「还没触发」 |
| 是否允许 squash / rebase 合并 | 合并按钮设置 | 影响提交历史的形状，也影响依赖提交信息的自动化 |
| 仓库的默认令牌权限 | 设置里的 Actions 权限 | 受限默认下 `contents: write` 会 403，而报错指向的是一行你没写过的配置 |

**收外部贡献不需要给对方写权限。** fork + PR 就够了；给了写权限，对方能直接推主干，而你的门禁与评审全都可以绕过去。

## 六、版本节点与发布说明

### 标签是「发版」这个动作本身

推一个符合约定的标签，就是对外宣布了一个版本。它**不会自己发生**——日常的提交与推送
不产生标签，也就不产生版本。要不要打、什么时候打，见 `publish.md` 的「该不该发」：
**没人明确要求，就不打。**

这一节剩下的内容都是**已经决定要发之后**的机制，不回答「该不该发」。

### 正文的唯一来源是版本库里一个文件

说明写在版本库里，由自动化原样贴到发布页。**不在命令行里拼、不在网页上现写**——那份有历史、能评审、能改。两种模式并存，由勘察的 `conventions.releaseNotesMode` 定：

| 模式 | 位置 | 适合 |
| --- | --- | --- |
| `dir` | `docs/release-notes/<标签>.md`，骨架见 `templates/release-notes.md` | 版本多、说明长、要单独评审每一份 |
| `changelog` | 根目录 `CHANGELOG.md` 里的 `## [<标签>]` 一节 | 版本少、要一个文件看全 |

**用哪种由项目现状决定，不要按偏好新建一处。**

### 顺序：说明先到远端，标签才触发发送

1. 写说明。
2. **提交并推送说明。**
3. 打标签并推送。
4. 等自动化跑完。
5. **回读确认**发布页上的正文与文件一致。

**反了自动化读不到文件，发版直接失败。** 失败时补推说明，再用 `workflow_dispatch` 手动触发——**不要挪标签**，也不要删了重打：标签不可变是它的价值所在，动过之后依赖它的下游全都错位。

### 标签形状不写死

带不带 `v` **由发布链路决定，不由习惯决定**：插件市场一类要求裸版本号；Go 的子目录模块要 `subdir/v1.2.3`，大版本要 `/v2`。勘察的 `conventions.tagPrefix` 是结论。

**工作流的触发行必须跟着改，否则永不触发。** 触发行写 `v*` 而标签是 `1.2.3` 时，推送成功、标签在、页面空白，没有任何一处报错。

### 每个项目一份 `RELEASING.md`

它回答三件事：说明写在哪、分哪几节、按什么顺序发。骨架见 `templates/releasing.md`。

### 含非 ASCII 正文的硬规则

Release / Issue / PR / 评论，正文里有中文、多行 Markdown、反引号或 `$` 时，**一律先写成 UTF-8 文件再按文件提交**：

```sh
gh release create "<tag>" --title "<tag>" --notes-file "docs/release-notes/<tag>.md"
gh pr create --title "<标题>" --body-file "<正文文件>"
```

中文直接拼进命令行会被编码层静默吃掉几个字，而接口仍返回成功。**提交后回读归一比对**：编码层、代理、平台的规范化都可能改写它，而它们都不报错。

### 更新已存在的 Release

重跑会用文件内容覆盖正文。**发布页上有人工改写时不要重跑**——那会抹掉人的编辑。完成判据是回读：正文与文件一致、附件在、版本号对。

## 七、持续集成

骨架在 `templates/ci-check.yml`。落盘三件事：按生态保留一块环境准备步骤（其余删掉）、把占位命令换成项目里真能跑的命令（与 `AGENTS.md` 的「构建与验证」同一批）、删掉模板顶部的说明注释。

**有用例要在分支基线差异上算时，`fetch-depth: 0` 是必须的。** 浅克隆时 `git diff A...B` 会返回空，而**空清单会被读成「没动高风险路径」，门禁绿着放行**——最坏的一种失败：它看起来是通过。

### 安全红线：`pull_request_target`

**判据是配对，不是关键词。** 用了 `pull_request_target` **并且**检出了提案那边的代码，才是危险形状：那个触发器拿得到密钥，它执行的又是提案里的代码，等于让任意陌生人拿你的密钥跑他的代码（这类攻击叫 pwn request）。只用它打标签、评论是合法用法。

需要「有密钥的步骤」时拆成两个工作流：一个无特权的跑检查并上传产物，另一个等它跑完**只消费产物**。

### 已有工作流时只追加 job

**绝不覆盖。** 里面可能有这个项目自己的门禁，覆盖之后它静默消失，而检查看起来还在跑。

### 产物入库的项目必须加重建比对

重新构建一次，与提交的产物逐字节一致，否则源码与产物迟早脱节：`git diff --exit-code` 那一行就是判据。

### 发布 job 要显式声明权限

```yaml
permissions:
  contents: write
```

**这一行不能只写在注释里**——删掉它，受限默认下发布步骤 403，而门禁会一直报「待配」。

### 配完自动化后的核对清单

- 触发行与 `conventions.tagPrefix` 一致。
- 里面每条命令本地都真跑通过。
- 跑一次，看它是绿的；绿之后**再故意改坏一处**，确认它真的会红——不会红的门禁等于没有。

## 八、失败与恢复

| 情况 | 怎么做 |
| --- | --- |
| 仓库改名 | 平台保留旧地址的重定向，但**别依赖它**：本地远端要改，文档里的地址也要改 |
| 推送被拒（non-fast-forward） | 先 `git pull --rebase`，**不要 `--force`** |
| 标签推错了 | 删远端标签重推，**仅当没人基于它发布过**；已发布就只向前补一个新版 |
| 自动化没跑 | 查 Actions 页面——它可能被整个禁用了，而脚本读不到这个设置 |
| Release 正文乱码 | 说明没走文件。改成 `--notes-file` 重发，并检查源文件编码 |

## 九、幂等

已有远端不重建；已有元数据只在缺的时候补，**不覆盖用户写过的描述**；已有的工作流先读再合并，不整份覆盖；重复建标签会失败，**那是正确行为**——它挡住的是「同一次发版发了两遍」。

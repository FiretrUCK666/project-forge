# 能力目录与插件类项目

## 何时读本文件

目标项目是**能力目录**（有 `SKILL.md` 的那种目录），或者是**插件**（VS Code 扩展、
Obsidian 插件、DSH 插件等被宿主加载代码的扩展）时读。

两类都有「宿主」，但**判定问题没有一条答案相同**，所以先分清是哪一类。

---

## 一、宿主加载的是指令，还是代码

| | 能力目录（skill） | 插件 |
| --- | --- | --- |
| 宿主拿它干什么 | 读它的**文字**，拼进上下文 | 运行它的**代码**，跑在宿主进程里 |
| 消费者 | 模型 | 宿主程序 |
| 「安装」意味着 | 复制到一个目录 | 装进运行时，可能要重启宿主 |
| 产物该入库吗 | **全部入库** | **按分发通道判**（见第三节） |
| 版本号对谁有意义 | 分发快照 | 宿主与市场（更新检查靠它） |
| 最典型的坑 | 名字不合法 → 宿主**静默丢弃**整份 | 产物没跟源码一起提交 → 用户拿到旧代码 |

判据是**宿主加载什么**，不是目录名字。一个目录里有 `SKILL.md` 但带大量代码，
它依然是能力目录——因为宿主读的是那份文字。

---

## 二、能力目录

### 判定三件事

1. **入口文件在不在**：根目录有 `SKILL.md`。
2. **frontmatter 合法吗**：`name` 与 `description` 都在且非空。
   **缺任一项，宿主会整份丢弃，而且不报错。**
3. **名字与目录名一致吗**：不一致在区分大小写的系统上就是另一个目录。

### 静默丢弃是最常见的坑

同一个症状（「它没生效」）有三种原因，用户看到的是同一件事：

| 原因 | 怎么查 |
| --- | --- |
| 缺必填字段 | 读 frontmatter，看 `name` 与 `description` |
| 名字形状不合法 | 小写字母、数字、连字符；不能有大写、空格、下划线 |
| 键名形状不对 | 扩展字段用连字符形式；驼峰旧键会让**整份**被丢弃 |

**这种失败最贵的地方在于它不报错。** 所以盘点时要**单独报出「被丢弃的」**，
不能与「没有」混在一起——前者修一下就好，后者要从零写。

### 资源引用一律用相对路径

形如 `references/<文件名>.md`。宿主会把它们解析到 skill 自己的目录下，这是这套格式的一
部分，也是它跨宿主可用的原因之一。写绝对路径会在换机器时失效。

### 分发范围

**整体可复制就是全部**：拿到这个目录的人应该能用。所以不要有指向仓库外部的相对引用；
`scripts/` 零第三方依赖（不然「复制过去就能用」是假话）；仓库自用的开发文件可以排除，
但排除规则要**写在结构里**，不要靠人记得删。

### 仓库自带的本地 skills

一个项目里可能有多个能力目录（`.dsh/skills/`、`skills/` 一类）。它们**是这个项目的一部分，
不是痕迹**。盘点它们是为了：确认每一份都合法（不合法的宿主不会加载，而用户以为它在），
以及别在清理时误删。

## 三、插件

### 两个标识严格分开

| 标识 | 在哪 | 改了会怎样 |
| --- | --- | --- |
| **宿主侧 ID** | 插件的清单文件里（宿主用它做命名空间） | 老用户的**配置与数据全部失联**。它是数据地址，不是标签 |
| **分发侧包名** | 包清单的 `name`、仓库名 | 只影响安装来源，宿主内部的地址不变 |

**发布之后宿主侧 ID 就不能再改了。** 它看起来像个名字，实际是数据库主键。

### 产物该不该入库

| 宿主怎么装它 | 产物进不进仓库 | 门禁 |
| --- | --- | --- |
| 直接从仓库或某个分支拉 | **必须进**：改源码必须同一次提交带上重建的产物 | CI 里重新构建一次，`git diff --exit-code` 确认一致 |
| 通过打包附件分发（`.vsix`、发布页附件、制品库） | **不进**，但打包清单要包含它 | 发布前核一次打包清单，确认入口产物在里面 |

判断依据是**「用户拿到的是仓库还是附件」**，不是「这是不是插件」。

第一条的门禁为什么必须做：产物和源码分开提交，迟早有一天它们不对应，而那时用户装到的是
旧代码，报的问题在你本地复现不出来。

### 宿主运行时依赖放哪

宿主自己提供的那些包要放在 `peerDependencies` 或 `devDependencies`，**不能进
`dependencies`**——进了会打包一份宿主的副本，然后两个实例打架。

判断依据：**这个包是宿主给我的，还是我要自己带走的。**

## 四、没有专章时怎么办

不同宿主有不同规矩，但**判定流程是同一个**。遇到没见过的宿主，按这五步查：

1. **入口清单叫什么**？（读宿主文档的「打包 / 发布」那一节）
2. **宿主侧 ID 是哪个字段**？在什么范围里唯一？
3. **宿主加载哪些文件**？（一个入口文件？一个目录？带不带资源？）
4. **宿主版本约束写在哪**？（`engines` / `minAppVersion` / `peerDependencies`）
5. **用户从哪儿装**？——这一条决定产物入不入库。

答案从**宿主自己的文档**里取，不猜。查不到就说查不到，不要按「另一个插件大概也这样」推
——每个宿主的这几条答案都不一样。

### 查到了之后

沉淀下来是可以的，但**只在它会被重复用到时才沉淀**。一次性处理的项目不需要写一份专章：
写下来的成本是有人要读它、要维护它，而一次性知识的寿命只有一次。

## 五、建库检查清单

不分能力目录还是插件，建仓库前过一遍：

- [ ] 入口清单文件在仓库根，字段齐全
- [ ] 宿主侧 ID 与分发侧包名已经分开，且知道哪个不能改
- [ ] 产物入库策略已经按分发通道定下来
- [ ] 版本号只有一个来源，标签与它同形
- [ ] 用户从哪儿装已经明确（决定要不要发制品库）
- [ ] 宿主运行时依赖不在 `dependencies` 里
- [ ] `README` 里写了宿主版本要求（从清单读，不凭印象）

## 事实来源

本文件涉及的外部易变事实：各宿主的清单字段名、ID 唯一性范围、加载文件集合、版本约束字段。
它们随宿主版本变化。**动手前查该宿主的官方文档**；本文件写的是判定流程，不是任何宿主的
字段快照。

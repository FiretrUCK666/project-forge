# 能力目录（skill 类项目）

## 何时读本文件

`references/plugin-project.md` 讲「宿主加载你的**代码**」，本文件讲「宿主加载你的**指令**」。
两份的六问答案不同，**不要互相代指**：代码那一份的产物入库、两个标识、构建可复现这些结论，
在指令这一类上大半不成立；本文件也不重复那几节的论证。

- 勘察判定项目是 `skill` 时（无论宿主是谁）。
- 需要判断能力目录的名字、发现方式、宿主校验、生效与分发怎么写时。
- **遇到一个没有专章的宿主时**——先读本文件（它给的是判定协议与生长规则）。

## 一、这一类项目的共同点：宿主加载的是指令，不是代码

不管宿主是编辑器、笔记应用还是某个 Agent，能力目录类项目都满足一条性质：

> **宿主加载的是一份指令文本，它不构建你的项目，也不在加载时执行你的代码。**

这条性质推出一整串看起来奇怪的约定。它们**不依赖任何具体宿主**：

| 因为宿主加载你的指令 | 所以 |
| --- | --- |
| 加载时不构建、不执行 | **构建失败不会让宿主拒绝加载**——产物入库那套判据在这一类上不适用 |
| 宿主按一个名字认出你、并用它路由 | 那个名字是**数据地址**（谁遮蔽谁、模型指名调用哪一份），不是显示文案 |
| 目录解析失败通常只记一条警告 | **失败是静默的**，模型侧分不清「不存在」与「不合法」（见第四节） |
| 内容随每次调用被读入 | 改正文不需要任何缓存失效动作，改摘要层才需要（见第五节） |
| 分发单位是整个目录 | 没有白名单可裁剪，带不带得上完全是你自己的选择（见第六节） |

**这几条是本文件的骨架**，下面逐个展开。各宿主的专章只补「在这个宿主里具体长什么样」，
不重复这些结论。

## 二、判定协议：先查清这六件事

遇到任何能力目录类项目（**包括没有专章的**），都要先查清这六件事。「查什么」是固定的，
「答案是什么」由宿主与项目自己决定。

| # | 要查什么 | 为什么必须查 | 从哪查 |
| --- | --- | --- | --- |
| 1 | **入口文件是哪个、在哪一层** | 发现深度、文件名大小写、目录形态都由它决定；位置错了整份不会被扫到 | 宿主文档里描述「去哪里找」的那一节 |
| 2 | **名字由谁认、形状要求是什么** | 它是路由与覆盖的依据，形状不合法会被整份丢弃 | 宿主的解析实现与其公开类型 |
| 3 | **宿主怎么发现它** | 扫描根有哪几处、顺序与优先级是什么、嵌套子目录算不算 | 宿主的发现实现 |
| 4 | **宿主校验什么** | 必填项、可选项、非法取值怎么处理——决定「写得对不对」与「会不会被丢」 | 宿主的解析实现与错误处理分支 |
| 5 | **怎么生效** | 摘要进目录、正文进提示、还有哪些入口会加载它 | 宿主的呈现实现与面向用户的说明 |
| 6 | **怎么分发** | 放哪个根、走什么通道、有没有额外门槛 | 宿主文档的分发与安装一节 |

**这六件事查清了，一个新宿主就已经被正确处理了。**

### 关键增量：哪些是宿主强制，哪些是项目自己的约定

上面六问查完，**还必须把每一条拆成两栏**：

| 分栏 | 判据 | 怎么在文档与汇报里说 |
| --- | --- | --- |
| **宿主强制** | 违反它，宿主真的会拒绝加载、丢弃或改变行为 | 可以说「宿主要求」「违反会被丢弃」 |
| **项目自己的约定** | 宿主根本不看，违反不会有任何症状 | 只能说「本项目约定」；**不得冒充宿主规则** |

最常见的错位就在这里：**目录名与名字不一致**在有的宿主里是一个真问题，在有的宿主里
宿主压根不校验（目录名只是定位用的）。勘察脚本会报出「不一致」，那**只说明项目内部不统一**，
把它说成「宿主要求两者一致」就会误导后来的人去改一个根本不影响加载的地方。

### 查不到的怎么办

按 `references/plugin-project.md` 第二节末尾那套退让处理：先在项目自己身上找证据，再查官方文档，
还查不到就**如实说明哪一项没查出来、以及它对结论有什么影响**，然后请用户确认。
本文件不复述那三级退让的内容——它只有一份真相源。

**不清楚就说不清楚**，比给一个看起来合理的答案好：错的答案会被照着执行，而不确定的答案会被核实。

## 三、名字是数据地址

这一类最容易改坏、后果最难查的一处，是**名字**。

| 它决定什么 | 改名或换名的后果 |
| --- | --- |
| 模型指名调用哪一份 | 旧名字那一格从此没人找得到 |
| 谁遮蔽谁、同层重名谁胜出 | 覆盖关系一起失效，可能冒出来一份本该被遮住的旧内容 |
| 用户手动调用的入口 | 手打的名字打不中 |

几条要点：

- **改名字不是改个显示文案**。这一类的「显示标题」通常与「路由用的名字」是分开的字段，
  两者混为一谈就会把显示需求变成破坏性变更——反过来也一样：为了改显示而动了路由名字，
  等于改了数据地址。
- **宿主不一定校验名字与所在目录名是否一致**。目录名可能只是定位用的（见第二节那两栏）。
  **不要靠猜**，去宿主的发现实现里看它拿哪个字段做路由、拿哪个字段做定位。
- **同层重名按宿主自己定的优先级裁决**，输掉的通常被隐藏并记一条警告。跨层则是更近的层
  遮蔽更远的层。裁决链有几级、按什么比，由宿主定义——新做一个能力目录前先把它读出来，
  否则「我明明有，为什么不生效」会卡在这里。

## 四、静默丢弃是这一类最常见的坑

**症状**：能力目录「好像不存在」。模型那边什么也没说，宿主那边只有一条警告。

三种丢弃原因，**每一种丢的都是整份**（不是丢一个字段）：

| 原因 | 典型表现 |
| --- | --- |
| 缺必填字段 | 少了必填的名字或描述，解析直接放弃 |
| 名字形状非法 | 写法合法但不在宿主允许的形状内 |
| 调用或可见性键非法 | 键的拼写、命名风格或取值不是宿主认的那一套 |

第三种最隐蔽：宿主往往会**同时接受新旧两套写法，但把其中一套判为非法**。用了被判非法的那套，
不是「这一个开关没生效」，而是**整份目录被丢弃**。

**唯一可靠的排查法**：先读宿主当前实现或官方文档，把契约确认下来，**再动自己的文件**。
不要靠猜着改元数据块——猜对了症状消失是因为你碰巧换了个写法，契约没搞清，下一次升级还会回来。
也不要靠日志：模型侧拿不到逐个目录的诊断，它**分不清「不存在」与「不合法」**，
所以「模型没看到它」这条证据什么都不证明。

## 五、两条不同的生命周期：目录摘要与正文

宿主处理这类目录时，其实是两条独立的生命周期。搞混它们，会得出「我改了怎么没生效」的错误结论：

| | 目录摘要 | 指令正文 |
| --- | --- | --- |
| 从哪来 | 解析入口文件的元数据块拼出来 | 入口文件里元数据块之后的全部正文 |
| 谁读它 | 放进模型可见的目录 / 列表 | 命中之后整段读进上下文 |
| 长度 | 通常**有上限**（是否可配、上限多少由宿主定义，查专章）；超出的部分等于不存在 | 通常**没有上限** |
| 什么时候读 | 发现或刷新目录时 | **每次加载** |
| 改了它要做什么 | 让宿主重新发现（重启、改目录结构或触发它认的刷新动作） | **什么都不用做**，下一次加载自然生效 |

推论两条：

1. **改正文不需要任何缓存失效动作。** 反复重启、反复改目录结构去「让正文生效」是白费力气，
   只要摘要层还是能被发现，正文改完下一次调用就是新的。
2. **改摘要里的字段才需要让宿主重新发现。** 而摘要里**哪些字段真正参与路由**（哪些只是被解析
   下来存着）由宿主自己定义——**查，别假定**。把一个宿主解析了却不参与路由的字段当成开关来调，
   会得到一个「配了但没用」的结果，而它看起来完全合理。

## 六、分发范围：整体可复制即全部

这一类**没有白名单**。分发的最小单元就是整个目录，多带少带不会被任何宿主裁剪：

| 问题 | 结论 |
| --- | --- |
| 能不能只带一部分文件 | 不能。宿主按目录整体加载，没有「排除某些子目录」的机制 |
| 带了不该带的东西会怎样 | **不会被裁掉**，会跟着走。体积、缓存、临时产物要在发布前自己清干净 |
| 版本控制里放什么 | 整个目录进库 |

与插件那条的差异点在这里：插件那一类的分发靠清单里的**白名单**声明，漏一个文件就装上加载不了，
多写的项不存在也可能不告警；这一类**没有那个机制**，两个方向的错误都只能靠自己查。
那条白名单的判据与做法见 `references/plugin-project.md` 的发布范围一节，本文件不复述。

顺带一条：因为宿主不构建，这类项目通常压根没有构建步骤，也就没有「产物必须入库」的问题。
这与插件那一份的结论**碰巧相同、理由完全不同**——不要拿那一份的理由来论证这一份。

## 七、这一类特有的坑

**这一节每一行都是「先查宿主当前实现的哪一处」，不是可以直接照着改的处方。** 这一类没有通用处方，
只有通用问法：

| 症状 | 先查什么 |
| --- | --- |
| 目录「好像不存在」 | 是否被整份丢弃、丢弃原因是什么（第四节）；宿主有没有逐目录的诊断手段 |
| 改了内容却没生效 | 改动落在摘要层还是正文层（第五节） |
| 覆盖没按预期生效 | 同层重名裁决链与跨层遮蔽（第三节） |
| 模型知道它却不调用它 | 摘要里**真正参与路由**的字段是哪些；可见性开关的取值形状 |
| 放进子目录的那份没被发现 | 宿主的发现深度；嵌套是不是被刻意排除的 |
| 放进自定义目录的那份没被发现 | 扫描根有哪几处、顺序与优先级、那一处是否被跳过 |
| 引用的子目录「不存在」 | 宿主是不是只给一句基准目录提示、不附带任何文件；那些目录名是不是只是普通名字、并没有特殊待遇 |
| 换台机器就不认了 | 入口文件名是否大小写敏感；目录名与名字的匹配规则 |

**没有处方，是因为同一句症状在不同宿主下的根因完全不同。** 猜着改元数据块是这一类最常见的
时间浪费，而且改完症状消失不等于契约搞清了。

## 八、宿主专章索引

| 宿主 | 专章 | 判定结果 |
| --- | --- | --- |
| DeepSeek Harness | `references/plugins/dsh.md` | `skill`（同一份专章同时出现在插件索引里） |

一个生态可以同时出现在两张索引里：它既加载代码类的扩展，也加载纯指令的能力目录，两者的契约
不同但宿主是同一个。专章按**宿主**组织，所以同一份文件会同时被两张索引指到。

**没有找到你的宿主**：按第二节的六问去查，把答案分成「宿主强制」与「项目自己的约定」两栏，
然后把宿主专有的取值（字段名、扫描根、形状规则、上限、重名裁决）写成新专章。本文件不承载这些。

## 事实来源

**本文件只承载通则，不承载任何宿主的具体取值，因此不带核对标记。**

这条纪律为什么成立：某个宿主的字段名、数量上限、界面路径、扫描根顺序都会随它的版本变。
把它们写进通则文件里，它们就会在某次宿主升级之后**变成假话**——而且是那种最难发现的假话：
文件结构没变、判据读起来仍然成立，只有具体的取值悄悄对不上了。等到它被发现时，
中间所有依据它做出的判断都得重新做一遍。

所以取值一律住在各自专章里，由专章的核对标记管保鲜。本文件负责的是**提问方式与推论方向**，
那部分不随版本变；专章负责**答案**，答案过期时只改那一处。

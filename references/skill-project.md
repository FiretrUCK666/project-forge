# 能力目录与插件类项目

## 何时读本文件

目标项目是**能力目录**（根目录有 `SKILL.md` 的那种目录），或**插件**（被宿主加载代码的扩展）时读。
两类都有「宿主」，但判定问题没有一条答案相同——先分清是哪一类，再往下读。

## 一、宿主加载的是指令，还是代码

| | 能力目录（skill） | 插件 |
| --- | --- | --- |
| 宿主拿它干什么 | 读它的**文字**，拼进上下文 | 运行它的**代码**，跑在宿主进程里 |
| 消费者 | 模型 | 宿主程序 |
| 「安装」意味着 | 复制到一个目录 | 装进运行时，可能要重启宿主 |
| 产物该入库吗 | **全部入库** | **按分发通道判**（见第三节） |
| 版本号对谁有意义 | 分发快照 | 宿主与市场（更新检查靠它） |
| 最典型的坑 | 名字不合法 → 宿主**静默丢弃**整份 | 产物没跟源码一起提交 → 用户拿到旧代码 |

**判据是宿主加载什么，不是目录名字。** 一个目录里有 `SKILL.md` 但带大量代码，它依然是能力目录
——因为宿主读的是那份文字。反过来，叫 `plugin` 却不被任何宿主加载代码的目录，不是插件。

## 二、能力目录

### 判定三件事

1. **入口文件在不在**：根目录有 `SKILL.md`。
2. **frontmatter 合法吗**：`name` 与 `description` 都在且非空。**缺任一项，宿主整份丢弃，不报错。**
3. **名字与目录名一致吗**：不一致时，在区分大小写的系统上它们就是两个目录。

### 静默丢弃：三种原因，一个症状

用户看到的都是「它没生效」：缺必填字段（读 frontmatter 看 `name` 与 `description`）；名字形状
不合法（只允许小写字母、数字、连字符）；键名用了驼峰（扩展键一律连字符形式，驼峰旧键会让
**整份**被丢弃）。

**这种失败最贵的地方是它不报错。** 盘点时要**单独报出「被丢弃的」**，不能与「没有」混在一起
——前者修一下就好，后者要从零写。混在一起报「没有能力目录」，用户会去新建一份，而他原本有一份。

### 宿主强制 vs 项目自己的约定

- **宿主强制的**（缺了就不加载）：入口文件名、必填字段、名字形状、目录名一致。写错了没有商量
  余地，也没有报错。
- **项目自己的约定**（写给自己人看的）：`references/` 怎么分、`scripts/` 命名、模板放哪。
  换一个项目可以不一样。

把项目约定当宿主强制，会让别处跑得好好的目录被判成不合法；把宿主强制当约定，就得到上面那三种
静默丢弃。

### 同名覆盖与优先级

宿主持有多份同名能力时有固定的裁决链：**同层按优先级排序，跨层近处遮蔽远处**。所以「装了两份、
只生效一份」不是 bug，是裁决结果。排查同名冲突按这条链走，不要猜「可能都加载了」。

### 双生命周期模型

| 部位 | 在哪 | 长度 |
| --- | --- | --- |
| **目录摘要** | frontmatter | **有长度上限**；改后要重新发现/刷新目录才生效 |
| **指令正文** | body | 无上限；每次命中时实时按需读入，改完不用重启 |

改 `description` 之后「它还是老样子」，是摘要被缓存了，不是改错了地方；改正文立刻生效，
但那部分不参与「要不要加载这个能力」的判断。

### 症状排障表

| 症状 | 先查宿主哪一处 |
| --- | --- |
| 完全没出现 | 目录名与 frontmatter `name` 是否一致 |
| 出现了但不触发 | `description` 里有没有能匹配的说法（它是路由依据，不是介绍） |
| 触发但内容不对 | 是否命中了一份同名覆盖（见裁决链） |
| 改了没生效 | 改的是摘要还是正文；摘要需要刷新目录 |
| 引用的文件打不开 | 引用是不是相对路径、是否指向了 skill 目录之外 |
| 脚本跑不起来 | `scripts/` 里有没有第三方依赖 |
| 装了但只在某些会话里生效 | 宿主是否按项目/用户层级分别装载 |
| 部分内容被截断 | 摘要是否超过了宿主给的长度上限 |

### 资源引用与分发范围

**资源引用一律用相对路径**（如 `references/<文件名>.md`），宿主会把它们解析到 skill 自己的目录下。
绝对路径换机器就失效，而失效的表现是「引用读不到」，不会指向路径本身。指向 skill 目录之外的
引用同样是悬空的（dangling）：复制过去之后它不存在。

分发范围的判据是**整体可复制**：拿到这个目录的人应该能用。所以不要有指向仓库外部的相对引用；
`scripts/` 零第三方依赖（否则「复制过去就能用」是假话）；仓库自用的开发文件可以排除，但排除
规则要**写在结构里**（放进一个本来就不分发的目录），不靠人记得删。

**仓库自带的本地 skills**（`skills/`、`.dsh/skills/` 一类）是这个项目的一部分，不是痕迹。盘点它们
是为了确认每一份都合法（不合法的宿主不会加载，而用户以为它在），以及清理时别误删。

## 三、插件

### 六问判定协议

动手之前把这六问答完，答不出来的那一条就是这次的主要风险：

1. 宿主侧 ID 是哪个字段，唯一性范围是什么？
2. 分发侧的包名是什么，和宿主侧 ID 是不是同一个东西？
3. 宿主加载哪些文件（一个入口？一个目录？带不带资源）？
4. 版本约束写在哪个字段，宿主按什么范围判兼容？
5. 用户从哪儿装（仓库、市场、发布页附件、制品库）？
6. 产物是随仓库走还是随附件走？

### 两个标识严格分开

| 标识 | 在哪 | 改了会怎样 |
| --- | --- | --- |
| **宿主侧 ID** | 清单文件里，宿主用它做命名空间 | 老用户的**配置与数据全部失联** |
| **分发侧包名** | 包清单的 `name`、仓库名 | 只影响安装来源，宿主内部的地址不变 |

**宿主侧 ID 是数据地址，不是标签，发布之后不能再改。** 它看起来像个名字，实际是数据库主键：
改名之后老用户装上新版，看到的是一个空白的插件，而他的旧数据还在、只是找不到了。

### 产物入库三态分流

| 宿主怎么装它 | 产物进不进仓库 | 门禁 |
| --- | --- | --- |
| 随仓库或随包走，且安装方不构建 | **必须入库**，改源码同一次提交带上重建的产物 | CI 里重新构建一次，`git diff --exit-code` 确认一致 |
| 通过打包附件分发（`.vsix`、发布页附件、制品库） | **不进库**，但打包清单必须包含它 | 发布前核一次打包清单，确认入口产物在里面 |
| 纯源码，安装方自己构建 | 不适用 | 按普通项目处理 |

**判据是「用户拿到的是仓库还是附件」，不是「这是不是插件」。** 第一态那条门禁为什么必须做：
产物和源码分开提交，迟早有一天它们不对应，而那时用户装到的是旧代码，报的问题你在本地复现不出来。

### 跨机器构建可复现两条铁律

1. **构建脚本严禁传本机绝对路径。** CSS Modules 一类工具把文件名算进类名哈希，绝对路径会让同一份
   样式在不同目录编译出不同类名——产物永不可复现。一律传**相对仓库根**的路径。
2. **首次提交前配 `.gitattributes`。** 内嵌源码的产物（source map、打包后的内联资源）对行尾差异
   极其敏感，换一台机器构建就会得到不同字节。

### 依赖与验证

**宿主运行时提供的包放 `peerDependencies` 或 `devDependencies`，不能进 `dependencies`。** 进了会
打包一份宿主副本，两个实例同时存在，而故障表现为随机的初始化失败。

**跟随版本要取完整版本列表**，不迷信「最新」标记——发布方的标记可能停在很旧的版本上。
**严禁用本地开发挂载（符号链接、路径依赖）代替打包后的隔离安装验证**：挂载绕过打包，
打包清单漏了文件也验不出来，而那正是用户那边唯一会坏的地方。

### 三级退让查证法

宿主文档没写清楚时按顺序退让，**每一步都要标注这是哪一级**：先查**宿主官方文档**（发布/打包那
一节）；再查**同类项目的实际做法**（别人的清单文件怎么写的）；最后才按**通用判据**推，且必须标注
「这是推断」。跳过前两级直接推，得到的是「看起来对」——而宿主的行为不会因为你的推断而改变。
各宿主的硬判据见 `references/plugin-ecosystems.md`。

## 四、没有专章时怎么办

五步查证，答案从**宿主自己的文档**里取，不猜：入口清单叫什么 / 宿主侧 ID 是哪个字段、在什么范围
里唯一 / 宿主加载哪些文件（一个入口？一个目录？带不带资源）/ 宿主版本约束写在哪
（`engines` / `minAppVersion` / `peerDependencies`）/ 用户从哪儿装——最后一条决定产物入不入库。

查不到就说查不到，不要按「另一个插件大概也这样」推：每个宿主的这几条答案都不一样。

**只在会被重复用到时才沉淀成专章。** 一次性处理的项目不写：写下来的成本是有人要读它、维护它，
而一次性知识的寿命只有一次。

## 五、建库检查清单

不分能力目录还是插件，建仓库前过一遍：

- [ ] 入口清单文件在仓库根，字段齐全
- [ ] 宿主侧 ID 与分发侧包名已经分开，且知道哪个不能改
- [ ] 产物入库策略已按分发通道定下来
- [ ] 版本号只有一个来源，标签与它同形
- [ ] 用户从哪儿装已经明确（决定要不要发制品库）
- [ ] 宿主运行时依赖不在 `dependencies` 里
- [ ] README 里写了宿主版本要求（从清单读，不凭印象）

## 事实来源

本文件涉及的外部事实会随平台/宿主版本变化，动手前查官方文档，本文件写的是判定流程而不是字段快照。

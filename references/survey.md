# 勘察

## 何时读本文件

每次任务开始时读。它回答：怎么跑勘察、读回来的字段什么意思、从事实到动作怎么判。

---

## 一、为什么必须先勘察

同一个动作在不同项目上后果不同。`git init` 在空目录里是起步，在别人仓库的子目录里是
**长出一个嵌套仓库**。这类错误的共同点是：**做的时候不报错，很久以后才发现。**

顺序是死的：先读事实，再判断，最后动手。勘察只读，所以读完本文件之前就可以先跑一遍。

| `maturity` | 含义 | 这次用多大劲 |
| --- | --- | --- |
| `empty` | 什么都没有 | **不做治理**，先让项目存在（选技术栈、写源码） |
| `greenfield` | 有源码但没版本库，或没文档 | 从零配齐 |
| `partial` | 有版本库和部分文档，缺东西 | 补齐缺口，**已有的一个字节都不动** |
| `mature` | 版本库、远端、文档、CI 都在 | 只体检 |

## 二、怎么勘察

```sh
node "<本 skill 目录>/scripts/survey.mjs" "<项目目录>" --markdown
```

`<本 skill 目录>` 是 `SKILL.md` 所在目录，`<项目目录>` 是被处理的项目——**两者通常不同**。
命令可在任意工作目录下执行，路径都是显式传入的。

| 参数 | 什么时候用 |
| --- | --- |
| 默认（JSON） | 给脚本与 AI 读 |
| `--markdown` | 要把报告给人看 |
| `--probe-auth` | 推送前确认凭据。它要问凭据助手，慢几百毫秒，默认关闭 |

**它不联网。** 远端可达性、仓库设置这类要联网的事不在勘察里——那会让「反复调用勘察」
变成奢侈，而勘察必须能随便调用。

**脚本读不到的东西自己补。** 脚本读不出「这个目录是干什么的」，所以勘察分两步：
脚本给事实，你读关键文件（主说明文档、清单、既有约定）补齐意图。只看脚本输出就下结论，
等于拿着体检报告猜职业。

## 三、字段含义

### `git`

| 字段 | 用途 |
| --- | --- |
| **`isRepoRoot`** | **这个目录本身是不是仓库根** —— 见下方专栏 |
| `workTreeRoot` | 实际工作区根。`isRepoRoot` 为假时用它解释「你在哪个仓库里」 |
| **`role`** / `roleReason` | `maintainer` / `contributor-fork` / `undetermined`——决定能不能推主干、打标签 |
| `branch` / `upstream` / `ahead` / `behind` / `dirty` | 推送判断 |
| `commits` / `commitsState` | 提交数。`unreadable` 时**不要当成 0**，那会把有历史的仓库带向「首次提交」 |
| `identity` / `identity.scope` | 提交署名，以及它来自哪一层 |
| **`auth`** | 推送认证现状 —— 见下方专栏 |
| `tags` / `trackedFiles` / `historyAuthors` | 版本号对照、仓库规模、换过几次人 |

**配置有三层，不是两层。** 最容易出的误判是：`~/.gitconfig` 不存在，就以为「这台机器上
没配过东西」——而全局工具的安装器常把配置写在 `system` 层（凭据助手就是典型）。
**看 `identity.scope`，不要用「某个文件在不在」推断。**

#### `isRepoRoot` 为假时必须停下来

此时 `git` 报出的远端、分支、提交数**全部属于外层仓库**，看起来完全正常，却与你要处理的
目录无关。照单全收的后果是把改动提交进、甚至推送到一个毫不相干的仓库。

正确动作：**停下报告**，问清是并入外层仓库还是单独建库；**答复之前不提交、不推送**。

#### `auth` 四档

| 取值 | 该做什么 |
| --- | --- |
| `available` | **直接推**。不要建议重新登录，那是让人做无用功 |
| `no-credential` | 唯一需要用户动手的一档，并且只说这一件事 |
| `undetermined` | 说「未确认」，**不许翻译成「没有凭据」** |
| `n/a` | 没有远端 |

### `ecosystem`

`kinds` 是**数组**，可命中多项。`publishable` / `private` 判能不能发；
`registryFree` 表示分发不经过制品库（Go 靠标签、能力目录靠克隆）。

两个容易看错的：

- **`docs-only`** 有两个前提：有 README，且除 Markdown 外没有源码或构建描述文件。
  「一堆 `.md` 但没有 README」判成 `unknown`——问一句比猜成文档项目稳妥。
- **`skill`** 指被宿主加载的**能力目录**。它与插件的分野见 `references/skill-project.md`：
  插件把代码加载进宿主进程，能力目录把指令加载进上下文，两边判定问题没有一条答案相同。

### `commands`

键是 `install` / `build` / `typecheck` / `lint` / `test` / `verify`。
**读不到就是读不到**：没有 `test` 就没有，不要按生态惯例编一个——编出来的命令会在 CI 里
失败，而那条失败看起来像「代码坏了」。

### 其余

| 字段 | 用途 |
| --- | --- |
| `workspace.declared` | 多包仓库。真则文档写清根与子包分工、CI 在根层跑；假则别去找子包 |
| `artifacts.runtimeRequirements` | 运行环境下限。**README 直接照抄它**，读不到就不写那一节 |
| `localSkills` | 仓库自带的 skills，盘点是为了**不误删**；`valid` 为假意味着宿主会静默丢掉它 |
| `ignores.unignoredOutputDirs` | 存在但没被忽略的产物目录——会进版本库 |
| `ignores.ignoredButTracked` | 已入库又命中忽略规则——忽略规则对已入库的文件无效 |
| `risks` | 凭据形状（`tracked` / `exposed` / `ignored`）、本机路径、大文件 |

**判据是形状，所以它知道的是「像凭据」，不知道「是不是真的」。** 报告里写「待确认」。
`tracked` 最要紧：它已经在历史里，改文件不管用。

## 四、从事实到动作

判定表在 `SKILL.md` 的「能力矩阵」。这里只补两条：

**保守优先**：同一行多列冲突时按更保守的列执行。既 `docs-only` 又有远端 → 远端不重建，
发布仍不做。

**「不发布」是正常结果，不是失败。**

---

## 五、勘察完成后必须做的一件事

**把结论说成一句话**，不是复述字段：

> 这个项目现在是 X，缺 A、B、C；这次做 D、E，跳过 F（因为 G）。

用户看这一句就能判断「你是不是搞错了我的项目」。同时**预告**只有用户能定的事（许可证、
署名、可见性、账号、收不收外部贡献、要不要自动发版）——此时只预告，真实提问集中到
写文档那步一次问完。

## 六、接着上次做

用户说「继续」时**不要把「做到哪一步」交给回忆**。三个机器载体：`maturity` 与 `gaps`
（重跑勘察即得）、`docs/work/` 下的工作记录、`AGENTS.md` 的「## 取舍」节。

**重跑勘察是第一步**：只读、几百毫秒，它给出的 `gaps` 就是「还剩什么」，比翻记录快。

项目里没有工作记录就说明这件事本来不需要跨会话：按当前 `gaps` 直接做。
**不要为了「显得有条理」凭空建一份工作记录**——它的成本是有人要读它、维护它。

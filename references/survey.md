# 勘察

## 何时读本文件

- 每次接到一个项目目录，动手之前——本文件定义「先读什么、读到的事实意味着什么」。
- 需要判断某个项目属于哪一类、该做哪些事、该跳过哪些事时。
- 对勘察脚本的输出有疑问，想知道某个字段的判定依据时。

## 一、为什么必须先勘察

同一套动作套到所有项目上，一定会做错事：给纯文档目录配发布流程是无用功，给已经配好
远端仓库的项目重建仓库是破坏，给一个不该进版本库的目录做首次提交会把几十万文件写进
历史。

所以第一原则是**只读先行**：勘察没有完成之前，不写任何文件。

勘察的产物是**事实**，不是结论。事实由脚本读出来，结论由本项目自己的判据推出来。
这条分工很重要：脚本只负责「读到了什么」，不负责「所以该怎么办」——因为判据会随项目
类型变化，而事实不会。

## 二、怎么勘察

```sh
node scripts/survey.mjs <项目目录> --markdown   # 给人看的摘要
node scripts/survey.mjs <项目目录> --json       # 给机器消费
```

脚本只用运行环境内置的模块，零依赖，不会因为项目里缺什么而跑不起来。

**脚本读不到的东西自己补**。脚本只看文件系统与版本控制的状态，它读不出「这个目录是
干什么的」。所以勘察分两步：

1. **脚本**给出结构化事实（有没有仓库、什么生态、缺哪些文档、有什么风险）。
2. **你**读关键文件补齐意图——至少读一遍项目的主说明文档（README 一类）、清单文件
   （如果存在）、以及任何看起来是项目约定的文件（已有的贡献指南、已有的内部文档）。

第 2 步不能省。只看脚本输出就下结论，等于拿着体检报告猜职业。

## 三、输出字段的含义

### `target`

解析后的绝对路径与目录名。目录名用于推导项目标识（例如仓库名），但要先做规范化。

### `git`

版本控制的现状。关键字段：

| 字段 | 含义 | 判定用途 |
| --- | --- | --- |
| `available` | 环境里有没有 git | 没有则整条版本管理链路不可用，如实报告 |
| `present` | 这个目录是不是已经在仓库里 | 决定是「初始化」还是「补齐」 |
| `branch` | 当前分支 | 决定推送哪个分支 |
| `remote` / `remotes` | 远端地址 | **有远端时先看它指向谁**：指向正本还是别人的 fork，决定了这个操作者是维护者还是贡献者 |
| `dirty` | 未提交的改动数 | 大于 0 时先存一个可回退的存档点 |
| `commits` | 提交数 | 0 表示还没有任何提交 |
| `identity` | 提交署名与它的作用域 | 空则必须补；`scope` 说明它来自仓库级还是继承自全局 |
| `upstream` | 上游跟踪分支 | 未设置时推送需要显式指定 |
| `tags` | 已有版本标签 | 与清单文件里的版本号对照，看是否已经对齐 |

### `ecosystem`

判定出的项目类型与**判定依据**。依据是给人和 AI 复核用的——判定错了，看依据能立刻
发现。

可能的值：`node`、`python`、`rust`、`go`、`java`、`ruby`、`php`、`dotnet`、
`dsh-plugin`、`dsh-skill`、`docs-only`、`unknown`。

注意：判定结果可以是**多个**（例如一个仓库里既有 Node 前端又有 Python 后端）。这时
按每个生态各自的规则分别处理，不要只挑一个。

`unknown` 表示既没有清单文件也没有文档——这时**不要猜**，直接问用户这是什么项目。

### `commands`

从清单文件推导出来的构建 / 测试 / 检查命令。**推导不出来时字段为空，这是正常结果，
不是错误**——空的含义是「这个项目没有声明这些命令」，此时不要自己编一条命令出来，
而应当去读项目已有的说明文档，或问用户。

有 `packageManager` 字段时，说明项目已经指定了包管理器——**沿用它的，不要换成别的**。

### `artifacts`

决定「产物入不入库」的既成事实：

| 字段 | 含义 |
| --- | --- |
| `publishScope` | 项目是否声明了发布范围（哪些文件会被分发出去） |
| `hooks` | 发布前后的钩子（说明「产物是构建出来的」） |
| `distDirsPresent` | 常见的产物目录是否存在 |
| `private` | 项目是否被标记为不可发布 |

这几个字段合起来回答一个问题：**拿到这个项目的人，会不会自己跑一次构建？**
- 会（这是源码，产物由使用者生成）→ 产物**不进**版本库
- 不会（这是被安装、被分发的东西）→ 产物**必须进**版本库

详细判据见 `references/version-control.md`。

### `docs`

文档现状：哪些已有、字节数多少、`.github` 下有什么。这是「文档套装」那一步的缺口清单。

### `ignores`

忽略规则的现状。特别看 `ignoredButTracked`：**已经被跟踪又被忽略的文件**。这是最
容易埋雷的一种状态——用户以为加了忽略就没事了，实际上文件还在版本库里。

### `outputs`

依赖目录与产物目录的存在情况。它们只影响体量统计与忽略规则，不影响能力判定。

### `risks`

| 字段 | 含义 | 处置 |
| --- | --- | --- |
| `secretFiles` | 形状上像敏感文件的文件 | 见下一节 |
| `secretContent` | 文件内容里出现凭据形状 | 见下一节 |
| `homePathLeaks` | 内容里出现构建机的私有路径 | 换台机器就失准，应当改成相对路径或环境变量 |
| `largeFiles` | 单个文件达到数十 MB | 先报告体量与占比，再决定外置存储还是忽略 |
| `symlinks` | 符号链接 | 跨平台行为不同，要提醒 |
| `nestedRepos` | 子目录里还有另一个仓库 | **停下报告**，问清楚是纳入还是忽略 |

风险字段是**提示**，不是判决。命中之后要打开那个文件确认，再决定怎么处理——脚本认
形状，不认语义。

### `scale`

文件数与总体积（**不含**依赖目录与版本控制目录）。用途是判断仓库边界：体量异常大的
目录不应当整体纳入仓库。

`truncated` 为真表示走查提前结束了（目录太大），这时体量数字是下界，不是准确值。

## 四、从事实到动作：判定表

勘察完成后，用这张表把事实翻译成「做什么」。它只是常见组合，不在表里的情况按同样的
思路推：**这个项目有没有那个能力，消费者在不在那个生态**。

| 勘察到的事实 | 该做 | 该跳过 |
| --- | --- | --- |
| 没有任何清单文件与文档 | 先问用户这是什么项目 | 发布相关的全部动作 |
| 没有仓库 | 初始化、属性声明、忽略规则、首次提交 | — |
| 已有仓库但没有提交 | 补属性与忽略规则，再做首次提交 | 不要重复初始化 |
| 已有仓库且有远端 | 只校验远端与元数据，补缺口 | **不要重建仓库** |
| 远端指向别人的仓库（fork） | 按贡献者处理：推自己的分支 | 不推主干、不打标签、不发布 |
| 有清单文件且声明了发布范围 | 可走发布链路 | — |
| 有清单文件但没有发布范围声明 | 先把发布范围显式声明出来 | 不要靠默认规则发布 |
| 项目被标记为不可发布 | 只做版本管理与文档 | 发布相关的全部动作 |
| 纯文档目录 | 版本管理 + 文档套装 + 远端 | 依赖、构建、发布 |
| 体量异常大（数十万文件 / GB 级） | 先确认仓库边界，只在合适的子目录建库 | 不要把整根纳入 |
| 存在敏感文件或凭据形状 | **停下**，报告并给出处置建议 | 在处置清楚之前不提交 |

这张表与 `SKILL.md` 的能力矩阵是同一件事的两种粒度：能力矩阵按**生态**分行（决定做
哪几个能力面），本表按**状态**分行（决定这些能力面里哪些该跳过）。两处冲突时以更保守
的为准——多问一句，好过做错一件不可逆的事。

## 五、勘察完成后必须做的一件事

向用户复述**一句话结论**：这个项目现在是什么状态、准备做哪几件事、跳过哪几件、以及
为什么跳过。

这句话的作用不是汇报，是**对齐**。勘察得出的判断可能与用户的预期不同（例如用户以为
这个项目该发布，而实际上它是个纯应用）——在这种分歧上，早问一句的成本远低于做完再
返工。

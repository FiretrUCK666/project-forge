# 版本管理

## 何时读本文件

以下任一情形成立时，必须完整读完本文件再动手：

- 要为该项目建立版本库（首次初始化，或目录里已有仓库但要补齐纪律）；
- 要写或修改文本属性声明、忽略规则、提交署名；
- 要执行提交、推送、回退、撤销，或判断某次改动该不该入库；
- 要判断某个文件、目录、数据、产物是否属于版本库；
- 要处理大文件、密钥、嵌套仓库、符号链接等边界情形；
- 要复核一次已完成的版本管理配置是否完整、是否正确。

本文件描述**机制与判据**，不描述某个项目的取值。凡需要具体值的地方（远端地址、
分支名、署名、产品标识），一律从项目自身的权威来源现场读取。

---

## 核心判据：什么该进版本库，什么不该

**拿到这个仓库的人，除了仓库内容之外，能不能自己把这份东西生成出来？**

- **能自己生成 → 不进版本库**：生成方式写在清单文件里、或由工具约定俗成，任何人一次
  命令即可复得；
- **不能自己生成 → 必须进版本库**：缺了它，别人拿到的仓库要么跑不起来，要么语义
  不完整。

判据问的是「可再生成性」，不是「重不重要」，也不是「大不大」：一份体积很小但别人
无法凭空复得的文件必须进库，一个体积巨大但一条命令就能装回来的目录绝不进库。

### 这条通则为什么能同时解释两个看似矛盾的现象

**现象一：依赖目录永远不进库。**
依赖目录（各生态的依赖安装目录）的内容完全由清单文件决定：清单声明了依赖与版本约束，
任何人执行安装即可得到等价、甚至更适配自己平台的副本。把它塞进库既不增加信息，又让
每次依赖变动产生海量噪声差异，还带来平台相关的二进制冲突。它是**典型的可再生成物**。

**现象二：被安装、被分发的包里，编译产物必须进库。**
因为**安装方不会替它跑构建**：安装流程只做「取回 + 解包 + 放置」。对安装方而言，编译
产物就是**不可自行生成**的输入。同理，镜像源、语言运行时的包仓库、各类制品库收录的
内容，都属于这一类。

两者不矛盾：判据问的是**接收方**，不是「文件类型」。同一个编译产物，在开发仓库里是
可再生成物，在发布包里是不可再生成物——因为接收方不同、能力不同。

### 怎么判断本项目的产物属不属于第二类

不要靠猜，去读项目的权威声明。按下列顺序找证据：

| 证据 | 在哪找 | 它说明什么 |
| --- | --- | --- |
| 发布范围声明 | 包清单里的发布文件范围字段（白名单或黑名单） | 被声明的文件会被打包发出去，安装方拿到它们且不构建 |
| 发布前钩子 | 清单里的发布时间钩子（打包前、发布前一类） | 有钩子说明发布时现构建，产物可能不必入库 |
| 安装后构建约定 | 清单的安装脚本、文档里的安装步骤 | 约定「安装方自己构建」时才允许产物不入库 |
| 安装源类型 | 安装命令指向包仓库还是源码地址 | 指向包仓库 = 安装方不构建，产物必须入库 |

判据来源是**这些声明本身**，不是某个固定文件名或字段名。不同生态的清单文件、字段名
与钩子名各不相同，一律现场读，不要假定。

### 补充分类

**数据文件、生成物、备份产物**通常属于「不该进库」——要么可由源生成，要么是一次性
本地产物，进库只会让仓库缓慢腐化。**密钥与敏感信息**不属于以上任何一类，而是**永不
进库**，无论是否可再生成（判据与处置见「密钥与敏感信息门控」）。

### 几种特殊的仓库形态

判定边界之前，先认出这几种「不是一个目录对应一个仓库」的形态：

| 形态 | 怎么认出来 | 边界要点 |
| --- | --- | --- |
| **工作树**（同一仓库挂到多个目录） | 目录里的 `.git` 是**文件**而不是目录，内容指向别处 | 它是同一个仓库的另一个检出，**共用同一份历史与分支**。在里面提交等于在原仓库上提交——不要误当成独立项目再建一个库 |
| **子模块 / 嵌套仓库** | 子目录里有自己的 `.git` | 见「嵌套仓库与特殊情况」：停下问清是纳入还是独立 |
| **裸仓库** | 没有工作区文件，只有仓库结构 | 不是用来开发的，不要往里写文件 |

工作树这一条最容易踩：看到 `.git` 是个文件，容易以为仓库坏了。它其实是正常的，此时
要按「已经在一个仓库里」处理，并确认用户想操作的是哪一份检出。

### 目录不在自己的仓库根上时

这是比上一条更常见、后果也更重的情况：目标目录只是**某个外层仓库的一个子目录**。

它的危险不在于报错，而在于**一切看起来都正常**——查询远端、分支、提交数都会如实返回
结果，只是那些结果属于外层仓库。照单全收就会把改动提交进、甚至推送到一个毫不相干的
仓库。

判据：这个目录是不是仓库的**工作区根**。不是的话，**先停下**，向用户说明「这个目录在
X 仓库的工作区内」，问清楚是要并入外层仓库还是在本目录单独建库；**在得到答复之前不
提交、不推送**。

## 执行顺序（顺序本身就是正确性的一部分）

### 1. 声明文本属性（必须在首次提交之前）

属性声明只对**之后**的检出与入库生效：一旦首次提交已落盘某一种行尾，后续所有机器都会
继承这个错误，而修正它需要重写历史——已推送时尤其昂贵。

**声明晚了的后果**：工作区文件可能残留另一套行尾，而仓库与 CI 检出时用另一套行尾，
于是**同一份源码在不同机器上产生不同字节的产物**。最容易暴露的是内嵌源码原文的产物
（映射文件、生成代码、快照文件、内联资源的打包结果）：它们逐字节记录了行尾，本机与
CI 永远对不上，表现为「本机构建通过、CI 上产物 diff 不断」这种极难归因的持续红灯。

**修正办法**：先确认属性声明齐备，再按属性重新检出（清空索引后强制重置，或重新
克隆），然后重建产物。只删报错文件、或只改本机编辑器设置，都不解决根因。

### 2 至 4. 忽略规则、提交署名、密钥扫描（均必须先于首次提交）

三件事都必须落在首次提交之前，各有不可交换的理由：

- **合并生成忽略规则**：否则扫描与提交会把本该忽略的内容一并纳入；而一旦提交，
  忽略规则对它就不再有效（见「忽略规则」末尾）。已有内容只增不改；
- **写入提交署名**：署名是**提交时快照**，之后再配置只能影响后续提交，首个提交会
  永久带着错误或不完整的署名。仓库级配置只作用于本仓库，属于安全动作；全局配置
  影响用户全部项目，默认不改（见「提交署名」）；
- **扫描密钥**：提交之后的扫描只能做事后处置，而正确处置是轮换密钥、重建历史——
  代价远高于提交前的一次扫描（见「密钥与敏感信息门控」）。

### 5. 首次提交

前四步齐备后，用一次提交建立干净的起点：文本属性正确、忽略规则正确、署名正确、无
敏感信息。此后所有历史都建立在正确的地基上。整条序列必须**幂等**：已存在且正确的
不动，缺项的只补缺项，内容冲突的**报告并停下**，已初始化过的仓库不重复初始化。

## 行尾与文本属性

需要统一声明，是因为：**跨平台协作**时没有声明会让同一份源码在不同机器上产生纯行尾
差异的巨量改动，把真实改动淹没；**CI 在别的系统上检出**时，仓库必须声明「以什么形式
存」，让所有人检出到一致字节，构建结果才可复现；而**默认值因平台而异**，「我这儿是
正常的」只说明本机默认值与别人恰好相同，换机器即失效。

### 声明什么

| 对象 | 声明方式 | 理由 |
| --- | --- | --- |
| 文本文件（默认） | 入库统一为 LF，检出是否转换由属性决定 | 仓库内字节唯一，产物才可复现 |
| 必须保留原样的文本 | 显式声明为不转换、入库即原样 | 某些脚本、配置、许可证文本、测试夹具对行尾敏感，转换会破坏其行为 |
| 二进制文件 | 显式声明为二进制 | 避免被当作文本做行尾转换与 diff，防止静默损坏 |

原则是**默认严格、例外显式**：默认统一，个别必须保留原样的与二进制逐个声明。不要
反过来——默认随意、再逐个纠正，必然漏项。

### 常见坑

- **加入得太晚**：属性文件只影响其后的检出与入库，此前的错误已经固化；
- **工作区已有文件不会自动重新规范化**：改属性声明不会让已检出的文件自动变回目标
  形式，必须重新检出（清空索引后重置，或重新克隆，二者等价）；
- **不要依赖编辑器或系统设置**：那是个人环境，不是仓库约定，一致只能来自仓库内的
  声明文件；
- **属性能否生效取决于检出工具**：若使用别的检出工具或归档下载方式，先确认它读取
  并遵守属性声明，否则需要显式重新规范化。

## 忽略规则

若项目已有忽略文件，**只追加缺失项，绝不重写**：重写会抹掉用户已有的忽略意图，而那些
意图往往记录了「哪些文件不能进库」的真实经验，属于不可再得的隐性知识。正确做法是读出
现有内容，识别已覆盖的类别，再追加缺失行。

判断某个文件该不该忽略，依据是「**它是不是可再生成的**」与「它是不是只对本机有效」，
而不是「它在不在某个流传的模板里」——模板解决普遍性，忽略解决本项目。下表的典型类别
只是举例，**具体以项目实际使用的工具为准**：读清单文件与构建配置，看真实会产出哪些
目录与文件，而不是照抄类别。

| 范围 | 典型忽略对象 |
| --- | --- |
| 通用 | 操作系统垃圾文件、编辑器与 IDE 工作目录与索引、临时与交换文件、备份产物与归档副本 |
| Node / 前端 | 依赖目录、构建与打包输出、工具缓存、覆盖率报告 |
| Python | 虚拟环境目录、字节码缓存、类型检查与测试缓存、构建产物与元数据目录 |
| Rust | 编译输出目录、本地工具链文件 |
| Go | 编译产物、测试与覆盖率产物、本地工具缓存 |
| Java | 构建输出目录、编译中间物、依赖缓存目录 |
| Ruby | 依赖目录、打包产物、本地配置覆盖 |
| PHP | 依赖目录、缓存与日志目录 |
| .NET | 编译输出目录、中间物目录、本地用户配置 |
| 项目特有 | 本地环境变量文件、本地配置覆盖（本机路径、端口、调试开关）、运行时日志与崩溃转储、临时数据库文件、本机生成的索引与下载缓存 |

同一生态内部也可能并存多个工具，仍以项目实际清单为准。

### 一个必须记住的边界

**忽略规则对已被跟踪的文件无效**：已提交过的文件即使之后加进忽略文件，仍然留在仓库
里，仍会被提交、被推送、被别人克隆到。要让它生效，必须先从索引中移除（保留工作区
文件），再提交这次移除。忽略规则只能防未来，不能修过去。

## 提交署名

| 层级 | 范围 | 默认策略 |
| --- | --- | --- |
| 仓库级 | 只影响当前仓库 | **默认只设这一层** |
| 全局 | 影响用户机器上所有仓库 | 不擅自修改 |

全局配置是**用户的个人环境**，不是本项目的配置：为某个项目写全局署名，会静默改变
用户在其他所有项目里的提交身份，属于越界且难以察觉的破坏。只有身份确实正确、且用户
明确要求时才动全局。

### 署名从哪里取

按「**项目自身的权威来源优先，其次当前环境事实**」的顺序推导：

1. 先读项目元数据文件里是否已声明作者、维护者或所有权信息（清单、许可证、贡献者
   文件一类）——有就用它，因为那是项目自己的声明；
2. 版本控制配置里若已有署名，直接沿用；
3. 都没有时，现场读取当前环境事实（当前用户标识、托管平台账号信息），据此确定。

**邮箱**优先使用托管平台提供的、**不暴露私人邮箱**的地址形式。理由：提交记录公开
且永久可检索，一旦写入真实邮箱，它会进入所有克隆、镜像与搜索引擎，事后无法收回；
平台的匿名地址可达、可在平台内路由，既不影响协作也不泄露个人信息。**禁止凭空编造**
署名：编造的署名会让历史失真，也让后续维护者误判责任人，宁可停下问用户。

### 拿不到正确署名时，不要卡在首次提交

这里有一个真实的时序矛盾：首次提交需要署名，而**正确的匿名邮箱往往要等知道托管平台
账号之后才能定**，那通常发生在更后面的阶段。硬等会把流程卡住，硬编又会留下错误署名。

正确的处理是**分两步走**：

1. **首次提交照常做**。此时署名取当下**能确证的事实**（项目自身的作者声明、已有的
   版本控制配置、当前环境身份）。不要为了凑一个漂亮的值而编造。
2. **拿到正确值后立即修正**。署名信息在**尚未推送**时是可以安全更正的——见「回滚
   分档」：已提交未推送的提交属于可回退的范畴。

**关键在于推送之前把这件事做完**。一旦推送，署名就随历史进入了所有克隆（与上面邮箱
那段的理由相同）；而在推送之前，它只是本地的一次提交，改掉没有任何代价。

因此这条约束不是「首次提交必须完美」，而是：**首次提交之前先把能确定的定下来，推送
之前把剩下的一定要确认掉**。若中途发现署名不对且**已经推送**了，不要改写已推送的
历史——按「回滚分档」用反向提交处理，或与用户确认后另行处理。

## 提交纪律

**一次实质变更一个提交**：一个提交对应一个可独立描述的意图，混在一起的提交无法单独
回退、无法单独审查，是后续所有混乱的源头。若某产物由源文件生成，**产生它的源改动与
产物本身必须在同一次提交里**，否则仓库会短暂存在「产物与源码不一致」的中间状态：
此状态下别人检出、构建、对比产物都会失败，CI 会红且难以归因。这条同样适用于生成物、
快照、锁定文件等一切由源派生的被跟踪文件。

**提交信息**要简短，说明**做了什么**；**禁止 emoji**；中文或英文都可，但**项目内保持
一致**，不要混用；不要用无信息量的占位文字。

**何时先存一个「改动前存档点」**：当接下来的操作**改动量大、有风险、或涉及批量重写**
时（大规模重构、批量格式化、依赖大版本升级、历史整理、批量重命名），先提交当前工作
区，形成一个干净起点。理由是版本管理最可靠的后悔药是「有一个已知良好、可精确回到的
状态」；工作区一旦被大规模改动冲刷，未提交的原始状态就无法恢复。存档点的价值不在于
它多完整，而在于它**一定存在**，代价只有一次提交。

---

## 回滚分档

按**改动走到了哪一步**选手段，越靠后代价越高、可选项越少。

| 状态 | 手段 | 代价 / 风险 |
| --- | --- | --- |
| 未提交（仅工作区改动） | 丢弃工作区改动 | 改动永久丢失，无备份；丢弃前先确认没有需保留的片段 |
| 已提交，未推送 | 回退到存档点 | 本地历史被改写；只要确定没被别人取用，代价很低 |
| 已推送 | 用反向提交抵消这次改动 | 历史保留两条记录，安全；但不清理历史，仓库记录会变长 |
| 已发布到制品库 | 只能发新版本修正 | 版本号不可复用、通常不可删除；用户可能已装上有问题的版本 |

**为什么已推送的历史永不改写**：推送之后**别人可能已经基于它工作**——克隆、拉取、
分支、基于该提交开发、在 CI 中引用它。改写历史会把这些人的基础从脚下抽走，导致他们
的本地历史与远端分叉，冲突排查成本远高于多一条反向提交。因此已推送的历史一律用
**反向提交**（新增一个抵消改动的提交）处理，而不是强制覆盖。

同样地，已发布到制品库的版本号**不可复用**：同名同号的制品可能已被缓存、被锁定、被
依赖声明固定引用。正确处置是发一个新版本修正，并在说明里写清修正了什么。

## 大文件与体积

版本库保存的是**每个文件的每一版内容**。一旦把超大文件提交进去，它的全部历史版本会
随克隆一起被每个使用者下载；而且**历史里的体积永久存在**——把当前文件删掉、把新版本
替换掉，都不会让仓库变小，因为旧对象仍在历史中。后果是不可逆的体验灾难：克隆变慢、
CI 检出变慢、磁盘占用失控，而修复它需要重建历史（对已推送仓库意味着所有协作者都要
重新克隆）。因此**入库前先看体量**。

不设死数字，按量级判断：单个文件达到**几十 MB** 量级就该停下来问它是否必须进库；
达到**上百 MB** 基本可判定不应直接进库；目录总体积或文件数量达到「克隆一次要等很久」
的量级，先确认仓库边界。判断先于动作：先测量（看目录体积与最大文件），再决定策略。

出路有两条。**外置存储**（大文件存储一类机制）在仓库内只保留指针文件，适合「必须做
版本管理的大文件」——保留版本能力，把体积放到仓库之外；但它不是万能：要求使用者额外
安装工具、需要服务端支持、克隆也多一步。**加入忽略**适合只对本机有意义的文件（本地
数据、临时导出、构建缓存）。如果某文件其实可由源生成或从外部稳定获取，正确做法是
忽略并在文档里写清获取方式。

### 历史已被污染时

正确做法是**重建历史**，而不是继续在上面叠加：把大文件从当前版本删掉只是掩盖问题，
历史里的体积仍在，而重建历史是唯一能让仓库真正变小的方法。因此必须在**推送之前**把
体量问题拦住——推送之后重建，代价是所有协作者重新克隆。

同理，**把仓库建在一个超大目录的根上是错的**：若目标目录里已有几十万文件、体积以
GB 计（例如整个用户主目录、整个磁盘分区、包含大量影像或数据的归档目录），在其中
初始化仓库会导致首次提交耗时极长、仓库体积失控、扫描与状态检查缓慢，且几乎无法回退。
正确做法是**先确认仓库边界**——这个项目真正的根在哪，哪些子目录属于它、哪些不属于，
只在合适的子目录建库。边界不明确时停下问用户，不要擅自在大目录的根上初始化。

## 密钥与敏感信息门控

**提交之前扫描**，不是提交之后：提交后的扫描只能做事后处置，而事后处置的代价是轮换
密钥加重建历史，且无法保证没有被取走。

| 类别 | 说明 |
| --- | --- |
| 环境变量文件 | 本地环境配置，通常含真实凭据 |
| 私钥与证书文件 | 私钥、密钥库、证书及其私密部分 |
| 凭据文件 | 各类服务账号、访问凭据、配置文件里的口令字段 |
| 令牌文件 | 访问令牌、刷新令牌、会话令牌 |
| 内容中的高熵串 | 正文里出现的长随机字符串、已知的令牌前缀 |

最后一项容易被漏：密钥不一定在「看起来像密钥的文件」里，也可能硬编码在源码、测试
夹具、文档示例或配置文件里。

**命中即停止**：不要「先提交完再处理」，也不要自行判断「这个可能不算敏感」而继续。
停止后要做的是：报告**文件与位置**（哪个文件、哪一行或哪个字段）；给出处置建议——
若该值只是占位或已失效，说明判断依据，若有效则按「已泄露」处理；从本次提交中排除它
（先从索引移除）并加入忽略规则，同时给出一份不含真实值的示例文件供他人参考格式。

从工作区删掉 与 从历史里去掉 是两件完全不同的事：前者只影响当前文件，历史里的旧版本
仍完整保存着那个值；后者需要重写历史，已推送时还要求所有协作者重新克隆。因此**一旦
提交过，必须视为已泄露**，正确处置是**轮换密钥**——在源头使其失效并换新；只删文件会
让一个仍然有效的密钥安静地留在历史里。**忽略规则只能防未来，不能防已经提交的**。

## 嵌套仓库与特殊情况

| 情形 | 判据 | 处置 |
| --- | --- | --- |
| 目录里已有另一个仓库（子模块或嵌套） | 子目录内存在独立的版本管理元数据 | **停下报告，问清楚**是纳入（作为子模块或直接合并）还是忽略，不要擅自决定 |
| 已存在指向别人仓库的远端（例如 fork） | 远端地址不属于当前操作者的发布目标 | 按**贡献者**对待：只推自己的分支、开合并请求，不推主干、不打标签、不发布 |
| 目录名含空格或非 ASCII | 路径本身 | 路径一律用引号包裹；**不同 shell 的引号与转义规则不同，不要依赖它** |
| 大小写不敏感的文件系统（部分系统的默认行为） | 仅大小写不同的两个路径被当作同一个 | 需要改名时用**两步重命名**（先临时名再目标名），不要依赖大小写差异 |
| 符号链接 | 仓库内存在指向外部的链接 | 跨平台行为不同（有的系统无法创建、有的会跟随或展开）；先确认目标是否在仓库内、是否各平台都需要，必要时改存真实文件或写清获取方式 |

## 幂等要求

本流程可能被重复执行（第二次、第三次接手同一个项目）。第二次及以后的执行必须满足：

| 现状 | 动作 |
| --- | --- |
| 已存在且正确 | **不动**，不重写、不追加等价内容 |
| 已存在但缺项 | **只补缺项**，保留已有内容与格式 |
| 已存在但内容冲突 | **报告并停下**，说明冲突在哪，由人决定，不覆盖 |
| 已初始化过的仓库 | **不重复初始化**，转为检查与补缺 |

判断「正确」与「冲突」按语义，不要按文本逐字比对：等价声明（同一意图的不同写法）
视为已存在，不构成冲突；互相排斥的声明（同一路径被同时声明为文本与二进制、同一文件
既被跟踪又被忽略）才是冲突。凡拿不准，报告并停下比擅自覆盖安全。

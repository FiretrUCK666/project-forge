# 版本管理

## 何时读本文件

动版本控制之前读：首次提交前、补忽略规则、查提交署名、扫凭据、处理大文件、挑选回滚方式，以及遇到「这个目录在别人仓库里」「`.git` 是个文件」这类不好判断的形态时。

## 判据：什么该进版本库

**一条通则**：拿到仓库的人，能不能用一条标准命令把它重新生成出来？

- **能** → 不进版本库（依赖、编译产物、缓存、本机状态）。别人的机器上会重新长出来。
- **不能** → 进版本库（源码、文档、配置、测试夹具、锁文件）。别人拿不到就没有。

这条通则能解释三个看起来矛盾的现象，而它们都没有例外：

| 现象 | 判据怎么用 |
| --- | --- |
| 插件把编译产物提交进仓库，**对** | 宿主安装插件时不替它构建，那个产物就是「别人拿不到就没有」 |
| 同一个插件把构建缓存也提交，**错** | 缓存能重新生成。区别不在「是不是产物」，在「能不能重新生成」 |
| 锁文件进仓库，**对** | 它不能从任何东西推导出来；别人拿不到就可能装上不同版本 |

按同一条通则速判常见文件：

| 该进 | 不该进 |
| --- | --- |
| 源码、测试、夹具里的固定数据 | 依赖目录（`node_modules`、`.venv`、`target`） |
| 配置模板（`.env.example`、默认配置文件） | 本机状态与真实密钥（`.env`、凭据文件） |
| 锁文件（`package-lock.json`、`Cargo.lock`、`uv.lock`） | 构建产物，除非分发通道不替接收方构建（缓存一律不进） |
| 项目的契约与流程文件（`AGENTS.md`、`README`、许可证全文） | 编辑器与操作系统的临时文件（`.DS_Store`、`*.swp`） |

## 执行顺序（顺序本身就是正确性）

1. **文本属性**（`.gitattributes`）——必须在首次提交之前。
2. **忽略规则**（`.gitignore`）。
3. **提交署名**（`user.name` / `user.email`）。
4. **凭据扫描**，按扫描结果处置。
5. 到这一步才**首次提交**。

前四步的顺序不能调，也不能省。理由一致：一旦进了历史，处理成本就从「改一个文件」变成「轮换凭据 + 重写历史」，而重写历史是不可逆的对外动作。

**接手一个已经在跑的项目时，这四步照样补。** 它们对已入库的历史不起作用，但对下一批提交起全部作用。补完只多做一件事：`git add --renormalize .` 把行尾一次性对齐，然后单独提交这一次规范化——不要把它混进任何功能改动里。

## 文本属性

```gitattributes
* text=auto eol=lf

# 必须在 Windows 上保留 CRLF 的脚本
*.bat text eol=crlf
*.cmd text eol=crlf
*.ps1 text eol=crlf

# 二进制：不做行尾转换，也不参与文本差异与合并
*.png binary
*.jpg binary
*.jpeg binary
*.gif binary
*.ico binary
*.webp binary
*.pdf binary
*.zip binary
*.gz binary
*.tgz binary
*.7z binary
*.woff binary
*.woff2 binary
*.ttf binary
*.otf binary
*.eot binary
```

两类例外都不能省。**必须 CRLF 的脚本**写成 LF 之后 Windows 会拒跑，而报错不指向行尾；**二进制**漏掉之后 git 会试图做行尾转换，文件在检出后损坏。

属性文件的匹配**从上到下**，后匹配覆盖先匹配——所以先写 `*`，再写例外，顺序反过来整个文件立刻失效。

已有历史里混进过 CRLF 时，补上属性后跑一次 `git add --renormalize .`，否则旧文件的行尾会永远保持原样。

同一个文件还管打包：`<路径> export-ignore` 让 `git archive` 跳过该路径。项目要产出「只含用户需要的东西」的压缩包时，排除规则写在结构里，不要靠人记得删——靠人记得的那一步，总有一次没人记得。

写完要看它真的生效，不能凭「我写了」。`git check-attr text eol -- <某个文件>` 会输出它实际命中的那两条规则；输出不是你以为的那两条，说明匹配顺序写反了，而文件本身没有任何异常。

## 忽略规则

**`.gitignore` 对已入库的文件无效。** 已经进去了的要先 `git rm --cached <路径>` 把它从索引里拿掉。勘察的 `ignores.ignoredButTracked` 非空就是在说这件事。

**模板要留口子**：`.env` 忽略，但 `.env.example` 要在库里，否则别人不知道该填什么。写法是单独一行 `!.env.example`，且必须写在忽略它的那条规则之后——先忽略再放行，顺序反了不生效。

## 提交署名

取值顺序 `local` → `global` → `system`。**看勘察的 `identity.scope`，不要用「某个文件在不在」推断**：全局工具的安装器常把配置写在 `system` 层，`~/.gitconfig` 不存在不代表这台机器没配过。

四条硬防呆，每一条都有代价：

- **默认只写 `--local`。** 严禁改 `--global` 污染用户的全局配置——那是他所有项目共用的，改坏之后每一个仓库都跟着变，而他在下一个仓库出问题之前不会知道是谁改的。
- **优先用 `users.noreply.github.com` 匿名邮箱。** 真实邮箱会永久写进每一个公开提交，而且删不掉。
- **读到系统占位署名（`Administrator` / `root` / `user` / `admin`）或临时署名未确认前，只许本地提交，严禁 `git push`。** 这类署名推上去之后，历史里的提交追溯不到人；改起来要重写历史。
- **接手老项目时做四方对齐**：git 署名 / 平台账号 / `LICENSE` 持有人 / 清单里的 `author`。四者不一致说明这个项目换过人，或者一直是别人代提交——先问清，再动。

**署名缺失是真缺口，但它可以后补**（改完配置，新的提交就对了）。卡在「没署名就不提交」只会让人绕过去用一个错误的署名，那更糟。正确做法：**照常提交，在汇报里说清缺什么、怎么补**。

老项目看 `historyAuthors`：判断标准不是「对不对」，是「这些提交还能不能追溯到人」。追溯不上的历史，出问题时帮不上忙。

**按路径存凭据时**（`credential.https://host/path`），查凭据要给三行：`protocol=https`、`host=github.com`、`path=<owner>/<repo>.git`。缺 `path` 就查不到，症状是「登录了却推不上去」，而所有报错都说认证失败。

## 特殊仓库形态

先判形态，再动手。这四种形态被当成普通仓库处理时，后果都不是报错。

| 形态 | 怎么认 | 严禁 |
| --- | --- | --- |
| **git worktree**（同一仓库的多个工作区） | `.git` 是**文件**不是目录，内容是一行 `gitdir: <路径>`。用 `git rev-parse --git-common-dir` 确认它指向共享的仓库目录 | **严禁误判为「仓库损坏」**，**严禁重跑 `git init`**——那会在工作区里套出一个新仓库，原有历史当场脱钩 |
| **子模块 / 嵌套仓库** | 子目录里有自己的 `.git`（目录或文件都可能） | 停下问边界：当子模块、各自独立、还是并入父仓库。三种处置互相不兼容，选错要拆历史 |
| **裸仓库** | `git rev-parse --is-bare-repository` 为真，目录里没有工作区 | 不能直接改文件——那里根本没有文件。先克隆出工作区，改完再推回 |
| **超大目录**（数万文件 / GB 级） | 勘察的 `scale.totalFiles` 与 `scanCoverage` | 建库前先确认根边界与要纳入的子目录。整根纳入可能几十分钟起步，还会把别人的数据搬走 |

## 凭据门控

**提交之前先扫。** 勘察的 `risks.secretFiles` 与 `risks.secretContent` 给出位置（精确到行）与状态，按状态分档处置：

| 状态 | 处置 |
| --- | --- |
| `ignored` | 安全，不要打扰用户——它本来就该待在那儿 |
| `exposed` | 提交前必须处理：加进忽略规则，或脱敏后换成模板 |
| `tracked` | **最要紧**：改文件不管用，见下面两条分流 |
| `undetermined` | 没有版本库可查。写「未核实」，不写「干净」 |
| `unverified-large` | 体量过大没做内容校验。同样写「未核实」 |

**已入库的凭据，按有没有推送过远端分两条路：**

| 情况 | 顺序 |
| --- | --- |
| **从未推送过远端** | 直接改写本地历史清除即可。没有别人拿得到过，不需要轮换 |
| **已经推送过远端** | **必须先去平台吊销并轮换密钥，再清历史。** 顺序反了毫无意义 |

**「删掉那行不等于没事。」** 凭据一旦进了远端历史，它就已经泄露了——即使后来删掉，历史里还有，克隆过的人手里也有。所以这一档的处理不是「改文件」，是「让那把钥匙失效」。这个区别不解释清楚，用户会以为删掉那行就没事了。

**已入库的凭据不该让整个任务停下来。** 正确顺序：把位置（文件:行）原样报给用户 → 说清处置是先轮换再清历史 → 其余不受影响的事照常做完。停下来的代价是「用户什么也没得到」，而问题一点没少。

## 提交纪律

- **一次实质变更一个提交。** 混在一起的两个改动，出问题时只能整段回退。
- **说清改了什么、为什么。** 读它的人（包括未来写发布说明的人）要能据此讲出一句使用者听得懂的话。
- **禁用 emoji，不用内部编号、任务代号、流程名充当说明。** 发布页面上的读者不知道它们是什么。
- **大改动或有风险的操作前，先提交一个干净存档点。** 出事时能回到「什么都还没坏」的那一刻，而不用去翻 stash。
- **源码与入库的派生产物必须同一次提交。** 分两次提交，中间那一刻的仓库是自相矛盾的，别人恰好检出这一版就会拿到源码与产物对不上的东西。

## 回滚分档

| 情况 | 怎么回 | 边界 |
| --- | --- | --- |
| 还没提交 | 直接改回去，或 `git restore` | 无风险 |
| 已提交、未推送 | `git reset --soft`（保留改动）或 `--hard`（丢弃） | 本地动作，可逆 |
| 已推送、在共享分支上 | **`git revert`** 造一个反向提交 | 历史不改，别人不用重拉 |
| 已发布到制品库 | **只能发新版本修正**。版本号单调递增，**永不复用或删除** | 已发布的版本不能改，也不能撤回 |

**强制推送与改写已推送历史永不自动执行。** 判据不是「我能不能」，是「有没有人已经基于它工作了」——而那个问题脚本答不了。

## 大文件

超过几十 MB 的文件进历史之后，每次克隆都要付它的代价，而且是永久的（历史不会缩小）。

| 状态 | 处置 |
| --- | --- |
| 还没提交 | 加进忽略规则，或换外部存储 |
| 提交了没推送 | 可以改写历史拿掉 |
| 已推送 | 改写历史 + 通知所有克隆过的人重拉。**不可逆**，先给清单确认 |

**先判该不该进，比后面怎么收拾重要得多。** 收拾一次要动历史、要通知所有人，而判断只花一秒。

同一个目录里出现 GB 级文件时，先分清它是数据还是测试夹具：数据换外部存储，夹具要压缩成小样本。两个都做不到，就别把它纳入版本库——那不是一个「以后再说」的决定，它每次克隆都要付一次。

## 幂等

重复执行结果相同：已有 `.gitattributes` / `.gitignore` 时只补缺的行，不覆盖；已配好的署名不改；已提交的改动不重复提交。**判据是第二次跑与第一次跑，文件字节相同。**

顺手一条：在大小写不敏感的文件系统上只改文件名大小写要两步——`git mv a tmp`，再 `git mv tmp A`。一步做完 git 认不出改名，远端会保留旧名字。

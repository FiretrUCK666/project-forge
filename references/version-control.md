# 版本管理

## 何时读本文件

要动版本控制时读：首次提交前、补忽略规则、查提交署名、扫凭据、处理大文件，
或遇到「这个目录在别人仓库里」。

---

## 判据：什么该进版本库

**一条通则**：拿到仓库的人，能不能用一条标准命令把它重新生成出来？

- **能** → 不进版本库（依赖、编译产物、缓存、本机状态）。别人的机器上会重新长出来。
- **不能** → 进版本库（源码、文档、配置、测试夹具、锁文件）。别人拿不到就没有。

这条通则能同时解释两个看起来矛盾的现象：**插件把编译产物提交进仓库**是对的（宿主安装时
不替它构建，那个产物就是「别人拿不到就没有」）；**同一个插件把构建缓存也提交**是错的
（缓存能重新生成）。区别不在「是不是产物」，在「能不能重新生成」。

**锁文件进仓库**也是这条：它不能从任何东西推导出来，而别人拿不到就可能装上不同版本。

### 目录不在自己的仓库根上时

`git.isRepoRoot` 为假 → **停下来**。此时 git 报的一切都属于外层仓库。问清是并入还是单独
建库，**答复之前不提交、不推送**。

---

## 执行顺序（顺序本身就是正确性）

1. **先声明文本属性**，必须在首次提交之前。
2. **忽略规则**、**提交署名**、**密钥扫描**——三件都必须在首次提交之前。
3. 到这一步才**首次提交**。

理由一致：一旦进了历史，处理成本不再是「改一个文件」，而是「轮换凭据 + 重写历史」。

---

## 文本属性

```gitattributes
* text=auto eol=lf
*.bat text eol=crlf
*.cmd text eol=crlf
*.ps1 text eol=crlf
*.png binary
*.jpg binary
*.jpeg binary
*.gif binary
*.ico binary
*.woff binary
*.woff2 binary
*.pdf binary
*.zip binary
```

两类例外都不能省：**必须 CRLF 的脚本**（写成 LF 之后 Windows 拒跑，而报错不指向行尾）、
**二进制**（漏掉之后 git 会试图做行尾转换，文件在检出后损坏）。

属性文件的匹配**从上到下**，后匹配覆盖先匹配——先写 `*`，再写例外。
已有历史混入 CRLF 时，补上属性后跑一次 `git add --renormalize .`。

---

## 忽略规则

**`.gitignore` 对已入库的文件无效。** 已经进去了的要先 `git rm --cached <路径>`
把它从索引里拿掉。勘察的 `ignores.ignoredButTracked` 非空就是在说这件事。

**模板要留口子**：`.env` 忽略，但 `.env.example` 要在库里，否则别人不知道该填什么。
写法是 `!.env.example`。

---

## 提交署名

取值顺序 `local` → `global` → `system`。勘察给出的 `identity.scope` 就是答案，
**不要用「某个文件在不在」推断**。

**署名缺失是真缺口，但它可以后补**（改配置之后新的提交就对了）。卡在「没署名就不提交」
只会让人绕过去用一个错误的署名，那更糟。正确做法：**照常提交，在汇报里说清缺什么、
怎么补**。

老项目接手时看 `historyAuthors`：多种署名混杂说明换过人或换过机器。判断标准不是「对不对」，
是「这些提交还能不能追溯到人」。追溯不上的历史，出问题时帮不上忙。

**按路径存凭据时**（`credential.https://host/path`），查凭据要给三行：`protocol=https`、
`host=github.com`、`path=<owner>/<repo>.git`。缺 `path` 就查不到，症状是「登录了却推不上去」。

---

## 提交纪律

- 一次实质变更一个提交：混在一起的两个改动，出问题时只能整段回退。
- 说清「改了什么、为什么」。读它的人（包括未来写发布说明的人）要能据此讲出一句
  使用者听得懂的话。
- 禁用 emoji，不用内部编号、任务代号、流程名充当说明。

---

## 回滚分档

| 情况 | 怎么回 |
| --- | --- |
| 还没提交 | 直接改回去 |
| 已提交未推送 | `git reset --soft`（保留改动）或 `--hard`（丢弃） |
| 已推送、在共享分支上 | **`git revert`** 造一个反向提交。历史不改，别人不用重拉 |
| 已推送、确定没别人基于它工作 | 可以改写历史，但那是**不可逆动作**，先给清单让人确认 |

**强制推送与改写已推送历史永不自动执行。** 判据不是「我能不能」，是「有没有人已经基于它
工作了」——而那个问题脚本答不了。

---

## 大文件

超过几十 MB 的文件进历史之后，每次克隆都要付它的代价，而且是永久的（历史不会缩小）。

| 状态 | 处置 |
| --- | --- |
| 还没提交 | 加进忽略规则，或换外部存储 |
| 提交了没推送 | 可以改写历史拿掉 |
| 已推送 | 改写历史 + 通知所有克隆过的人重拉。**不可逆**，先给清单确认 |

先把「该不该进」判对，比后面怎么收拾重要得多。

---

## 凭据门控

**提交之前先扫。** 勘察的 `risks.secretFiles` 与 `risks.secretContent` 给出位置（到行）
与状态，按状态分三档：

| 状态 | 处置 |
| --- | --- |
| `ignored` | **安全**，不要打扰用户——它本来就该待在那儿 |
| `exposed` | **提交前必须处理**：加进忽略规则，或脱敏后换成模板 |
| `tracked` | **最要紧**：改文件不管用，要**先轮换凭据**，再从索引移除 |

**已入库的凭据不该让整个任务停下来。** 正确顺序：把位置（文件:行）原样报给用户 → 说清
正确处置是先轮换再清历史 → 其余不受影响的事照常往下做。停下来的代价是「用户什么也没得到」，
而问题一点没少。

**为什么这件事值得单独说：** 凭据一旦进了公开历史，**它就已经泄露了**——即使后来删掉，
历史里还有。所以这一档的处理不是「改文件」，是「让那把钥匙失效」。这个区别不解释清楚，
用户会以为删掉那行就没事了。

---

## 幂等

重复执行结果相同：已有 `.gitattributes` / `.gitignore` 时只补缺的行，不覆盖；
已配好的署名不改；已提交的改动不重复提交。

判据：**第二次跑与第一次跑，文件字节相同。**

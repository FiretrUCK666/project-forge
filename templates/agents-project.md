## 工程修改守则与硬性规范

- **先看再动，贴合既有结构**：改之前先读现有实现、依赖与相邻代码，摸清这个项目已经怎么做事；能并入现成机制的就别另起炉灶，改动范围尽量小。
- **治本不治标，不留双轨**：先查清故障为什么发生再动手，不用「加个判断挡住它」「出错就重试一次」把症状往后推；被替换掉的旧逻辑一并清干净，不让新旧两套做法并存。
- **小步验证，严控依赖**：每改一处就确认跟它相关的地方还正常；不擅自引入第三方依赖，确需引入时先说明理由并取得确认。
- **测试正反双向**：修缺陷先写一个能稳定复现的失败测试；新增判定或解析逻辑必须同时覆盖正面用例与易误判的反面用例。
- **不写履历，文档同步**：代码、注释与文档只描述当前状态，不写「以前是……后来改成……」；凡涉及用户可见行为、命令或配置的变化，必须同一次提交更新 `README.md`。

## 版本管理与回滚底线

- **提交纪律**：一次实质变更一个独立提交，提交信息说清「改了什么、为什么」，不用内部编号充当说明；大改动或高风险操作前先提交一个干净存档点；项目若有入库的构建产物、锁文件或自动生成目录，必须与源码改动在同一次提交中更新。
- **回滚四档**：
  - 未提交 → 丢弃工作区改动；
  - 已提交未推送 → 回退到存档点；
  - **已推送到远端 → 一律用反向提交，严禁强制推送或改写已推送历史**；
  - 已发布版本 → 只能发新版本修正（版本号单调递增，**永不复用或删除已发布版本**）。

<!-- project-forge: if has-release -->
### 版本号与发版死锁防护

版本号以 `{{VERSION_SOURCE}}` 为唯一权威来源；**兼容性下限（最低支持版本）只上移、不下移、默认不动**（上移须同步修改清单与 `README.md` 的环境要求节）。

**日常与发版是两件事，默认只做前一件：**

- **日常**：改完 → 跑门禁 → 提交 → **推自己的分支 → 开 PR**。合并交人，**不打标签、不建发布页、不发制品库。**

  **推到哪一档由「能不能撤回」决定，不由「是不是对外」决定**：推自己的分支、开 PR、
  改 PR 都能撤回（删分支、关 PR），属于日常；合并默认分支、发布、改可见性、改写历史
  撤不回来，要先给人看清单。**强制推送与改写已推送历史永不自动执行。**
- **发版**：只有明确说要「发版」时才做，顺序严格按 `{{RELEASING_DOC}}`——先提交并推送发布说明（`{{RELEASE_NOTES_TARGET}}`）到默认分支 `{{DEFAULT_BRANCH}}`，确认就绪后再打标签推送（反过来会让远端自动化因读不到说明文件直接失败）。
- **不自己判断「该发版了」**：攒了几个改动、版本号看着该抬了、上一个标签隔得有点久了——都不是发版理由。发版是一个对外动作，要人点头。
- **回读才算发完**：标签推上去之后要确认发布页正文与说明逐字一致、附件在、制品库版本已就位。命令返回 0 只说明它自己认为成功了。

## 日常协作：改动怎么落地

- **第一步：先判角色（不靠猜）**。

  <!-- project-forge: if has-remote -->
  先核对远端与源仓库：`origin` 与项目声明的源仓库一致，你就是**维护者**；不一致（或存在不同的 upstream、或未声明源仓库没法比对）一律按**贡献者（Fork）**处置——从 `{{DEFAULT_BRANCH}}` 拉新分支 → 门禁全绿 → 推自己的分支 → 开 Pull Request（详见 `CONTRIBUTING.md`），**严禁直接推正本主干、打标签或发版**。
  <!-- project-forge: endif -->
  <!-- project-forge: if no-remote -->
  这个项目还没有远端，所以眼下只有本地提交。**但落在高风险路径上的改动仍然要有一次独立审查**，结论写进工作记录——审查不依赖远端存在，它依赖「这处改坏了不会当场失败」。
  <!-- project-forge: endif -->

- **第二步：按变更规模五档分流（先分流再动手）**——

  | 档 | 典型情形 | 动手之前必须有 |
  | --- | --- | --- |
  | 纯文档 / 局部小修 | 措辞、注释、README、几行以内且不改变行为 | 无额外要求，直接改并跑通门禁 |
  | 局部缺陷修复 | 有明确复现路径的坏行为 | 先核实复现四要素（期望 / 实际 / 步骤 / 环境），并写出能稳定复现的失败测试，再改实现 |
  | 局部变更 | 改一处，但会改变现有行为 | 先有最小可勾选待办，勾一条做一条 |
  | 较大特性 / 跨模块重构 / 触碰接口契约或下方「高风险路径」 | 一处改动牵动多处 | 开工前先在 `{{WORK_DIR}}` 建工作记录，冻结可验证的验收标准并获人工确认后再动手；**AI 只写方案草稿，不能自己批准** |
  | 与既有契约冲突 | 新需求与现成接口、数据格式或包边界打架 | 先修契约，并在同一个变更内同步上下游，不许只改一头 |

  任务跨会话时，在工作记录里维护断点与「决策与放弃（试过走不通的方案）」。

- **第三步：独立审查与合并风险三档**——

  | 风险档 | 涵盖 | 合并前必须满足 |
  | --- | --- | --- |
  | 低风险 | 文档、注释、新增测试、非核心小修 | 门禁全绿，且有一个可回滚的点 |
  | 中风险 | 常规业务逻辑、小版本依赖升级 | 门禁全绿 + 审查通过；合并后通知维护者 |
  | 高风险 | 触碰下方「高风险路径」表里的任何一处 | **必须派发独立新上下文审查**（只给本文件、diff、门禁输出与冻结的验收标准，**绝不给执行者的思路与上一轮结论**）；审查通过前必须完成**故障注入验证**（删掉一行核心改动，确认测试真的变红；还原后确认变绿）；且**必须由人工最终合并** |

- **一票否决红线**：任何弱化门禁的改动（删测试、放宽断言、加跳过标记、改松 CI）或外部贡献者的 PR，**无论风险档位一律转人工审批**。

- **第四步：合并收尾与平台交互防乱码**——固定 6 步：
  1. 合并 PR（**不勾选自动删分支**）；
  2. 回读确认 `state=MERGED`；
  3. 更新工作记录与 Issue；
  4. `git switch {{DEFAULT_BRANCH}} && git pull`；
  5. `git branch -d <分支>`；
  6. **先查有没有未合并的下游堆叠 PR 以该分支为 base，确认没有才** `git push origin --delete <分支>`。

  通过平台命令创建或更新 Issue、PR、Release、评论时，**含中文或非 ASCII 的正文一律先写入系统临时目录的 UTF-8 文件，用 `--body-file` / `--notes-file` 提交**，提交后回读比对并删掉临时文件；**严禁在命令行直接拼接正文字符串**。

- **日常到此为止**：合并就是一次改动的终点。**发版是另一件事**，要人明确说才做
  ——见上面「版本管理与回滚底线」那一节。别把「这条改完了」顺势读成「该发版了」。

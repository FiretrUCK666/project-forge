说明本项目运行在什么前提下、项目根在哪、有哪些可变的配置来源、改动何时生效。

要点：

- 不写死平台与绝对路径；需要时用命令发现（当前平台、主目录、工具版本）。
- 说明「改哪一部分需要重启 / 重新加载，改哪一部分立即生效」。

## 硬性规范

逐条编号，每条一句话说清要求与理由。这些是「不许破」的底线，例如：

1. 提交信息与文档不得包含 emoji。
2. 只使用官方依赖，不修改上游源码。
3. 命名一致性：同一概念在所有位置用同一个名字。
4. 数据键 / 接口路径一旦发布不得改名（会破坏已有用户的数据与集成）。
5. 不新增依赖，除非先说明理由并经确认。

## 版本管理流程（必守）

说明本项目使用什么版本管理方式、有哪些远端、以及「谁做什么」：

- 若只有本地仓库：说明提交纪律、以及何时需要一个可回退的存档点。
- 若有远端：说明推送目标、分支模型、以及 tag / Release / 制品库三者各自的作用。
- 明确哪些动作需要用户明确点头（发布、公开、改写历史）。
- 取值一律现场读（远端地址、当前分支、署名、账号），不在本文件里写死。

### 提交纪律

提交信息简短说明这次改了什么，中文或英文都行但保持一致，**禁止 emoji**；一次实质变更
一个提交，不要把无关改动混在一起。**产物与产生它的源改动必须同一次提交**，否则历史里
会留下产物与源码不一致的中间状态。

**改动量大或有风险的操作之前，先提交当前状态**，保证永远有一个可回退的干净起点。

### 版本号语义

三档，判据是**消费者会不会被迫改自己的代码**：

| 档 | 什么时候用 |
| --- | --- |
| 修补 | 改了实现，使用者的用法完全不用动 |
| 新增 | 多了能力，旧用法照常可用 |
| 破坏性 | 使用者必须改自己的代码才能继续用 |

两条硬纪律：**单调递增、永不复用**（同一个版本号不能发第二次）；**已发布的版本不可
删除**（别人的依赖锁定文件里可能已经写了那个号，删掉会让他们的构建坏掉）。

<!-- 为什么有这一条：不适用时不出现：项目没有版本号时，「一个权威来源」没有对象 -->
<!-- pf:if has-version -->
版本号只有**一个权威来源**：项目清单文件里那一个字段。不要在别处再写一份。
<!-- pf:endif -->

### 抬版本号的判据

判据只有一条：**使用者会不会因此看到变化**。随包发出去的说明改一个字都要抬；不进包的
内部文档、重构、测试与构建脚本不抬——用户看不到的改动硬抬版本是噪音。

<!-- 为什么有这一条：不适用时不出现：制品库发布与随包分发的抬号判据不同，写法也该不同 -->
<!-- pf:if has-registry-publish -->
本项目的结论：**随包发出的说明文档改一个字都要抬**——不抬会出现「仓库里的说明已经改了，
制品库上还是旧的」；**不进包的内部文档与重构、测试、构建脚本不抬**。
<!-- pf:endif -->

## 改动怎么落地（日常）

**先判「审不审」，再判「谁能合」，最后判「谁握合并按钮」。**这三件事经常被混成一句，
混掉的后果很具体：**一个人合了，而压根没人审**——CI 绿了、门禁过了，改动就进去了。

<!-- 为什么有这一条：不适用时不出现：没有可推的地方，就没有维护者与贡献者之分 -->
<!-- pf:if has-remote -->
### 第一步：判角色——决定你能做到哪一步

**同一个改动，维护者与贡献者能做的动作不同。判断靠项目自身的事实，不靠问。**

| 事实 | 结论 |
| --- | --- |
| 远端 `origin` 与项目**声明的源仓库**是同一处 | 维护者，走下面全部流程 |
| 两者不同，或存在一个与 `origin` 不同的 `upstream` 远端 | **贡献者**（Fork） |
| 项目没有声明源仓库，也没有 `upstream` | **判不了**——按贡献者处置 |

**贡献者的路线是固定的**：与上游同步 → 从主干拉新分支 → 门禁全绿 → 推到自己仓库的那条
分支 → 向正本开提案。**不推正本主干、不打标签、不发版**——前两者没有权限；而请求事件天然
拿不到密钥，需要钥匙的步骤不会跑，也不会泄。

**判不了为什么按贡献者走**：走错这一边的代价只是少做几步；走错另一边，代价是把改动推进
一个不属于自己的仓库，而那一步收不回来。

判定为贡献者时，**严格按 `CONTRIBUTING.md` 与项目里的提案模板走**：那里写着这个项目自己的
提交路径、门禁命令与提案该填什么。

### 第二步：判这件事有多大——先分流，再动手

**这是整条路的第一个分叉。**判错方向不会报错，只会让一个大改动按小改动的流程走完。

| 判定结果 | 开工前必须完成的产物 | 允许改代码的时机 |
| --- | --- | --- |
| 纯文档 / 纯调研 | 无 | 立即 |
| 局部缺陷修复 | 一个能复现它的失败测试 | 先有失败测试 |
| 局部变更（不触接口 / 数据 / 权限 / 验收边界） | 最小可勾选的待办 | 先有待办与失败测试 |
| 较大功能 / 重构 / 跨端 / 触契约 / 范围或不清 | 设计文档（草稿 → **人工批准**）+ 计划 | 设计文档批准后 |
| 与既有契约冲突 | 先修契约，在同一变更内同步上下游 | 修订确认后 |

**AI 只写草稿，不能自己批准。**草稿不是实现依据。拿不出已批准的产物时**停下并交人**，
写清选项与影响，不猜、不静默选边。分流结论写进提案的「实现依据」一栏。

### 冻结验收标准：动手之前

**这是审查循环能收敛的唯一原因。**没有事先说定的清单，审查就只能回答「还能不能再找出
一个问题」——而那个问题永远找得到。任何代码都还能再补一处边界处理。

写法：工作记录的目标与验收一节里放一个块，一条标准一行，每条都要能被**一条命令或一条
断言**证明。

```pf-done
C1: 第一条可判定的验收标准（一条命令或一条断言能证明它）
C2: 第二条
```

提案正文里放一行指针：`工作记录: docs/work/YYYY-MM-DD-xxx.md`。**指针必须指向本次改动里
的文件**——指向一份没改过的，等于拿旧标准给新改动背书。

### 审查：只回答「哪几条没过」

审查必须来自**另一个上下文**（子代理或新会话），**不复用执行者那一轮，也不复用上一轮
审查那一轮**——带着别人的判断去读，读出来的是复核，不是审查。

只给材料清单，不给转述。这三样一律不给：执行者的对话与思路、**上一轮审查的结论**、
任何「请确认没问题」式的引导语。

产出是一条提案评论，里面带这个块：

```pf-review
round: 1
fail: C2
inject: 删掉某处兜底分支 → 3 个用例变红 → 还原全绿
```

| 字段 | 必填 | 取值 |
| --- | --- | --- |
| `round` | 是 | 第几轮，正整数。同一轮只能有一个说法 |
| `fail` | 否 | 冻结清单里的 id，逗号分隔。**空 = 全部通过** |
| `inject` | **判通过时必填** | 故障注入记录 |
| `escalate` | 否 | 这条标准本身有问题 → 停自动返工，交人 |

**没有「结论」字段，这是刻意的。**结论由脚本从 `fail` 与 `escalate` 算出来。让审查者写
一句结论，机器就得去读那句中文里「通过」是肯定还是否定——否定的写法列不完，每漏一种，
方向都是放行。换掉输入形状之后，正文怎么写都不影响判定。

**不能发明标准**：`fail` 引用的 id 必须在冻结清单里。要加就回工作记录正式加。

**判通过必须交故障注入**：在最终那一版代码上删掉一行防御代码、或反过来一处判断，
跑对应用例，**看着它变红**，还原确认变绿。测试全绿有两种可能——代码对，或者测试是空的，
只看绿灯分不出来。真没有可注入的代码时写清理由，空着不行。

### 什么时候停：两条止损

同一条标准**连续两轮**没过 → 方向错了，不是「再修一轮就好」。
轮次超过返工上限 → 自动返工到顶。

任一成立 → 合并需要维护者加豁免标签。**豁免只免止损，不免「还有标准没过」**：
止损说的是「这样下去不会收敛」，人可以说「我知道」；而「C2 没过」是事实，认了风险也不改变它。

### 三个角色，靠「谁握合并按钮」分开

| 角色 | 做什么 | 绝不做什么 |
| --- | --- | --- |
| **编排**（主会话） | 分析、冻结验收标准、派活、守关卡、向使用者汇报 | 不改业务代码、不写审查评论、**不转述审查结论**、不自己判通过 |
| **实现**（新上下文） | 改代码、跑门禁、提交、推送、开或更新提案 | 不审、不合 |
| **审核**（另一个新上下文） | 独立复核、做故障注入、**自己发评论**、判通过时**当场合掉** | 不改代码、不提交 |

**审查评论由审查者自己发**——转述是一次取舍，「这个问题不严重」通常在转述那步被削掉。
**通过之后由审查者合**——编排者手上没有「我看看要不要合」这个环节，也就没有「再看看、
再修修」这个循环。**编排者不能自己充当审查。**

### 谁能合：按「收不收得回来」分档

| 档 | 什么算这一档 | 必须审 | 谁能合 |
| --- | --- | --- | --- |
| 低 | 文档、注释、新增测试、非关键路径的小修 | 否 | 门禁全绿 + 零阻塞 + 有回滚点 → 可以自动合 |
| 中 | 业务逻辑、改测试逻辑、依赖小版本升级 | **是** | 同上，**合完通知到人**，留一个可撤销的窗口 |
| 高 | 落在下面「高风险路径」表里的任何一处 | **是，没有例外**（单人、私有项目也一样） | **必须人合** |

高档为什么不能自动合：这些风险**在合并之前就已经不可逆**——凭据泄漏了，回滚不会让它
没泄漏过；门禁被弱化，下一次就没有东西拦得住；数据迁移写错了，回滚脚本也可能写错。
**回滚不恢复原状**，所以不能靠「反正能回滚」兜。

**一条独立的硬规则**：改动里出现弱化门禁的痕迹（跳过测试、放宽断言、降覆盖率门槛、
动 CI 配置），不管风险档、不管审查结论，**一票否决转人工**。它「通过了」是因为判据被
改松了，而改判据这件事必须有人看。

### 协作参数

这两项是本项目的决定，不是工具的默认值。改这里即可改行为，不用改脚本。
**不填也能用**：下面就是默认值，`scripts/review-record.mjs` 读不到这张表时用的也是它们。

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| `rework_cap` | 2 | 自动返工上限。超过后合并需要豁免标签 |
| `waiver_label` | `pf:human-approved` | 豁免标签名。它只豁免止损，不豁免「还有标准没过」 |

### 外部来的改动

**外部报告**（别人提了问题）：先核实四件事——期望什么、实际什么、怎么复现、什么环境。
缺关键信息就先出追问清单贴在问题下面，**不盲猜写代码**。然后查工作记录防撞车、领活、
拉分支、先写失败用例和防误判的反例，再改实现。**每一步都要在那条问题上留评论**——
那是别人看得见的地方，只留在自己会话里等于没写。

**外部提案**（别人改好了）：**先只读审 diff，不检出**——检出之后一次装依赖就可能执行
陌生人的代码。重点看四处：工作流配置、依赖的生命周期钩子、门禁判据有没有被改松、
发布范围与锁文件。**没有关联问题不是退回的理由**——很多人直接提改动，这是合法的；
缺的是「要解决什么、改了什么、怎么验证、影响谁」这四件事。**外部提案一律人合。**

### 打回与返工

- **不新建分支、不新建第二个提案**，在原分支追加提交，更新同一个提案；
- 提案最新提交仍等于被退回那版时，拒绝重提——防止拿同一版本反复送审；
- 有单轨道时审查结论**同时**写到提案和问题两边，缺任一侧视为审查未完成；
- 合并后才发现的问题 → 按新问题处理，不得用同一单绕过流程。

<!-- pf:if no-remote -->
### 没有远端：只有本地提交

改动直接提交，**没有提案与合并这一套**。**但审查这件事不随远端消失**：落在高风险区的
改动仍然要有一次独立审查，只是它没有提案可挂——**结论写进工作记录的断点那一节**，
格式不变（哪几条标准没过、故障注入记录）。**「没有提案」不等于「不用审」**——
门禁与审查是两件事，而这件在单人、本地、无远端的项目上恰恰更容易被跳过。
<!-- pf:endif -->

### 审查：派一个新上下文

审查的独立性**不在于换个模型，而在于不继承别人的判断**。所以要**派一个新上下文**（子代理
或新会话），只给它一张材料清单——让它自己看、自己查。把执行者的思路喂给它，它只会顺着
复核，那叫复核，不叫审查。

| 给它 | 不给它 |
| --- | --- |
| 本文件、**改动全文**、门禁命令与原始输出、工作记录（含冻结的验收标准）、贡献指南与发版规范（有才给）、平台上的问题与提案**正文** | 执行者的对话与「我的思路」、**上一轮审查的结论**（包括提案评论里那几轮）、任何「请确认没问题」式的引导 |

**下一轮重新派一个新的**：让同一个子代理「再看看」，它已经带着上一轮的结论了。轮次不是
成本，带着偏见的第二轮才是。

**主 Agent 不能自审**：同一个上下文里再读一遍，只会读出「刚才那套没问题」。
也**不要转述审查结论**——转述是一次取舍，「这个问题不严重」通常在那一步被削掉。

**要读改动之外的文件来验证调用链，允许**：但要把「读了哪些额外文件、为什么」写进报告——
否则大仓库里它会淹没在无关文件里。

<!-- 为什么有这一条：不适用时不出现：没有可推的地方时，结论写进工作记录，不写提案评论 -->
<!-- pf:if has-remote -->
**每轮都要留记录**：本轮的结论**作为评论发到提案上**（字段块见上一节），工作记录的断点与
最近更新跟着改。**「最后补一份总结」等于把中间几轮的判断丢掉**——而下一轮要接的正是那几轮。
<!-- pf:endif -->

### 工作记录：跨会话靠文件，不靠记忆

对话历史会被压缩、会丢；文件不会。所以一件事只要**跨过一次会话**、或**可能换人接手**，
就该有一份工作记录。五分钟的小改不写——那是把流程当成了目的。

| 项 | 怎么做 |
| --- | --- |
| 放哪 | 先看项目里已有的：`docs/work/`、`docs/tasks/`、`todo/`、`work/`——探到哪个用哪个，**不要为了统一而搬家**（搬家会让所有旧引用断链）；一个都没有才建 `docs/work/` |
| 叫什么 | `YYYY-MM-DD-一句话主题.md`：**日期在最前**，写建单那天、之后不改；**不带编号**（半年后没人认得出）；**不带状态**（状态会变，写进名字就要改名） |
| 日期写在哪 | 表头：建单日期、最近更新；事件日期写进对应的表；关联的问题与提案写**编号 + 日期**，不复制正文 |
| 一个还是一套 | 默认一个文件，里面用节管；只有要贴大量附件、设计细节要独立演进时才拆目录 |
| **执行者写谁** | 写**身份**，不写代词：提交署名加平台账号，都现场取。**「本次会话」「我」等于空话**——这一格的用处只有一个：这件事该找谁问 |
| 完成后放哪 | **留在原目录**，状态改「已完成」。不建 `done/` 子目录：搬家断链 |

每份至少写清**状态、目标与验收（含冻结的标准）、计划、放弃过什么、断点**——
缺任何一样，下一个人就得重新问一遍。

**对话本身不落盘**：它会丢，也不是给下一个人读的形态。真正留下记录的是三样——
工作记录（状态、决策、断点）、提交信息（改了什么）、提案与审查评论（为什么、谁拦过）。

**不要为问题建文件夹**：问题原文在平台上，仓库里只放我们自己的记录。两份副本一定会漂移。

### 合并与收尾：顺序不能反

```
合并 → 验证真的合并了 → 关工作记录与关联问题 → 切回主干并更新 → 删本地分支 → 删远端分支
```

```sh
gh pr merge <编号> --merge          # 1) 合并。不要带「合并并删分支」，那是两件事
gh pr view <编号> --json state       # 2) 回读验证真的合进去了，别凭退出码
git checkout <主干> && git pull      # 3) 先切回主干并更新（删本地之前必须做）
git branch -d <分支>                 # 4) 再删本地，用 -d 不用 -D
git ls-remote --heads origin <分支>  # 5) 先判远端还在不在
git push origin --delete <分支>      # 6) 还在才删
```

命令以 `gh` 为例——它只是一种通道。没装它时用平台工具或网页做同样的动作，
**顺序与回读要求不变**。

三个坑各有根因：**①** 合并与删除混在一条命令里，失败时分不清是「没合进去」还是「合进去了
但删分支失败」，而这两种情况的下一步完全相反；**②** 还停在分支上时 git 不允许删当前分支，
且主干没更新时 `-d` 会认为它没合入而拒绝；**③** 先删远端会丢掉本地分支的上游追踪引用，
逼你用 `-D` 强制删除，而那正是唯一那道保护网。另有两个特例：平台开着「自动删除已合并
分支」时，第 6 步报「远端引用不存在」**是完成态**；**有未合并提案以这条分支为基底时不能
直接删**（会把它连带关掉）——先给下游提案改基底，或者先留着。

**写回平台时正文一律走文件**：创建或更新问题、提案、审查评论，正文先写进 UTF-8 文件再用
`--body-file` 一类参数提交，**不在命令行里拼正文**。shell 的引用与编码规则因平台而异，
中文与反引号可能被静默吞掉，而这类损坏的共性是**接口仍然返回成功**。提交后回读比对一次。
**那个文件放系统临时目录、用完就删**。

## 依赖版本同步

构建与测试所对的依赖版本必须**跟随实际在用的版本**——不写死、也不靠宽松范围蒙过去。

同步动作：读当前实际在用的版本作为目标 → 逐个确认目标版本确实存在 → 写进开发依赖
声明（**只动这里**）→ 安装 → 跑构建与验证全绿 → 若伴随破坏性变更，按新契约改写而不是
用宽类型绕过。

**注意与「最低支持版本」的区别**：这里的跟随版本只有开发者看得到，每次上游升级都跟上
去；而使用者能看到的最低下限是另一个概念，**只在真不兼容时上移**，且兼容性声明与面向
使用者的文档必须一起改。两者混为一谈，就会要么把下限无谓抬高、要么让文档与实际不符。

**不要用「查询最新版本」的单值命令判断版本**：发布方的「最新」标记可能停在很旧的版本
而实际已有更新的版本。要取完整版本列表，从末尾找目标版本，并逐个确认它确实存在——同一
批发布里个别包可能停更，不能假定「同号」普遍成立。

## 高风险路径

<!-- pf:author: 下面那张表由**作者**填，脚本只读不改：写清这个项目里「改了会让门禁从此少查一项」的那几处。表格形状与判据照着上一节的说明。填了之后重跑本脚本不会把它冲掉（这一节标着 pf:author，合并时保留既有内容）；留空则那条门禁不生效。 -->

**改在这里出错不会当场失败，而是让门禁从此少查一项。** 动到下面任何一处，提案必须有
独立审查记录——这条由 `review-record.mjs` 判（它读的就是这张表），有远端时 CI 在提案上跑它。它随落盘自动拷到本项目的 `scripts/` 下（不用手工拷），零依赖、单文件。

**这张表是空的就等于没配**：脚本读不到路径时会明说「这一趟没查」，不会静默放行，
但也拦不住任何东西。填的时候按这个项目真实的高风险处填：

| 路径 | 为什么 |
| --- | --- |
| `<替换成这个项目的第一处>` | 判据错了不报错，只会从此少查一项 |
| `<替换成这个项目的第二处>` | 写进别人的东西，改坏了要等他们踩坑才发现 |

**路径要能被认出来**：目录写 `src/rules/`（不带尾斜杠也认，会补成前缀形式），单个文件写
`AGENTS.md`；格子里可以带说明。**认不出来的行会让门禁直接报错**——认不出来不等于没有，
静默跳过正是「表填了但门禁永不触发」那个 bug 的形状。

判据是**目录前缀**，不是逐文件清单：清单要人记得改，而目录不会长出新的一处。
写目录时**结尾带上 `/`**，写单个文件时不要带。

## 文档同步

本项目有两类面向不同读者的文档，**描述同一件事，但读者不同**。这条总规则与它的判据
（读者是谁决定怎么写、改完要检查另一份是否失准）**由上面的内核段落给出，本节不复述**：
同一份规范写两处，迟早会有一处失准。

下面只写内核没有覆盖的那两类内容：**不由人手工维护的派生内容**，以及**多语言版本**。

### 派生内容用工具同步，不手工维护

有一类内容**完全由别处的信息决定**：目录由标题决定、徽章由外部服务决定、依赖清单由
依赖声明决定、模块表由实现的接口决定。它们不该手工维护——手工维护的派生内容一定会
漂移（加了一节忘了加目录项、改了标题忘了改锚点），而这类错误的症状很隐蔽：
**锚点写错的表现是「点了没反应」，不报错、不显眼**，作者也不会去点自己的目录。

判据一句话：**这份内容能不能由一条命令从源头重新算出来？** 能，它就不该手写。

做法：用脚本从源头生成，插在成对标记之间（标记之外一个字节不动），改完重跑即同步；
并在持续集成里加一条「重新生成后与提交一致」的检查——这样漂移会当场暴露，而不是
等到某个读者点了没反应。

与「本文件的定位与编辑规则」里那条「写意图不写快照」是同一个道理：**快照会过期，
派生关系不会**——把派生关系交给工具，剩下的只有源头需要维护。

### 双语说明文档要**成对**维护

本项目的 `README*.md` 是**同一份文档的两个版本**，**改一份时必须打开另一份一起看**，改完
要能回答「另一份同步了吗？」。**默认语言那份是权威**：另一份是它的翻译，两者不一致时以
权威版为准，并同步另一份。

**不要机械对译**：两种语言的读者关心的问题不同，按那份语言里读者能看懂的写法重写。
**不要新增没人维护的语言**——一份没人维护的第二语言 README 比没有更糟。

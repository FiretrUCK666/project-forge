### 提交纪律

提交信息简短说明这次改了什么，中文或英文都行但保持一致，**禁止 emoji**；一次实质变更
一个提交，不要把无关改动混在一起。**产物与产生它的源改动必须同一次提交**，否则历史里
会留下产物与源码不一致的中间状态。

**改动量大或有风险的操作之前，先提交当前状态**，保证永远有一个可回退的干净起点。

### 回滚分档

| 状态 | 手段 |
| --- | --- |
| 未提交 | 丢弃工作区改动 |
| 已提交、未推送 | 回退到存档点 |
| 已推送 | 用反向提交——**不改写已推送的历史** |
<!-- pf:if has-registry-publish -->
| 已发布到制品库 | 只能发新版本修正；已发布的版本号不可复用，通常也不可删除 |
<!-- pf:endif -->

**不改写已推送的历史**：不用强制推送、不对已推送的提交做变基——别人可能已经基于它工作。
这特别在发布过的项目上尤其重要：历史一旦公开，任何人都可能已经基于它建了分支。

### 版本号语义

三档，判据是**消费者会不会被迫改自己的代码**：

| 档 | 什么时候用 |
| --- | --- |
| 修补 | 改了实现，使用者的用法完全不用动 |
| 新增 | 多了能力，旧用法照常可用 |
| 破坏性 | 使用者必须改自己的代码才能继续用 |

两条硬纪律：**单调递增、永不复用**（同一个版本号不能发第二次）；**已发布的版本不可
删除**（别人的依赖锁定文件里可能已经写了那个号，删掉会让他们的构建坏掉）。

<!-- pf:if has-version -->
版本号只有**一个权威来源**：项目清单文件里那一个字段。不要在别处再写一份。
<!-- pf:endif -->

### 抬版本号的判据

判据只有一条：**使用者会不会因此看到变化**。随包发出去的说明改一个字都要抬；不进包的
内部文档、重构、测试与构建脚本不抬——用户看不到的改动硬抬版本是噪音。

<!-- pf:if has-registry-publish -->
本项目的结论：**随包发出的说明文档改一个字都要抬**——不抬会出现「仓库里的说明已经改了，
制品库上还是旧的」；**不进包的内部文档与重构、测试、构建脚本不抬**。
<!-- pf:endif -->

### 发版规则

<!-- pf:if has-version -->
- **标签名必须与清单文件里的版本号一致**，不一致会让后续自动化对不上。
- **版本号只有清单文件里那一处是权威**，标签名照它写，不要在别处再维护一份。
<!-- pf:endif -->
<!-- pf:if no-version -->
- **本项目没有版本号**（不发布制品，或清单里没有该字段），所以标签命名规则自定。
  要求只有三条：**单调、不重复、可排序**（例如 `v<日期>` 或 `v<序号>`）。
  没有版本号时**不要编一个出来**——那会造出一个没人维护、却看起来权威的数字。
<!-- pf:if is-go -->
- **Go 例外**：Go 清单本来就没有版本字段，但标签仍须 `v` 加语义化版本（子目录前缀与
  大版本后缀按该生态惯例），不要用日期方案。
<!-- pf:endif -->
<!-- pf:endif -->
<!-- pf:if has-release-spec -->
- **发版前先读本项目的发版规范**（`{{RELEASE_SPEC_FILE}}`）：说明写在哪个路径、分成
  哪几节、这一版该不该抬版本号，都以它为准。**本节不复述那些细节**——两处都写，迟早会
  有一处失准，而失准的那一处会在发版当天才暴露。
<!-- pf:endif -->
<!-- pf:if no-release-spec -->
- **本项目没找到发版规范**：说明写在哪个路径、分成哪几节，现在没有权威出处。**写说明之前
  先落一份**，不要凭记忆决定分几节——否则发布自动化读的那个路径会变成「只有工作流知道的
  一个字符串」。如果你其实有一份、只是名字不同，把它指过来（名字写进这一行的位置）并照它
  执行，不要另起一份。
<!-- pf:endif -->
- **发布说明写给人看，不是给维护者看**：正文要回答**这一版更新了什么、修复了什么**，

  要不要跟着更新」**——前者是过程记录，后者是产品通信。写的时候拿这个判据自查：
  **不熟悉这个项目的人读完，能不能说出哪一处变化影响他**。
- **不要复制提交主题当正文**。提交记录可以拿来做素材，但必须改写成使用者看得懂的说法；
  **不该写的**：内部编号、任务代号、分支名与提交哈希，对使用者无影响的重构与测试数目。
  判据是**读者读不读得懂**，不是条目齐不齐。
<!-- pf:if has-registry-publish -->
- **发布前先预演一次打包**，看清将要发出去的文件清单与体积——不看就不发。发布范围
  声明**对从仓库源安装同样生效**：仓库里有某个文件，不代表使用者手里会有它。
<!-- pf:endif -->
- **含非 ASCII 字符的正文绝不经 shell 传递**：它本来就是一个 UTF-8 文件，由自动化按字节
  读取，不要用命令行把它拼进任何请求。经 shell 传递时，损坏的共性是**接口仍返回成功**，
  只有打开页面才看得出乱码。

- **发到哪个制品库由生态决定，不要凭记忆拼命令**。按该生态官方文档当前的说法写；
  没有把握时查文档或问用户。**不知道就说不知道，比给错命令好。**

## 改动怎么落地（日常）


**先判「审不审」，再判「谁能合」。这两件事不同，混成一句就会留下「人合了但没人审」这个洞。**

**这张表先回答审不审**：

| 这次改了什么 | 必须独立审查 |
| --- | --- |
| 落在下面那张「高风险路径」表里的任何一处 | **是，没有例外**（单人、私有项目也一样） |
| 业务逻辑、测试逻辑、依赖小版本 | 是 |
| 注释、文档、新增测试、非关键路径小修 | 否 |

**「高风险路径」由本项目自己填，而且它还用来自动判**：`review-record.mjs` 从
本文件的 **`## 高风险路径` 那一节**读那张表，CI 在提案上跑它。**一节两用**——给人看的说明，
同时也是机器的判据来源，不会出现「文档写了、代码判的是另一套」。

**要填的表在下面的「## 高风险路径」一节里，不是这里。** 这一节只讲判据，那张表在那边；
下面这个表只是形状示意（**填在这里不生效**，脚本只读那一节）：

| 路径（示意，别填在这） | 为什么 |
| --- | --- |
| `<改判定 / 改检查逻辑的那几个目录>/` | 判据错了不会报错，只会从此少查一项 |
| `<落盘骨架 / 模板目录>/` | 写进别人项目里的东西，改坏了要等他们踩坑才发现 |
| `<CI 工作流目录>/` | 门禁本身的门禁 |
| `<决定产物范围的那个文件>` | 它决定使用者拿到什么 |

**为什么高风险那一档连单人项目也要审**：审查在这里不是表决，是**换一个上下文重看一遍**。
同一个上下文里再读一次，只会读出「刚才那套没问题」。这与项目有几个参与者无关——
单人项目里没人替你看着，那正是更需要它的时候。

**「审过了」必须留下可查的痕迹**：同一份提案下有一条来自**另一个上下文**的结论行
（通过 / 不通过）与逐条发现。没有这条痕迹的提案，**无论门禁多绿都不算审过**——
门禁判的是「现有检查有没有过」，它不判「这次改动有没有让检查变松」。两件事完全正交。

**谁能合，按「收不收得回来」分档，不按「谁看代码」分**：

| 档 | 什么算这一档 | 必须审 | 谁能合 |
| --- | --- | --- | --- |
| 低 | 文档、注释、新增测试、非关键路径的小修 | 否 | 门禁全绿 + 零阻塞 + 有回滚点 → 可以自动合 |
| 中 | 业务逻辑、改测试逻辑、依赖小版本升级 | **是** | 同上，**合完通知到人**，留一个可以撤销的窗口 |
| 高 | 认证、权限、支付、数据迁移、CI 配置本身、依赖锁文件、发布配置、密钥相关 | **是，没有例外** | **必须人合**，没有例外 |

高档为什么不能自动合：这些风险**在合并之前就已经不可逆**——凭据泄漏了，回滚不会让它
没泄漏过；CI 配置被弱化，下一次就没有东西拦得住；数据迁移写错了，回滚脚本也可能写错。
**回滚不恢复原状**，所以它们不能靠「反正能回滚」兜。


改动有三个来路，**信任等级不同**：外部报告（别人提的问题）、外部提案（别人提的改动）、
我们自己的日常改动。混进同一条流程，要么过度仪式，要么留下洞——所以先判入口，再决定路径。
**日常小改不走完整仪式**：把流程当目的，很快就会没人守。

### 第一步：判角色——决定你能做到哪一步

判断靠项目自身的事实，不靠问：远端 `origin` 与这个项目声明的源仓库是同一处吗？

- **是** → 维护者，走下面全部流程；
- **不是**（或存在一个与 `origin` 不同的 `upstream` 远端）→ **贡献者**：与上游同步 → 从主干
  拉新分支 → 门禁全绿 → 推到自己仓库的那条分支 → 向正本开改动请求。**不推正本主干、不打
  标签、不发布**——前两者没有权限，而请求事件天然拿不到密钥，需要钥匙的步骤不会跑也不会泄；
- **判断不了时按贡献者走**：这是更安全的一次错误，代价只是少做几步。**注意这份契约是怎么
  渲染的**：脚本判不出角色时仍按「可能是维护者」给内容（单人项目常见的样子就是有 `origin`、
  没声明源仓库、没有 `upstream`）。你若明知自己在别人的仓库里，按上面那条贡献者的路线走，
  不要照契约里的发版步骤做。

<!-- pf:if has-contributing -->
判定为贡献者时，**严格按 `CONTRIBUTING.md` 与项目里的提案模板走**：那里写着这个项目自己的
提交路径、门禁命令与提案该填什么。

### 第二步：判性质——只有维护者这一侧需要问

问三条，任一命中就走**分支 + 提案**：

| 问什么 | 命中的含义 |
| --- | --- |
| 主干受不受保护 | 受保护就不能直推，只能走提案 |
| 会不会有第二个人改这个仓库 | 有，就必须有审查；而审查只能发生在合入之前 |
| 改动可不可见、收不收得回 | 随包发出的文档、命令、行为是可见的；认证、权限、CI 判据、发布配置是收不回的 |

三条都不命中（单人、私有、主干没有保护、改动不可见且随时可回退）→ **主干直推**：改文件 →
跑「构建与验证」全绿 → 确认改动范围 → 提交 → 推送。**判断不了时按「命中」处理。**

走**分支 + 提案**时，顺序是：需要跨会话跟踪的（外部报告、大活）先建工作记录 → 从最新主干
拉分支 → 在分支上提交并推送 → 按项目的提案模板开提案 → 独立审查 → 按风险档位合并 → 按
「合并与收尾」那一节的顺序收尾。

**用户可见的改动要抬版本号**（判据见「版本管理」那节），产物入库的项目抬号之后**要重新构建**
——版号是构建时进包的，顺序不能颠倒。

### 没有远端：只有本地提交

改动直接提交，**没有提案与合并这一套**。**但工作记录照样适用**——跨会话的事记在文件里，
不靠回忆。

**审查这件事不随远端消失**。前面「什么时候必须审」那张表照样成立：落在高风险区的改动
仍然要有一次独立审查，只是它没有提案可挂——**结论写进工作记录的断点那一节**，格式不变
（第几轮、谁审的、通过还是需要返工、逐条发现）。有远端时评论是痕迹、正文是索引；没有
远端时工作记录同时是这两样。**「没有提案」不等于「不用审」**——门禁与审查是两件事，
而这件在单人、本地、无远端的项目上恰恰更容易被跳过。

### 工作记录：跨会话靠文件，不靠记忆

对话历史会被压缩、会丢；文件不会。所以一件事只要**跨过一次会话**、或**可能换人接手**，
就该有一份工作记录。五分钟的小改不写——那是把流程当成了目的。

| 项 | 怎么做 |
| --- | --- |
| 放哪 | 先看项目里已有的：`docs/work/`、`docs/tasks/`、`todo/`、`work/`——探到哪个用哪个，**不要为了统一而搬家**（搬家会让所有旧引用断链）；一个都没有才建 `docs/work/` |
| 叫什么 | `YYYY-MM-DD-一句话主题.md`：**日期在最前**，写建单那天、之后不改（它是唯一不会变的东西，所以不会带来改名）；**不带编号**（半年后没人认得出，还会重排）；**不带状态**（状态会变，写进名字就要改名） |
| 日期写在哪 | 表头：建单日期、最近更新；事件日期写进对应的表（决策表的时间列）；关联的问题与提案写**编号 + 日期**，不复制正文 |
| 一个还是一套 | 默认一个文件，里面用节管；只有要贴大量附件、设计细节要独立演进时才拆目录 |
| **执行者写谁** | 写**身份**，不写代词：提交署名（作者名与邮箱）加平台账号，都现场取。**「本次会话」「我」等于空话**——这一格的用处只有一个：这件事该找谁问；换个人打开这份记录，代词指不到任何东西。别人克隆之后填的应当是他自己的署名，这也是它必须现场取、不能写死的原因 |
| 完成后放哪 | **留在原目录**，状态改「已完成」。不建 `done/` 子目录：搬家断链，而它仍是同一件事的历史 |

**已经在用的老文件不强制改名**（改名断链）：新单照这条走，老单留在原处。**分支名不带日期**：
分支是短期对象，合并后就删；它的起止时间记在「分支」那一行与平台上的提案记录里。
**发布说明也不带日期**：它在打标签之前写好，写进去的日期很可能不是发布那天。

**不要为问题建文件夹**：问题的原文在平台上，仓库里只放我们自己的记录。两份副本一定会
漂移，而漂移没人盯得住——需要对应关系时，在记录里写清问题编号。

**对话本身不落盘**：它会被压缩、会丢，也不是给下一个人读的形态。真正留下记录的是三样——
工作记录（状态、决策、断点）、提交信息（改了什么）、提案与审查评论（为什么、谁拦过）。

每份至少写清**状态、目标与验收、计划、放弃过什么、断点**——缺任何一样，下一个人就得重新
问一遍。就按这五样搭一份，不要为了好看再加别的节。

<!-- pf:if has-remote -->
### 审查：派一个新上下文，不继承判断

审查的独立性**不在于换个模型，而在于不继承别人的判断**。所以要派一个**新上下文**（子代理
或新会话），只给它一张材料清单——让它自己看、自己查。把执行者的思路喂给它，它只会顺着
复核，那叫复核，不叫审查。

| 给它 | 不给它 |
| --- | --- |
| 本文件、**改动全文**、门禁命令与原始输出、工作记录、**贡献指南与发版规范**（有才给）、平台上的原始记录（问题与提案**正文**） | 执行者的对话与「我的思路」、**上一轮审查的结论**（包括提案评论里的那几轮）、任何「请确认没问题」式的引导 |

**「平台原始记录」只给正文，不给上一轮评论**：审查的结论本来就落在提案评论里，把评论一起
塞过去，等于让它顺着上一轮的判断复核。要它重看新一版，就把它当成第一次。

**外部提案不一定有关联问题**：没开问题不是退回的理由——很多人直接提改动。缺的是「要解决
什么问题、改了什么、怎么验证、影响谁」这四件事；答不上来就写评论问清楚，不要猜他的意图改。

- **每轮都要留记录**：本轮的审查结论**作为评论发到提案上**、工作记录的断点与「最近更新」
  跟着改，两者与当轮改动**同一次提交**。「最后补一份总结」等于把中间几轮的判断丢掉——
  而下一轮要接的正是那几轮，它得知道上一版为什么被打回。

**评论是痕迹，提案正文那一栏只是索引。** 只填正文不写评论，等于让执行者自己给自己出证明，
而一项独立审查的全部意义恰恰在于它不是执行者自己给的。实测发生过：跑完两轮审查、所有门禁
全绿，而提案上的评论数是 0——因为契约里只写了「写回提案评论」，没有任何机器判据看评论。
现在判据核两层，索引对不上评论就是红的：

| 层 | 判据 |
| --- | --- |
| 索引（提案正文的「## 审查记录」） | 有哪几轮、每轮谁审的、结论是什么 |
| 痕迹（提案评论） | 每一轮的结论都能在评论里找得到一条对应，且**结论与索引里写的一致**。空评论过不了；合格的最小形态是**一个带 `round` 与 `verdict` 的字段块**——**写得好不好不判**，机器判不了 |

**issue 也一样**：别人贴来一段问题，追问他缺什么、你核了哪几件事、最后怎么处理的，
每一步都要在那条 issue 上留一条评论。那条 issue 才是别人看得见的地方，只留在自己的会话里
等于没写——换个人接手时，他读不到你判断过什么。

**要读改动之外的文件来验证调用链，允许**：但要把「读了哪些额外文件、为什么」写进报告——
否则大仓库里它会淹没在无关文件里，而报告看不出它到底核了什么。

- **它默认只读**：逐条发现返回给主 Agent，由主 Agent **发成提案评论**（正文走文件，见下）；
  它自己发也可以，同样走文件。写在对话里等于没写。
- **下一轮重新派一个新的**：让同一个子代理「再看看」，它已经带着上一轮的结论了。要看新一
  版，就把它当成第一次。
- **产出写三处**：提案评论（逐条：文件与行、什么问题、标**阻塞**还是**建议**）、工作记录的
  断点（卡在哪、下一步从哪接）、提案正文的索引一行（第几轮、结论）。
- **终止条件四条**：阻塞项为零、门禁全绿、阻塞项在减少（连续两轮卡在同一处就是方向错了，
  停下升级给人，不要继续烧）、**记录齐全**（本轮的提案评论、断点与「最近更新」已提交，
  门禁要的那几处文档与改动对得上；由审查的人查，不是执行者自称）。
- **主 Agent 不能自己充当审查**：同一个上下文里再读一遍，只会读出「刚才那套没问题」。



**一条独立的硬规则**：改动里出现弱化门禁的痕迹（跳过测试、放宽断言、降覆盖率门槛、
动 CI 配置），不管风险档、不管审查结论，**一票否决转人工**。它「通过了」是因为判据被
改松了，而改判据这件事必须有人看。

**外部来的提案要先只读、再检出**：检出之后一次本地装依赖就可能执行陌生人的代码。所以先用
只读方式看 diff，重点看 CI 配置、依赖装起来就会执行的那些钩子脚本、门禁判据有没有被改松；
确认干净之后再检出到本地跑测试。**外部提案一律人合**：进主干是维护者替他承担后果。

### 合并与收尾：顺序不能反

```
合并 → 验证真的合并了 → 关工作记录与关联问题 → 切回主干并更新 → 删本地分支 → 删远端分支
```

```sh
gh pr merge <编号> --merge          # 1) 合并。不要带「合并并删分支」，那是两件事
gh pr view <编号> --json state       # 2) 回读验证真的合进去了，别凭退出码
git checkout <主干> && git pull      # 3) 先切回主干并更新（删本地之前必须做）
git branch -d <分支>                 # 4) 再删本地，用 -d 不用 -D
git ls-remote --heads origin <分支>  # 5) 先判远端还在不在
git push origin --delete <分支>      # 6) 还在才删
```

命令以 `gh` 为例——它只是一种通道。没装它时用平台工具或网页做同样的动作：合并、看状态、
查堆叠、删分支都有等价入口，**顺序与回读要求不变**。

三个坑各有根因：**①** 合并与删除混在一条命令里，失败时分不清是「没合进去」还是「合进去了
但删分支失败」，而这两种情况的下一步完全相反；**②** 还停在分支上时 git 不允许删当前分支，
且主干没更新时 `-d` 会认为它没合入而拒绝——顺序反了会掉进「明明合过却删不掉」的循环；
**③** 先删远端会丢掉本地分支的上游追踪引用，逼你用 `-D` 强制删除，而那正是唯一那道保护网。
另有两个特例：平台开着「自动删除已合并分支」时，第 6 步报「远端引用不存在」**是完成态**；
**有未合并提案以这条分支为基底时不能直接删**（会把它连带关掉）——先给下游提案改基底，
或者先留着。删之前先 gh pr list --base <分支> --state open 查一眼，不靠记得。

**写回平台时正文一律走文件**：创建或更新问题、提案、审查评论，正文先写进 UTF-8 文件再用
`--body-file` 一类参数提交，**不在命令行里拼正文**。shell 的引用与编码规则因平台而异，中文与
反引号可能被静默吞掉，而这类损坏的共性是**接口仍然返回成功**。提交后回读比对一次。
**那个文件放系统临时目录、用完就删**：不要写进仓库（会被提交，也会被门禁当成产物），也不要
留在 `.git/` 里（不会被提交，但清理时没人敢删）。提交信息、提案正文、评论正文都算这一类。

## 依赖版本同步

构建与测试所对的依赖版本必须**跟随实际在用的版本**——不写死、也不靠宽松范围蒙过去。

同步动作：读当前实际在用的版本作为目标 → 逐个确认目标版本确实存在 → 写进开发依赖
声明（**只动这里**）→ 安装 → 跑构建与验证全绿 → 若伴随破坏性变更，按新契约改写而不是
用宽类型绕过。

**注意与「最低支持版本」的区别**：这里的跟随版本只有开发者看得到，每次上游升级都跟上
去；而使用者能看到的最低下限是另一个概念，**只在真不兼容时上移**，且兼容性声明与面向
使用者的文档必须一起改。两者混为一谈，就会要么把下限无谓抬高、要么让文档与实际不符。

**不要用「查询最新版本」的单值命令判断版本**：发布方的「最新」标记可能停在很旧的版本
而实际已有更新的版本。要取完整版本列表，从末尾找目标版本，并逐个确认它确实存在——同一
批发布里个别包可能停更，不能假定「同号」普遍成立。

## 高风险路径

<!-- pf:author: 下面那张表由**作者**填，脚本只读不改：写清这个项目里「改了会让门禁从此少查一项」的那几处。表格形状与判据照着上一节的说明。填了之后重跑本脚本不会把它冲掉（这一节标着 pf:author，合并时保留既有内容）；留空则那条门禁不生效。 -->

**改在这里出错不会当场失败，而是让门禁从此少查一项。** 动到下面任何一处，提案必须有
独立审查记录——这条由 `review-record.mjs` 判（它读的就是这张表），有远端时 CI 在提案上跑它。它随落盘自动拷到本项目的 `scripts/` 下（不用手工拷），零依赖、单文件。

**这张表是空的就等于没配**：脚本读不到路径时会明说「这一趟没查」，不会静默放行，
但也拦不住任何东西。填的时候按这个项目真实的高风险处填：

| 路径 | 为什么 |
| --- | --- |
| `<替换成这个项目的第一处>` | 判据错了不报错，只会从此少查一项 |
| `<替换成这个项目的第二处>` | 写进别人的东西，改坏了要等他们踩坑才发现 |

**路径要能被认出来**：目录写 `src/rules/`（不带尾斜杠也认，会补成前缀形式），单个文件写
`AGENTS.md`；格子里可以带说明。**认不出来的行会让门禁直接报错**——认不出来不等于没有，
静默跳过正是「表填了但门禁永不触发」那个 bug 的形状。

判据是**目录前缀**，不是逐文件清单：清单要人记得改，而目录不会长出新的一处。
写目录时**结尾带上 `/`**，写单个文件时不要带。

## 文档同步

本项目有两类面向不同读者的文档，**描述同一件事，但读者不同**。这条总规则与它的判据
（读者是谁决定怎么写、改完要检查另一份是否失准）**由上面的内核段落给出，本节不复述**：
同一份规范写两处，迟早会有一处失准。

下面只写内核没有覆盖的那两类内容：**不由人手工维护的派生内容**，以及**多语言版本**。

### 派生内容用工具同步，不手工维护

有一类内容**完全由别处的信息决定**：目录由标题决定、徽章由外部服务决定、依赖清单由
依赖声明决定、模块表由实现的接口决定。它们不该手工维护——手工维护的派生内容一定会
漂移（加了一节忘了加目录项、改了标题忘了改锚点），而这类错误的症状很隐蔽：
**锚点写错的表现是「点了没反应」，不报错、不显眼**，作者也不会去点自己的目录。

判据一句话：**这份内容能不能由一条命令从源头重新算出来？** 能，它就不该手写。

做法：用脚本从源头生成，插在成对标记之间（标记之外一个字节不动），改完重跑即同步；
并在持续集成里加一条「重新生成后与提交一致」的检查——这样漂移会当场暴露，而不是
等到某个读者点了没反应。

与「本文件的定位与编辑规则」里那条「写意图不写快照」是同一个道理：**快照会过期，
派生关系不会**——把派生关系交给工具，剩下的只有源头需要维护。

### 双语说明文档要**成对**维护

本项目的 `README*.md` 是**同一份文档的两个版本**，**改一份时必须打开另一份一起看**，改完
要能回答「另一份同步了吗？」。**默认语言那份是权威**：另一份是它的翻译，两者不一致时以
权威版为准，并同步另一份。

**不要机械对译**：两种语言的读者关心的问题不同，按那份语言里读者能看懂的写法重写。
**不要新增没人维护的语言**——一份没人维护的第二语言 README 比没有更糟。

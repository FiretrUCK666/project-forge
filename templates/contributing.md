## 提问与反馈

遇到问题、想要新能力、发现文档不清楚，都请到本仓库的 Issue 区提出。请先搜索已有的
Issue，避免重复。

**报缺陷用仓库里的缺陷报告模板**（`.github/ISSUE_TEMPLATE/bug_report.md`）：一个能被定位的
报告该有的东西，那个模板会逐项问出来。**要求只写在模板里，本文不另抄一份**。

**想要新能力、或者觉得某处行为该改，用需求模板**（`.github/ISSUE_TEMPLATE/feature_request.md`）：
它先问你要解决什么问题，再问改成什么样。如果问题只在特定条件下出现，把那个条件写出来。

模板会随项目生成；纯文档项目没有模板时，按上面四件事写清楚即可。

## 提出改动

1. **较大改动建议先开一个 Issue** 说明你想改什么、为什么——涉及接口契约变更或新增依赖时，
   先在 Issue 里讨论清楚再动手，避免写完才发现方向不对。

   **小修与文档修正直接提拉取请求就行。没有关联 Issue 不是退回的理由**：只要提案说清了
   解决什么问题、改了什么、怎么验证，它就是有效贡献。
2. 在分支上改，然后开拉取请求：
   - **没有本仓库写权限（Fork 贡献者）**：先 **fork** 到你自己的账号，克隆你的 fork（习惯将自己 fork 设为 `origin`、正本设为 `upstream`），从正本默认分支拉出新开发分支，**只推到自己的 `origin` fork**，再从该分支向 `upstream` 开拉取请求；**在上游 PR 处于 `OPEN` 状态期间不要删除自己 fork 上的这个分支**，否则 PR 会被自动关闭；
   - **有写权限（协作者 / 维护者）**：直接从主干拉一个分支并向主干开拉取请求；
   - **只改文字**（错别字、文档表述）：在网页上点开文件、点铅笔图标改完提交即可，
     GitHub 会替你建好分支与拉取请求——这条路跑不了下面的提交前门禁，别用它改代码。
3. 跑完提交前门禁（见下），全绿再提交。
4. 提交拉取请求，按仓库里的[提案模板](.github/pull_request_template.md)填写——
   最重要的一栏是**怎么验证的**：贴实际跑过的命令与结果，不要只写「测试通过」。
   如果改动同时涉及命令行参数、导出接口或项目结构，请一并同步相关说明文档。

**内部流程不对外设门槛。** 仓库维护者内部会按改动规模走五档分流（决定何时建 `docs/todo/` 任务单或 `docs/specs/` 设计规范）；**外部贡献者不需要提前补齐内部工作单**，只需要按上面的提案模板写明改动目的与实测证据即可。

第一次提拉取请求、或不确定 fork 怎么用，看 GitHub 官方的[参与项目](https://docs.github.com/zh/get-started/exploring-projects-on-github/contributing-to-a-project)。
fork 落后于正本时，在自己 fork 页面点 **Sync fork** 即可。

**不要往正本主干推送，也不要打版本标签或发布制品**——那些由维护者执行。
另外请别把改动留在自己 fork 主干上就算了事：**必须开拉取请求**才会被处理。

**维护者也不会随手发版。** 一次改动合进主干就是终点；打标签、建发布页要单独决定。

**合并由独立审查收尾，不是谁随手点一下。** 审查通过之后，由那个审查者直接合并——它拿到了冻结的
验收标准、你的 diff、门禁原始输出，并且亲手做过一次故障注入。外部来的提案也一样：防陌生人的那一层
在**审查之前**（先做只读静态扫描工作流与生命周期脚本变动，经维护者显式确认并禁用生命周期脚本后才跑门禁），不在合并这一步。

**唯一会转给人点头的，是弱化门禁的改动**：删测试、放宽断言、加跳过标记、把检查改成警告、改松 CI。
别的改动做错了，下一次门禁会红；这一类做错了，以后每一次都不会红，而它看起来只是「构建绿了」。

**维护者自己也走同一条路。** 有写权限不等于直接推主干：同样是拉分支 → 门禁全绿 → 推分支 →
开拉取请求 → 独立审查 → 合并。判据是**能不能撤回**：推分支、开提案都能撤回，属于日常；
合并进主干、发版撤不回来，要单独决定。

### 平台脚本与非 ASCII 字符规范

通过终端工具或命令行脚本创建、更新 Issue、PR 或评论时，若正文包含中文或非 ASCII 字符，
**严禁在命令行参数中直接拼接正文字符串**（跨平台终端编码差异容易导致乱码）；
请一律先将正文写入系统临时目录的 UTF-8 文件，通过 `--body-file` 提交后回读校验并清理临时文件。

## 提交前门禁

改完必须全绿才算完成。按顺序（与 `AGENTS.md` 构建与验证节保持一致）：

```sh
# 构建
# 静态检查
# 测试
# 自检
```

如果项目把生成产物提交进了版本库，改完源码后必须**重新构建并一起提交**——否则产物
与源码会脱节。

## 硬性规范

从项目的 `AGENTS.md` 里摘出对贡献者同样成立的几条（例如：命名一致性、不新增依赖、
数据键不得改名）。**完整规范以 `AGENTS.md` 为准**，这里只列最关键的部分，不要重复
维护一份。

**审查结论按「冻结的验收标准逐条过没过」给，不给「整体不错」这类评价。** 一条有效意见指向具体
标准（「C2 没过——脚本加了参数，文档没提」）；一条感受型意见是讨论，不是审查，拿它当阻塞理由，
循环永远收敛不了。

## 提交信息

一句话说明这次**改了什么、影响谁**。中文或英文都可以，但**提交信息与项目既有历史风格
保持一致**——沿用已有的前缀或格式，**不混用多套格式**，不用内部编号、任务代号或分支名
充当说明；判据是发布页上的读者能读懂。一次实质改动一个提交，不要把无关改动混在一起。

**提交信息是发版时那段「这一版更新了什么、修复了什么」的素材**，所以用使用者能读懂的
话写：写实际改了什么，不要写只有内部人才认得出的缩写。

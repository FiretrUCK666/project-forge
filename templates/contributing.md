## 提问与反馈

遇到问题、想要新能力、发现文档不清楚，都请到本仓库的 Issue 区提出。请先搜索已有的
Issue，避免重复。

为了让问题能被定位，请一并附上：

- 你使用的版本（清单里的版本号，或提交哈希）
- 你的运行环境（操作系统、相关运行时的版本）
- **完整的报错文本**（不要只描述现象，也不要只截一行）
- 最小复现步骤（如果问题能稳定重现）

## 报告缺陷

一个可用的缺陷报告包含四件事：期望发生什么、实际发生什么、怎么复现、在什么环境上。

如果问题只在特定条件下出现，把那个条件写出来——它往往就是根因所在。

## 提出改动

1. 先开一个 Issue 说明你想改什么、为什么。涉及行为变化或新增依赖的，先在 Issue 里
   讨论清楚再动手，避免写完才发现方向不对。
2. 把仓库弄到你自己的账号下，在分支上开发：
   - **没有本仓库写权限**（大多数情况）：先 **fork** 一份到你自己的账号，克隆 fork
     出来的那份，在它上面拉分支开发，最后开拉取请求；
   - **有写权限**（协作者）：直接从主干拉一个分支即可。
3. 跑完提交前门禁（见下），全绿再提交。
4. 提交拉取请求，说明改了什么、为什么、怎么验证的。

**不要往本仓库推主干，也不要打版本标签或发布制品**——那些由维护者执行。没有写权限时
你本来也推不动主干，但请注意别把改动留在自己的 fork 主干上就算了事：那样维护者看不到，
**必须开拉取请求**才会被处理。

### 插件类专属

- **产物与源码同一次提交**：安装方不会替你构建，产物缺了就是加载失败。改完源码必须
  重新构建并一起提交，不要分两次。
- **两标识不要混改**：宿主侧标识是用户数据的地址（配置键、存储单元、界面挂载点），
  改名会丢用户数据；分发侧标识只影响安装。加作用域、换发布者只动分发侧。
- **本地挂载与正式分发是两条路**：开发时指向本地目录挂载，改完按该生态的生效规则
  验证（例如一侧要重启宿主、一侧刷新页面即可，具体见本项目的 `AGENTS.md` 与对应专章）；
  给别人用时走安装或分发，需要装新版本。不要用开发链接代替隔离安装的验证。
- 宿主版本约束见 `AGENTS.md`（跟随版本与最低支持版本是两回事），不要自行升级下限。

## 提交前门禁

改完必须全绿才算完成。按顺序（与 `AGENTS.md` 构建与验证节保持一致）：

```sh
# 构建
# 静态检查
# 测试
# 自检
```

如果项目把生成产物提交进了版本库，改完源码后必须**重新构建并一起提交**——否则产物
与源码会脱节。

## 硬性规范

从项目的 `AGENTS.md` 里摘出对贡献者同样成立的几条（例如：禁止 emoji、命名一致性、
不新增依赖、数据键不得改名）。**完整规范以 `AGENTS.md` 为准**，这里只列最关键的部分，
不要重复维护一份。

## 提交信息

一句话说明这次**改了什么、影响谁**。中文或英文都可以，但**不要使用 emoji**。一次实质
改动一个提交，不要把无关改动混在一起。若项目历史有既定的提交格式约定，沿用它，不要
引入第二种格式。

**提交信息是发版时那段「这一版更新了什么、修复了什么」的素材**，所以用使用者能读懂的
话写：写实际改了什么（「修好了导出报表时缺最后一页」），不要用内部编号、任务代号或
分支名充当说明——发布页面上的读者不知道那是什么。修问题与加能力可以自己加前缀区分
（例如 `fix:` / `feat:`），沿用项目已有习惯即可。

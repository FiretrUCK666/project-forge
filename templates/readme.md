## 这是什么

用两三段说清楚：它解决什么问题、以什么形态提供（库 / 命令行工具 / 插件 / 服务 /
文档集）、有什么明显的边界（不做什么）。

## 安装

给出最短的一条可复制路径，再给出其他可选来源。

```sh

```

若有多个来源（制品库 / 仓库源 / 手动下载），用一张表说明**各自的差别**，让读者能自己
选：拿到的是什么、靠什么判断有没有更新、适合什么场景。

## 更新

**怎么把已装的版本升上去**，以及**怎么知道有新版**。

这是使用者最常问的三件事之一（另两件是「怎么装」和「怎么用」），而它依赖前面的分发
方式，所以两者要写得一致：

| 你的安装方式 | 怎么更新 | 怎么知道有新版 |
| --- | --- | --- |

要点：

- 只写**实际存在的**更新方式。不发布制品就不写「用包管理器升级」——写了做不到，比
  不写更糟。
- **说明会不会破坏兼容**：升级通常是安全的还是有注意事项，给一句判断依据（例如
  「小版本升级可直接覆盖，大版本先看发布说明」）。
- **告诉使用者去哪里看变更**：发布说明、变更记录、还是提交历史。指一个具体的去处，
  不要只说「见发布说明」而不说在哪。

## 环境要求

写**具体的最低版本**，并说明这个数字的含义。不要写「或更高」这类无法兑现的承诺，
也不要写「最新版」这种无法判断的说法。

建议表述：本项目在 `<具体版本>` 上验证通过；更新的版本预期可用但未逐一验证；
遇到加载或兼容问题请到反馈渠道提出。

## 遇到问题

按症状列几条最常见的，每条给出**怎么判断**和**怎么办**。

最后指向反馈渠道（Issue 地址），并说明为了能定位问题，提问时请附上哪些信息
（版本、环境、完整的报错文本）。

# 发版规范

本文件回答一件事：**这个项目怎么发版**——说明写在哪、写成什么样、按什么顺序发、出错了
怎么补。读者是维护者与替他动手的 AI。

## 何时读本文件

- 用户说要**发版**、发布、发一版、发出去时；
- 要判断这一版该不该抬版本号、该不该写说明时；
- 发版失败（自动化报错）需要补救时。

**日常改动不要读它**：日常只提交、推送，不发版。发版是独立的一步，只有明确说出来才做。

## 一、说明写在哪

| 项 | 本项目的值 |
| --- | --- |
| 目录 | `docs/release-notes/` |
| 文件名 | 与标签名**逐字相同**加 `.md`：标签 `v1.2.3` → 文件 `v1.2.3.md`；裸版本标签 `1.2.3` → 文件 `1.2.3.md` |
| 谁写 | 发版的人在**打标签之前**写好，和代码一起提交 |
| 谁读 | 使用者——自动化把它原文贴到发布页上 |

**这两项是自动化的输入，不是随手起的名字**：发布工作流按标签名去取这个文件，取不到就
失败。所以它们只能在这里定义一次，改的时候两处一起改。

## 二、说明分哪几节

顺序固定，只写这两节：

```markdown
# v1.2.3

## 这一版更新了什么、修复了什么

## 需要你动手的
```

**第二节没有内容时整节省略**，不要留一句「无」——一句「无」会让读者以为自己在找什么。

写之前先复制骨架，把标记删掉再往里写。**留着那个标记的说明发不出去**：发送端见到它就
拒绝，发版直接失败。这是刻意的——一份只有小标题的空壳贴到发布页上，比这次发版失败糟。

```markdown
# v1.2.3

## 这一版更新了什么、修复了什么

<!-- pf:needs-summary 这一段还没写。写完删掉这一行。 -->
```

## 三、写什么、不写什么

判据只有一条：**一个不熟悉这个项目的人读完，能不能说出哪一处变化影响他。**

| 该写 | 不该写 |
| --- | --- |
| 行为、界面、交互、报错文案的变化 | 内部编号、任务代号、分支名、提交哈希 |
| 使用者要不要跟着做什么（迁移、改配置、注意新默认值） | 对使用者没有影响的重构、测试数目、文件行数 |
| 破坏性变化，以及不改会怎样 | 只有维护者才看得懂的流程名与简称 |
| 出问题时的判断依据（什么症状对应什么原因） | 这一版的开发过程、谁做的、审了几轮 |

**不要拿提交信息直接当正文。** 提交信息说的是「改了什么」，读者是历史；发布说明说的是
「使用者该知道什么」，读者是使用者。前者可以拿来做素材，但必须改写成后者。

## 四、发版顺序（顺序反了会失败）

1. **写说明**：`docs/release-notes/<标签名>.md`；
2. **提交**：把说明和这一版的代码改动一起提交；
3. **推送**：推到远端主干。**这一步不能省**——自动化是在远端取文件的，本地有、远端没有
   等于没有；
4. **打标签并推送标签**：标签名与版本号同源（用清单文件里的那个号，不要另写一份）；
5. **回读发布页**，确认正文与你写的那份一致。

第 3 步与第 4 步之间的顺序是关键：**说明必须先在远端**。工作流在标签推上来那一刻去读
文件，读不到就失败——这是它拦住「忘了推说明」的方式，不是它坏了。

## 五、发不出去怎么办

| 现象 | 原因 | 怎么办 |
| --- | --- | --- |
| 工作流报「找不到说明文件」 | 说明没提交，或提交了没推送 | 补提交、补推送，再手动触发一次工作流并填标签名；**不要重打标签** |
| 工作流报「还是骨架」 | 说明里还留着未填充的标记 | 把说明写完，删掉标记，重推后手动触发一次 |
| 工作流报认证失败 | 凭据缺失、过期，或权限范围不含写发布 | 换凭据；**不要靠重试解决**，先确认为什么没有权限 |
| 发布页已经有了，但正文是旧的 | 标签推得比说明早 | 补推说明后手动触发一次，它会更新正文 |

两条纪律：**标签推错了不挪它**（改已推送的标签等于改别人的依据），而是往前修；
**发布页上已经手工改过正文时不要再跑工作流**，它会用说明文件覆盖掉那些手工内容。

## 六、禁忌

- 不要在说明里写凭据、内网地址、私人联系方式——发布页是公开可读的，而且一经发布收不回；
- 不要为了「先占位」发一个空壳再补——改发布页要人手去做，而等着补的那一版通常没人补；
- 不要把发版混进日常提交：标签是里程碑，不是每次提交的附庸。

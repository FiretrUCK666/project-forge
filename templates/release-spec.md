# 发版规范

本文件回答一件事：**这个项目怎么发版**——说明写在哪个文件、分成哪几节、按什么顺序发、
出错了怎么补。读者是维护者与替他动手的 AI，所以它是这个项目发版的唯一依据。

`AGENTS.md` 只留一行指针指向本文件：那份契约每次会话都会注入，把发版细节抄进去既白占
预算，又制造第二处会漂移的副本。

## 何时读本文件

- 用户说要**发版**、发布、发一版、发出去时；
- 要判断这一版该不该抬版本号、该不该写说明时；
- 发版失败（自动化报错）需要补救时。

**日常改动不要读它**：日常只提交、推送，不发版。发版是独立的一步，只有明确说出来才做。

## 一、说明写在哪

| 项 | 本项目的值 |
| --- | --- |
| 目录 | `docs/release-notes/` |
| 文件名 | 与标签名**逐字相同**加 `.md`——标签 `vN.M.P` 对应文件 `vN.M.P.md`；裸版本标签（不带 `v`）就照它的字面写 |
| 谁写 | 发版的人在**打标签之前**写好，和代码一起提交 |
| 谁读 | 使用者——自动化把它原文贴到发布页上 |

**这里不要写任何具体版本号**：规范里出现具体号，发一次版它就变成一句过时的话，而读的
人还容易把它当成「当前版本」。版本号唯一的权威来源是标签，需要时现取。

**说明正文里也不要写发布日期**：它是在打标签**之前**写好的，写进去的日期很可能不是真正发布
那天；日期由标签与发布页承担，正文只写读者要看的事。

**目录与文件名是自动化的输入，不是随手起的名字**：发布工作流按标签名去取这个文件，取不到就
失败。所以它们只能在这里定义一次，改的时候两处一起改。

## 二、说明分哪几节

**节的数量不是规矩，是「这份说明要回答几个问题」。** 多一节就多一次读者的阅读负担；
少一节则是这次发版该说的事没说。所以下面只有一节是固定的，其余按这一版的实际内容增删。

### 必需的一节：这一版更新了什么、修复了什么

永远在，哪怕只有一行。它回答的是**这一版变了什么**（使用者要不要跟着做点什么，是另一件
事，写在按需的节里）：

- 行为、界面、命令、报错文案变了什么；
- 它可能踩过的哪个问题被修了；
- 有没有破坏性变化（旧用法还能不能用）。

判据只有一条：**不熟悉这个项目的人读完，能说出哪一处变化影响他。**

### 按需的节：有这类内容才写

| 什么时候需要 | 这一节回答读者什么 | 常见名字（用本项目顺口的，不要求照抄） |
| --- | --- | --- |
| 使用者**不动手会出问题**：装法变了、配置项改名、数据要迁移、旧用法失效 | 我该做什么，不做会怎样 | 「要怎么跟着升级」「升级须知」「迁移」 |
| 有**环境边界**：插件对宿主版本、库对运行时、服务对系统组件 | 我的环境还能不能用 | 「兼容范围」「运行要求」 |
| 有**已知但这次没修**的问题 | 我遇到的算不算已知问题、要不要等 | 「还没解决的」「已知问题」 |
| 这次**修掉了一个值得单独说**的缺陷 | 我之前踩的坑还在不在 | 「修好了什么」 |

**没有这类内容时整节省略**，不要留一句「无」——一句「无」会让读者以为自己在找什么。

### 三条约束

- **默认 1–3 节**：多数项目一版就是「变了什么」加一节「要不要跟着动」。
- **超过 3 节时先回头看**：那是这份说明在替别的文档干活（迁移指南、接口文档、版本历史）。
  把细节挪进对应的文档，这里只留一句指针——发布页不是文档站。
- **不要加只对维护者有意义的节**：开发过程、谁审了几轮、任务编号、内部分支名。
  读者读完不知道「这跟我有什么关系」。

### 加自己的节：可以，但要留下记录

项目的读者不是模板能猜全的（有人要「性能变化」，有人要「数据集来源」）。要加就按三步：

1. **写进下面「本项目用哪几节」那张表**，并用一句话回答「这一节让读者知道什么」；
2. **同时检查另外两处**：读这份说明结构的脚本（如果有）与发布自动化——一处改了另一处
   没改，会在发版当天才暴露；
3. **不要加只对维护者有意义的内容**（同上面那条约束）。

### 本项目用哪几节

默认菜单在上面；本项目按自己的读者**删减**后写在这里。这张表就是本项目的决定，
写说明时照它写：

| 顺序 | 节 | 回答读者什么 | 什么时候写 |
| --- | --- | --- | --- |
| 1 | `这一版更新了什么、修复了什么` | 变了什么、要不要跟着更新 | 每次 |
| 2 | `要怎么跟着升级` | 我该做什么，不做会怎样 | 有迁移、配置变更或破坏性变化时；没有就整节省略 |

**第二节没有内容时整节省略**，不要留一句「无」——那会让读者以为自己在找什么。

写说明时先复制骨架，把标记删掉再往里写。**留着那个标记的说明发不出去**：发送端见到它就拒绝，项目自己的工作流也应在贴出正文之前
查这两条（模板 .github/workflows/release.yml 就是这么写的，所以没有凭据、没有联网也能拦住）。这是刻意的——一份只有小标题的
空壳贴到发布页上，比这次发版失败糟。

```markdown
# vN.M.P

## 这一版更新了什么、修复了什么

<!-- pf:needs-summary 这一段还没写。写完删掉这一行。 -->
```

## 三、写什么、不写什么

判据只有一条：**一个不熟悉这个项目的人读完，能不能说出哪一处变化影响他。**

| 该写 | 不该写 |
| --- | --- |
| 行为、界面、交互、报错文案的变化 | 内部编号、任务代号、分支名、提交哈希 |
| 使用者要不要跟着做什么（迁移、改配置、注意新默认值） | 对使用者没有影响的重构、测试数目、文件行数 |
| 破坏性变化，以及不改会怎样 | 只有维护者才看得懂的流程名与简称 |
| 出问题时的判断依据（什么症状对应什么原因） | 这一版的开发过程、谁做的、审了几轮 |

**不要拿提交信息直接当正文。** 提交信息说的是「改了什么」，读者是历史；发布说明说的是
「使用者该知道什么」，读者是使用者。前者可以拿来做素材，但必须改写成后者。

## 四、发版顺序（顺序反了会失败）

1. **写说明**：`docs/release-notes/<标签名>.md`；
2. **提交**：把说明和这一版的代码改动一起提交；
3. **推送**：推到远端主干。**这一步不能省**——自动化是在远端取文件的，本地有、远端没有
   等于没有；
4. **打标签并推送标签**：标签名与版本号同源（用清单文件里的那个号，不要另写一份）；
5. **回读发布页**，确认正文与你写的那份一致。

第 3 步与第 4 步之间的顺序是关键：**说明必须先在远端**。工作流在标签推上来那一刻去读
文件，读不到就失败——这是它拦住「忘了推说明」的方式，不是它坏了。

**结构检查是发送端的事，不是平台的保证**：本 skill 自带的发送工具会在发出去之前查一遍
（没标题、标题与标签不是同一个号、有空节、两节同名、还留着骨架标记，任一条都拒绝发送）。
但**这个项目用自己的命令发**（`gh release` 一类）时没有这道门——它只把文件按字节贴上去。
所以别指望「先发出去再改」：没有检查的发送端会让你发出去，而发布页收不回来。

## 五、发不出去怎么办

| 现象 | 原因 | 怎么办 |
| --- | --- | --- |
| 工作流报「找不到说明文件」 | 说明没提交，或提交了没推送 | 补提交、补推送，再手动触发一次工作流并填标签名；**不要重打标签** |
| 发送端拒绝，说结构不对 | 没标题、空节、同名节、标题不是同一个号，或还留着骨架标记 | 按报出的那一条改说明；这类问题在发出去之前就能看到 |
| 工作流报认证失败 | 凭据缺失、过期，或权限范围不含写发布 | 换凭据；**不要靠重试解决**，先确认为什么没有权限 |
| 发布页已经有了，但正文是旧的 | 标签推得比说明早 | 补推说明后手动触发一次，它会更新正文 |

两条纪律：**标签推错了不挪它**（改已推送的标签等于改别人的依据），而是往前修；
**发布页上已经手工改过正文时不要再跑工作流**，它会用说明文件覆盖掉那些手工内容。

## 六、禁忌

- 不要在说明里写凭据、内网地址、私人联系方式——发布页是公开可读的，而且一经发布收不回；
- 不要为了「先占位」发一个空壳再补——改发布页要人手去做，而等着补的那一版通常没人补；
- 不要把发版混进日常提交：标签是里程碑，不是每次提交的附庸。

# 发版规范

这份文件定的是**制度**，不是某一次发版的记录：说明写在哪、写什么、怎么跨多版本全量采集与去噪、按什么顺序发、发不出去怎么排障。每次发版都照它做，不另写一份临时说明。

**日常合入默认分支即止，不打标签不发版。** 只有人明确说「发版」时才走下面这套顺序。

| 动作 | 什么时候做 | 会留下什么 |
| --- | --- | --- |
| **提交** | 每完成一件事 | 本地一条记录，推之前可以改 |
| **推送分支 / 开 PR** | 门禁全绿 | 远端多一条记录，可撤回（删分支、关 PR） |
| **合并进默认分支** | 独立审查通过后由审查者直接合并（弱化门禁须人点头） | 别人可能已经基于它工作，撤不回来 |
| **发版** | **只有人明确要求「发版」** | 标签 + 发布页 + 制品库版本，**对外生效，永不回收** |

合并之后就是「日常」的终点。**不要把「合进去了」当成「该发版了」**——攒了几个改动、版本看着该抬、上个标签隔得久，都不是理由。

这几档的分界是**能不能撤回**，不是「是不是对外」：推自己的分支、开 PR 都能撤回，属于日常，不必等人点头；独立审查通过后由审查者直接合入默认分支（涉及弱化门禁仍须人点头）；而**发版**、改可见性、改写历史撤不回来，只由人决定。

## 说明写在哪

两种模式二选一，由项目现状决定，写进本文件之后不再来回换：

| 模式 | 位置 | 什么时候用 |
| --- | --- | --- |
| A（默认） | `docs/release-notes/<标签>.md` | 大多数项目。一个标签一份文件，**文件名与标签逐字相同**（标签是 `v1.2.0`，文件就是 `v1.2.0.md`） |
| B | 项目根目录 `CHANGELOG.md` 的 `## [<标签>]` 节 | 存量项目已经在用单文件变更记录，改造它会打断已有读者的习惯 |

模式 B 的标签写在方括号里，例如 `## [v1.2.0]`；发布自动化从这一节起、到下一个同级标题止，把中间那段正文当作这一版的说明。

**两种都行，但必须选一种写清。** 混用会让自动化读到一份、读者看到另一份。

## 分哪几节

下面是精炼通用菜单，可按项目习惯自由增删小节名称或沿用 `CHANGELOG.md` 分组（**没有条目的节直接删去，绝不留「无」字空节**），只要求保留一级标题、非空正文、删掉草稿占位标记且不写内部脚本路径：

- **重点变化** —— 新功能与使用者可感知的行为变更，合并同类提交，一条一句。
- **修复问题** —— 用户可见的缺陷修复，说清「原来会怎样、现在怎样」。
- **不兼容变更与迁移** —— 按需。有破坏性变更、改配置、换命令或最低支持版本抬升时写清迁移顺序。
- **升级方式** —— 按需。给出用户侧真实可执行的安装或升级命令。
- **已知问题** —— 按需。写清现象与绕法。

## 写什么、不写什么

| 写（最终用户与接入方明显能感知的变化） | 不写（对外部读者全是噪音） |
| --- | --- |
| 重点新能力与对外行为、命令、输出变化 | 内部重构与目录、函数重命名细节 |
| 「原来会怎样，现在怎样」的可见问题修复 | 测试或夹具增删、CI 流水线微调 |
| 兼容性、最低运行版本变化与按顺序执行的升级动作 | 文件搬移流水账、内部编号、分支名或晦涩源码符号 |
| 同主题多笔改动合并概括后的简洁人话 | 原封不动照搬提交记录或「优化了体验」类空话 |

判据只有一条：**不熟悉这个项目内部结构的使用者读完，能不能直接说出哪一处变化影响他、该怎么升。** 答不上来就重写。

## 发版 5 步，顺序不能反

**支持任意跨度与自定义版本号**：长周期多轮迭代后允许直接跨越多级版本或指定自定义目标号（例如 `v1.0.0` 后历经多轮迭代直接发 `3.0.0` 或 `v4.0.0`），不假设每次只能按一位小步递进；新号以项目声明的唯一权威版本号与本次 Git 标签同步为准。

1. **全区间采集与去噪核对**：始终从**上一个可达发布标签到 `HEAD`**（首发无标签时覆盖全量提交史）完整采集；先跑 `node .agents/skills/dev-govern/scripts/govern-audit.mjs release-prep [--version <目标版本>]`（或等效公开入口核对）检查候选变更、最低支持版本升降信号与有改动的公开界面是否遗漏，再按上节铁律去噪写成人类语言。
2. **写说明并改清单版本号**：说明按既定模式落盘；版本号只改唯一权威来源（`package.json` / `pyproject.toml` / `Cargo.toml` / 清单等），两者放在同一次提交里。
3. **跑门禁与打包预演**：本地门禁全绿，需要打包的项目先按发布流程演一遍产物。
4. **先提交并推送到默认分支**：发布自动化从默认分支读说明文件，读不到就直接失败。
5. **最后打标签并推送**，然后**回读确认**发布页正文与制品库上的内容。

第 4 步和第 5 步反了，就是发版最常见的失败：标签推出去了，说明还在本地。此时**严禁挪动已推送的标签**，正确做法是补推说明之后手动重跑那条工作流。

## 发不出去怎么排障

| 现象 | 原因与处理 |
| --- | --- |
| 自动化说找不到说明文件 | 说明没推，或标签先推了。补推说明，再用 `workflow_dispatch` 手动触发并填标签名；**严禁挪动已推送的标签** |
| 自动化说版本号不匹配 | 清单里的版本号与标签不同号。改清单、提交、推送，再手动重跑（标签已推则发补丁版对齐） |
| 说明文件是空的、或还留着未填的占位标记 | 说明没写完。补完、删掉占位标记再重跑；未填的草稿必须由自动化拦下 |
| 发布页正文被人工改过 | **不要重跑工作流**——重跑会用文件内容覆盖，抹掉人的编辑 |

## 发布页上的附件

**产物是附件还是入库，由分发通道决定，不由偏好决定：**

- 安装方会自己构建、宿主直接从仓库或制品库加载产物的：产物**进版本库**，与源码改动同一次提交更新；
- 宿主从发布页附件下载产物的：编译产物**绝不进版本库**，只在发版时挂成附件。

两种做法不能同时用。同时用的后果是版本库里那份慢慢过期，而它看起来仍然是「最新构建」。
